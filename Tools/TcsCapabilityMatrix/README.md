# TCS 能力覆盖度矩阵

把 LOL 海克斯大乱斗的技能、装备、增幅、符文拆成「效果原语」，逐条对照 TCS V2 文档，
判断 TCS 的表达力能不能覆盖它；不能的话，缺的到底是**机制**、**裁决**、**文档**，还是**依据**。

## 怎么用

双击 `index.html`。纯静态，零构建，不需要服务器，不需要联网。

| 视图 | 回答什么 |
| --- | --- |
| 能力矩阵 | 行＝效果原语，列＝判定单元（文档族里的一块契约），格＝这块文档能不能承接该原语 |
| 需求覆盖 | 1752 条真实需求的逐条裁决，可按类别/裁决/来源筛选与搜索 |
| 缺口报告 | 补哪块文档收益最大（阻塞需求数 + 独占阻塞数），以及每个单元缺哪些原语 |
| 版本差分 | 海克斯 16.20 → 16.22 的新增/移除/判定变化 |
| 文档状态 | 判定依据还是不是最新的：哪篇文档改了、哪几格判定要复核 |
| 方法与说明 | 判定口径、数据来源、证据边界、已知局限 |

右上角「导出 Markdown 报告」把当前判据与全部结果导成一份可归档的 Markdown，
末尾第七节记下这份结论基于哪个文档基线、基线之后文档动过没有；
「打印 / 存 PDF」走浏览器打印，样式已针对打印反色优化。

视图支持深链接：`index.html#gaps` 直达缺口报告。

## 判定口径

六态，严重度从高到低：

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 缺机制 | 已判定框架不提供此类能力 | 是否进铁律①：先找真实消费者 |
| 缺依据 | 所属域无文档也无草稿 | 先写该领域文档（现在连判都没法判） |
| 需补裁决 | 被未决项挡住（N13/N10/N5/N6/N8 一类） | 在族外草稿里把未决项裁掉 |
| 缺文档 | 已有草稿或已裁内容，只差正式化 | 把已裁结论正式化进 `tcs-remake-v2` |
| 归宿主 | 设计上明确由宿主实现（`01-定位与判据.md` §5.6） | 不算缺口 |
| 已覆盖 | 框架已有正式文档且明确覆盖 | 无需动作 |

需求级裁决由上表聚合：全「已覆盖」→ **可实现**；含「归宿主」且无其它缺口 → **需宿主配合**；
其余 → **受阻**。原语全为空 → **未标注**。

**「缺什么」必须分四类，混报即失去可执行性**：缺机制要新建，缺裁决要先裁，缺文档只需正式化，
缺依据要先写文档——四种动作的负责人、工作量、先后顺序都不同。

## 证据边界（重要）

**这是设计期判定，不是运行时验证。** TCS 插件的 `Source/` 已于 2026-11-18 随 V1 物理删除，
当前 HEAD 没有可编译代码，任何「能跑通」的结论都无从验证。本工具判定的是
「文档所描述的能力能否承接该效果」，属于**表达力对标**。

另外，LOL 与 DNF 不是 TCS 的消费者（三消费者是 LAC 自走棋 / 第三人称动作 / 幸存者+搜打撤）。
本工具的结论不能直接当作「TCS 该加什么机制」的排期依据——那需要真实消费者。

## 目录

```
index.html              六个视图的骨架
style.css               深色主题 + @media print 反色
app.js                  视图渲染、筛选、Markdown 报告导出、hash 路由
core.js                 纯判定逻辑（UMD，可被 Node 直接 require）
build-corpora.mjs       把 data/requirements/*.json 内联成 data/corpora.js
test-core.mjs           Node 冒烟测试：知识库自洽 + 数据自洽 + 裁决分布
fetch-corpora.mjs       从 aramkit / DDragon / CommunityDragon 抓原始快照到 data/raw/
annotate-crawl.mjs     由原始快照重建六份语料；默认预演，--write 才落盘
prim-map.mjs           Riot 技能标签 / 公式节点类型 → 效果原语的映射表
check-docs.mjs         文档变更检测：把判定格备注里的章节号做成锚点并记哈希
data/model.js           判定知识库：88 条原语 / 13 个判定单元 / 23 个判定档
data/annotate.js        需求→原语的三级标注规则（Riot 标签 / 数据商语义 / 文案正则）
data/corpora.js         自动生成，勿手改
data/doc-snapshot.js    自动生成，check-docs.mjs 写的基线快照（页面读这个）
data/doc-snapshot.json  同一份数据的完整版，含每篇文档每个章节的哈希
data/requirements/      抓取清洗后的需求语料（六份，工具真正读取的数据）
data/raw/               原始快照：aramkit / ddragon / cdragon 三源分版本目录
data/raw/sidecar/       每条技能命中对象的 DataValues 与 mSpellCalculations 原文
data/raw/legacy/        --write 覆盖前的旧语料备份（本目录不在版本控制内）
```

`file://` 下 `fetch` 本地 JSON 会被 CORS 拦，所以语料必须内联成 `corpora.js` 用 `<script>` 加载。

## 改数据

只改判定口径（不动需求语料）：

```bash
# 1. 改 data/model.js（原语 / 判定单元）或 data/annotate.js（标注规则）
# 2. 重新内联
node build-corpora.mjs
# 3. 跑冒烟测试（知识库自洽、未标注率、裁决分布、报告生成）
node test-core.mjs
```

如果动到备注里的章节锚点（新增/改写判定格），跑一次 `node check-docs.mjs --update` 重建基线——
否则基线里的锚点集合还是旧的，页面会报「引用的章节不存在」。只改判定状态、不动锚点则不需要。

## 重建语料（游戏发新版本时）

```bash
# 1. 改 fetch-corpora.mjs 顶部的 PIN（aramkit resource 目录名、DDragon/CDragon 版本号）
node fetch-corpora.mjs            # 抓原始快照到 data/raw/，180 个文件约 13 MB
node annotate-crawl.mjs           # 预演：只比对，打印差异，不动 data/requirements/
node annotate-crawl.mjs --write   # 确认后落盘（旧语料自动备份到 data/raw/legacy/）
node build-corpora.mjs            # 重新内联，刷新页面即生效
node test-core.mjs
```

预演不写语料，但会刷新 `data/raw/sidecar/`（每条技能命中对象的 `DataValues` 与
`mSpellCalculations` 原文，173 个英雄约 1.1 MB）；只有在检出差异时才另写
`data/_rematch-diff.md`（逐条改动的技能清单）。
sidecar 不参与判定，是留给后续把「具名数值 + 属性系数」拆成可求值表达式时用的原料——
这一层数据一旦过期就取不回来，所以每次抓取都存。

### 技能槽位是怎么匹配的

aramkit 给的是 `Q/W/E/R/P` 五个槽位，CommunityDragon 给的是技能对象，两者没有共用 ID，
必须重新配对。四遍扫描，前面的遍优先：

| 方式 | 规则 | 条数 |
| --- | --- | ---: |
| exact | 对象叶名 == 英雄名 + 槽位字母（如 `AhriE`、`EliseR`） | 536 |
| numeric | 冷却 / 射程 / 耗蓝三个数组逐位比对（容差 0.01） | 178 |
| passive | P 槽取叶名含 `passive` 的对象 | 129 |
| unresolved | 取不到，原语留空 | 22 |

必须先把**全部** exact 做完再做 numeric，否则数值匹配会抢走别的槽位的精确对象。
并列时取 `DataValues` 更多的那个。

> 早期临时脚本对没命中 exact 的技能是「拿同英雄其它技能代标」，结果伊莉丝 Q/W/E/R 全挂着
> 蜘蛛形态 E 的数据、奥拉夫五槽共用一套标签并集。这批数据已按上表重算——
> 用 329 条旧 fallback 反向搜索，只有 37 条能在该英雄的对象里找到唯一匹配，
> 说明它是多对象拼接产物，无法复现也不具备语义正确性。

## 判定依据会不会过期

这套判定的前提是「某条原语由某篇文档的某一节承接」，依据写在 `data/model.js` 的备注里，
形如 `数值聚合器.md §2.1`。TCS 的文档还在改，一节内容换了，原来的判定就可能不再成立。
`check-docs.mjs` 负责把这件事变成可检测的：

1. 从 `data/model.js` 的备注里抽出所有 `文件名.md §章节号`，解析成锚点；
2. 记录每篇被引用文档的文件哈希、每个被引用章节的内容哈希（含子章节）；
3. 与基线比对，得出「哪篇变了、哪几节变了、哪些判定格要重看」。

```bash
node check-docs.mjs            # 检测：打印变更文件、待复核判定格、锚点体检
node check-docs.mjs --update   # 把当前文档状态记为新基线（复核完判定之后才跑）
```

检测结果会出现在三个地方：页面顶部横幅（有变更时变红并给「看待复核清单」按钮）、
「文档状态」视图（六张卡片 + 变更清单 + 待复核判定格表 + 锚点体检）、
以及能力矩阵里对应的格子（左侧橙色标记 + hover 提示状态）。
`check-docs.mjs` 每次运行都会重写 `data/doc-snapshot.js`，页面靠它拿到当前状态；不跑它就看不到变更。

它只做两件事：**Level 1** 文件级（文件哈希变了）与 **Level 2** 章节级（`##` / `###` 标题树的内容哈希变了，
含子章节、章节被删、章节被新增）。不做 Level 3 语义级——判断「这一节改了以后原判还成不成立」需要读懂内容，
那一步只能人工做，工具负责把范围从 97 个判定格缩到几个。

配套的「锚点体检」与变更无关：它检查备注里写的章节现在是否还存在。
`section-cited-missing` 说明备注引错了节号或文档改了小标题，`unresolved-file` 说明文件名写错或文档被移走。

判定格锚定率目前是 66/97：有正式文档或草稿的 66 格全部带章节锚点，剩下 31 格属于 State / Skill / damage / Targeting
这类连草稿都没有的域，本来就没有章节可引。

## 数据来源

| 语料 | 条数 | 版本 | 来源 |
| --- | ---: | --- | --- |
| 海克斯增幅 | 216 / 239 | 16.20 / 16.22 | aramkit `augments.json` |
| 英雄属性 | 173 | 16.22 | DDragon `champion.json` + aramkit 大乱斗平衡调整 |
| 装备 | 197 | 16.22 | aramkit `items.json` |
| 符文 | 62 | 16.23.1 | DDragon `runesReforged.json` |
| 英雄技能 | 865 | 16.22 | aramkit `champion-skills` + CommunityDragon `mSpellTags`/`mSpellCalculations` |

海克斯「旧版/新版」在数据层是按版本目录快照区分：16.20 → 16.22 是**整池替换**
（新增 41 条全在 3xxx 号段，移除 18 条全在 12xx–21xx），不是两套并存。所以工具只存一份数据 + `version` 切片。

## 已知局限

- 需求→原语的映射来自 Riot 官方技能标签与伤害公式节点，不来自人工阅读技能文案。
  技能槽位靠叶名 / 数值数组 / 被动名三重复用匹配（见上表），22 条 `unresolved` 因取不到对应对象，
  原语只能退回文案推断，其判定结果比 `exact` 的弱。
- 技能原语目前只到「这一条技能有哪些效果」（`totalValue`/`magicDamage` 等），
  还没拆到「每个伤害分支的 DataValues 与公式树」，所以 `dmg.instant` 是粗粒度标签而非可求值表达式。
- 海克斯增幅的原始逻辑配置在服务端，客户端资源里拿不到（`map12.bin.json` 里没有任何 augment 数据），
  只能判到「文案描述的效果」，判不到实现细节。
- 判定单元是**文档族的一块契约**，不是代码模块；文档没写的领域一律落「缺依据」，
  那是文档进度问题，不是框架能力问题。
- 只有 LOL。DNF 接入后置。

## 为什么不做成在线服务

判定知识库是**手写资产**（88 条原语、23 个判定档、断在哪个文档的哪一节），
它的价值在于被评审、被修正、被 diff，不在于并发与部署。
零构建单页让「改一条判定 → 刷新就能看结果」的回路最短，也让这份资产能直接进版本库被 review。
