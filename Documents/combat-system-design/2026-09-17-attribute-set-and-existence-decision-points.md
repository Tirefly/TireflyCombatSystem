## 零、裁决结论（2026-09-17）

**D2-14 属性存在性：能力与推荐用法分开书写。**
- **框架能力 = 允许**：`AddAttribute` / `RemoveAttribute` 是常驻能力，引擎**不禁止**运行期动态增删——"无法预测其他开发者在自己的项目里如何操作"（用户口径），故不替使用者设限。
- **推荐用法 = 结构**：roster 由 AttributeSet 在**初始化 / 重置**时确定；运行期只动 modifier（挂/移除/改基值/来源级联）——即文档一直假定的用法。
- **不做溯源（A3 撤销）**：实例不加来源字段。**动态增删的代价显式写明**（用户 2026-09-17 **逐条确认接受**）——不记"谁加的" ⇒ ①**撤销粒度只能到"整条属性"**（两个来源都要 `Health` 时，一个撤销只能整条删，另一方需求被静默破坏；要来源级需宿主层记账）；②`RemoveAttribute` 销毁实例 ⇒ **槽位内 modifier 一并丢弃**，而这些 modifier 的**来源可能仍然存活**（buff 还挂着、装备还穿着）——贡献**不会自动恢复**（施加只发生一次，无重放机制），属**静默丢失**；③**重新加回 = 全新实例**（base value 回定义默认、`bDirty` 重置、槽位为空，`SetBaseValue` 写过的等级成长值不保留）。
  - **②与③已被 §五 冻结/解冻裁决取代（2026-09-18）**：`RemoveAttribute` 不再是"销毁"，而是**冻结**（整条实例含槽位进暂存区）；"加回"不再是"全新实例"，而是**解冻搬回**（基础值/槽位原样）。本条保留为**决策留痕**（当时的否方案与代价记录），实现口径以 §五 与 Task 5 提案 delta 为准。
- **AttributeSet 与运行期动态集合分离**（用户口径）：Set 的职责**只有初始化/重置**，它不是"运行期属性集合的唯一入口"，也不承担"运行期增删的语义"——两者解耦。

**D2-15 AttributeSet 形态**：B1a + B2 + B3a（用户选定）
- **B1a 粒度**：Set 是资产，**引用点在实体侧配置**（实体 Def / Actor BP 上的组件引用）；引擎**不认识"游戏模式"轴**——换情景 = 宿主换实体身上的 Set 引用（或换实体）。
- **B2 持有与施加**：Set 资产 = **GameInstance 级 Const 内容**（归 DefLibrary 管辖面，与 Def 族同款主资产身份）；"某单位当前用哪套 Set" = **World 级**可变状态；施加动作 = World 级，入口在 `RegisterEntity` 之后、穿过 DefLibrary `IsRuntimeReady()` 门禁之后（06 §2.1/§2.2）。
- **B3a 切换语义**：`ApplyAttributeSet(Unit, Set)` = 把该单位的属性集合**置为这套**（diff 替换：旧 Set 独有 → 移除、新 Set 独有 → 添加、**共有保留实例**——不打断在飞 modifier、不丢 `SetBaseValue` 改过的 base value）；`ClearAttributeSet(Unit)` = 整组清空（供重生成单位用，显式声明"在飞 modifier 随之失效"）。
- **引用形状**：`TArray<FGameplayTag> DefTags`（与"Def 资产文件可改名/挪目录、按 `[PrimaryAssetType, DefTag.GetTagName()]` 解析"一致），由 DefLibrary 解析；**覆写列首版不做**（"同属性不同情景不同基础值"走宿主 `SetBaseValue`，日后要数据驱动再加列，向后兼容）。**身份载体 2026-09-22 由 `TArray<FName> DefIds` 改 tag**（提案 `switch-identifiers-to-gameplay-tags`）。

**落地时机**：AttributeSet 随 **M6（DefLibrary/WorldRegistry 落地轮）** 同批；D2-14 的"能力/推荐用法"姿态**可立即回写文档**（无代码改动）。

## 二、决策点 A：属性存在性 = 结构，还是动态？

### A0 语料现状（五条证据，一致指向"结构"）

1. 02 §2.2a：「**基础值：属性表默认 → 实体注册时初始化**；等级成长 = 宿主升级事务 `SetBaseValue`」——注册期定**集合**，运行期只动**数值**。
2. D2-5 事务：写操作 =「挂/移除/**改基值**」——挂/移除指 **modifier**（D2-2），改基值指 base value；**没有一类是"增删属性"**。
3. D2-8 实例形状：`{Base, CachedCurrent, Dirty, Bounds, ModifierSlots}`——对比 `FTcsAttrModInstance` 有 `Source` 字段，**实例没有来源位**。
4. 02 §5 网络姿态：「复制 **modifier** 操作流（挂/移除/来源）」——属性存在性不在复制面内。
5. 02 §2.2a「三种修正器存放地总表」+ §2.2「modifier 生死完全绑定来源句柄」——**buff / 装备 / 技能在全部文档里一律被描述为 modifier 来源**，没有任何一处说它们增删属性。

**结论**：语料不是"中立"，而是**已经默认了 A1**。"装备授予一条新属性"这类需求目前是**语料外的假设**，不是既有设计——若要支持，是**改设计**（要动上表 #1/#2/#3 三处），不是"补一个字段"。

### A1（推荐）属性 = 结构：注册期确定 roster，运行期只换整组

- 语义：单位被注册时按"该单位的 AttributeSet"建出属性实例集合；此后**只允许**动 modifier（挂/移除/改基值/来源级联）。属性集合的变更只有一种形式：**换 Set（整组 roster 替换）**——由 AttributeSet 的 diff 替换承担（见 §三 B3）。
- 代价：宿主不能"临时给一个单位加一条属性"——必须走"换 Set"或"改词表子集"。
- 收益：实例保持**纯数值形状**（零来源字段）；事务、网络操作流、复制契约**一律不用扩**；M2 保持"纯函数聚合器 + 静态结构"的简单心智。
- 连锁影响：**无**（这是语料现状的显式化）。

### A2 动态增删、不做溯源

- 语义：`AddAttribute` / `RemoveAttribute` 可在运行期自由调用，但实例不记"谁加的"。
- 代价：**"撤谁"无法回答**——A 来源加了 Health、B 来源也要 Health，A 走了只能整条删（B 的属性凭空消失）；且事务/操作流/复制契约都要扩到"属性增删"（§一 #2/#3）。
- 收益：宿主最自由。
- 判断：**不建议**——省下的字段换来的是一类无法表达的语义（部分撤销），而"整组替换"已经覆盖了绝大多数真实需求。

### A3 动态增删 + 实例来源字段（完整动态）

- 语义：`FTcsAttributeInstance` 增 `Source: FTcsSourceHandle`（或来源集合），`AddAttribute` 增来源参数，撤销按来源级联（与 modifier 同构）。
- 代价：①实例形状变更 + 门面签名第三次变更；②事务与操作流扩面；③**"属性下线时在飞的 modifier 怎么办"**需要新语义（modifier 的 Target 指向已不存在的属性实例）；④词表/UI 侧要能表达"这条属性由什么授予"。
- 收益：装备/天赋真正能"授予属性"，且能精确撤销。
- 判断：**只有当你确认要"运行期由内容源动态授予属性"时才选**。它是一条完整的能力线（含语义#3 的未决问题），值得独立一轮设计与验收，不该为 Task 4 的"顺手支持"而半途落地。

### A 对比表

| | A1 结构（推荐） | A2 动态无溯源 | A3 动态 + 溯源 |
|---|---|---|---|
| 实例形状 | 不变（纯数值） | 不变 | +Source |
| D2-5 事务面 | 不变 | 扩"属性增删" | 扩"属性增删" |
| 02 §5 操作流 | 不变 | 扩 | 扩 |
| 部分撤销 | 由 Set diff 承担 | ✗ 无法表达 | ✓ |
| M2 复杂度 | 最低 | 中 | 高（含新的失效语义） |
| 与语料一致性 | 一致（现状显式化） | 冲突（需改 3 处） | 冲突（需改 4 处 + 新语义） |

## 三、决策点 B：AttributeSet 的粒度、持有、施加

### B0 语料现状（四条）

1. 02 §2.2a「属性表默认 → **实体注册时初始化**」——**施加时机天然在注册路径上**（措辞已定）。
2. 06 §2.1 双层引导：**Const 定义 = GameInstance 级**（DefLibrary，无世界可查、供图鉴/UI）；**可变状态 = World 级**（WorldRegistry/单位桶）；门禁 = `IsRuntimeReady()` **单出口**、失败清单透传。
3. 06 §2.2 组件第 1 职责：`Initialize → RegisterEntity`（分配句柄、**创建桶**）——**建桶的唯一入口**。
4. 06 §3 入口服务：实体组件暴露 `GetHandle()` / **`GetAttributes()`** / 可选 `GetBrain()`——属性入口已在组件面。
   （判据来源：`MEM-20260902-05` —— **先枚举全部消费场景，再定生命周期级别**；Const 内容可跨 PIE 共享，需隔离的只有可变状态。）

### B1 选集粒度（谁决定"这个单位该有哪些属性"）

- **B1a（推荐）实体侧引用**：Set 是资产（`UTcsAttributeSetAsset`），**引用点在实体侧的配置**（实体 Def / Actor BP 上的组件引用），一实体配置一个 Set。
  - 模式差异怎么表达：**宿主在生成/切换模式时换实体身上的 Set 引用**（或换实体），引擎不认识"模式"这个轴。
  - 收益：TCS 不引入新概念轴（"游戏模式"是宿主词汇，非战斗本体论）；粒度天然可到"每个实体"。
- **B1b 引擎引入"模式 → Set"映射**：TCS 认识 `GameMode`/`Scenario` 概念并维护映射表。
  - 代价：给 M2/M6 引入一个**与战斗无关的宿主概念**（LAC 单机自走棋甚至没有"模式"），且映射归谁维护、模式标识从哪来都要新定义。
  - 判断：不建议——违反"插件不替项目规定情景"的一贯口径（D5-17 v3 同款原则："TCS 提供选项，开发者自行选择"）。
- **B1c 逐单位显式施加**（`ApplyAttributeSet(Unit, Set)` 由宿主自己调）：最灵活、零新词汇，但**没有声明位**——"这个单位的属性从哪来"无处可查（排障/图鉴/复制都要问宿主）。
  - 判断：作为 **API 存在**是对的（切换模式要用），但不应是**唯一**表达——否则又回到"语义散在宿主代码里"。

### B2 持有级别与施加者（按 MEM-20260902-05 判据）

| 角色 | 级别 | 理由 |
|---|---|---|
| Set 资产本身 | **GameInstance 级**（Const 内容） | 与 DefLibrary 同族：无世界可查、跨 PIE 共享、供图鉴/配置工具读 |
| "某个单位当前用哪套 Set" | **World 级**（可变状态） | 模式切换/单位重生成会改它；与单位桶同寿命 |
| 施加动作 | **World 级**，入口 = 注册路径 | 06 §2.2 建桶唯一入口；门禁 = DefLibrary Ready（单出口） |

**推荐**：Set 资产归 **DefLibrary 管辖面**（与 Def 资产同族，`[PrimaryAssetType, DefId]` 主资产身份一体适用）；施加由 **World 级**在 `RegisterEntity` 之后（门禁通过后）执行；组件 `GetAttributes()` 顺带暴露"当前 Set"查询。
不建议把施加放进 DefLibrary（它是 Const 面，不应写 World 状态）。

### B3 切换语义（模式切换时怎么变）

- **B3a（推荐）diff 替换**：`ApplyAttributeSet(Unit, NewSet)` = 旧 Set 独有 → `RemoveAttribute`；新 Set 独有 → `AddAttribute`；共有 → **保留实例**（不重建、不打断已有 modifier）。
  - 收益：切模式不打断在飞的 buff/装备（它们的 modifier 还挂在原实例上）；`AddAttribute`/`RemoveAttribute` 已是现成原语（Task 4 已落地）。
- **B3b 全清重建**：清空后按新 Set 重建。
  - 代价：**在飞 modifier 全部失效**（Target 指向被销毁的实例），且丢运行期缓存的 base value 变化（等级成长会被重置）——除非宿主显式搬运。
  - 判断：不建议作为默认语义；可作为显式 `ClearAttributeSet(Unit)` 单独提供（供"重生成单位"用）。
- 未定细节（建议一并钉）：**Set 内引用用 `TArray<FGameplayTag> DefTags`**（与 Def 资产"文件可改名/挪目录"的主资产身份一致，由 DefLibrary 按 `[类型, DefTag.GetTagName()]` 解析），而非直接软引用 Def 资产；**覆写列（同一属性在不同模式不同基础值）首版不做**——需要时走宿主 `SetBaseValue` 事务，日后要数据驱动再加一列（向后兼容）。

## 五、冻结/解冻兜底（**已裁决 2026-09-18：冻整条属性**；设计定稿，代码待落地）

用户追问"运行时动态增删属性带来的三个麻烦能不能解决"，并**自行提出**"冻结/解冻"方案；agent 复核后建议把冻结单位从"只冻数值效果"提升为"**冻整条属性**"，用户 2026-09-18 选定**冻整条属性**。**实施排期 = plan1 Task 5（聚合管线轮）**——与该轮的 `RemoveBySource` 同批实现（共存规则必须与之同时落地与验证）；规格 delta 草稿见本文档 §附录（Task 5 提案时复制，不另立独立提案）。

### 三个麻烦长什么样（具体场景）

- **麻烦一「装备穿脱，等级加成丢了」**：角色 10 级，装备给了一条「护甲」，宿主按等级把它写成基础值（5 + 等级×2 = 25）。脱下装备 → 护甲这条属性被删 → 再穿上 → 护甲重建出来是 5，**等级加的那 20 没了**。
- **麻烦二「buff 还在身上，数值没了」**：一个 buff 给「攻击力 +50」。有人（或某次重置）把「攻击力」整条删掉 → 属性连同槽位里那 +50 一起消失。但 **buff 本身还在**（没到期、没被移除），系统也没有"再施加一次"的动作，所以那 +50 **不会回来**。装备/buff 看着好好的、数值就是不对——最难查的一类问题。
- **麻烦三「两个东西都要同一条属性」**：装备和天赋都要求角色有「生命值」。天赋到期撤了 → 系统只知道"有人要删生命值"，不知道"装备也还要" → 只能整条删掉，**装备那边的需求被悄悄破坏**。

**根子一句话**：属性身上只记了"数值是多少"，**没记"是谁让它存在的"**。所以框架分不清"没人要了"和"还有人要"；删的时候也只能把整条连里面的效果一起扔掉。

### 定案：冻整条属性（把"删除"改成"搬进暂存区"）

- **`RemoveAttribute` = 冻结**：把**整条属性实例**（基础值 / 边界 / 值域模式 / 修正器槽位）从单位容器搬进暂存区，不销毁、不丢数据，输出日志（属性名 + 冻住的效果数）。
- **`AddAttribute` = 解冻优先**：暂存区有同名实例 → 整条搬回（基础值取回冻结前的值、效果原样还在），输出日志；没有 → 按定义行新建（现行为）。
- **双态约束**：同名实例不得同时存在于容器与暂存区（搬移语义保证；两处都有会导致重复计算）。
- **单位注销**：暂存区随单位容器一并释放。

**为什么冻"整条"而不是只冻效果**（agent 建议、用户选定）：代码量几乎相同（都是"从容器挪到另一个容器"），但多保住基础值 ⇒ **麻烦一顺带解决**；且读侧语义与"删除"完全一致（这条属性就是不存在），**不需要引入"停用/禁用"这种第二状态**——后者正是"软删"方案复杂的根源。

**必须同时加的一条硬规则**：`RemoveBySource`（聚合管线轮落地）**必须同时扫描容器与暂存区**。否则：来源在属性被冻结期间结束 → 它按惯例撤销时在容器里找不到自己的效果（已被搬走）→ 该效果**永远滞留**；属性被加回来时解冻执行，那 `+50` **凭空出现且永久留着**——比丢数值更难查。加上这条后方案自洽：暂存区只是"效果暂时没地方挂"的地方，来源生死照旧由持有者按既有纪律走。

### 代价变化（相对 2026-09-17 的三条）

| 原代价 | 现状 |
|---|---|
| ① 撤销粒度只能到"整条属性"（两个来源都要时，一个撤销只能整条删） | **仍存在**，但后果降级：属性被冻结而非销毁，数值效果与基础值都留着、加回即恢复；不再"永久丢失"。要来源级仍需宿主层记账 |
| ② `RemoveAttribute` 丢弃槽位内修正器（来源仍存活 ⇒ 静默丢失） | **已消除**（冻结保留槽位内容） |
| ③ 重新加回 = 全新实例、基础值回定义默认 | **已消除**（整条实例进出，基础值保留） |

**残留（如实记录）**：属性缺失期间读它 = 0（依赖它的公式会看到 0）；"两个来源都要同一条属性"仍会整条删（粒度不变，只是伤害变轻）。

**明确不做**（保持简单）：暂存区条目上限、保质期清理、解冻时校验来源存活性（框架**判断不了**来源死活——`FTcsSourceHandle` 只是编号、无存活性登记，属既有设计）；"来源级精确撤销（记一本'谁要它'的账）"（原解法一）与"软删/停用状态"（原解法二）均判定为过重、不做。

  - **修订（2026-09-18，首轮 PIE 实测暴露）**：草稿原写 `bDirty = false`，落地后发现**值域收口会被整段跳过**——"从定义行抄来的缓存初值"被当成已结算值：基础值 150、边界 0..100、Clamp 的属性会一直读到 150，直到某个后续写入把它标脏（静默错值）。改为**新建即脏**：初值在"批外读取或提交"这一刻由管线结算（那一刻单位上的属性图通常已搭好，**定义/添加顺序不影响结果**）；不宜在 `AddAttribute` 内立即结算——动态边界会读到尚未添加的引用属性（求值 0）→ 把原值钳成 0 且无人再标脏。规格 delta 正文以 Task 5 提案 `specs/attribute-store/spec.md` 为准（本附录为草稿留痕）。
- `RemoveAttribute(Unit, FTcsAttributeName)`：**冻结**——把整条实例（含基础值/边界/值域模式/槽位内容）从 `Attributes` 搬入暂存区 `FrozenAttributes`，MUST **不销毁、不丢弃槽位内容**，MUST 输出冻结日志（含属性名与槽位数）。拒绝面（ensure + false）：单位未注册、属性名为空、该单位未持有此属性。

**场景**：①*移除属性 = 冻结而非销毁*——返回 true、`FindInstance` 为空、整条实例出现在暂存区（`FindFrozenInstance` 非空且字段保真）、输出冻结日志；②*添加属性 = 解冻优先*——属性被冻结后（期间其基础值可能被宿主改过）再次 `AddAttribute`，暂存区整条搬回：基础值/边界/值域模式/槽位与冻结前一致（**不回落到定义默认值**），并输出解冻日志、暂存区条目消失。

### ADDED：属性冻结暂存区

`FTcsAttributeStore` MUST 持有暂存区 `FrozenAttributes`（`TMap<FTcsAttributeName, FTcsAttributeInstance>`）：

- **整条进出**：冻结与解冻都以**整条实例**为单位（基础值 / 边界 / 值域模式 / 修正器槽位一并保留）——这是"装备穿脱不丢等级加成"与"buff 还在、数值不丢"两条兜底的实现基础。
- **双态约束**：同一属性名 MUST NOT 同时存在于 `Attributes` 与 `FrozenAttributes`。
- **查询口**：`FindFrozenInstance(Name)`（mutable/const，未命中返回 nullptr，**不 ensure**）。
- **与来源撤销的共存（MUST）**：来源撤销（`RemoveBySource`）**MUST 同时扫描实例槽位与暂存区**，否则来源在"属性被冻结"期间结束、其修正器永久滞留，属性恢复时**凭空多出数值**（比丢数值更难查）。
- **生命周期**：暂存区随单位容器生存——`UnregisterUnit` / `Deinitialize` 释放；MUST NOT 引入条目上限、保质期清理或"解冻时校验来源存活性"（框架判断不了来源死活：`FTcsSourceHandle` 只是编号、无存活性登记，属既有设计）。

**场景**：①*冻结后整条保真*（基础值/边界/值域模式/槽位数逐字段一致）；②*解冻后恢复原值*（基础值为冻结前的值、槽位仍在、`bDirty` 沿用冻结前状态）；③*双态互斥*；④*单位注销释放暂存区*。
