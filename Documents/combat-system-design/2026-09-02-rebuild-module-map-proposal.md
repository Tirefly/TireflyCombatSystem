## 0. 重建前提（动手前必须承认的四件事）

### 0.1 冲突披露：悬空的 OpenSpec 提案（来自 task-open 记忆卡 MEM-20260819-09）

### 0.2 "从零" ≠ 从零思考

三份调研的**结论**是资产，从零重建的应当是**代码与结构**，不是认知。已定且继续有效的裁决：

| 修饰符聚合 recalc 式：Override(0)>Add(10)>PercentAdd(15)>Mul(20)，脏标记惰性重算，1e-5 阈值 | 对照提案 | 直接继承 |

### 0.3 怀疑必须清单化（否则会带着惯性重蹈覆辙）

"陷入怀疑"不能是模糊的不安。TCS 调研已知的结构性问题清单——重建必须逐条给出"新系统如何避免"的答案；**若你的怀疑不在此清单内，先说出来，再动手**：

1. **策略类爆炸**：~40 个策略类（TSubclassOf×17 / FInstancedStruct×6），大量分支只有单一实现 → 应由数据驱动规则替代的，不该做成类。
2. **无中心事件总线**：组件间靠直接调用/组件查找，隐性耦合 → 裁决2a 已给解法。
3. **无 ScaledDt**：计时语义悬空（既无 TimerManager 也无缩放处理）→ 裁决2b 已给解法。
4. **组件中心 vs 千人战场**：UTcsStateComponent 挂 Actor 的模型与 Mass 小兵层冲突 → 两级单位架构已定，但新系统核心必须"可脱离 Actor 运行"。
5. **高风险三连**：orphan-scan 子目录误删、ReadyNow 分支跳过 OnReady、ready 不等 DefAsset 预加载 → 新系统引导时序重做。
6. **Fragment 机制悬空**：state-fragment 提案未落地，生命周期扩展点缺失 → §0.1 处置。
7. **幽灵依赖与死代码**：GameplayMessageRouter 幽灵依赖等 → 重建起点干净，无此问题。

### 0.4 第二系统效应防线

从零重建的最大心理风险：为了证明旧系统"错"，把新系统做得过度泛化。防线三条：

- 每个模块写**显式非目标**（本文各模块已带）；
- 竖切验收：每完成一层就跑一条真实链路，不在无消费者的层上堆功能；
- YAGNI（用户画像既定偏好）：AbilityKit 的 92 包规模是反面参照，我们是单插件。

## 1. 依赖铁律（"低耦合"的可检查标准）

不喊口号，用五条可 grep 检查的规则定义"低耦合"：

1. **依赖只允许向下**：M(n) 不得 include M(n+1) 及以上任何头文件。
2. **跨域通信只走两扇门**：M0 事件总线，或显式接口（UINTERFACE）。
3. **运行时实例不持有 UCLASS 强引用**：`TSubclassOf<>` 只允许出现在定义资产（M1）侧。
4. **强类型 key 空间隔离**：AttributeId / StateId / EffectId / CueId 各自独立枚举或命名空间，禁止打包共享一个整数域（AbilityKit 的 ModifierKey↔AttributeId 混用教训）。
5. **数据驱动验收线**：策划新增一个 buff/技能 = 纯数据资产 + 表格行，**零 C++ 改动**；只有新增原语/规则类型才动 C++。

"高内聚"的检查标准：每个模块能用一句话说清它对外的**词汇**（类型）与**服务**（入口函数），内部变更不外溢。

## 2. 模块地图（M0–M8）

        M8 编辑器与工具          M7 表现

             ▲                                    
        M6 集成（横切：组件/Mass/StateTree/引导，挂在 M2–M5 上）

### M0 内核（Foundation）
- **职责**：句柄与实例注册表/池、事件总线+订阅表（裁决2a）、时钟（TickableWorldSubsystem 泵 ScaledDt，裁决2b）、诊断（CVar/日志类目/DeveloperSettings/断言/Explain 钩子）。
- **铁律**：零战斗语义；不 include 任何战斗头文件；可脱离 Actor/World 语义运行（Mass 兼容）。
- **非目标**：不做任何"通用 ECS"、不做网络同步、不做反射工具箱。
- **依据**：TCS 13-foundation 报告；AbilityKit core 层（事件/池/定时器/确定性/诊断）；裁决2a/2b。

### M1 词汇与数据契约（Vocabulary & Contracts）
- **职责**：Tag 词汇表规范（宿主透明值、不预设分类学，MEM-20260821-01）；强类型 key 空间（铁律4）；Def 资产基类 + 定义注册表 + 预加载/就绪状态机（修 ReadyNow 三连）+ 校验器；DataTable 双轨 authoring（TCS 03 已验证的设计，继承）。
- **特性**：M1 只供骨架；各域模块（M2–M5）自带自己的定义切片，**不预先为所有域定义**（防过度设计）。
- **依据**：TCS 01/02/03 报告；MEM-20260819-07 配置内聚标尺。

### M2 属性/数值（Attributes & Modifiers）
- **职责**：强类型属性容器；Modifier{来源句柄、Tag、通道、值、时限}；recalc 聚合管线（已定裁决：优先级带序、组内顺序无关公式、脏标记惰性重算、1e-5 阈值）；clamp 管线（TCS 05 经验）；事务提交 + TG_PostUpdateWork flush（TCS 04 思路）。
- **非目标**：不做 GAS 兼容层、不做网络复制（若拍板需要则回补）。
- **依据**：TCS 04/05 报告（TCS 唯一"确定做对了"的部分，思路全收）；AbilityKit Attributes/Modifiers。

### M3 状态/Buff（States）
- **职责**：State 定义 ↔ USTRUCT 实例+句柄+池（裁决：struct 做状态）；生命周期 apply/refresh/stack/expire/remove，计时走 M0 时钟；Tag 关系规则表（裁决1）；回合制等生命周期扩展 = 通用 Fragment 机制 + 消费层模块（MEM-20260819-07 三问标尺的落点，承接被冻结的 TCS 提案思路）。
- **依据**：TCS 06/07/08 报告；裁决1；AbilityKit。

### M4 效果执行（Effects）——最大模块，拆三个子模块
- **M4a 事件与触发**：事件分类表（sync-immediate vs frame-end pump，**待拍板**）；触发器行 12 字段（提案 v1 **待拍板**）；订阅随句柄生命周期配对清理。
- **M4b 原语执行**：FEffectStep 17+3 原语集（提案 v1 **待拍板**）；链/Gate/Branch/Parallel/Repeat（含熔断）/OnError；执行上下文与变量。
- **M4c 查询与投射**：SelectTargets/targeting、SpawnProjectile/SpawnArea。
- **依据**：AbilityKit Pipeline/Triggering/combat 原语；FEffectStep 提案 v1；12 条通用设计门。

### M5 技能（Skill/Cast）
- **职责**：施法账本（双账本思想继承自 TCS 09 但重做）；GCD/前摇/后摇/打断/Cancel/冷却（冷却链路封闭，作者约定 + 模块账本，沿 MEM-20260819-09 已确认的冷却结论）；边界 = 技能是原语链的**编排者**，效果是**原子**。
- **依据**：TCS 09 报告；AbilityKit Ability 聚合运行时。

### M6 集成（Integration，横切）
- **职责**：两级单位适配——军官=全功能组件、小兵=Mass fragment+processor（核心逻辑须可脱离 Actor 调用）；StateTree 决策集成（只做决策/编排；修 `FStateTreeExternalDataDesc::ID` 裸读的 WITH_EDITORONLY_DATA 坑）；bootstrap/预加载时序（修高风险三连）；M0 tick 泵接线。
- **依据**：TCS 06/10/11 报告；unreal-state-tree 技能；裁决2b。

### M7 表现（Presentation）
- **职责**：Cue 接口——核心只发 cue 事件/调 `ICuePlayer` 接口；Niagara/动画/震屏/音频均为宿主适配，核心零 include。
- **依据**：FEffectStep PlayCue；裁决3（可视化跟随数据形状）。

### M8 编辑器与工具（Editor & Tooling）
- **职责**：定义资产编辑体验与校验器（濒死配置扫描）；按数据形状的可视化（修饰符=表、状态=表、原语链=管线图，裁决3）；Explain/调试面板；DataTable 热重载。
- **非目标**：不做 K2 节点、不做通用图编辑器框架。
- **依据**：TCS 12 报告；裁决3；AbilityKit Explain/TestKit。

## 3. 实施顺序：三个方案

### 方案 A：纯自底向上（M0→M1→M2→…→M8 串行）
- 优点：依赖最干净，每层落定时下层全部就绪。
- 缺点：前期数周无任何可运行反馈；M0/M1 无消费者约束，**第二系统效应最容易在此发作**（把内核做成框架乐园）。

### 方案 B：垂直切片优先
- 优点：最快见到活系统（一条伤害链打通），契约错误最早暴露。
- 缺点：切片外的模块契约可能被切片需求带偏，回头返工；一次性要同时设计 5 个模块的最小集，认知负载大。

### 方案 C（推荐）：叶先行、竖切验收
节奏（R=轮，一轮≈一个模块的一次拍板→文档循环）：
- **R0 立场文档**：为什么重建 / 继承什么（§0.2 表）/ 放弃什么（§0.3 清单逐条对应解法）/ 处置两个悬空提案。——把"怀疑"变成文档，这是整个重建的地基。
- **R1 M0-min**：只做第一竖切需要的最小内核：句柄+注册表/池、事件总线、时钟泵。**明确不做**诊断面板等。
- **R2 M2 属性层完整**：第一个正式模块。
- **R3 竖切**：M4b 单原语 Damage 跑通 定义→属性→效果→Cue（M1 属性切片、M7 stub 一并就位）。
- R4 M3 状态 → R5 M4a+M4c → R6 M5 → R7 M6（两级单位+StateTree）→ R8 M7/M8 补全。
- 推荐理由：
  1. M2 是全图**依赖叶**，下面只有 M0-min，无先决悬案；
  2. 其设计决策已成熟（recalc 聚合已定裁决），且 TCS 已证明该管线可行——是唯一可直接继承的高置信结论，先重建它能立刻建立信心锚点；
  3. 强类型 key 空间必须**最早冻结**（它决定 M3/M4/M5 的接口形状）；
  4. 验证最便宜：编译 + 一张测试属性表定向人工检查，无需整套系统；
  5. 策划可见度最高（属性表即所得），最早兑现"数据驱动"承诺。

## 4. 每模块工作法（逐个拆解分析的固定流程）

每个模块一轮（或数轮）：
1. **输入**：三份调研中该模块相关报告的结论 + 既有裁决 + 记忆卡标尺。
2. **决策点清单**：3–5 个必须拍板的问题，各带 2–3 方案 + 取舍 + 推荐。
3. **拍板**：用户逐项确认（显式拍板，记入决策日志）。
4. **产出**：`NN-module-<name>.md` 设计文档（本目录），含职责/类型词汇/入口服务/非目标/依据。
5. 检查点纪律照旧（约 5 轮实质交流或阶段边界产卡）。
