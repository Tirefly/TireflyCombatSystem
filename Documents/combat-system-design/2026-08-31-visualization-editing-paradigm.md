## 1. 背景与问题

一个战斗系统的技能脚本、Buff 脚本，到底适合用什么样的可视化模式来执行编辑：**行为树、状态机、状态树，还是离散 EventGraph**（类似 GAS 的 GameplayAbilityBlueprint）？

## 2. 决定性原则：编辑范式跟随数据形状

**编辑器不是中立皮肤**——行为树编辑器只能编辑行为树数据，状态树编辑器只能编辑状态树数据，蓝图图编辑器编译的是蓝图字节码。**选编辑器 = 选运行时。**

裁决 1/2 已钉死数据形状：技能=步骤链协程（FEffectStep）、Buff=触发器表+修饰器聚合、状态关系=Tag 矩阵、行为流转=StateTree。因此本问题的大半答案被推论得出：**凡是自带执行模型的候选，采用它就等于推翻已定裁决**。剩下唯一的选择是：每种已定数据形状配哪种"视图"。

## 3. 四候选逐一裁决

| 候选 | 自带执行模型 | 与已定数据形状的匹配 | 裁决 |
|---|---|---|---|
| 行为树 | 竞争性选择 + 装饰器 | 技能链可用 Sequence 硬套，但选择器/装饰器语义对线性异步流程全是噪音；Buff 规则表完全不匹配 | ✗ 采编=换执行器 |
| 状态机 | 状态流转 | 技能步骤链硬掰成状态——撞 MaxStates=8、每步一次状态选择开销【源码调研】 | ✗ |
| 状态树（StateTree） | 同上 + 编译烘焙 + 值拷贝绑定 | 最差：吃全部源码级硬伤，运行时不可动态实例化 | ✗✗ |
| EventGraph（GAS 式 exec-pin 图） | 若借 BP 实现 = 蓝图 VM | **exec-pin 潜在动作图恰是"异步命令序列"的天然视图**：节点=异步操作，exec 线=继续点，等待=挂起 | ✓ **借范式，不借运行时** |

**GAS GameplayAbilityBlueprint 的图范式与实现是两回事**：采纳前者（潜在任务链的可视化），拒绝后者（每技能一个 BP 类、编译成 VM、UObject 实例执行）——图编辑器画的是自己的 `FEffectStep` 数据，执行的仍是已定的协程泵。

## 4. 结论：不是四选一，是按数据形状分配视图

| 编辑对象（已定数据形状） | 编辑范式 | 开发成本 |
|---|---|---|
| 技能步骤链（协程） | **自研管线步骤图**（exec-pin 风格：步骤节点 + 等待/分支/并行子图），数据即 `FEffectStep` 引用 | 高（放验收期） |
| Buff 触发器/修饰器（规则表） | **表格 + 行内详情**——规则的本质是表，不是图；单条效果链展开时用行内迷你图 | 低（先行） |
| 状态关系（Tag 矩阵） | **关系矩阵视图**（裁决 1 已定） | 低 |
| 行为流转 | StateTree 自带图视图【源码调研：SStateTreeView】 | **免费（零开发）** |

## 5. ACT 类技能加分形态：管线图 + 时间轴混合

步骤链绑定 Montage 时间后，编辑器可渲染**时间轴 lane**（前摇/生效/后摇轨道 + 取消窗口标注）——"管线图 + 时间轴"混合视图比纯节点图更贴帧数据需求【设计判断】。它仍只是步骤数据的另一种投影，不改数据模型。

## 6. 实现路径与节奏（重申已定顺序）

1. **现在**：DefAsset 列表编辑器（Details + DetailCustomization）——Buff 表与技能步骤列表先行；
2. **第二步**：运行时调试 overlay（单位 Buff 栈/技能游标/Tag 容器实时视图）；
3. **验收期**：自研管线图——技术路线走 UE 经典 `UEdGraph/UEdGraphNode/SGraphPanel` 框架（Material/Anim/Niagara 同款）自绘自定义节点【通识，5.8 具体 API 届时核对】；**不走 K2 自定义节点**（会把图编译回蓝图 VM，等于借了要拒绝的运行时）。
