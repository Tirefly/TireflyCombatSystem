# 2026-09-02 — Mass 连续内存与数据布局备忘（讨论记录，未拍板）

- 日期：2026-09-02
- 状态：**讨论记录 / 未来优化抽屉**——本轮无拍板、无设计变更；触发时机 = M3 落地后的 1000 单位压测数据
- 动机（用户原话）：中央注册表、非 Tick 聚合等设计都以千人战场（Mass）为目标；"Mass 的核心优化策略我记得就是连续内存，所以想看看 TCS 未来能不能在框架基底就实现"——针对 BuffInstance / SkillInstance / SkillEntry / Attribute / AttributeModifier 的**连续内存访问 + 动态增删改查**

## 1. 结论先行

1. **原语已在手**：`TTcsInstancePool`（稠密数组 + 代际 + FreeList，plan1 Task 1）就是 DOD 存储核——"动态增删改查 + 连续内存"的**机制问题已解**：增 = FreeList 弹槽/尾追加 O(1)；删 = Swap-with-last + Generation+1 O(1)；查/遍历 = 稠密数组顺序访问；稳定引用 = 句柄 Index+Generation（D0-2）。
2. **剩下的是粒度**：池目前住在 per-unit 桶内（桶内连续）；问题是"要不要域级全局连续"。
3. **审计结论：现有热路径吃不到多少 SoA 红利**——本系统热循环是"按脏属性聚合 + 到期堆到期驱动 + 目标遍历"，**没有跨单位扫描全部实例的循环**；更频繁的查询形态是分组查询（"单位 X 的 buff 列表"），全局 SoA 反而打散分组。
4. **推荐目标形态**：**域级全局稠密池 + 单位级轻索引**（混合式）——数据连续与分组保留兼得，机制平移非重写，句柄契约（D0-2）零改动。
5. **时机纪律**：M3 按桶形态实现（现设计）→ 1000 单位压测 → 数据说话再做池上移平移（有界重构）。

## 2. 原语已存在（plan1 Task 1）

```cpp
template <typename TInstanceType, typename TTagType>
class TTcsInstancePool {
    TArray<TInstanceType> Instances;   // 稠密连续内存
    TArray<uint32>        Generations; // 悬空防护（代际校验）
    TArray<uint32>        FreeList;    // O(1) 增删
};
```

这正是 ECS/DOD 存储的句柄原语（Index+Generation+FreeList）。**框架基底已经实现**——讨论的实delta 只是"池的宿主从桶挪到域层"。

## 3. 访问模式审计（五类型，谁真的吃连续内存红利）

判据：DOD 收益 = 热循环"顺序扫过大量条目、只碰少数几个字段"。

| 类型 | 访问模式 | 全局 SoA 收益 |
|---|---|---|
| FStateInstance（BuffInstance） | 到期堆/事件驱动——**没有逐帧扫描全部 buff 的循环**；查询形态是分组查询（单位 X 的 buff 列表） | 低 |
| FCastRun（SkillInstance） | 施法期瞬态、生命周期极短 | 低（池化已解决分配） |
| FLearnedSkillEntry | 长寿命、低变动、按单位查询 | 低 |
| FAttributeInstance | **聚合热路径**（脏属性重算） | 中——按 (单位,属性) 分组才有效；全局 SoA 反而打散分组 |
| FTcsAttributeModifier | **聚合热路径**（脏属性遍历 ModifierSlots） | **现状已连续**——每属性一个稠密数组，按消费方分组恰好正确 |

重要发现：聚合关键对（Attribute + Modifier）**现状已是连续的**——ModifierSlots 按属性分组的稠密数组，与聚合循环的访问模式吻合。全局 SoA 会把按属性分组拆散，需要二级索引重建分组——负收益。

## 4. 全局 SoA 真正能吃的三个场景

1. **快照/复制/回放**：稠密数组批量 memcpy/序列化（存档、Explain 全量导出、调试器快照）；
2. **Mass 小兵批量处理**：未来若小兵逻辑改为"按系统批处理同构实体"（真正的 ECS 式 tick），SoA + 按类型分桶遍历才真正吃到缓存；
3. **内存碎片/分配抖动**：已被池 + FreeList 解决（非 SoA 独有收益）。

## 5. 推荐目标形态（混合式：域级全局稠密池 + 单位级轻索引）

```cpp
// 域子系统内（以 State 域为例）
TTcsInstancePool<FStateInstance> GlobalInstances;   // 域级全局稠密池（连续）
TMap<FTcsCombatEntityHandle, FUnitIndex> UnitIndex; // 单位级轻索引

struct FUnitIndex {
    TArray<FTcsStateHandle> InstanceHandles;   // 该单位的实例句柄列表（轻）
};
```

- 数据连续（全局池）+ 分组保留（单位索引）；
- 增删 = 全局池 O(1) + 单位索引数组 O(1)；
- **句柄契约零改动**——Handle 的 Index 从"桶内下标"变"全局池下标"，语义不变（D0-2 不动）；
- 改动量 = TTcsInstancePool 从桶内挪到域子系统层、Bucket 轻量化——**机制平移，有界重构**。

## 6. 时机纪律与触发条件

1. **现在不动**：竖切（plan1/plan2）无状态桶，M3 才出现 per-unit 池——现在做域级池 = 给零消费者造基础设施（缺失 vs 有意纪律）；
2. **M3 按桶形态实现**（现设计，D3-1 拍板口径不变）；
3. **压测规格**：1000 单位 × 5 buff × 10 modifier——测聚合（脏属性重算）/到期处理/范围查询的帧耗时 + cache miss；对照组 = 桶形态 vs 域级池+轻索引；
4. **触发条件**：压测证明分组查询或快照成为瓶颈 → 执行第 5 节平移；否则抽屉继续关着；
5. **不做投机性字段拆分**（SoA 拆字段）——除非压测显示某个循环真的在逐字段扫大数组。
