## 2. 装置抓到的缺陷（本节是本 Task 最有价值的产出）

### 缺陷 1（**产品缺陷，已修**）：`ECT_OnCastStarted` 档扣了资源却不发 `CostApplied`

- **现象**：检查 `F2` 报 `FAIL`——`CostApplied` 次数 **0**，而同一行的 `F1` 显示资源**确实扣了**
  （`100.000→70.000`）。
- **根因**：Task 2 把"发事件"的职责切给了调用方（`CommitCost` 是**纯扣减**、拿不到条目身份），
  而**激活路径这一处漏了那一行**——只调了 `CommitCost`，没调 `BroadcastCostApplied`。
- **为什么这是真缺陷而不是"判据太严"**：扣减是**可观察的状态改变**，没有对应事件
  ⇒ 订阅者的 UI 永远不刷新（`MEM-20260902-12`「事件与可变性 API 成对」点名的那类**静默不一致**）。
- **修法**：激活路径与 `OnEvent` 降级路径**两处都补发**；代码内留注记标明"初版漏了、装置 F2 报 FAIL"。
- **可证伪**：修复后 F2 `PASS`（次数=1，句柄/单位/属性/数量逐项吻合）。

### 缺陷 2（**装置缺陷，已修**）：检查 `I3` 假失败——谓词轮询了"时间派生量"

- **现象**：`I1`（到期成立）/`I2`（恢复可放）**全 PASS**，只有问事件计数的 `I3` 报 `FAIL`（次数=0）。
  症状极具误导性：看起来像"事件没发"。
- **实测时序（同一帧内，报告原文）**：
  ```
  冷却已起 … 时刻=2.791        ← 谓词成立（Now 已越过 EndTime）
  [FAIL] I3 次数=0            ← 此刻 CooldownEnded 还没发
  冷却到期 条目=3/7            ← 到期回调这才跑、这才广播
  ```
- **根因（引擎层，可复现）**：初版谓词写 `GetTrackRemaining(...) <= 0.0`，而
  **"时间到了"与"事件到了"是两件事**。两者是**同一个到期堆**的条目，而
  `FTcsExpiryHeap::AdvanceTo` 按 `(DueTime, Sequence)` **升序**回调——
  等待件 `DueTime` = 起等+0.05（更早）、冷却件 = 起冷+1.0（更晚）⇒ **等待件先回调**。
  无头**首帧把时钟一次推到 2.79**（首帧 `DeltaSeconds` 是常规帧百倍量级，本仓既有实测）
  ⇒ 两者**同帧到期**，顺序完全由 `DueTime` 决定。
- **判据来源**：这正是 `TcsDevCombatClockWait` 头文件**判据 2** 点名禁止的形态
  （"轮询被测事件本身，MUST NOT 轮询一个相邻但不同的量"），其反面教材即 R6 的"坑一"
  （问"完成了吗"却轮询"墙钟过了几秒"）。⇒ **同一类错误本轮第二次命中**。
- **修法**：谓词改为直接问 `CooldownEndedCount >= 1`，使两个量不再可分。
- **可证伪**：修复后 `I3 PASS`（次数=5）。

### 缺陷 3（**装置缺陷，已修**）：跨帧读事件计数，订阅却已退订

- **根因**：初版在**立即面结束**时就退订四枚订阅，而 `I1~I3` 是**跨帧**的
  ⇒ 尾段落定时订阅已断。
- **修法**：退订移进**尾段回调**。
- **纪律（已写进代码）**：凡"跨帧尾段要读事件计数"的装置，退订 MUST 排在落定之后。

### 缺陷 4（**装置缺陷，已修**）：保活手法用错形状

- `TStrongObjectPtr` **不可拷贝** ⇒ 无法按值捕获进 `TFunction`（实测 `C2039 'ToSharedRef'`）。
  初版想用 `TSharedRef` 包一层——**那是错的形状**。
- **正确手法 = 照 R6 先例**：**文件级 `TStrongObjectPtr`**（`GR65DeferredObserver`）持有保活，
  尾段捕获**弱引用**。判据：`UTcsEventHandler` 由总线**弱引用**持有，没有别的 GC 根时会被回收
  （R6 `GSkillLayerDeferredObserver` 的注释原文即此）。

## 4. 取证边界（**如实，MUST NOT 读成"已全面验证"**）

### 4.1 无头面为何不足以覆盖全部判据

R6 已用血换来一条结论并**给了两个实例**：**无头跑过 ≠ 验证过**。第二个实例比第一个更阴——
编辑器 PIE 里 `Reject` 的检查 `e` 会 `FAIL`，而**无头下同一检查 `PASS`**
（每条无头命令各自一个独立进程、进程间不共享登记表 ⇒ 每条命令总是"第一个"登记那些身份
⇒ **无头明确给出假绿灯**）。

**本轮属"无头易给假绿灯"的判据（MUST 在 PIE 复验）**：

| 判据 | 为何无头可能给假绿灯 |
|---|---|
| `D1`/`D2` **组轨跨条目共享（真 GCD）** | 组槽是**单位级**、跨命令残留；单进程无头下"先跑谁"固定 |
| `F1`/`F2` **TOCTOU** | 需"门禁过后、提交点前资源被花掉"，依赖同进程内多条命令的次序 |
| `B1` 空轨道阴性对照 | 若同进程内先跑过别的命令，登记表/账本状态不同 |
| 跨 PIE 残留 | 无头每条命令一个进程，**结构上测不到** |

### 4.4 ★★ 编辑器 PIE 面抓出的两处夹具缺陷（本档最有价值的产出）

> **两处都是夹具（`TcsDev`）缺陷，不是插件缺陷。** 插件的门禁/提交逻辑在两处都**表现正确**。
> **两处都在无头下拿到绿灯** —— 与 §4.1 预先声明的形态同族，**夹具缺陷 P1 是它的第三个实例**。
>
> **⚠ 编号说明**：本节两条编号为 **`P1`/`P2`**（P = Probe，**夹具**缺陷），
> 以区别于 §2 的 **缺陷 1~4**（那四条里有三条是**插件**侧、一条是夹具侧）。

#### 夹具缺陷 `P1`（**判据级**）：跨帧谓词"问对了哪件事、却问错了哪一条" ⇒ `I2` 误报 FAIL

- **现象**：PIE 下 `Run` = **22/1**（`I2` FAIL），而**无头下 23/0**；两轮 PIE **逐字复现**。
- **日志时序（硬证据）**：
  ```
  冷却已起 …R65SelfTrack  轨道 1/1 起冷 CDR=0.000 时刻=79.259   ← 被测轨（1.0s）
  冷却已起 …R65Cdr        轨道 1/1 起冷 CDR=0.500 时刻=79.259   ← CDR 轨（0.5s，同时刻起冷）
  01.08.02:905  冷却到期 条目=3/7 轨道=0        ← **CDR 先到期**，全局计数被顶到 1
  01.08.02:950  条件成立（轮询 10 拍，0.550s）  ← 等待**提前落定**
  01.08.02:950  技能激活被拒[冷却中] … 剩余=0.450  ← 自身轨**还剩 0.450s**（真值！）
  01.08.02:950  [FAIL] I2 回执=2 期望 6          ← **夹具误报**
  ```
- **根因**：`TcsDevCombatClockWait` 判据 2 要求"**轮询被测事件本身，MUST NOT 轮询一个相邻但
  不同的量**"。初版问的是**时间派生量**（已修）；第二次改问事件后，问的是**全局**
  `CooldownEndedCount`——而**同一轮里并存多条时长不同的轨道**，CDR 轨先到期就把全局计数满足了。
  ⇒ **"事件发生了吗"问对了，但"哪一条的事件"问错了。**
- **无头为何给假绿灯**：无头首帧 `DeltaSeconds` 是常规帧的**百倍量级** ⇒
  **两条轨在同一帧一起到期** ⇒ 全局计数与自身轨计数**恰好重合**、不可分。
- **修法**：谓词改按**条目身份**筛（新增文件作用域的 `GR65CooldownEndedByEntry`，
  键 = `FTcsSkillEntryHandle`）。**复验硬证据**：`I1` 的 `ElapsedSeconds` 由 **0.550s → 1.333s**
  （越过被测的 1.0s），`I3` 显示**全局计数 = 5** 而自身轨 = 1 ⇒ 可见被修掉的污染量。
- **★ 这是 `TcsDevCombatClockWait` 判据 2 的第三次命中**（前两次见该头文件的坑一/坑二）。
  **推广**：**"问事件"还不够，还要问"哪个主体的事件"**——凡共享计数表被多个主体写入，
  按全局计数等待就是等错了量。**该教训已写进等待头的注释面**（见 §7）。

#### 夹具缺陷 `P2`（**前提级**）："未持有"这个前提**只在无头下成立** ⇒ 检查 `e` 误报 FAIL

- **现象**：PIE 下 `Reject` = **6/1**（`e` FAIL），而**无头下 7/0**。
- **根因两重**：
  1. **前提在 PIE 下不成立**：`e` 拿 `Attribute.Armor` 当"未持有"的属性，而本装置的
     `Bootstrap->ApplySliceAttributes` 会一次授予 `Health/MaxHealth/Attack/**Armor**` 四条
     （`TcsDevBootstrap.cpp:122-125`）⇒ 单位**真的持有 Armor**。
     **日志实证**：`属性新建 Unit=3 Attribute=Attribute.Armor BaseValue=5.000000`。
     ⇒ `TryGetBaseValue` **正确地**返回 `true`，是夹具判它 FAIL。
     **无头下**内容资产发现 0 条 ⇒ 属性定义表为空 ⇒ 四条一条也没加成
     ⇒ "未持有"**只在无头下成立**。
  2. **取向单一，测不到该口存在的理由**：本口的理由是"`GetBaseValue` 对未持有返回 0.0，
     与'确实持有且基值为 0'**不可区分**"。初版只验"未持有 ⇒ false"这一向
     ——**恰恰验不出"持有且基值为 0"会不会被误报成未持有**。
- **修法**：① 改为**两向都验**；② **另造一个不调 `ApplySliceAttributes` 的裸单位**取得真正的
  未持有态（**MUST NOT 用 `RemoveAttribute`**：它对未持有是 `ensureMsgf`，而"已持有"这一前提
  恰恰随环境而变——那正是本缺陷的成因 ⇒ 会按环境吐红字）。
  另造单位使两向前提都由本段自建，**与内容资产是否装载无关**。

#### 4.4.1 两处缺陷的共同教训

**"无头跑过"与"PIE 跑过"的差集不是噪音，而是判据本身的适用域。** 两处缺陷都不是
"PIE 里环境更脏"，而是**夹具把一个只在无头下成立的前提当成了普遍前提**
（`P1` 的"两轨同帧到期"、`P2` 的"属性表为空"）。
⇒ **凡夹具依赖"某个量恰好如此"的，MUST 问"这个前提是谁建立的、在另一条路线上还成立吗"。**

**影响面实测 = 0**：全仓 `.uasset` 扫 `ECT_OnEvent` / `TriggerEventTag` **零命中**
⇒ 枚举数值变化（`ECT_Manual` 3 → 2）不影响任何已存资产。

**规格面落点** = 提案 `remove-cost-onevent-timing`（`skill-cost`：**3 REMOVED + 3 ADDED**）。
**为什么用 REMOVED+ADDED 而非 MODIFIED**（值得记，是校验器逼出来的正确形状）：
MODIFIED **整块替换**，要求 scenario 标题**逐字保留**；而本需求有两条 scenario 标题
（"四档时机且无打断档"、"`OnEvent` 档激活时不扣…"）**天然以被删的档位命名**
⇒ 保留它们就是让规格继续宣称一个已不存在的档位，改成 REMOVED+ADDED 才能如实改名。
**代价**：归档后需求**净增 0**（3 删 3 增），但**名称变了**——其中一条由
"消耗配置的数据形状（**策略与时机**）"改为"（**策略与三档时机**）"，
"消耗事件与 `OnEvent` **中继**"改为"消耗事件与 **`CostApplied`**"。

### 8.2 `OnCastCompleted` 档扣费失败时"施法仍报成功" —— **确认为有意，维持**

**裁定原文（用户）**："这是个切实存在的状况，不过我觉得只要 `CanActivate` 的时候，
`CanAfford` 判定过了，就可以默许通过。"

**状况**：`ECT_OnCastCompleted` 档在施法**完成**时提交。门禁⑤ 在**激活**时已判过"付得起"，
而提交在**完成**时——中间隔着整段施法时间，资源可能被别处花掉；此时提交点的重查（TOCTOU 防护）
会拒绝，**而施法已报 `SAR_Success`、`Completed` 事件照发**，宿主拿不到"没付成"的信号。

**处置 = 维持现状**（据此裁定）：**"门禁已过即视为默许"** —— 扣费失败不改变施法结果。
**留痕面已够**：提交点留 `Warning`（"提交消耗被拒[重查未过]"），宿主若要预判可用查询口
`CanAfford`。**MUST NOT** 为零消费者给 `FinishCastRun` 的四个调用点加"费用状态"形参
（那会让四处都被迫处理一个与它们无关的值）。

**本裁定的意义**：它把此前只有我一人判断的一处**升格为规格级决定**——
原先它只是代码注释里的一句"有意"，现在有用户裁定背书。**但仍在 `SPEC-04-skill` 侧待补明文**
（下一步，见 §8.3）。
