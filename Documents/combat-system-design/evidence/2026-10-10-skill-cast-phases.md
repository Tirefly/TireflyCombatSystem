## 2. ★ 关键判据与阴性对照（本轮的证据核心）

### 2.1 `P2` 瞬发 = 激活当刻完成（甲′ 裁定的运行时判据）
空时段表技能激活后：**在册 run 数不增**（`0→0`）、`Completed=1`、`PhaseChanged=0`、**`Interrupted=0`**、
条目 `RunHandles` 为空。

**为什么"判据 MUST 含打断零次"**：若实现走的是"激活 → 建 run → 立刻 `TerminateRun`"（复用打断路径），
读数会是 `Interrupted=1 / Completed=0` —— 只验"run 已归还"的实现会**全绿**，
而那种实现把**一次成功的瞬发施法报成了"被打断"**（玩家侧可观测的语义错误）。
⇒ 本项是本轮**最关键**的一条，因为它是甲′ 裁定（四路终结中"完成"这一路）唯一的直接读数。

### 2.2 `P3` 三档互不混同（阴性证据）
同一次查询里：`DefSwitches=假`（定义开关）/ `PhaseTable=真`（当前段字段）⇒ **两档读数互异**。
**为什么必须有这一条**：装置刻意让**定义开关与当前段字段真值相反** ⇒
若实现"三档都读定义开关"或"都读当前段"，两档会给出**同一个值**，
而**任何单独一档的检查都会照常通过**（各自都"符合预期"）⇒ 单靠逐档检查判不出"没真的分派"。

### 2.3 `P4` / `P4b` 打断成对（拒绝必须无副作用）
- `P4`（可打断段）：返回真、`Interrupted=1`、**`Completed=0`**、句柄解析得 `nullptr`；
- `P4b`（不可打断段，**阴性对照**）：返回**假**、零事件、**且"运行态仍可解析 + 在飞读数不变"**。

**`P4b` 的第三项为什么必要**：只验"没有事件"会让"**静默把运行态弄坏了**"的实现全绿
（例如误摘了 `RunHandles` 或提前归还了槽位，而事件恰好没发）。⇒ 判据 MUST 含"**运行态仍可解析**"。

### 2.4 `P6` 重入终结只发一次事件（Task 3 遗留边界的收口）
首次终结返回真、**二次返回假且静默**（守卫命中、零 `ensure`）；`Interrupted` **1→1**。

**它闭合的是 Task 3 自认的那半**：`TcsCastOps.cpp` 当时只挡住了"双次归还槽位"，
**"打断事件发两次"仍在**（其注释自认归属即本 Step）。本轮按状态侧已验证的解决体例
（进出广播窗口成对标记/解除）收口 ⇒ `Interrupted` 二次后**仍为 1**。
> **注意本轮只验"事件不重复"这一条**：`P6` 的读数取自一次同步回调内重入；
> **跨帧重入未单独取证**（见 §6 边界 5）。

### 2.5 `P5` 重定向栈（挂 / 摘 / 优先 / 后挂，四条各自可判）
```
P5 重定向读数：基线=EffectChain.Check.CastProbe 挂上=EffectChain.Check.CastRedirectProbe
              高优先=EffectChain.Check.CastProbe 后挂=EffectChain.Check.CastRedirectProbe 在册=3

```
- **基线**半：未挂任何重定向 ⇒ 起链 = 定义自己声明的链，且**不产生"未实现"的 Warning**（未命中是正常路径）；
- **挂上**半：读数取**实际起链身份**（不是"重定向表里有几条"）；
- **高优先** / **后挂**：两条判据**各自可证伪**（低优先那条**仍在册却落选**；同优先级取后挂）；
- **摘除**半：按来源**恰摘 3 条**（挂了几条就摘几条 = 成对性），随后起链**变回**全局定义
  ⇒ **挂与摘各取一次读数**（只验"挂上生效"会让"摘除没实现"或"摘错了"全绿）。

### 2.6 `P9` 主链启动档"进入指定时段"（**本轮最后补上的一档**，判据成对）

## 4. ★ 本轮抓出并修掉的 9 处真实缺陷（症状 → 根因 → 判据）

> **分类先说清**：**缺陷 1~5、7、8 是装置/夹具缺陷**（产品读数在同一次日志里是正确的）；
> **缺陷 6 是产品侧信号污染**（行为正确、但每次施法终结留一条无意义红字）。

### 缺陷 1：跨帧 lambda 按引用捕获形参 `World` ⇒ 悬空引用 ⇒ 定时器一拍即崩溃（**最险**）

- **症状**：`T5-phase-run2.log` 出现 `Fatal error!` + `Unhandled Exception: EXCEPTION_ACCESS_VIOLATION
  reading address 0x0000000000000296`（实测：该日志 `EXCEPTION_ACCESS_VIOLATION` 命中 **1** 次、
  `GetTimerManager` 命中 **1** 次；调用栈**落在该 lambda 内部**）。
- **根因**：延时段检查用 `World->GetTimerManager().SetTimer(...)` 注册跨帧回调，
  而 lambda 以 `[&]`/`[&World]` **按引用捕获形参 `World`**。命令函数**返回后**形参的生命周期已结束
  ⇒ 回调里再用它即读已释放栈内存。
- **判据**：**跨帧 lambda 的一切捕获都必须是值或弱引用**。特别是——
  **"形参指针按引用捕获"在同步调用里永远正确、只在跨帧时炸**，
  所以这类缺陷**不会**在"跑完立刻检查"的写法里暴露，只在**跨帧**时暴露。
- **修法**：改按值捕获 `TWeakObjectPtr<UWorld>`（跨帧回调统一口径）。

### 缺陷 2：`FTimerHandle` 按值捕获于 `SetTimer` 之前 ⇒ 清的不是自己 ⇒ 定时器永不停

- **症状**：`T5-phase-run3.log` **3.54 MB**、`SUMMARY PhaseDeferred` 命中 **3 497 次**
  （每 0.05 秒刷一条，`轮询拍数` 一路涨到 3500+）。**数值全对、只是停不下来**。
- **根因**：`FTimerHandle` 在 `SetTimer` **之前**就被跨帧 lambda **按值捕获** ⇒
  捕获到的是**尚未填写的无效句柄** ⇒ 回调里 `ClearTimer(捕获的那个句柄)` **清的不是自己**
  ⇒ 轮询永不停。
- **判据**：**句柄必须放进共享状态（`TSharedPtr`）**，回调在**调用时刻**经共享状态读它；
  "按值捕获句柄再清它"这种写法**在单拍情形下看似正确**，只有**多拍**才暴露。
- **修法**：句柄放进 `TSharedPtr` 共享状态，回调读共享状态里的句柄。

### 缺陷 3：延时段按"固定秒数"赌取样时刻 ⇒ 无头首帧步长极大 ⇒ 取样比完成早 28 毫秒

- **症状**：初稿按固定 `1.2` 秒后取样 ⇒ 读成 `Completed=0`（**假 FAIL**）。
  实测根因：**无头模式首帧 `DeltaSeconds` 是常规帧的百倍量级**，战斗时钟**两帧就冲过三段**，
  而墙钟才走了几十毫秒 ⇒ 补拍比完成**早 28 毫秒**。
- **根因**：把"墙钟时间"当成了"战斗时钟时间"来估计取样点。
- **判据**：**MUST 轮询"完成"这一事件本身**（run 从池里消失即完成），**MUST NOT 赌固定秒数**；
  并 MUST 设**上限**（本轮 = 200 拍）、**超时如实报失败**（**MUST NOT 当通过**）。
- **修法**：改为轮询完成事件 + 上限 200 拍 + 超时判失败。

### 缺陷 4："完成当刻的运行态字段"被事后再查 ⇒ 读成 -1 的 FAIL

- **症状**：`T5-Phase-final.log` 的 `PhaseDeferred` 行读成 `完成当刻下标=-1`，
  对应检查 `P8 多时段终值` **FAIL**。
- **根因**：**判据没错、取样时刻错了**——完成之后槽位**已归还**、句柄悬空，
  事后再查运行态自然得到 `-1`（"查不到"），而不是"下标不对"。
- **判据**：需要"**事件当刻**的运行态字段"时 MUST **在事件回调内取快照**——
  依据是本仓既有的两条纪律：**订阅是同步当场派发**、且"**先广播后归还槽位**"
  保证**事件当刻是读得到的最后时刻**。事后补查必然读到悬空。
- **修法**：观察者新增"事件当刻运行态快照"（`bHasLiveRunSnapshot` / `LastLivePhaseIndex` /
  `CompletedPhaseIndex`）⇒ 读数由 `-1` 变为正确的 **2**。
  **实测对照**：修前 `T5-Phase-final.log` = `下标=-1` + `P8 多时段终值` FAIL；
  修后 `T5-Phase-v2/v2b/v3` 与最终基线 = `下标=2` + 该检查 PASS。

### 缺陷 5：观察者 `GetWorld()` 为 `nullptr` ⇒ 整段快照恒不落定

- **症状**：观察者里的"事件当刻快照"**恒不落定**（`bHasLiveRunSnapshot` 永远为假）。
- **根因**：观察者用 `NewObject` 创建时**未指定 outer** ⇒ `UObject::GetWorld()` 靠 **outer 链**找世界，
  找不到 ⇒ 返回 `nullptr`。
- **判据**：装置内需要世界的对象 MUST **显式取世界**（本仓既有口
  `TcsDevSliceRigInternal::FindSliceRigWorld()`），**MUST NOT 依赖 `NewObject` 的隐式 outer 链**。
- **修法**：改用 `FindSliceRigWorld()`。

### 缺陷 6：`FinishCastRun` 里新加的 `RemoveBySource` 对"未注册单位"留 Warning ⇒ 信号污染

- **症状**：**每次施法终结一条红字**（`参数...`/属性侧 `RemoveBySource` 对未注册单位告警）。
- **根因**：新落地的四路终结例程对 `Run.Unit` 直接调 `RemoveBySource`，
  而**施法并不要求该单位在属性门面注册**（链与属性是两套登记）⇒ 该 Warning 对合法场景也发。
- **判据**：**"常规验收命令零红字"是硬验收信号** ⇒ 一个**合法且常见**的场景 MUST NOT 留红字
  （红字会把这个信号淹掉，且会诱导后来者去"修"一个不存在的问题）。
- **修法**：先 `ResolveStore` **非确保预判**（该口不 ensure）再调 `RemoveBySource`。

### 缺陷 7：`SkillCast.Reject` 命令缺"装置自持空链登记" ⇒ 混进 3 条非预期 Error

- **症状**：该命令的红字清单里混进 **3 条**
  `LogTcsEffect: Error: UTcsEffectSubsystem::ExecuteChain: 链 EffectChain.Check.CastProbe 未登记——拒绝起链`。
- **根因**：该命令的 `R7` / `R7b` / `R8` / `R9` / `R10` 五份合成定义都指向 `EffectChain.Check.CastProbe`，
  但**本命令从不登记那条链**（只有主命令 `TcsDevSkillCastProbe.cpp` 登记过）
  ⇒ 链定义库**按契约**拒绝起链并留 Error。**那是夹具缺口、不是本命令要测的拒绝面。**
- **判据（为什么必须修、而不是把它加进清单）**：预期红字清单的**全部价值在于"逐条都是有意构造的"**
  ——混进 3 条并非故意的红字，会让"**清单与实测逐条对账**"这道检查**失效**
  （读清单的人无法区分"设计如此"与"夹具漏了"）。
- **修法**：本命令开头也登记该空链（**幂等**）。**实测**：红字 **7 → 4**（清单见 §3.2）。

### 缺陷 8：两发 run 同时在飞 ⇒ 全局观察者把 A 的计数记进 B ⇒ "**恰 N 次**"判据被污染

- **症状**：`P8` 的 `PhaseChanged` **期望 2、读到 3**；`Completed` **期望 1、读到 2**。
  **两个数都各多 1**——而多出来的那一发恰好等于新加的 `P9` 的两段时段推进（进入第 2 段 = 1 次
  `PhaseChanged`，走完 = 1 次 `Completed`）。
- **根因**：`P9` 的**两段** run 与 `P8` 的**三段** run 在**同一时刻**都在飞，而两者由**同一个**
  `UTcsDevSkillCastObserver` 观测；该观察者订阅的是**全局事件**（`TcsEvent.Cast.PhaseChanged` /
  `Completed`），**不带 run 过滤** ⇒ 一发 run 的事件被记进了另一发的计数。
- **判据**：**"恰 N 次"这类计数判据 MUST 保证"同一观察者名下只有一个在飞 run"**。
  这条不是"观察者写错了"——**订阅全局事件是它的正确设计**（它要观测的是"本会话发生过什么"）；
  **错的是把两件事同时放进同一个观测窗口**。
- **修法**：`P9` 改为由 `P8` 的**完成回调串行唤起**（**先落定 `P8` 的读数，再起 `P9`**），
  且 `P9` **第一步就 `ResetCounts()`**（见 `TcsDevSkillCastProbe_Phase.cpp:800-819` / `:188`）。
- **★ 为什么这条缺陷值得单列（而不是"改个调用顺序"就完了）**：
  它的**症状长得像"判据错了"**（数字不对）⇒ 最自然的反应是去**改判据**（把 2 改成 3 就"过"了），
  而那会把一条**真实的正确判据**永久性地削弱。⇒ 纪律原文：
  **判据没错、并发错了；MUST NOT 为了让读数好看而放宽判据。**
  **同一形态在本轮出现第二次**（见 §5 的"夹具时长"）——**"同一个判据两处结论相反"是本轮的重复病灶**。

### 缺陷 9：跨帧判据的计数器没跨帧存活 ⇒ **11 条判据对"比对 `Passed=`"的复核者完全不可见**（**最易被放过**）

- **症状**：初稿的计数只有 `SUMMARY Phase: Passed=29` 一处，而 `phase` 日志全文有 **46** 条 `[PASS]` 行
  ⇒ **差值 11 条**（`P8` 的 6 条 + `P9` 的 5 条）**不对应任何计数**。
  危险之处在于：**差值是"不存在"而不是"显示为错"** ⇒ 一个比对 `Passed=29` 的复核者
  **看不到任何异常**，只会以为"就测了 29 项"，从而**静默漏掉 11 条判据**。
- **根因**：这 11 条都**跨帧落地**（判定发生在定时器回调里），而计数器当时是
  `RunSkillCastPhaseProbe` 的**栈上局部量**、函数返回即销毁 ⇒ 回调**物理上取不到它**
  ⇒ 初版只好让这些判据走 `ReportSkillCastProbe`（**只打日志、不累加 `Passed`/`Failed`**）。
  **这不是"忘了写计数"，是"计数器活不到判定发生的那一刻"**。
- **判据**：**判据一旦跨帧，其计数器亦 MUST 跨帧存活**；且**每一行带计数的 SUMMARY MUST 自带
  `Passed=`/`Failed=`**——否则读者**无法从计数发现这些判据的存在**。
  **反过来的判据同样成立**：只供屏显的**数值读数**（`6` 条 `TcsDevRig` 行）**MUST NOT** 混进判据计数，
  否则"判据数"会被数值行虚高。
- **修法**：计数器改为 `TSharedPtr<FSkillCastProbeCounter>` **堆持有**、由两个定时器回调
  **按值捕获**（`P8` 用 `TSharedPtr` 复制、`P9` 取址传入），且**两条延时段 SUMMARY 各自打印计数**
  （见 `TcsDevSkillCastProbe_Phase.cpp` 的三行 `SUMMARY`）。
- **闭合判据（可复算）**：三行计数**累计可对账** —— `Phase: 29` → `PhaseDeferred: 35`（**+6**）
  → `PhaseEnterDeferred: 40`（**+5**）；且 `40` + `6` 条 `TcsDevRig` 屏显行 = **`46`** = 全日志 `[PASS]` 行数 ✅。
- **★ 这条缺陷的元教训**：它**不是被"跑一遍"发现的**，而是**被"对账"发现的**——
  `29` 与 `46` 两个数一直并存在同一份日志里，**只有把"计数器"与"行数"放在一起比才暴露**。
  ⇒ 纪律：**验收装置 MUST 让"计数"与"实际印出的判据行"可对账**；只有一处计数而无法对账时，
  它对**漏掉判据**这件事是**盲的**。
