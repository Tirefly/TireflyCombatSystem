## 0 背景：为什么拿 AbilityKit 的 targeting 当参照

被参照对象是 `com.abilitykit.combat.targeting`——一个**纯 C#（`noEngineReferences: true`）、可组合、确定性、低分配**的目标搜索管线，作者本人为它写过一篇设计文章（附 48 条断言的三方对账）。

选它当参照的三条理由：

1. **同构度最高**：TCS 与它是同一类东西——把"找目标"做成**分段管线 + 策略契约**，而不是每个技能各写一遍遍历过滤排序；
2. **可验证**：它有用真实源码支撑的设计取舍，且**作者自己给出了缺口清单**（空间索引不内置、MOBA 侧全表过滤、包外 Selector 无评分视图）——这些"已知不做什么"比"做了什么"更有参考价值；
3. **它的失败模式与成功模式都被记录下来**：文章里六条"接入易踩边界"直接对应 TCS 将来的同类风险。

**同时必须承认两者不可直接照搬的三个差异**：

| 维度 | AbilityKit | TCS | 影响 |
|---|---|---|---|
| 运行环境 | 纯 C#，自持实体世界，无引擎 | UE5 C++，实体世界归宿主（`ITcsEntityQuery` 注入），Mass 适配是未来态 | 它可以把索引、Provider、实体访问都收进包里；TCS **必须**把这些留给宿主 |
| 定位 | 通用战斗工具集（多端、可服务端） | 框架插件（多宿主项目：LAC 自走棋 + 未来 ARPG） | 它偏"提供全套"，TCS 偏"立契约 + 少量默认" |
| 规模假设 | 候选可到数百、结果 1~8，明确讨论了空间索引与流式 Top-K | 自走棋棋盘规模小、无空间维度 | **它的性能章节大半不适用**，但**它的职责分层全部适用** |

## 1 五段管线对账：TCS 已经有几段

AbilityKit 的管线是五段（其文章原文即"Provider → Rule → SearchOrder → Selector → Mapper"）。逐段对账：

| # | AbilityKit 段 | 职责 | TCS 对应物 | 差距 |
|---|---|---|---|---|
| 1 | `ICandidateProvider` | 候选从**哪个业务集合**取数（推送式，结构体 Consumer） | `ITcsEntityQuery::EnumerateEntities`（宿主实现，`TFunctionRef` 推送） | ⚠ **是全局单例入口，不是"每次查询可配的来源"**——无法表达"以这个敌人为中心的窄集合" |
| 2 | `ITargetRule` | **资格**过滤（声明顺序、首个失败短路） | `FTcsTargetFilterStrategy::Pass`（执行器 AND 短路保序） | ✅ 等价 |
| 3 | `ITargetScorer` × `SearchOrder` | **每个排序项返回 float 分；严格字典序；每项独立升降序；全等后稳定键决胜** | **无** | ❌ **核心缺口**（详见 §2.1） |
| 4 | `ITargetSelector` | 按**已定义的顺序**取前 K 或全排序 | `FTcsTargetSelectorStrategy::Resolve`（选择器自己决定一切） | ⚠ 有"选择"但无"顺序契约" |
| 5 | `ITargetMapper<T>` | ID → 业务对象，失败跳过 | **无（且不需要）** | ✅ 缺口合理（详见 §2.9） |

**这张表的结论**：

> TCS 现在的形状是"**过滤式选择**"——能表达"**谁合法**"，不能表达"**谁更优**"。
> AbilityKit 的形状是"**两段式：先资格（Rule）、后偏好（Scorer + 严格顺序）**"，并用**稳定键决胜**把整条链钉成确定性的。

**这不是"少一个可选功能"，而是"少了一个相位"**：TCS 把"顺序"隐含在"选择器自己怎么写"里，于是

- 顺序逻辑**无法复用**（"最近的敌人"用在 3 个技能里就要写 3 遍，或写 3 个几乎相同的选择器）；
- 顺序逻辑**没有确定性约束**——选择器内部可以任意决定并列时谁先出（AbilityKit 用"稳定键升序"强制，TCS 无此纪律）；
- **没有可组合性**——"先按距离、距离相同按血量"这类字典序需求，在 TCS 里只能靠一个自定义选择器实现。

### 1.1 为什么这是本次调研最该吸收的一条

因为它同时解决**灵活性**与**性能**（正是你最初问的两个目标）：

- **灵活性**：资格与偏好分离后，"选最近的敌人"= 一个通用"距离评分器" + 一个"取前 1"选择器，**配置即可，零 C++**；换玩法只换评分项，不换选择器；
- **性能**：AbilityKit 的规则短路（Rule 先跑、Scorer 后跑）意味着**被资格淘汰的候选根本不进评分**——这是"先过滤后打分"的性能动机（UE EQS 官方原文同样理由："filter Tests are done before scoring Tests… so that fewer Items are returned and need to be scored"）。TCS 现在没有评分，等于连这个优化位都没有。

## 2 逐条吸收判据（14 条，每条的裁决与理由）

裁决分四档：**✅ 吸收** / **⏳ 延后（记录触发条件）** / **➖ 不吸收（理由在案）** / **⚠ 需你裁决**。
列**顺序即建议优先级**。

### 2.1 排序契约：有序比较项 + 稳定键决胜（✅ 吸收，最高优先）

**AbilityKit 原文口径**：`SearchOrder{ Scorer, Direction }` 有序数组；严格字典序、每项独立升降序；**所有项相等后按稳定键（EntityKey）升序决胜**。

**为什么必须吸收**（2026-09-30 修订：原首条论据被用户纠正，见下）：

- **首要理由 = 选择条件的多样性**（事实由用户提供：**LAC 策划设计的技能远不止"最近 / 血最少"两种选择条件**）。多样性 ⇒ 若没有声明式排序，"每个条件一个选择器"就是 N 份分散在宿主、不受框架校验、策划改不动的逻辑。排序相位把它压成**排序项数组**：每个技能声明自己那组条件，**配置面表达、零代码增量**；
- 它把"顺序"从"选择器实现细节"提升为"查询声明的数据"，于是顺序**可配置、可校验、可组合**——"先按威胁、同威胁按距离"这类字典序只能靠它表达；
- **并列时的确定性**：TCS 的 `10 §3` 只写了"遍历序稳定 + 过滤保序"——一旦有偏好，"并列时谁先"就成了新的分叉点，当前**无任何约束**；
- ⚠ **证据更正（2026-09-30）**：本文初稿曾把"**帧同步可重现性**"列为首要理由。但 `openspec/project.md` 明文"**LAC itself is single-player today**"——单机无联网，该论证**在当下不成立**，降级为"为将来的联网/回放留位"。并列确定性因此是**中优先理由**，不是首条。

**吸收形态建议**：

- 新增**排序项**概念（`Scorer` 策略 + 方向），与 Filter 并列成为查询的显式输入；
- **稳定键**用 `FTcsCombatEntityHandle` 的（Index, Generation）升序——TCS 句柄天然带代际，比 AbilityKit 的 `EntityKey`（需宿主提供 `IEntityKeyProvider`）更省一层；
- 纪律（直接抄 AbilityKit 的教训）：**资格条件 MUST NOT 伪装成极低分**——"死亡/满血/不可选中"归 Filter，不归 Scorer。这条要写进规格，因为它是配置期最容易犯且最难查的错。

**⚠ 内置评分器的边界规则（2026-09-30 用户拍板，取代本文初稿的"向 `FTcsParamValue` 对齐"建议）**

用户原则：**"TCS 属于可复用插件，理论上不应该直接干涉宿主项目生命值属性的配置方法。"**

这条泛化为一条可复用判据（与本仓既有纪律同源——`10 §2.2`"**框架零默认 Filter**：怎么算存活、怎么算敌人是宿主语义"）：

> **凡是需要宿主词汇的内置策略，插件一律不提供。**
> 判据 = 该策略**引用了什么词汇**：只引用框架自己的契约（如"实体有位置"）⇒ 可内置；引用宿主词汇（属性名、Tag 词表、阵营关系）⇒ 归宿主。

据此重分类：

| 排序条件 | 依赖词汇 | 归属 |
|---|---|---|
| **距离最近 / 最远** | `ITcsEntityQuery::GetLocation`（**机制层已有契约，零宿主语义**） | ✅ **插件内置（P-A 唯一内置的评分器）** |
| 血量最低 / 护甲最低 / 攻击最高 | 宿主属性词表（`Tcs.Attr.Health` 等） | ❌ 宿主实现 |
| debuff 最多 / 未受控优先 | 宿主 Tag 词表 | ❌ 宿主实现 |
| 谁标记过我 / 与谁最近（关系量） | 宿主关系数据 | ❌ 宿主实现 |

**因此本文初稿那条"评分器契约向 `FTcsParamValue`（参数源体系）对齐"的建议作废**——它等价于让 TCS 认识 `AttributeScaled` 这类宿主侧属性源，正是上述判据禁止的事；且 `FTcsParamValueSource` 是"从上下文/参数表求一个值"的机制，**并非为逐候选求值设计**，硬掰会让评分器多背一层与排序无关的语义。

**P-A 因此必须补第三个宿主插槽家族（这是初稿遗漏的）**：

| 槽 | 现状 | P-A 动作 |
|---|---|---|
| `ITcsTargetSelectorHost` / `FTcsSelHostDelegate` | ✅ 已落地（SCRIPT-8） | — |
| `ITcsTargetFilterHost` / `FTcsFilterHostDelegate` | ✅ 已落地 | — |
| **`ITcsTargetScorerHost` + 转发器**（拟名·未实现） | ❌ 缺 | **新增**——否则"血量最低"无处安放，宿主只能去写 C++ 策略类型 |

**性能纪律（写进规格）**：评分器调用频次是"**逐候选 × 逐排序项**"，高于过滤器。宿主插槽走跨语言反射（`UFunction::Invoke`），热路径上不便宜 ⇒ 规格 SHOULD 建议"**排序评分优先用 C++ 策略；脚本插槽用于低频 / 非关键排序**"，并给出判断依据，不让宿主自己撞上去。

> **★ 跨轮耦合（2026-09-30 登记）**：这个"第三个插槽家族"与 **R4.5-b（R-1 参数源插槽）**、**R4.5-c（R-2 两张注册表插槽）** 是**同一形态的三个实例**（`UINTERFACE(Blueprintable)` + `BlueprintNativeEvent` → USTRUCT 转发器），三者分散推进会把同一套验证装置（C# 实现 + 同世界原生 GC + 跨 PIE 寿命检查）写三遍。**权威登记与并批取舍见 `LEDGER-reflection`（`reflection-backlog.md`）《★ 宿主插槽家族的耦合关系》**——本文只留指针，不重复内容。

**P-A 需交付的内置评分器清单（最终）**：**距离**（唯一内置）。属性量 / 状态量 / 关系量条件全部走宿主——经上述插槽（脚本可达）或 C++ 策略（快路径）。

因此 P-A 落地前的必需输入由"策划条件清单"收窄为：**确认"距离"是唯一需要插件内置的条件**（用户 2026-09-30 已确认："先只内置一个距离最近，因为这是 LAC 一定会使用到的"）。策划清单仍有用，但降级为"用于验证宿主侧条件的覆盖面"，不再是 P-A 的阻塞项。详见 附录 A10.3.1。

### 2.2 浮点边界：NaN 排除 / 正负无穷保留（✅ 吸收，随 §2.1 同批）

**AbilityKit 事实**（已源码核实）：任一排序项返回 **NaN ⇒ 该候选在进入选择前被排除**；正负无穷**仍按方向参与排序**；且 `DistanceToEntityScorer` 在"无位置能力"时返回 **`float.NegativeInfinity`**（不是 NaN、不是 0）——**升序查询下它会排到最前**。

**为什么吸收**：这是"浮点评分如何进入确定性管线"的完整边界定义。如果不写死，宿主评分器返回 NaN 时会静默产生一个"排最后的候选"或"随机位置"，比淘汰更难查。

**纪律**：TCS 用 `double`，边界同构（NaN 排除 / ±Inf 保留）；**"缺位置"这类"无法评分"情形 MUST 返回 NaN**（= 淘汰），MUST NOT 返回 `NegativeInfinity`（AbilityKit 那个返回值在升序查询下是个陷阱，规格里要显式禁止照抄）。

### 2.3 Top-K 契约（✅ 吸收 K 的语义，⏳ 流式实现延后）

**AbilityKit 事实**：`MaxCount` 语义 = "**按完整字典序取前 K 项**"（不是"按某一个 Scorer 截断"）；实现分两档——普通选择器（收集全量再排序取前 K）与**流式标记接口**（引擎融合，边遍历边维护 K 个最优槽）。

**裁决**：

- **K 的语义必须吸收**——它是"同时打 3 个最近的敌人"这类需求的唯一表达方式，且语义必须与"完整字典序"绑定（否则会和 §2.1 打架）；
- **流式实现延后**——其复杂度是 `O(H × K × M)`（AbilityKit canonical 文档自述"最坏约 O(H×K×M)；不是堆式 O(H log K)"，且明确警告"**不能仅凭『流式』名称推断更快**"）。自走棋候选规模小、K 小，先做"全量排序取前 K"就够；**契约与实现分开**，将来换实现不动契约。

### 2.4 逐候选诊断（⚠ 需你裁决：进公开契约还是留调试面）

**AbilityKit 事实**：`SearchCandidateDecision` 五态（`Invalid` / `Duplicate` / `RuleRejected` / `ScoreUnavailable` / `Eligible`）+ 可选观察接口 `OnDecision(候选, 决策, 失败规则索引, 失败规则名, 首个排序项分)`；回调异常被引擎 `try/catch` 吞掉、**不影响选择结果**。

**价值**：它直接回答调试期最高频的问题——"**这个候选为什么没进结果**"，且**归因是结构化的**（不需要宿主在每个 Filter 里手写日志）。

**成本与风险**：

- 若进公开契约，**热路径会多一次可选回调**（AbilityKit 自己承认实现方"须自行保证热路径零分配"）；
- 若只留调试面，则**将来想升级为脚本层可读的诊断时要改契约**（`targeting-strategy` 是被脚本层消费的能力，加字段是 MODIFIED 而非 ADDED）。

**我的倾向**：**进契约但只在预览路径上生效**（结合 §2.3 / 附录 A7.3）——执行路径零成本，调试与 reticle 都能拿到归因。这是"避免后来又改契约"与"不污染热路径"的折中。

### 2.5 候选来源可窄化（✅ 吸收，但形态要改）

**AbilityKit 事实**：Provider 负责"**从哪个业务集合取数**"，Rule 只过滤已给出的候选；**加形状规则不降低候选枚举的 `O(N)` 成本**；性能优化"首先发生在阵营索引和空间粗筛"。作者进一步给了**谓词下推决策表**（稳定/可索引/多查询共享的条件 → Provider；随单次技能变化的 → Rule；需精确几何 → Provider 粗筛 + Rule 精筛）。

**TCS 的障碍**：`ITcsEntityQuery` 定义在 **TcsEffect**（机制层），TcsTargeting 依赖它 ⇒ **不能在 TcsTargeting 里新造一个平行契约**（会逼 TcsTargeting 反向具名新领域类型，违反最小编译集纪律 `MEM-20260902-13`）。

**两档吸收形态**：

| 档 | 做法 | 代价 |
|---|---|---|
| **低（推荐先做）** | **不动契约**——在规格里写明"性能责任分工"：框架保证 Visitor 零分配 + 每候选只取一次位置；**候选窄化归宿主 `ITcsEntityQuery` 实现** | 零改动；但"窄化"缺少表达入口，宿主只能在 `EnumerateEntities` 里全表遍历 + 自己筛 |
| **高（需评估）** | 给 `ITcsEntityQuery` 加一个**可选的窄化枚举入口**（如"按 AABB / 按集合枚举"），或引入 `ITcsEntityQuery2` 之类的扩展面 | 改 TcsEffect 的契约 = 跨模块 MODIFIED；且要防"框架假装认识空间语义"（AbilityKit 作者明确反对把产物做成万能入口） |

**倾向**：先走低档，把高档记成延后项（触发条件 = LAC 首个"候选枚举确实成为瓶颈"的实测）。理由：自走棋无空间维度、棋盘单位少；AbilityKit 那条"索引留给项目层"的结论本身就支持这个次序。

### 2.6 选择器产出的守恒（✅ 吸收，随 §2.1 同批）

**AbilityKit 事实**：候选去重的提交顺序是**"规则通过 + 评分成功之后才提交稳定键"**（`CandidateConsumer.Consume`），并有契约测试把这个顺序钉死；重复策略由查询声明（`DuplicatePolicy`），且**去重只约束候选进命中集之前，不约束自定义 Selector 的输出**。

**为什么吸收**：TCS 现在完全没有去重概念——若宿主 Provider 因索引重叠产出重复句柄，结果集里就会有重复目标，**下游伤害步骤会对同一目标打两次**。这是一个当前无人防守的真实缺口。

**吸收形态**：查询声明"是否去重 + 按什么键去重（默认句柄）"，并明确"去重发生在资格与评分之后"。

### 2.7 组合器（⏳ 延后，触发条件明确）

**AbilityKit 事实**：内置四个复合 Provider（`Concat` / `UnionDistinct` / `Intersect` / `Except`），语义细则齐全（并集保留全局首次代表项、交集/差集沿用第一来源顺序、顺序拼接保留重复）。

**裁决**：**延后**。理由：TCS 目前连"单一来源可配"都还没有（来源是宿主全局实现），先补来源可配再谈来源组合；且仓规"无消费者不预设"。触发条件 = 出现"附近且可见且敌方，再排除已命中"这类复合表达需求。

**但有一条要现在记**：AbilityKit 把**复合来源**（交并差）与**单候选排除**（`BlacklistRule` / `ExcludeEntityRule`）明确分成两层，且指出"查询级去重只负责候选流去重，**不能代替交集或差集**"。这条区分要写进将来的组合器设计，避免把"排除某个目标"做成一个 Provider。

### 2.8 索引与空间结构（➖ 不吸收，理由在案）

- AbilityKit **不内置空间索引**（已 grep 证实 0 命中），并把它列为"不属于当前内核"；但它的 MOBA 侧**因此吃了全表遍历 + 双目录的苦**（作者自述"最明显的项目层结构与性能问题"）。
- **TCS 的结论比它更硬**：自走棋无空间维度、棋盘单位少、`ITcsEntityQuery` 归宿主 ⇒ **在 TcsTargeting 内建任何索引对当前项目零收益**，且违反最小编译集纪律。
- **升级触发条件**（要写进规格当决策依据）：LAC 出现实测瓶颈，或第三视角 ARPG 宿主落地（那时"空间索引"从零收益变成必需，且应在**宿主或新模块**里做，仍不进 TcsTargeting）。

### 2.9 映射阶段 `ITargetMapper<T>`（➖ 不吸收，理由在案）

AbilityKit 需要它，因为它的实体身份是 `EntityId(ulong)`，下游要业务对象必须映射一层。

**TCS 不需要**：`Context.Targets` 就是 `FTcsCombatEntityHandle` 数组，**下游步骤消费的也正是句柄**——加映射层只会多一次转换与一次"映射失败静默跳过"的隐藏分支。若某个步骤真需要对象，它应通过既有的**按句柄访问器**（SCRIPT-1/8 已交付的门面手法）自行解析。

### 2.10 池化与复用缓冲（✅ 吸收，但**作为实现手段而非独立概念**）

- **不吸收**：AbilityKit 的"9 个池 + 租约 + `SearchResult` 不得带出租约作用域"整套机制——它是为**引用型结果对象**（可被长期误持）设计的，代价是引入了一套所有权纪律（调研报告里"复制稳定 ID 是契约级必需项"就是这么来的）。
- **吸收**：TCS 的句柄是**值类型**，天然的"复制即安全"，所以 TCS 只需**复用缓冲**（执行器/预览持有的 scratch 数组），不需要池化基础设施、更不需要租约语义。
- **这条同时是性能判据的落点**（详见 §2.10）。

### 2.11 查询目录与装配缓存（➖ 不吸收，理由在案）

AbilityKit 有 `TargetQueryDatabase`（查询目录 + 装配缓存），因为它面向"数百个技能、查询由配置 id 引用"的场景。

**TCS 不需要**：**链本身就是配置载体**——`FTcsStepSelectTargets` 直接内嵌选择器/过滤器策略实例，"查询"不是一个需要独立登记与 id 引用的实体。加目录只会制造第二份真相（链里一份、目录里一份）。

### 2.12 注册表两层协议（➖ 不吸收，TCS 已有更强形态）

AbilityKit 有通用组件的 Attribute 注册 + 项目配置工厂的另一层 Attribute 协议（`[TargetRule]` / `[MobaTargetSourceProvider]` 等），并靠 CodeGen 生成 Factory Manifest（且调研发现**该清单当前是空的、实际走反射回退**）。

**TCS 已有更强的形态**：`FInstancedStruct` + `meta=(BaseStruct=...)` 让策略**直接内嵌在配置里**，无需 code→factory 的翻译层，也没有反射回退的性能隐患。这条明确**不吸收**，并可作为"TCS 在设计上比它前进一步"的记录。

### 2.13 确定性纪律（✅ 吸收并**强化**）

| AbilityKit 的纪律 | TCS 现状 | 吸收动作 |
|---|---|---|
| 严格字典序 + 稳定键决胜 | 无（只有遍历序 + 过滤保序） | 随 §2.1 一起立 |
| NaN 排除 / ±Inf 保留 | 无 | 随 §2.2 一起立 |
| 跨运行时 `cos` 用 CORDIC 确定性桥（避免 libm 1-ulp 漂移） | **无对应物**——TCS 若在形状/评分里用 `FMath::Cos`、`Sqrt` 等，跨平台可能有 ULP 差异 | **TCS 的额外风险**：UE 的 `FMath` 不保证跨平台位一致。建议规格显式声明"评分与形状判定 MUST NOT 依赖超越函数的精确值"，或对扇形这类必须用三角的判定给出定点化策略 |
| "顺序不稳定 → 客户端/服务端/回放三方分叉" | `D0-1` 已有此意识但未覆盖排序 | 把"同分决胜"补进 `10 §3` 的确定性纪律 |

**2.13 的最后一行是本次对账里 TCS 独有的、AbilityKit 明确踩过的坑**——它的扇形规则专门用 CORDIC 求 cos 来避免跨运行时漂移，说明"浮点数学函数跨端不一致"是该仓库的**已知系统性风险**。TCS 若做扇形/锥形判定的角度比较，**必须先定这条**。

### 2.14 成熟度自述的借鉴（✅ 吸收为文档纪律）

AbilityKit 文章第八章有一句极有价值的方法论：

> "**公开介绍应以可编译运行时代码为准，不能把规划中的目录或类型名当成已实现能力。**"

并且它的包内文档确实骗了人：`DistanceToEntityScorer2D`（不存在的类型，5 处引用）、`OrientedRectShapeRule`（不存在）、`ctx.SetService<ISearchStats>()`（不存在）——**照包内文档抄示例会编译不过**。

## A5 推导一：形状必须与"中心"和"资格"正交（否则组合爆炸）

"以最近的敌人为中心、画半径 300 的圆、只要相克阵营"这一句需求里，含三个独立维度：

| 维度 | 归谁 | 回答的问题 | 现状 |
|---|---|---|---|
| **中心** | `ITcsTargetSelectorStrategy` | 以谁为参照（自己 / 事件目标 / 最近的敌人 / 指示器指向点） | 已有契约 2 个默认实现 |
| **形状** | **新增** `FTcsTargetShape` | 从这个中心出发，多大范围算内 | 本文范围 |
| **资格** | `ITcsTargetFilterStrategy` | 范围内的候选，谁还有资格（阵营 / 存活 / 不可选中） | 已有契约 |

**判据**：形状 MUST 是"判定"而不是"选择器的一种"。若把形状做成 `FTcsSelRadiusArea` 之类的**选择器子类**，"中心"语义会被迫在每个形状里重写一遍，组合数 = 形状 × 中心 = 6×N。

**同源依据**（AbilityKit 调研 §3.2 的对应结论）：该框架把形状做成 `CircleShapeRule` / `SectorShapeRule`（**Rule 而非 Provider**）——形状只过滤 Provider 已给出的候选，不产生候选。TCS 落法同构：**形状不枚举世界、只判定调用方给的点**。

**与仓内先例一致**：`FTcsParamValueSource` / `FTcsParamView` 已在用"策略基类 + 正交组合"这套心智，本文不引入新范式。

### A5.1 但还有第四个槽：**中心**（本文档初稿的漏洞，在此补上）

形状需要"从哪儿量"。这个中心**不能塞进形状**（否则形状被迫查世界，破坏 §4.2 的同源保证），也**不能塞进选择器**（否则"以最近的敌人为中心"这类中心语义要在每个形状里重写——正是 §2 要避免的组合爆炸）。

因此 `FTcsStepSelectTargets` 从**两槽变四槽**：

| 槽 | 类型 | 语义 | 缺省行为 |
|---|---|---|---|
| `Selector` | `FInstancedStruct`（选择器族） | **谁进入结果集** | 空 ⇒ `Context.Targets` 原样 + Warning（现有口径不变） |
| `Shape`（新） | `FInstancedStruct`（形状族） | **多大范围算内** | 空 ⇒ **不施加形状约束**（不是"全部淘汰"） |
| `CenterSelector`（新） | `FInstancedStruct`（选择器族，复用同一契约） | **从哪儿量**（其产出只取**首个**作为中心） | 空 ⇒ 取 `Context.Targets[0]` |
| `Filters` | `TArray<FInstancedStruct>` | **范围内的候选谁还有资格** | 空 ⇒ 全过（现有口径不变） |

**判定顺序**：`CenterSelector` 解析中心 → `Selector` 得候选 → **形状判定** → `Filters` 过滤 → 保序写回。

**为什么复用选择器族做中心槽**（而不是新造"中心策略"契约）：

- 中心语义与"选中谁"高度同构——"自己 / 事件目标 / 最近的敌人 / 指示器指向点"这些正是选择器已有的能力，新造一个平行契约 = 每种中心都要写两遍；
- 中心槽只用产出的**首个元素**——"选最近的敌人当圆心"因此天然成立（`FTcsSelSelf` → 自己；将来的"最近敌人"选择器 → 敌人）；
- 校验面少一个契约：只需校验"中心槽为空时 `Context.Targets` 必须非空，否则形状约束无从施加 ⇒ 保留原目标集 + Warning"。

**代价（在案）**：同一个契约承担两种语义（"选结果"vs"定中心"），读者需要靠字段名区分。备选方案是造 `FTcsTargetCenterStrategy` 平行契约，代价是"最近敌人"要写两份。**本文选复用**，但这条请重点审（Q-6）。

## A6 推导二：形状需要三个入口，缺一不可

| 入口 | 用途 | 消费者 | 形态要求 |
|---|---|---|---|
| ① **判定** | "这个点在不在形状内" | 执行器、宿主自研选择器 | 单点、无分配、可跨语言 |
| ② **枚举** | "范围内有哪些实体" | 执行器、预览、将来的 AI | Visitor（不分配中间数组） |
| ③ **预览** | "这次技能会打到谁" | 宿主 reticle、PIE 调试命令 | 纯函数、可复用缓冲 |

**为什么 ② 不能省**：若只给 ①，执行器与预览各写一遍"遍历 + 取位置 + 判定"，两处会漂移；且 `ITcsEntityQuery::GetLocation` 每次是虚调用，遍历代码重复写会放大成本。

**为什么 ③ 不能省**（本文最关键的一条）：

> **指示器不是中立皮肤，预览 = 第二次执行。** 预览与执行走不同调用路径（预览无链上下文、可能跨帧、在客户端），一旦两条路径的筛选逻辑不完全一致，指示器会**系统性骗人**——玩家看到打中 A，实际打了 B。

GAS 项目里 `AGameplayAbilityTargetActor` 之所以既是"算"又是"预览"的同一载体，正是这个理由。TCS 的对应做法 = 把"选择器+形状+过滤器"这段逻辑**只写一份**，执行器与预览都调它。

**能力边界声明**（必须写进规格，否则形状会退化成万能 Rule）：

> 形状检测是**纯几何判定**——回答"这个点在不在这个范围内"。它 **不回答**"中间有没有墙/是否可达"：遮挡、视线、寻路可达性属其他层（AbilityKit 中同在 combat 包但分属 navigation / collision 子系统）。形状内 MUST NOT 出现射线检测、导航查询或阵营判断。

### A7.2 契约签名（提案输入）

```cpp
USTRUCT(meta=(Hidden))
struct TCSTARGETING_API FTcsTargetShape
{
    GENERATED_BODY()

    // ① 判定：点在不在形状内。Center 由调用方解析（形状 MUST NOT 查世界）。
    virtual bool IsInside(const FVector& Center, const FVector& Point, double Scale) const { return false; }

    // ② 表现友好出口：形状的外接边界（Decal 尺寸 / Niagara 缩放 / Cue 读取）
    //    返回 false = 本形状不支持给边界（调用方降级）；MUST NOT 用于判定。
    virtual bool TryGetBoundingExtent(const FVector& Center, const FVector& Forward, double Scale, FBox& OutBounds) const { return false; }
};
```

**两个实现细节的判据**：

- **`Center` 是值而不是"谁"**：形状不持有 `FTcsCombatEntityHandle`、不接受 `ITcsEntityQuery`。这样"预览与执行同源"是结构保证的——两者只是喂了不同的 Center。
- **`Forward` 参数所有形状都接**：2D 形状内部把 `Forward` 投影到自己的平面。判据 = 调用方不必为 2D/3D 写两套调用代码；2D 投影后长度近零时 MUST 降级为"平面内默认朝向"并留 Warning，不得静默产生空扇形。

### A7.3 枚举与预览入口（框架侧，非虚函数）

```cpp
// 形状枚举：范围内有哪些实体（Visitor 式，零中间数组）
void EnumerateEntitiesInShape(
    ITcsEntityQuery* EntityQuery,
    const FTcsTargetShape& Shape,
    const FVector& Center, const FVector& Forward, double Scale,
    TFunctionRef<void(FTcsCombatEntityHandle)> Visitor);

// Dry-run 预览：不跑链、只跑"选择器 → 形状 → 过滤器"，返回会命中谁
// 形态 A（零分配，C++ 宿主与调试命令用）
void PreviewTargets(
    const FTcsTargetSelectorStrategy& Selector,
    const FTcsTargetShape& Shape,
    TConstArrayView<const FTcsTargetFilterStrategy*> Filters,
    const FTcsEffectContext& Context,
    ITcsEntityQuery* EntityQuery,
    FTcsTargetScratch& Scratch,                 // 复用缓冲，见 附录 A8.1

UFUNCTION(...)
void PreviewTargetsForCaster(FTcsCombatEntityHandle Caster, ... , UPARAM(ref) TArray<FTcsCombatEntityHandle>& OutTargets);
```

> **形态 B 的必要性**：宿主 reticle 可能写在脚本层（UnrealSharp）。`TFunctionRef` 进不了 `UFUNCTION` 签名（本仓 SCRIPT-5 已实测：`ITcsEntityQuery` 因 `TFunctionRef` 被定为 C++ 专用面）。若只给形态 A，脚本层就做不了 reticle——那正好是 D-6 要服务的主消费者。故**两个形态同批交付**，形态 B 走 `UPARAM(ref) TArray&` 家法（与 `ITcsTargetSelectorHost::ResolveTargets` 一致）。

### A7.4 D-4 拆类型方案的代价与兜底

| 代价 | 兜底 |
|---|---|
| 选错维度：扁平棋盘上选了 3D 球 → 参数正常、编译正常、运行不报错，只是判定悄悄用 3D 距离 | 每个 3D 类型的 `DisplayName` / `ToolTip` 明写："三维球体：高低差影响命中。扁平棋盘请用 Circle2D"——纯元数据、零代码 |
| picker 列表 6 项（不是 3 项） | 命名规则已让两种维度一眼可分（§4.1） |

**收益（含一条意外收获）**：每个类型参数面干净、无"配了不生效"的字段；且**"忘了选形状"在 picker 结构上不可能发生**——槽位为空时 picker 列 6 个类型，必须选一个，没有"默认形状"可漏配 ⇒ 早先设想的 `FTcsShape_None` 语义陷阱**自动消失**。

## A8 性能判据

### A8.1 执行器与预览的 4 处局部成本（必须修）

| # | 现状 | 问题 | 修法 |
|---|---|---|---|
| 1 | `Selector->Resolve(..., Candidates)` 值返回 `TArray` | 每次选择一次堆分配 | 复用缓冲（`FTcsTargetScratch`），Resolve 写入调用方提供的数组 |
| 2 | `FilterStruct.GetPtr<FTcsTargetFilterStrategy>()` 在**候选内层循环** | N×M 次类型校验；且迫使"空槽位不淘汰候选"的妥协 | 候选循环**外**一次性解析 Filter 指针数组；空槽位在解析期 Warning |
| 3 | 0 个 Filter 时仍走双重循环 | 白跑 | 早退分支 |
| 4 | `PassedTargets` → `MoveTemp(Context.Targets)` 后旧缓冲释放 | 高频选择下的分配抖动 | 中间缓冲与 `Context.Targets` 的扩容由同一 Scratch 承担 |

**为什么现在必须修**：D-6 的预览是**运行期**设施，reticle 会在瞄准态每帧刷新 ⇒ 上述每一项从"偶发开销"变成"每帧开销"。**先修再上形状**，顺序不可颠倒。

### A8.2 形状不是性能位（但也不能假装它免费）

- 形状判定必然**逐候选**（`O(候选数)`），**不降低枚举成本**——AbilityKit 作者原文即"加 `CircleShapeRule` 并不降低候选枚举的 O(N)"。真正的裁剪位在**候选来源**（宿主 `ITcsEntityQuery` 的索引：自走棋是格位/阵营索引，不是空间索引）。
- 因此框架侧的性能责任只有两条：**枚举走 Visitor 不分配**、**形状判定不重复取位置**（`GetLocation` 每候选只调一次，喂给形状与过滤器共用）。

### A8.3 预览路径的三条纪律

1. **纯函数**：预览 MUST NOT 写 `Context`、MUST NOT 推进运行态、**MUST NOT 消费随机源**。第三条最隐蔽——若预览每帧抽随机数，会改变执行时的随机序列，破坏帧同步可重现性。需要随机的选择器 MUST 从 Context 取种子（而非内部状态）。
2. **宿主实现无副作用**：`ITcsEntityQuery` 的三个方法在预览期 MUST NOT 有副作用；`Selector` / `Filter` 的宿主插槽实现同理（规格显式声明，否则宿主会在 `EnumerateEntities` 里做缓存写入）。
3. **性能分层提示**：预览会穿过 `ITcsTargetFilterStrategy`，而 Filter 可能是脚本插槽（跨语言 `UFunction::Invoke`）。规格 SHOULD 提示"预览路径的 Filter 建议走 C++ 快路径"，避免宿主误判框架慢。

## A9 确定性与一致性判据

| # | 判据 | 理由 |
|---|---|---|
| C-1 | 预览结果的顺序 MUST 与执行一致（稳定序 + 过滤保序） | 否则指示器高亮的先后与命中结算顺序不符 |
| C-2 | 形状的贴边语义 MUST 定死并写进规格（`<=` 或 `<`，全族统一） | 玩家会拿视觉高亮对照"贴边到底打不打" |
| C-3 | 预览与执行 MUST 都以**逻辑位置**为准；表现层插值仅供绘制 | 两者差一帧就会在贴边时不一致 |
| C-4 | 作用中心在**指令确认瞬间冻结**并写入战斗请求；执行侧用冻结值 | 否则"玩家看到打中 A、确认后打了 B"（指示器欺骗的第二形态） |
| C-5 | **预览结果不承诺与执行结果一致**（中心可移动、目标可死亡）——规格显式声明 | 避免把预览当契约；与 `10 §1`"Targeting 不保证效果最终生效"同一口径 |
| C-6 | 同分决胜在引入评分时 MUST 与评分同批定义（建议：句柄升序） | 后补 tie-break 会改变既有结果集 |
