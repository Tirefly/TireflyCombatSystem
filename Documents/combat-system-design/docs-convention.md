## 1. 为什么需要这份文件

本工作区此前没有任何文档规范文件，结果是：45 篇文档的写法各成一体——状态行三种口径互相矛盾、同一份文件同时干四件事、交叉引用近 3 000 处却没有一条可点击、缩写编码出现 `R` 承载三套含义。

**规范的目标不是"整齐"，是三件具体的事**：① 读者能在 30 秒内判断一篇文档能不能信、信到什么程度；② 引用能被解析（谁引谁、引到哪一节）；③ 新增文档有确定的位置与形状。

**规范不追溯重写历史**：本文生效前写下的措辞（尤其是 2026-09 上旬的决策文档）保持原貌，只在"高风险项"上逐步收敛——判据见 §6。

## 2. 文档类型（七类，唯一分类）

每篇文档 MUST 属于且仅属于一类；类型决定它落在哪个子目录（见 `INDEX.md` 的目录表）。

| 类型 | 代号 | 回答什么问题 | 载体 | 现有篇数 |
|---|---|---|---|---|
| **模块规格** | `SPEC` | "这个模块对外提供什么、边界在哪" | 一模块一篇，长期维护 | 11 |
| **决策记录** | `DEC` | "当时为什么这么定、否决了什么" | 一议题一篇，拍板后冻结正文 | 10 |
| **决策日志** | `LOG` | "逐条拍板的流水（含日期、依据、落档点）" | 按模块轮次分片，只追加 | 8 |
| **实施计划** | `PLN` | "这一轮具体怎么做、怎么验" | 一轮一份，交付即冻结 | 5 |
| **调研与证据** | `RSCH` / `EVID` | "结论的证据是什么、边界在哪" | 一次性冻结；证据 MUST 附可复核锚点 | 9 |
| **台账与追踪** | `LEDGER` | "哪些事没做、谁在做、做到哪" | 活文档，勾销不删条目 | 4 |
| **治理** | `GOV` | "编号什么意思、文档怎么写、从哪进" | 唯一三件：`INDEX` / `GLOSSARY` / `CONVENTION` | 3 |

**禁止的类型混用**（现行四例，属历史遗留）：
- README 同时承担索引 + 决策日志 + 检查点 + 实施记录（四种）→ 已在重构中拆分。
- `plans/plan-r3-content-guide.md`（旧名 `2026-09-21-r3-slice-content-guide.md`）§1–§4 是操作手册、§5 是已执行结果 → 允许，但 MUST 在状态行写明"已执行完毕"。
- `research/csharp-authoring.md`（旧名 `2026-09-23-csharp-tcs-logic-authoring-research.md`）是调研 + 实施后回填 → 允许，但回填段 MUST 带独立标题与日期。
- `research/scripting-language-ustruct.md`（旧名 `2026-09-23-scripting-language-ustruct-research.md`）是调研 → 保持。

## 3. 身份块（每篇文档 MUST 有，放 H1 之后）

```markdown
- **文档 ID**：`SPEC-01-attributes`
- **类型**：模块规格（TcsAttribute / M2）
- **状态**：生效中
- **权威范围**：本模块对外类型、聚合管线、事务与网络姿态；决策理由不住这里（见 LOG-02）
- **最后更新**：2026-09-23
```

**字段纪律**：

| 字段 | 取值 | 说明 |
|---|---|---|
| 文档 ID | `INDEX` / `GLOSSARY` / `CONVENTION` / `SPEC-<模块>` / `DEC-<议题>` / `LOG-<轮次>` / `PLN-<轮次>` / `RSCH-<主题>` / `EVID-<日期>-<主题>` / `LEDGER-<域>` | **文件名可变，ID 不变**——`GLOSSARY.md` 的映射表是 ID → 当前路径的唯一出处 |
| 类型 | §2 的七类之一 + 简短限定 | 便于 `grep` 分类统计 |
| 状态 | §4 的五个状态词之一，**只能取一个** | 身份块用英文代号（`ACTIVE`/`PENDING`/`FROZEN`/`ARCHIVED`/`LIVING`），与 §4 中文词一一对应；**禁止"v1+ / v2 双口径同行"式写法** |
| 权威范围 | 一句话：**本文独有的是什么 + 什么不在本文** | 防"三处真相" |
| 最后更新 | `YYYY-MM-DD` | 与正文里的修订记录 MUST 一致 |

## 4. 状态词（五个，唯一受控词表）

| 状态 | 含义 | 身份块代号 | 读者该怎么做 |
|---|---|---|---|
| **生效中** | 当前有效，读它作准 | `ACTIVE` | 直接引用 |
| **待落地** | 内容已定稿，但代码/资产未实现 | `PENDING` | 引用时 MUST 同时说明实现状态 |
| **冻结** | 交付即冻结（计划、证据、已归档决策） | `FROZEN` | 只作历史留痕与追溯，不代表现状 |
| **历史存档** | 已被后续文档取代 | `ARCHIVED` | MUST 在文首加存档横幅（见 §7） |
| **活文档** | 持续更新（台账、术语规约、登记册） | `LIVING` | 引用时 MUST 带日期或条目号 |

**明令禁止的写法**：① 同一文档三处版本口径互斥；② H1 里的状态与正文状态行矛盾（现行六例，见 §6 收敛计划）；③ 用 `v1/v2/v3` 冒充状态——版本号是修订序号，进"修订记录"节，不进状态字段。

## 5. 交叉引用格式（四轨，按引用对象选）

> 背景：全库现有引用形态为 裸文档号 540 / 文档号+节号 283 / **裸节号 771** / 文件名 309 / **行号 479** / Markdown 链接 **0**。
> **裸节号与行号引用是本工作区最大的隐性成本**：前者脱离上下文即歧义，后者改内容即失效。

| 引用对象 | 格式 | 示例 | 说明 |
|---|---|---|---|
| 本工作区文档 | Markdown 链接：方括号内写文档 ID、圆括号内写相对路径，后接节号 | [`SPEC-01-attributes`](spec/02-module-attributes.md) 后写 `§2.3` | **MUST 用完整 ID（含主题词）而非裸编号、也非裸文档号**；路径由 `GLOSSARY.md` §5.1 映射表维护。**禁止裸编号**：`SPEC-09` 会被读成"第 9 篇"，而 `SPEC-09` 的主题词是 `editor`、文件却是 `spec/09-module-damage.md`（编号 / 主题词 / 文件序三轨互不相同） |
| 决策编号 | 编号 + 一次展开 | `D5-17（描述视图策略化）` | **首次出现 MUST 展开**；同一文档内后续可只写编号 |
| OpenSpec 规格 | `openspec/specs/<能力>/spec.md`（可带需求名） | `openspec/specs/param-value/spec.md` | 规格是**可执行需求**的真相源，不引节号（节号会变） |
| 源码 | `` `路径:符号名` `` 或 `` `路径:行号` `` | `TcsParamValueSource.h:Evaluate` | **优先符号名**；行号只在"冻结类文档（`DEC`/`RSCH`/`EVID`）"里允许，`SPEC`/`LEDGER` 禁止 |

**禁止**：① 裸节号（`§2.2` 不写文档）；② `SPEC`/`LEDGER` 里写行号；③ 用口语简称指代文档（"2026-08-31 总线文档"——MUST 写 `DEC-2026-08-31-event-bus`）。

**行号口径警示**：本工作区历史文档的行号引用采用 **`read`/`grep` 工具口径**（含文件末尾空行不计的口径差异）；用 `PowerShell Get-Content | Measure-Object -Line` 核对会得到不同数值（如 README = 273 vs 229），**换工具核对会得出"引用错位"的假结论**。

## 6. 写作纪律（七条）

1. **一份文档一件事**：类型决定内容边界（§2）；跨类型的补充 MUST 另开文档并在 `INDEX.md` 登记。
2. **单行不超长**：日志式条目按"一事一行"书写；**单行 >400 字符**视为格式缺陷（现行约 180 行超限，README 50 行、台账 25 行）。超长行是行号引用失效与无法 review 的共同来源。
3. **过期内容三选一**，禁止第四种做法（现行 25 处删除线与多个"增补块"属未收敛）：
   - 被取代 → 移入 `HISTORICAL/` 并加存档横幅；
   - 局部失效 → 原句加删除线 + **当句**给出取代者（`~~旧写法~~ → 见 §X`）；
   - 仍未定 → 保留但 MUST 标"待拍板"。
4. **禁止隐性多真相**：同一规格（如五带枚举、折叠器单份、双轨制）MUST 只有一处**定义**，其他处只写指针。判据：`grep` 该定义的关键词，命中 >1 处即违规。
5. **计数即事实**：文档里写"共 N 条/项" MUST 与表格行数一致；台账的条目计数只在 `## 变更记录` 里逐次宣告，正文标题不写数字。
6. **规格的 `## Purpose` 是可执行需求的门面**（2026-09-29 立）：`openspec/changes/archive/` 归档时 CLI 会为新能力写入占位句 `TBD - created by archiving change <id>. Update Purpose after archive.`——**该占位句 MUST 在归档后改掉**，否则 `openspec validate --all --strict` 判 `✗`（24/24 全失败，实测于 2026-09-29）。两条硬判据：① 不得是 archive 写的占位句或 `TBD`/`TODO` 标记；② **正文长度按非 ASCII 字符数 ≥ 50**（纯字符数达标也会被判 "too brief"——实测 68 字符的中文描述仍失败）。写什么：一句话说清这个能力**是干什么的**，素材取自该规格自己的需求标题。
7. **收敛纪律**：本文生效后新增文本 MUST 遵守；存量文本按"高风险优先"逐步收敛（§6.1 附清单）。

> **验证纪律（2026-09-29 补，来自一次真实漏检）**：结构类校验（需求必须有 `#### Scenario:`、必须有 `MUST|SHALL`）可以离线用脚本替代；**但 overview 类语义判据（`## Purpose` 占位、长度门槛）只有官方 CLI 能查出来**。故规格层改动后 MUST 跑 `openspec validate --all --strict --no-interactive`（CLI = `@fission-ai/openspec`，全局 npm 安装），不得以离线脚本通过作为规格合规的证据。

## 7. 冻结与存档

- **冻结**（`PLN` / `EVID` / 已归档 `DEC`）：交付后不再修改正文；后续信息以"实施注记"引用块追加，并写清日期。
- **存档**：进入 `HISTORICAL/` 的文档 MUST 在 H1 之后加：

  ```markdown
  > **历史存档（YYYY-MM-DD）**：本文已被 `<新文档 ID>` 取代，仅作追溯留痕，不代表现状。
  > 取代点：<一句话说明哪些结论仍有效、哪些已失效>
  ```

- 存档文档的**引用者 MUST 一并修正**（指向新文档），修正后再移入 `HISTORICAL/`。
