# TCS 网络同步与性能优化审查（讨论基线）

## 1. 文档目的

本文档用于整理当前 `TireflyCombatSystem` 插件中，与以下主题直接相关的代码事实、风险判断和讨论入口：

1. 哪些当前设计可能影响网络同步正确性。
2. 哪些当前设计可能影响网络同步性能。
3. 哪些模块和功能的运行时性能开销占比可能较大。
4. `State` 模块生命周期流程中，哪些位置存在可以减负但不改变语义的空间。

本文档不是最终实施方案，也不是 OpenSpec proposal。
本文档的用途是先建立一份可讨论、可质疑、可逐项确认的技术基线，后续再根据确认结果拆成具体实现方案。

## 2. 当前结论摘要

基于当前源码，先给出三个初步判断：

1. `TCS` 当前更接近“本地权威运行时框架”，还不是“已经完成联机同步边界设计”的战斗框架。
2. 当前最可能的性能热点是 `Attribute` 模块的 `Modifier -> Recalculate -> Clamp -> Constraint Propagation` 计算链；`State` 模块次之，`Buff` 模块在周期 Buff 和大量有限时长 Buff 场景下会明显抬升。
3. `State` 生命周期里最值得优先减负的不是核心阶段语义，而是“重复比较、重复扫描、重复排序、重复刷新”这类外围成本。

## 3. 当前代码事实

### 3.1 网络同步相关事实

1. 当前插件源码中，没有形成完整的 `Replication / RepNotify / RPC` 主链。
2. `State`、`Buff`、`Attribute` 的核心入口目前仍然是本地直接调用的运行时函数，而不是显式区分 `Authority` 和 `Remote` 的网络入口。
3. `FTcsSourceHandle` 已实现 `NetSerialize`，说明来源句柄已为网络传输做过准备，但这不等于 `State / Buff / Attribute` 已有完整同步方案。
4. `State` 和 `Attribute Modifier` 的部分排序/合并决策依赖本地时间戳，而不是依赖服务器统一序号或统一网络时钟。
5. `StateTree`、`Buff Period`、`State 生命周期` 当前都基于本地 Tick 推进。

### 3.2 运行时容器相关事实

1. `UTcsStateComponent` 内部核心容器包括：
   - `FTcsStateInstanceIndex StateInstanceIndex`
   - `FTcsStateTreeTickScheduler StateTreeTickScheduler`
   - `TMap<FGameplayTag, FTcsStateSlot> RuntimeStateSlots`
2. `UTcsAttributeComponent` 内部核心容器包括：
   - `TMap<FName, FTcsAttributeInstance> Attributes`
   - `TArray<FTcsAttributeModifierInstance> AttributeModifiers`
   - `TMap<int32, TArray<int32>> SourceHandleIdToModifierInstIds`
   - `TMap<int32, int32> ModifierInstIdToIndex`
3. 这些运行时结构非常适合本地查找、排序和增删改，但并不适合直接按当前形态做网络复制。

### 3.3 Tick 与调度相关事实

1. `UTcsStateComponent::TickStateTrees()` 会逐帧调度运行中的 `StateTree` 实例。
2. `UTcsBuffComponent::TickBuffLifecycles()` 会逐帧推进有限时长 Buff 的剩余时间。
3. `FTcsBuffPeriodDriverTask::Tick()` 会在 Buff 实例树里逐帧累计时间，并按周期发出 `Event.Buff.PeriodTick`。
4. `UTcsSkillComponent` 当前虽然开启了 Tick，但目前逻辑非常轻，仅保留了 `0.1s` 间隔的空框架。
5. `FTcsStateSlotDebugEvaluator::Tick()` 会定期生成调试字符串快照，这是开发期成本，不是业务语义成本。

## 4. 网络同步风险清单

## 4.1 未建立明确的联机权威边界

### 当前代码事实

1. `State` 的应用入口仍然是 `UTcsStateComponent::TryApplyState()`。
2. `Buff` 的应用入口仍然是 `UTcsBuffComponent::ApplyBuff()`，其内部继续转向 `StateComponent->TryApplyState()`。
3. `Attribute` 的增删改和 Modifier 应用也都是本地组件方法直接执行。

### 风险判断

如果未来客户端也直接运行这些入口，而不是先通过服务器统一裁决，再把结果同步给客户端，那么：

1. 本地状态可能先分叉，再尝试“事后纠正”。
2. 同一效果在服务端和客户端的排序、合并、时序结果可能不同。
3. 后续每个模块都会被迫补大量“同步补丁”，而不是从一开始就站在统一权威模型上。

### 当前建议

后续如果做联机，优先先定一件事：

`TCS` 是否采用“服务器权威执行，客户端只消费结果”的主模型。

如果答案是“是”，则后续优化方向会清晰很多；如果答案是“不是”，则必须单独设计客户端预测与回滚策略。

## 4.2 本地时间戳参与排序和合并

### 当前代码事实

1. `UTcsStateComponent::CreateStateInstance()` 会给 `StateInstance` 写入 `ApplyTimestamp`。
2. `UTcsAttributeComponent::ApplyModifier()` 和 `HandleModifierUpdated()` 会写入 `ApplyTimestamp / UpdateTimestamp`。
3. `State` 的同优先级策略 `UseNewest / UseOldest` 会依赖 `ApplyTimestamp`。
4. `BuffMerger_UseNewest / UseOldest / StackByInstigator` 会依赖 `ApplyTimestamp`。
5. `Attribute Modifier Merger_UseNewest / UseOldest` 会依赖 `ApplyTimestamp / UpdateTimestamp`。

### 风险判断

这些时间戳当前是本地 `UTC ticks`，在单机环境中合理，但在联机环境中会带来两个问题：

1. 服务端和客户端即使收到“逻辑上相同”的事件，时间戳也不会完全一致。
2. 同步重放时，合并结果和排序结果可能因为时间戳不同而发生分叉。

### 当前建议

如果后续进入联机化阶段，需要优先决定：

1. 是否把这些排序依据改成“服务器分配的单调序号”。
2. 是否把“时间戳仅用于调试”和“排序依据”彻底拆开。

## 4.3 本地 Tick 推进状态树与 Buff 周期

### 当前代码事实

1. `StateTree` 实例 Tick 由 `UTcsStateComponent::TickStateTrees()` 在组件侧统一推进。
2. `Buff` 周期事件由 `FTcsBuffPeriodDriverTask::Tick()` 在实例树内按 `ElapsedTime` 发射。
3. `UTcsBuffComponent::TickBuffLifecycles()` 会直接扣减 `RemainingDuration`。

### 风险判断

只要客户端也在本地推进这些逻辑，而不是只接收服务器结果，就可能出现：

1. 时长不同步。
2. 周期事件触发帧不同步。
3. 生命周期结束帧不同步。

### 当前建议

后续要明确：

1. 哪些逻辑必须只在服务器推进。
2. 哪些逻辑允许客户端做纯表现层预测。
3. 哪些最终结果必须用紧凑快照回灌给客户端。

## 4.4 当前运行时结构不适合直接复制

### 当前代码事实

1. `RuntimeStateSlots` 是 `TMap<FGameplayTag, FTcsStateSlot>`，槽位内还保存状态实例数组和运行时 Gate 状态。
2. `StateInstanceIndex`、`StateTreeTickScheduler`、`ModifierInstIdToIndex`、`SourceHandleIdToModifierInstIds` 都是为了本地高效访问而设计的辅助结构。
3. 这些容器的维护逻辑依赖大量本地对象指针、索引和运行时调度状态。

### 风险判断

如果未来试图“直接复制整个运行时容器”，大概率会遇到：

1. 复制数据量大。
2. 脏数据判断复杂。
3. 本地辅助索引与网络同步数据耦合过深。
4. 后续维护成本高于收益。

### 当前建议

如果走联机，建议优先考虑“紧凑结果复制”，而不是“运行时内部结构复制”。

例如：

1. `Attribute` 同步最终值和必要边界状态。
2. `State` 同步紧凑状态实例快照。
3. `Buff` 同步堆叠数、剩余时长、关键显示数据。

## 5. 当前最可能的性能热点

## 5.1 Attribute 模块：最可能的第一热点

### 当前代码事实

1. `ApplyModifier()` 会对输入修改器分组、写时间戳、分流到 `BaseValue` 和 `CurrentValue` 两条路径。
2. `RecalculateAttributeBaseValues()` 会对传入修改器执行：
   - 合并
   - 排序
   - 执行
   - Clamp
   - 事件记录
   - 约束传播
3. `RecalculateAttributeCurrentValues()` 会对当前全部 `AttributeModifiers` 执行同样一轮完整计算。
4. `EnforceAttributeRangeConstraints()` 会进行多轮迭代，直到收敛或达到最大迭代次数。
5. `RemoveModifiersBySourceHandle()` 当前代码中已明确标注存在 `O(K^2)` 退化风险。

### 风险判断

当以下条件叠加时，`Attribute` 模块会很容易成为第一热点：

1. 属性数量较多。
2. 动态范围依赖较多。
3. Modifier 数量较多。
4. Buff/State 经常增加、更新、移除 Modifier。

### 初步结论

如果后续要先做性能 Profiling，我会优先看 `Attribute` 模块。

## 5.2 State 模块：最可能的第二热点

### 当前代码事实

1. `TickStateTrees()` 会按帧扫描调度中的状态实例并推进实例树。
2. `OnStateTreeStateChanged()` 会读取当前激活状态，并进入 `RefreshSlotsForStateChange()`。
3. `RefreshSlotsForStateChange()` 会构建 Added/Removed 集合，再遍历全部槽位绑定。
4. `UpdateStateSlotActivation()` 会执行：
   - 清理过期状态
   - 状态排序
   - Prepare 扩展点
   - Gate 一致性检查
   - 槽位模式处理
   - 再次清理
   - 槽位变化回调
5. 大多数状态应用、移除、Gate 变化最后都会进入槽位刷新链。

### 风险判断

只要角色数量、状态实例数量、槽位数量上来，`State` 模块就会形成稳定的长期帧成本。

### 初步结论

`State` 模块的热点不一定像 `Attribute` 那样在某一次操作里瞬间爆发，但它更容易长期压帧。

## 5.3 Buff 模块：在周期 Buff 和大量有限时长 Buff 场景下会显著抬升

### 当前代码事实

1. `TickBuffLifecycles()` 每帧遍历 `DurationTracker.TrackedInstances`。
2. 对每个有限时长 Buff，都会检查阶段、扣减剩余时长、处理到期逻辑。
3. 周期 Buff 额外会在实例 `StateTree` 任务里执行周期累计和事件发送。

### 风险判断

如果一场战斗里周期 Buff、DOT、HOT、可刷新堆叠 Buff 很多，`Buff` 模块的成本会从“中等”快速升高。

### 初步结论

`Buff` 模块当前不像 `Attribute` 那样天然是第一热点，但在技能密集、持续效果密集的战斗中，完全可能变成第二热点。

## 5.4 调试路径是开发期成本，不应与业务热点混在一起

### 当前代码事实

1. `FTcsStateSlotDebugEvaluator::Tick()` 会定时生成字符串快照。
2. `GetSlotDebugSnapshot()` 和 `GetStateDebugSnapshot()` 都会做排序、格式化和字符串拼接。

### 风险判断

这些逻辑本身不是业务语义的一部分，不能把它们和真正的生命周期成本混为一谈。

### 当前建议

讨论性能时，先分清：

1. 业务成本。
2. 调试成本。
3. 编辑器专用成本。

## 6. State 生命周期可减负点

本节只讨论“减负但不改变语义”的方向。

## 6.1 StateTree 状态变化 Diff 路径

### 当前代码事实

1. `OnStateTreeStateChanged()` 每次都会取当前激活状态数组。
2. `AreStateNamesEqual()` 当前会复制数组并排序后再比较。
3. `RefreshSlotsForStateChange()` 会再构造 Added/Removed 集合，并遍历所有槽位绑定。

### 可减负空间

1. 可以减少重复排序。
2. 可以减少“全表扫描”次数。
3. 可以增加反向映射 `StateTreeStateName -> SlotTag`，把“全槽位遍历”收敛成“只处理变更状态名”。

### 讨论重点

这里是我认为最安全、也最值得优先动的 `State` 减负点之一。

## 6.2 槽位刷新批处理

### 当前代码事实

1. `RequestUpdateStateSlotActivation()` 已有 `PendingSlotActivationUpdates` 机制。
2. 但当前很多路径仍然会在同一帧多次进入槽位刷新链。
3. `DrainPendingSlotActivationUpdates()` 只是做了“排空”，还没有把“同帧多次语义变化”压成“单次最终结算”。

### 可减负空间

1. 同一帧同一槽位只结算一次最终结果。
2. 批量移除或批量 Gate 变化时，按槽位聚合刷新，而不是逐个实例刷新。

### 讨论重点

这是第二个高性价比减负点。

## 6.3 小槽位排序短路

### 当前代码事实

`UpdateStateSlotActivation()` 里会对槽位中的状态进行排序。

### 可减负空间

当槽位内状态数为 `0` 或 `1` 时，不需要排序。

### 讨论重点

这是一个小优化，但风险低、语义稳定、适合顺手纳入。

## 6.4 批量移除优先走索引，而不是扫所有槽位

### 当前代码事实

1. `RemoveStatesByDefId()` 当前会遍历所有槽位再查找要移除的状态。
2. 组件本身已经维护了 `StateInstanceIndex`。

### 可减负空间

先用索引命中目标实例，再按槽位分组回收，可以减少很多无意义扫描。

### 讨论重点

这不会改变生命周期语义，只会改变“怎么找到目标实例”。

## 6.5 同槽位多状态移除后只做一次最终刷新

### 当前代码事实

状态最终移除后，会继续触发槽位刷新请求。

### 可减负空间

如果同一槽位在同一批次内移除了多个状态，理论上只需要在末尾做一次最终收敛刷新。

### 讨论重点

这类优化需要注意不要改变事件顺序语义，但本身是可做的。

## 6.6 调试字符串构造应尽量留在显式调试路径

### 当前代码事实

槽位快照和状态快照字符串都包含排序和拼接成本。

### 可减负空间

后续如果正式做性能收敛，应尽量把这些逻辑限制在：

1. 编辑器环境。
2. 显式调试命令。
3. 开发调试开关开启时。

## 7. 当前不建议直接动的点

以下位置虽然可能贵，但当前不建议在没有更明确目标前直接改：

1. `Gate` 一致性语义。
2. `PriorityOnly / AllActive` 槽位模式本身。
3. `State` 移除时顺带清理 `Modifier` 的共享主链语义。
4. Buff 到期后的响应式叠层处理语义。

原因很简单：这些点属于核心执行语义，先动它们，最容易把“性能优化”做成“行为变更”。

## 8. 待确认决策清单

## D1. TCS 联机是否采用服务器权威模型

需要确认：

1. `State / Buff / Attribute` 是否统一由服务器执行。
2. 客户端是否只做表现层预测。
3. 当前阶段是否完全不做预测。

## D2. 联机同步粒度

需要确认：

1. 是同步紧凑结果，还是同步运行时内部结构。
2. `Attribute` 是否只同步最终值。
3. `State / Buff` 是否同步紧凑实例快照。

## D3. 时间戳和排序依据

需要确认：

1. 是否保留本地 `UTC ticks` 仅作调试用途。
2. 是否改成服务器统一序号作为排序依据。
3. 是否拆分“调试时间戳”和“业务排序键”。

## D4. 第一阶段性能分析入口

需要确认：

1. 是否先只分析 `Attribute` 模块。
2. 是否同时把 `State` 槽位刷新链也纳入第一阶段。
3. 是否暂时把 `Skill` 排除在第一阶段之外。

## D5. State 生命周期优化边界

需要确认：

1. 第一阶段是否只允许做“去重复、去全量扫描、去重复排序”。
2. 是否暂时不动核心阶段语义。
3. 是否把事件顺序视为必须保持不变的约束。

## 9. 建议讨论顺序

如果要逐项讨论，我建议按下面顺序推进：

1. 先确认联机权威模型。
2. 再确认联机同步粒度。
3. 再确认时间戳是否继续参与业务排序。
4. 再讨论 `Attribute` 模块第一阶段性能收敛。
5. 再讨论 `State` 生命周期减负的第一阶段切入点。
6. 最后再看 `Buff` 生命周期与周期 Buff 的进一步优化。

## 10. 当前建议的下一步

当前最适合的下一步不是立刻写代码，而是先把下面三件事逐条确认：

1. `TCS` 的联机目标到底是什么。
2. `Attribute` 性能收敛是否作为第一优先级。
3. `State` 生命周期优化是否先限定在“完全不改语义”的范围内。

在这三件事确认后，再拆成具体实现文档，会更稳。
