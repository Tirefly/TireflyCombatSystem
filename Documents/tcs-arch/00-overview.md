## §1 这篇的位置：11 篇模块档案的三处空白

11 篇按**编译单元**切，所以它们只能审**存在的东西**。而需求层里恰好有两块**没有编译单元**的内容，以及一批**横跨多篇**的重复账。三处空白各不相同：

| 空白 | 为什么 11 篇都装不下它 | 本文件的位置 |
|---|---|---|
| 旧 `SPEC-09-editor` / `SPEC-10-presentation` | 它们对应的模块 `TcsEditor` / `TcsCue` **在 `Source/` 下不存在** ⇒ 没有任何一篇的「审核对象」是它们 | **§2**（两个无代码模块） |
| 同一件事在多篇各记一次 | 每篇只对自己模块负责，重复登记在单篇里是**正确的**（读者只看一篇时不能漏），但它同时是 `G-21` 的受害面 | **§3**（跨模块归位） |
| 「决定不做」的决定 | 规格只给「实现了的」留格子（`G-20`）；11 篇各自的 §6 都写了「未实现」，但没人汇总「哪些是**决定不做**」 | **§4**（已决定不做） |
| `G-1..G-32` 的形态归并 | 32 条全局待办以**发现顺序**编号，跨 11 篇交错出现，没有按**形态**归类过 | **§5**（判据归并） |

> **一句话**：11 篇回答「每个模块今天是什么」，本题回答「**没模块的那些、跨模块的那些、以及不打算做的那些**」。

## §2 两个无代码模块

### 2.1 共同的形态：**机制全落地、词汇零落地**【实测】

两篇旧规格都是 `PENDING`，最自然的读法是「什么都没做」。**实测是反的**——它们的**机制**几乎全部落地了，只缺那个把机制用起来的**模块**：

| 旧规格的机制 | 落地状态 | 落在哪 |
|---|---|---|
| 帧末派发通道（`SPEC-10` §3 D4-2） | ✅ **已落地** | `TcsCore` 的 `PublishFrameEnd` / `FlushFrameEnd` / `ETcsEventDispatch::EED_FrameEnd` |
| 预览读 `PeekPending`（`SPEC-10` §3 D2-5） | ✅ **已落地，三处** | `FTcsAttributePipeline::PeekPending` / `UTcsAttributeSubsystem::PeekPending` / `ITcsAttributeProvider::PeekPending` |
| 步骤基类型 + 执行器自注册宏（`SPEC-10` §1） | ✅ **已落地** | `FTcsEffectStep` 家族 + `UE_DEFINE_EFFECT_STEP_EXECUTOR` |
| 保存期校验（`SPEC-09` §2 / §8） | ✅ **已落地，7 个类** | 7 个 Def 资产各自的 `IsDataValid`（`WITH_EDITOR` 段） |
| 双轨制「表 = 编辑期、资产 = 运行期」（`SPEC-09` §5） | ✅ **已落地**（且落地的是「不实现」的那一半） | 运行期零 DataTable 加载路径（实测 `LoadAll` / `EnsureLoaded` 零命中） |
| 表行轨 4 个 struct（`SPEC-09` §5） | ⚠️ **半落地** | `FTcsAttributeDefTableRow` / `FTcsAttrModDefTableRow` 有消费者；`FTcsBuffDefTableRow` / `FTcsSkillDefTableRow` **全仓各 1 处 = 仅声明** |
| Cue 词汇 `FCueEvent` / `ICuePresenter` / `PlayCue` / `bMergeable` | ❌ **零命中** | — |
| 中心校验器模块 / 可视化 / Explain / 同步器 | ❌ **零命中** | — |

⇒ **两个 `PENDING` 模块的真实状态不是「什么都没做」，而是「寄居」**：机制住在别的模块里，词汇不存在。

### 2.2 一个必须写下来的判据：**判「未实现」MUST 先问「它是不是换了载体」**【实测】

`SPEC-09-editor` 的 §2 是一张**校验规则表**（六条规则）。R0 的设想是「一个叫 `TcsEditor` 的模块来跑这些规则」，今天落地的是「**每个 Def 资产自己在 `IsDataValid` 里跑自己那一部分**」。

⇒ 同一份规格有两种读法，结论完全相反：

| 读法 | 结论 |
|---|---|
| 当成「**一个模块的功能表**」 | **零兑现**——`Source/TcsEditor` 不存在 |
| 当成「**一份校验规则清单**」 | **六条里四条有对应实现**（见 §2.3 的逐条表） |

**这不是文字游戏**。它决定后续动作：按前一种读法会去建一个中心模块（而 `IsDataValid` 已经把七类规则各自落地了，建了就是两套账）；按后一种读法只会去补缺的那两条。

> **判据（新增，进 §5 的判据表）**：一个 `PENDING` 模块的规格里，若某节写的是**规则 / 数据形状 / 校验点**而不是**门面 / 注册表 / 生命周期**，则该节 MUST 先按「**换了载体的需求**」核一遍（去哪了：每个资产自己？上游模块？宿主？），再判「未实现」。**反向也成立**：`ARCH-11` 的 U-6（`ICombatEntityQuery` 有两个实现者）是同一个动作在「有模块但没消费者」一侧的形态。

### 2.5 两篇的共同结论：**它们不欠代码，欠一个决定**

两篇旧规格加起来 **95 行**，是全部 12 篇里最短的两篇。但**短不是它们的问题**——

| 事实 | `SPEC-09-editor` | `SPEC-10-presentation` |
|---|---|---|
| 行数 | 53 | **42**（最短） |
| 收束节 | `§8` 验收钩子（3 条，零可执行） | `§6` 验收钩子（1 条，零可执行） |
| 订正率 | ~33% | **~15%**（第二低） |
| 机制落地度 | **高**（校验规则 4/6 有载体） | **高**（帧末队列 / `PeekPending` / 步骤基类型全落地） |
| 词汇落地度 | **零**（无模块） | **零**（无模块） |

⇒ **它们的形态一致**：`PENDING` 这个词让读者以为「一团空白」，实际是「**地基全在、门窗全无**」。

**按 `G-20`（「决定不做」无处可写）**，这两篇真正缺的不是实现，是**一句话**：

> 「`TcsEditor` / `TcsCue` **不做，直到 `<条件>`**」——条件是什么、谁来触发，两篇都没写。

⇒ 台账里有痕迹（`PRES-1` 记了 `TcsCue` 本体「M9 收尾轮移出 R3 后从未被任何条目认领」，`TOOLS-1`~`TOOLS-7` 记了编辑器的七个子项），**但台账不是规格**，读者不会去那里找「这个模块还做不做」。

## §8 结论

### 8.1 三句话

1. **两个没有代码的模块，形态完全相同，且都不是「什么都没做」**——`TcsEditor` / `TcsCue` 的**机制**几乎全部落地（帧末队列 / `PeekPending` / 步骤基类型 / 7 个 `IsDataValid`），缺的只是把机制用起来的**词汇**。`PENDING` 让读者以为「一团空白」，实际是「**地基全在、门窗全无**」。
2. **编辑器需求的一半已经被 `TcsDev` 吃掉了，而 `TcsDev` 可整体删除**——这是本仓最重要的一条未记录边界。它双向成立：往下，22 处「装置是唯一消费者」的读数会在摘除时同时归零；往上看，正因为需求已被吃掉，**没人注意到「决定不做」这句话从未被写下**（`G-20` 的最严重形态）。
3. **八类判据 + 三个元判据是这个档案最可复用的产出**，而其中最反直觉的一条是 `G-32`：**规格完整度是缺陷的可发现性，不是发生率**。⇒ 审核 MUST 分开记「代码有没有缺陷」与「规格还在不在」，**因为后者决定前者会不会被后人发现**。

### 8.2 一句值得记住的话

> **档案里更正了 176 条债，而它们当中没有一条，是被「读规格」发现的。**

**全部 176 条都来自「拿代码去对规格」这个动作**，反过来从未发生——**没有一条是「读规格时觉得不对，然后去代码里验出来的」**。

原因在 `G-30` / `G-32`：规格**不会因为写错而报错**。`openspec validate --strict` 只校验「需求至少有一个 Scenario」「Scenario 用四个 `#`」这类**结构**，它不校验：

| 规格里的东西 | 谁校验 | 结果 |
|---|---|---|
| 符号名是否存在（`RegisterStateDef`） | 无人 | **躲过 3 篇审核**（§3.1 X-2） |
| 跨能力引用是否悬空（`attribute-moddef`） | 无人 | **躲过 2 轮归档**（`G-9`） |
| 标「归 X 范围」而 X 里没有它 | 无人 | **躲过 1 篇审核**（`G-24`） |
| Scenario 是否真的会通过 | 无人 | **躲到被删空**（`ARCH-08` D-2 的假失败 Scenario） |
| 需求正文里的条目数对不对 | 无人 | **十步剩零步**（`G-30`） |

⇒ 这是给下一轮的**唯一一条硬建议**：**规格的价值不在「写下来」，在「能被机器对回代码」**。今天这五类错误全部靠人眼，而人眼只在「主动去对」时生效——**而这个动作在本仓一期只发生过一次**（本次审核）。
