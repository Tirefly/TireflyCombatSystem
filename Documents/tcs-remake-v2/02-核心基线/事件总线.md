# 核心基线 · 事件总线（EventBus）

> **定位**：V2 五项核心基线之一（Entity / Instance / Clock / EventBus / NumericAggregator）。
> **回答什么问题**：**发生了什么**。

**审核状态图例**：✅ 已裁决并批准 ｜ ⚠️ 待审 ｜ ❓ 待调研

> **本文件的写法**：只写最终设计与已裁决的架构，不复述历史实现。

---

## 0. 本域只回答一件事

**「发生了什么」以 Tag 为路由，通知给关心它的人。**

### 0.1 投放语义

> **总线 MUST 把事件与其载荷准确、及时地送达本次派发时在册的全部匹配订阅者。**
> **总线 MUST NOT 保存、缓存或重放任何载荷。**

| 要求 | 含义 |
|---|---|
| **准确** | 送到的是同一个 `Type` 与同一份 `Data`；不拷贝、不转换、不推测 |
| **及时** | 在 `Publish` 调用返回前送达，**MUST NOT 攒批到帧末**（§1.2 已裁不建帧末通道） |
| **全部匹配者** | 派发开始时在册的每个匹配槽位都被调用一次，MUST NOT 因同一订阅者被调用多次而合并 |
| **不缓存** | 载荷只在调用期间有效（§1.1.8）；晚订阅者 MUST NOT 收到旧载荷 |

它**不**负责：

| 不做 | 归谁 |
|---|---|
| 事件的语义（什么算伤害、什么算死亡） | 各领域 |
| 业务层的顺序保证 | 各领域 |
| 「谁该关心这个事件」的判定 | 订阅方自己 |
| **状态快照 / 粘性事件**（记住上一次载荷给晚订阅者） | **不做**——那是状态查询，不是事件分发 |

## 1.1 事件总线 ✅

### 1.1.1 形态总览

| 项 | 设计 |
|---|---|
| 路由键 | `FGameplayTag` |
| 载荷寻址 | `const UScriptStruct*`（类型） + `const void*`（数据） |
| 底层回调 | **类型擦除的零堆分配函数对象** |
| 注册路径 | **两条**：C++ 直收回调 / 反射收 UObject + UFunction |
| 派发遍历 | **锁定长度 + `bAlive` 跳过 + 深度归零落地** |
| 频道匹配 | 精确匹配为默认，**层级匹配显式开启** |
| 每次派发分配 | **0** |

### 1.1.2 载荷：类型擦除 + 注册期绑定

**派发侧只有一种形状**，所有载荷类型共用同一条派发循环：

```cpp
// 第一参数是捕获物：thunk 靠它找到自己的上下文
using FTcsEventDispatchFn = void(*)(void* Object, FGameplayTag Channel,
                                   const UScriptStruct* Type, const void* Data);
```

**语言与类型的差异在注册期被吸收**，不在派发热路径上分叉。两条路径的 thunk 捕获物都装进 `FTcsEventSink::Inline`，不额外增加槽位字段：

| 路径 | thunk 的捕获物 | 字节 | 落点 |
|---|---|---|---|
| C++ | `{ TCallable* }`（回调本体放外部）或内联 `TCallable` | ≤ `sizeof(Inline)` | `Inline` |
| 反射 | `{ UObject*, UFunction* }` | 两个指针 | `Inline` |

**`FunctionName` MUST 在注册期解析成 `UFunction*` 并进入 thunk 捕获物，MUST NOT 成为槽位字段**：

> **Why Not 把 `FunctionName` 存进槽位**：注册期就能解析完，存字符串等于把一次查表推迟到每次派发。

**`PayloadType` 两条路径都填，MUST NOT 留空**：

| 路径 | 来源 |
|---|---|
| C++ | 模板参数 `FPayloadType::StaticStruct()` |
| 反射 | 调用方传入的 `UScriptStruct*` |

> **Why Not 让路径 A 留空（不校验）**：类型擦除后 `Data` 只有 `const void*`，不留类型标签就只能做 unchecked cast——同一频道发两种载荷即 UB。

### 1.1.3 底层回调：手写零堆分配函数对象 ✅

```cpp
struct FTcsEventSink
{
    void*  Object = nullptr;     // 指向 Inline 内的捕获物（本框架禁止指向堆）
    FTcsEventDispatchFn Func = nullptr;
    void (*Destroy)(void*) = nullptr;   // 析构 Object 指的那份捕获物
    alignas(16) uint8 Inline[24] = {};  // 捕获物的实际存储

    // 直函数指针调用，不经过虚函数层
    void Invoke(FGameplayTag Channel, const UScriptStruct* Type, const void* Data) const
    {
        Func(Object, Channel, Type, Data);
    }
};
```

**`Object` 与 `Inline` 不是并列关系，而是「指针 + 它指向的缓冲」**：

| 字段 | 角色 |
|---|---|
| `Inline[24]` | 捕获物的**实际存储** |
| `Object` | 指向 `Inline` 内的捕获物；`Func` 靠它还原强类型 |
| `Func` | 类型擦除的 thunk，**第一参数就是 `Object`** |
| `Destroy` | 对 `Object` 执行捕获物析构 |

> **Why Not 让 `Object` 指向外部堆**：那就允许了堆分配。捕获物 MUST 落在 `Inline` 里，尺寸由 `MakeSink` 的 `static_assert` 守住。
> **Why 必须有 `Object` 这一跳**：`Inline` 是 `uint8[24]`，`Func` 要的是**强类型**的捕获物地址；`Object` 就是那个已转型的指针。

```cpp
// C++ 路径的 thunk：注册期把强类型回调塞进 Inline，派发期原样还原
template <typename FPayloadType, typename TCallable>
FTcsEventSink MakeSink(TCallable&& Callback)
{
    // 上限取自本结构自己的缓冲尺寸——MUST NOT 写外部字面量
    static_assert(sizeof(TCallable) <= sizeof(FTcsEventSink::Inline),
                  "捕获物装不进内联缓冲，会退化成堆分配");
    ...
}
```

**三条设计约束**：

| # | 约束 | 理由 |
|---|---|---|
| ① | **捕获物尺寸编译期断言**（`<= sizeof(FTcsEventSink::Inline)`） | 保证**永远不堆分配**，不会因为捕获变大而静默退化 |
| ② | **直函数指针调用**，不引入虚函数层 | 派发少一次间接 |
| ③ | **不嵌套**（不把回调包进另一个回调） | 嵌套会让捕获物翻倍、堆分配不可避免 |

**关于 ① 的现实代价**：捕获装不下会**编译失败**。这是刻意的——替代路径是「捕获小数据（指针 / 索引），把大对象放外部」。

> **断言上限 MUST 取自 `sizeof(FTcsEventSink::Inline)`，MUST NOT 写字面量。**
> **Why Not 写 `24` / `16`**：该缓冲是本框架自己的成员，尺寸就是真值；外部 `TFunction` 的内联尺寸是 `#ifndef` 可覆盖、且可为 0（全部堆分配）的，拿它当判据必然错。

### 1.1.4 订阅：句柄式生命周期 ✅

```cpp
USTRUCT(BlueprintType)
struct FTcsEventSubscription
{
    // 身份（每总线自发号，永不复用；0 = 无效）——蓝图只读这一项
    UPROPERTY(BlueprintReadOnly, Category = "Tcs|Event")
    int64 SubscriptionId = 0;

    // 定位段：频道槽位下标 + 该槽位的世代号（不暴露蓝图）
    UPROPERTY(NotBlueprintVisible)
    int32 SlotIndex = -1;
    UPROPERTY(NotBlueprintVisible)
    int32 SlotGeneration = 0;

    bool IsValid() const { return SubscriptionId != 0; }

    // 等价于总线上的 Unsubscribe(本句柄)；总线引用由持有者提供
    void Unsubscribe(UTcsEventBusSubsystem& Bus) const;
};
```

**句柄 MUST 自带定位段**，注销才能 O(1)。

| 段 | 作用 | 蓝图可见 |
|---|---|---|
| `SubscriptionId` | 身份；查 `Channels` 定位到哪个频道 | 是 |
| `SlotIndex` | 频道内槽位下标 | **否** |
| `SlotGeneration` | 校验该下标仍属于本次订阅 | **否** |

> **Why Not 只存 `SubscriptionId`、注销时扫描**：千级实体同时死亡时，扫描是 O(注销数 × 槽位数)，全挤在同一帧。

| 要求 | 理由 |
|---|---|
| 句柄**可被蓝图 / 脚本持有** | 脚本侧必须能主动注销，否则只能等 GC 兜底 |
| 句柄**必须是身份**（每总线自发号、永不复用） | 下标会被回收复用给后来的订阅，**MUST NOT** 用下标作身份 |
| 句柄**自带注销能力** | 调用方不必持有总线引用 |

> **订阅身份与实例句柄同构**：都是「自发号、永不复用、`0` 无效」的身份。总线内部用 `TMap<int64, 频道>` 从身份找频道，再用句柄里的 `SlotIndex` 直接定位槽位——**两跳 O(1)，不扫描**。

### 1.1.5 两条注册路径 ✅

```cpp
// 路径 A：C++ 直收回调（满足铁律 3：不需要派生任何类型）
template <typename FPayloadType, typename TCallable>
FTcsEventSubscription Subscribe(
    FGameplayTag        Channel,
    TCallable&&         Callback,      // void(FGameplayTag, const FPayloadType&)
    ETcsEventMatch      Match = ETcsEventMatch::ExactMatch);

// 路径 B：反射（蓝图 / 脚本）
FTcsEventSubscription SubscribeReflected(
    FGameplayTag        Channel,
    UScriptStruct*      PayloadType,   // 期望的载荷类型
    UObject*            Sink,
    FName               FunctionName,
    ETcsEventMatch      Match = ETcsEventMatch::ExactMatch);
```

**路径 B 的过滤位置**：频道过滤与类型过滤**都在派发侧（C++）完成**，脚本虚拟机**不会收到不关心的频道**。

**两条路径共用同一套存储与同一个派发循环**，差别只在注册期的 thunk 如何构造。

### 1.1.6 派发：稳定下标 + `bAlive` + 深度归零 ✅

**问题**：派发循环正在遍历订阅数组时，回调里增删订阅会导致迭代失效。

**解法**：**槽位永不压缩**——注销只把该槽位置为不存活，下标交给 `FreeIndices` 复用。于是「指针/地址稳定」与「注销 O(1)」同时成立。

```cpp
struct FTcsEventSlot
{
    FTcsEventSink        Sink;
    FGameplayTag         Channel;
    ETcsEventMatch       Match;
    const UScriptStruct* PayloadType;      // 两条路径都填；MUST NOT 为空
    int64                SubscriptionId;   // 身份（与句柄一致）
    int32                Generation;       // 每次占用该下标自增；旧句柄据此判失效
    bool                 bAlive = false;   // 占用位；false = 该下标当前无有效订阅
};

// 栈内新增的条目：下标已预留，但槽位尚未落地
struct FTcsPendingSlot
{
    FTcsEventSlot Slot;
    int32         SlotIndex;
};

struct FTcsEventChannelState
{
    TArray<FTcsEventSlot>    Slots;          // 稳定下标：MUST NOT 压缩
    TArray<int32>            FreeIndices;    // 空闲下标栈
    int32                    DispatchDepth = 0;
    TArray<FTcsPendingSlot>  PendingAdds;
};
```

**`Slots` MUST 保持稳定下标，MUST NOT 压缩**——这是整个设计的支点。

| 选择 | 注销成本 | 稳定下标 | 结论 |
|---|---|---|---|
| `RemoveAtSwap` 压缩 | O(1) 但**下标全乱** | ❌ | **不可用** |
| 稳定下标 + `bAlive` 惰性回收 | **O(1)** | ✅ | **采用** |
| 只存 `SubscriptionId`、注销时扫描 | O(s) | ✅ | 不可用（千级并发注销） |

> **Why Not 用 `SlotGeneration` 兼容压缩**：`RemoveAtSwap` 换位后，指向旧下标的句柄无法被修正——**持有句柄的调用方不在总线控制范围内**。世代号能检出失效，但检出后只能退化成扫描。

**三个入口**：

```cpp
// 派发：遍历 [0, Slots.Num())，跳过 bAlive == false 的槽位。
// 每次派发零分配。成本 = Slots.Num()，而它只在「空闲栈为空」时才增长——
// 即 Slots.Num() 的稳态上界 ≈ 该频道的订阅数峰值，不是历史累计注册数。
void Publish(FGameplayTag Channel, const UScriptStruct* Type, const void* Data)
{
    FTcsEventChannelState& State = Channels.FindOrAdd(Channel);

    State.DispatchDepth += 1;

    const int32 Count = State.Slots.Num();   // 锁定长度：遍历期间不缩容
    for (int32 Index = 0; Index < Count; ++Index)
    {
        FTcsEventSlot& Slot = State.Slots[Index];

        if (!Slot.bAlive) { continue; }                       // 已注销 / 空槽
        if (!Matches(Slot, Channel, Type)) { continue; }       // 频道 / 类型过滤全在 C++ 侧

        Slot.Sink.Invoke(Channel, Type, Data);
    }

    State.DispatchDepth -= 1;

    if (State.DispatchDepth == 0)
    {
        Flush(State);   // 应用 PendingAdds；回收空闲下标
    }
}

// 注销：O(1)，只碰句柄自己记着的那个下标。
void Unsubscribe(FTcsEventSubscription Handle)
{
    FTcsEventChannelState& State = Channels[Locate(Handle.SubscriptionId)];

    // ① 还在待添加队列里：摘除，并把已预留的下标还回去（否则该下标永久泄漏）
    const int32 NumRemoved = State.PendingAdds.RemoveAllSwap(
        [&](const FTcsPendingSlot& P) { return P.Slot.SubscriptionId == Handle.SubscriptionId; },
        EAllowShrinking::No);
    if (NumRemoved > 0)
    {
        State.FreeIndices.Add(Handle.SlotIndex);
        return;
    }

    // ② 已落地：校验世代后置空，O(1)
    if (!State.Slots.IsValidIndex(Handle.SlotIndex)) { return; }
    FTcsEventSlot& Slot = State.Slots[Handle.SlotIndex];
    if (!Slot.bAlive || Slot.Generation != Handle.SlotGeneration) { return; }   // 陈旧句柄

    Slot.Sink.Destroy(Slot.Sink.Object);
    Slot.bAlive = false;
    State.FreeIndices.Add(Handle.SlotIndex);
}

// 新增：栈外立即落地，栈内进 PendingAdds（无条件，不分频道）
FTcsEventSubscription Subscribe(...)
{
    FTcsEventChannelState& State = Channels[Channel];

    // 先定下标与世代：空闲下标复用，避免 Slots 无界增长
    int32 SlotIndex;
    if (State.FreeIndices.Num() > 0) { SlotIndex = State.FreeIndices.Pop(EAllowShrinking::No); }
    else                             { SlotIndex = State.Slots.AddDefaulted(); }

    // 世代只增不减：旧句柄据此判失效
    const int32 Generation = State.Slots[SlotIndex].Generation + 1;

    FTcsEventSlot NewSlot{ ..., .SubscriptionId = NextSubscriptionId++,
                           .Generation = Generation, .bAlive = true };

    // 栈外立即落地；栈内入队（Flush 时按 SlotIndex 落地）
    if (State.DispatchDepth == 0) { State.Slots[SlotIndex] = NewSlot; }
    else                          { State.PendingAdds.Add({ NewSlot, SlotIndex }); }

    return FTcsEventSubscription{ NewSlot.SubscriptionId, SlotIndex, Generation };
}
```

**四条保证**：

| # | 保证 | 靠什么 |
|---|---|---|
| ① | 遍历期间数组**不缩容**，元素地址稳定 | 锁定 `Count`；槽位永不压缩 |
| ② | **派发中注销的订阅，本次派发立即不再收到** | `bAlive` 在遍历时被检查 |
| ③ | 派发中新增的订阅**本拍不生效**（含嵌套同频道的内层派发） | 新增进 `PendingAdds`，不进 `Slots` |
| ④ | 新增统一在**深度归零**时落地 | 深度计数 |

**为什么 ③ 必须连内层也算**：若新增直接 append，`Slots.Num()` 会变大，内层派发重新锁 `Count` 时就会看到它们——「本拍不生效」的语义被嵌套破坏。

**Flush 的时机只有一个：深度归零。** 派发入口**不做** flush——入口处的待处理列表天然为空（上一轮归零时已清），在那里加 flush 只会掩盖「某次没走到归零」的缺陷。

```cpp
// Flush：只在 DispatchDepth == 0 时调用。不做任何下标压缩。
void Flush(FTcsEventChannelState& State)
{
    // 待添加落地：下标在 Subscribe 时已预留，此处写回槽位即可。
    // 注销已在 Unsubscribe 步骤 ① 从队列摘净，此处无需再判。
    for (const FTcsPendingSlot& Pending : State.PendingAdds)
    {
        State.Slots[Pending.SlotIndex] = Pending.Slot;
    }

    State.PendingAdds.Reset();   // 保留容量，不还内存
}
```

#### 注销为什么是 O(1) ✅

**判据：`Unsubscribe` 的成本 MUST 与「该频道订阅数」无关。**

| 阶段 | 成本 | 说明 |
|---|---|---|
| 找到频道 | O(1) | `SubscriptionId → 频道` 用 `TMap` |
| 摘除 | **O(1)** | 直接用句柄里记的 `SlotIndex`，不扫描 |
| 校验 | O(1) | `bAlive && Generation == Handle.SlotGeneration` |

**「千级实体同帧死亡」的成本 = O(死亡数)**，不是 O(死亡数 × 订阅数)。

**本设计的唯一残余成本**：`Publish` 仍要扫过 `[0, Slots.Num())`，其中可能夹杂已不存活的槽位。

| 项 | 结论 |
|---|---|
| 上界 | `Slots.Num()` ≈ **该频道订阅数峰值**（空闲下标被复用，不会无限增长） |
| 每次派发成本 | O(峰值订阅数)，不是 O(历史累计注册数) |
| 是否可消除 | **不可**——稳定下标的必然代价 |
| 何时恶化 | 若某频道曾有过一次极大订阅峰，`Slots.Num()` 永久停在峰值 |

> **Why Not 定期压缩 `Slots`**：压缩会让所有存量句柄的 `SlotIndex` 失效，只能改成「压缩时递增全局世代、逼所有调用方重新注册」——代价远大于收益，且把一次性的峰值变成了周期性的全量失效。

⇒ **接受这个上界**：它是「O(1) 注销」的对价，且以**订阅峰值**为界，与事件频率无关。

**三种注销情形的统一处置**：

| 情形 | 处置 | 理由 |
|---|---|---|
| 订阅还在 `PendingAdds` 里 | 当场从队列摘除 | 注销语义是「以后不再收到」，不能因为还没落地就被复活 |
| 订阅已落地（栈内 / 栈外都一样） | 置 `bAlive = false`，下标压回 `FreeIndices` | **不压缩下标**，所以栈内外无差别；句柄仍可安全复用 |

> **Why Not 栈外直接压缩、栈内惰性**：一旦压缩，所有持有该频道句柄的调用方下标全部失效，而调用方不在总线控制范围内。**稳定下标是 O(1) 注销的前提。**

> **纪律**：延迟**只对派发调用栈内部的修改**有意义。栈外的 Apply / Remove 一律**直接生效**，不进待处理列表。

#### `Matches` 的定义 ✅

```cpp
bool Matches(const FTcsEventSlot& Slot, FGameplayTag Channel, const UScriptStruct* Type) const
{
    // ① 类型：MUST 精确相等。两条路径的 PayloadType 都非空（见 §1.1.2）
    if (Slot.PayloadType != Type) { return false; }

    // ② 频道：默认精确匹配；PartialMatch 才沿父链比较
    if (Slot.Match == ETcsEventMatch::ExactMatch) { return Slot.Channel == Channel; }
    return Channel.MatchesTag(Slot.Channel);
}
```

| 判据 | 约定 |
|---|---|
| 类型比较 | **指针相等**即可——`UScriptStruct*` 是注册期解析的唯一实例，不需要名字比较 |
| 类型 MUST NOT 放宽 | 子类 / 结构兼容一律**不做**：那会让订阅者收到它没声明能处理的结构 |
| `PayloadType` 为空 | **非法状态**，注册期就应被 `check` 挡住，不在此处兜底 |

### 1.1.7 频道层级匹配：显式开启 ✅

```cpp
enum class ETcsEventMatch : uint8
{
    ExactMatch,     // 默认：A.B 只收 A.B
    PartialMatch,   // 显式：A.B 收 A.B 与 A.B.*
};
```

**默认必须是 `ExactMatch`。**

| 理由 | 说明 |
|---|---|
| 精确匹配是「我就要这一条」的直白语义 | 层级匹配是「我要这一类」，是更强的假设 |
| 层级匹配有额外成本 | 需要沿 tag 父链逐层查找或预摊平 |
| 默认 MUST 是最省的形态 | 需要层级的调用方显式开启，成本可归因 |

### 1.1.8 载荷生命周期：受控借用 ✅

**契约**：载荷指针**只在派发调用期间有效**。

| 允许 | 禁止 |
|---|---|
| 在回调内**读**载荷 | 把载荷指针**存起来**延后使用 |
| 在回调内**拷贝**载荷到自己的容器 | 在回调内**修改**载荷 |
| 在回调内**发布新事件** | 在回调内**长时间阻塞** |

> **Why Not 值语义（每次拷贝）**：拷贝对高频事件是直接成本，而绝大多数订阅者只读。

**代价必须明确写进契约**：反射路径的消费者（蓝图 / 脚本）**MUST 当场拷贝**，否则悬空。

### 1.1.9 订阅生命周期闭合 ✅

**纪律**：施加时注册、撤销时注销，由**同一个所有者**配对完成。

**总线无法强制这条，但它是使用契约的一部分**：

| 错误形态 | 后果 |
|---|---|
| 只注册不注销 | 订阅永远增长，派发越来越慢 |
| 注册在 A 对象、注销在 B 对象 | 生命周期不一致，容易漏删 |
| 在回调里注册但不留句柄 | 无法注销 |
| **反射路径的对象先被销毁，订阅没注销** | **槽位里的 `UObject*` 已失效，派发会打到失效对象** |

**第四条 MUST 由注销路径解决**：

> **宿主 MUST 在对象销毁时注销它的全部订阅。** 总线**不提供**对象存活查询，MUST NOT 在派发热路径上判断「订阅者还在不在」。

| Why Not 总线自己判失效 | 说明 |
|---|---|
| 需要弱引用 | `FTcsEventSink` 是零堆分配的函数对象，装不下 `TWeakObjectPtr` 而不破坏内联预算 |
| 需要每派发一次检查 | 那是把一次不可控的 GC 语义塞进每个事件的成本里 |
| 有唯一正确时机 | 对象销毁是**确定的**时刻，宿主在那里注销即可；派发期判断是**猜测** |

### 1.1.10 业务需求

| 游戏 | 特殊要求 |
|---|---|
| LAC | 跨实体联动 MUST 有序且可回放 |
| 第三人称动作 | 帧内 MUST 有序 |
| 幸存者 ARPG | 千级实体 × 高频事件 |

### 1.1.11 路由结构不预设

> **压测数据到手前，MUST NOT 为路由加按实体过滤的快路径，也 MUST NOT 改路线形态。**

缺什么：**「订阅者总数」与「实际匹配该频道的订阅者数」的比值**——见族外 `Documents/tcs-remake-v2-drafts/未决-核心基线.md` §4。

## 1.2 帧末派发通道：**不建** ✅

### 1.2.1 它要解决的问题

**防重入与无限连锁**：状态类事件（伤害 / 死亡）若在派发过程中再次触发同类事件，会形成重入。

### 1.2.2 不建的判据

> **没有事件分级清单，就不该有一个帧末通道。**

这个通道要成立，必须先有一张**分级表**：哪些事件立即派发、哪些帧末派发。**该表不存在**，于是通道的存在只是每帧一次空调用。

### 1.2.3 与动作游戏的冲突

动作游戏里「伤害判定 → 死亡 → 表现」MUST 在**同一帧**完成。延迟一拍破坏手感。

⇒ **帧末派发不是「更好的」派发，只是一个特定语义下的选择**，不能作为默认。

### 1.2.4 重开此通道的触发条件

> **先写清分级表，再加通道**；一次只加一条，且该条 MUST 当场有发布者。分级表不存在时 MUST NOT 建通道。
