# 核心基线 · 数值聚合器（NumericAggregator）

> **定位**：V2 核心基线之一（Entity / RuntimeInstance / Clock / EventBus / NumericAggregator / GameplayTag）。
> **回答什么问题**：**一堆修改怎么合成一个数**。

**审核状态图例**：✅ 已裁决并批准 ｜ ⚠️ 未定 ｜ ❓ 待调研

> **本文件的写法**：只写最终设计与已裁决的架构，不复述历史实现。

---

## 1. 它是什么

**一句话**：给定一个基数与一组「运算 + 数值」条目，求出一个数；**结果与条目的输入排列无关**（由固定的浮点归约顺序兑现，见 §2.3）。

**本质是一个纯函数**——零状态、零副作用、零领域词汇。

这也是它有资格成为核心基线的根本原因：它比池和堆更纯——输入只包含基值、运算条目和覆盖策略；它不持有来源句柄。

---

## 2. 算法

### 2.1 单值公式 ✅

```text
① 若有 OverrideFinal：按策略选出该带的赢家，直接返回赢家值。
② 否则，若有 OverrideBase：按策略选出该带的赢家；有效基值 = 赢家值，否则 = BaseValue。
③ Value = (有效基值 + ΣAdd) × (1 + ΣPercentAdd) × ΠMul + ΣFlatAdd。
```

| 类 | 运算带 | 含义 |
|---|---|---|
| 累加 | `Add` | 线性加到有效基值，空带为 `0` |
| 累加 | `PercentAdd` | 同带百分比相加，再作为一个因子作用于已加 `Add` 的值，空带为 `0` |
| 累加 | `Mul` | 独立倍率连乘，空带为 `1` |
| 累加 | `FlatAdd` | 在全部倍率之后平加，空带为 `0` |
| 覆盖 | `OverrideBase` | 仅替换基值，四带照常参与 |
| 覆盖 | `OverrideFinal` | 直接返回，跳过基值覆盖和四带 |

**封闭枚举，无 Custom 位。** 只有一个 `PercentAdd` 带：基值 `100` 上的 `+20%` 与 `+30%` 合为 `150`；若明确配置成独立的 `Mul 1.2` 与 `Mul 1.3`，则为 `156`。两种业务含义不同，聚合器不做隐式转换。

**一次调用只计算一个值，不提供 Segment。** 例如，若项目需要分别读取或修改「基础攻击力」和「额外攻击力」，可将它们建模为独立属性，并由项目统一定义总攻击力的派生关系。分量的命名、依赖和取值时点不属于聚合器；同一套四带折叠也不应在调用方重写。

### 2.2 它不做什么（同等重要）✅

| 不做 | 谁做 |
|---|---|
| 不产生条目 | 调用方（各自的容器） |
| 不求值条目内的数值 | 调用方（收集期求值） |
| 不预筛条目（如竞争组） | 调用方 |
| 不做值域收口（clamp / wrap） | 调用方 |
| 不登记依赖边 | 调用方 |
| 不决定「谁该进聚合」 | 调用方 |

**一句话**：它只吃**已经摊平好的**条目；值入口吐出 `double`，另有一条**明细入口**吐出「这个数是怎么来的」（§3.3）。所有上下文相关的判断都在外面。

### 2.3 它保障的两件事

1. **顺序无关**——同一浮点环境下，同一基值、策略和有效条目集合，仅改变条目排列，不改变结果或可报告的覆盖来源。
   四带均按 `(OrderSeq, Value)` 升序归约（同用 `TcsCompare`，见 §5.4）；这是浮点定序，不给普通条目赋予业务优先级。
2. **单一实现**——值和明细走同一套算术、定序与覆盖选优；各领域需要同样的算术时共用它，不各写一份。

## 3. 接口形态（最终）✅

> **以下按依赖顺序排列**：任何被使用的类型都定义在使用点之前。

```cpp
// 外部符号（不属本文件）：
//   TConstArrayView / TArray / TInlineAllocator / TOptional —— UE 视图、容器与可选值
//   std::abs / std::signbit（<cmath>）、std::is_floating_point_v（<type_traits>）—— 标准库
//
// 本文件**不引入 FTcsSourceHandle**——见 §3.2 的裁决。

enum class ETcsAggregateOp : uint8
{
	Add,           // 线性加到有效基值
	PercentAdd,    // 唯一百分比累加带
	Mul,           // 独立倍率连乘
	FlatAdd,       // 所有倍率之后平加
	OverrideBase,  // 只替换基值，四带照常
	OverrideFinal, // 直接返回，跳过其他求值
};

enum class ETcsOverrideStrategy : uint8
{
    LatestApplied,   // 施加序最大者胜（= 最近一次「首次施加」）。刷新不改变它，见 §3.2
    EarliestApplied, // 施加序最小者胜（= 最早一次「首次施加」）。刷新不改变它，见 §3.2
    MaxValue,        // 数值最大者胜（默认）
    MinValue,        // 数值最小者胜
    MaxAbsValue,     // 绝对值最大者胜
    MinAbsValue,     // 绝对值最小者胜
    HighestPriority, // Priority 最大者胜
};

struct FTcsAggregateEntry
{
	ETcsAggregateOp   Op       = ETcsAggregateOp::Add;
	double            Value    = 0.0;
	int32             Priority = 0;   // 仅 Override 带 + 仅 HighestPriority 策略时读
	uint64            OrderSeq = 0;   // 参与带内归约定序；覆盖按施加序选优时使用，也用于平局归因。
	                                  // 0 = 无可追踪施加序（流程域用它，见 §4.3）。
};

// 实际参与公式的基值与四带归约结果。
struct FTcsAggregateFoldDetail
{
	double EffectiveBaseValue;
	double SumAdd;
	double SumPercentAdd;
	double ProdMul;
	double SumFlatAdd;
};

// 只报告实际生效的覆盖；来源序号 0 表示不可追踪。
struct FTcsAggregateOverrideDetail
{
	ETcsAggregateOp Op; // 仅 OverrideBase 或 OverrideFinal
	uint64 WinnerSeq;
};

struct FTcsAggregateDetail
{
	double Value = 0.0; // 与值入口逐位相同
	TOptional<FTcsAggregateOverrideDetail> Override; // 缺省 = 未发生覆盖
	TOptional<FTcsAggregateFoldDetail> Fold;         // 缺省 = 最终值覆盖，未执行公式
};

// 两个入口使用相同的基值、摊平条目与策略；值入口不构造明细。
double EvaluateAggregatedValue(
	double BaseValue,
	TConstArrayView<FTcsAggregateEntry> Entries,
	ETcsOverrideStrategy Strategy = ETcsOverrideStrategy::MaxValue);

FTcsAggregateDetail EvaluateAggregatedDetail(
	double BaseValue,
	TConstArrayView<FTcsAggregateEntry> Entries,
	ETcsOverrideStrategy Strategy = ETcsOverrideStrategy::MaxValue);
```

**实现形状**（**一律用精确关系，不用近似相等**——模糊相等不满足传递性，会破坏顺序无关）：

```cpp
// ── 比较器先定义：被下面的 IsStronger 与求值两处使用 ─────────────

// 三方比较：返回 -1 / 0 / +1，对浮点给出**全序**（含 NaN 与 ±0），不做减法
// 全序是「顺序无关」的实现前提：排序键与 IsStronger 共用这一把尺
template <typename T>
int32 TcsCompare(const T& A, const T& B)
{
    if (A < B) { return -1; }
    if (B < A) { return +1; }

    if constexpr (std::is_floating_point_v<T>)
    {
        // 走到这里只剩两种可能：真相等，或至少一侧 NaN
        const bool bANaN = (A != A);
        const bool bBNaN = (B != B);
        if (bANaN || bBNaN)
        {
            // 契约违约（§5.4），但仍给出全序：NaN 视为最小 ⇒ 结果可复现
            return bANaN ? (bBNaN ? 0 : -1) : +1;
        }
        // 有限且数值相等：±0 必须分开，否则位级结果仍依赖遍历顺序
        if (std::signbit(A) != std::signbit(B))
        {
            return std::signbit(A) ? -1 : +1;
        }
    }
    return 0;
}

// 依次比较策略、有符号值；仍打平时，用可追踪施加序稳定来源归因。
bool IsStronger(const FTcsAggregateEntry& A, const FTcsAggregateEntry& B, ETcsOverrideStrategy Strategy)
{
	int32 Order = 0;   // A 对 B：正 = A 更强

	switch (Strategy)
	{
	case ETcsOverrideStrategy::LatestApplied:
		// 0 表示无施加序：若与非 0 混用，无施加序恒弱于有施加序；同为 0 则策略级打平。
		if ((A.OrderSeq == 0) != (B.OrderSeq == 0)) { Order = (A.OrderSeq != 0) ? +1 : -1; }
		else { Order = TcsCompare(A.OrderSeq, B.OrderSeq); }
		break;
	case ETcsOverrideStrategy::EarliestApplied:
		if ((A.OrderSeq == 0) != (B.OrderSeq == 0)) { Order = (A.OrderSeq != 0) ? +1 : -1; }
		else { Order = -TcsCompare(A.OrderSeq, B.OrderSeq); }
		break;
	case ETcsOverrideStrategy::MaxValue:        Order = TcsCompare(A.Value, B.Value); break;
	case ETcsOverrideStrategy::MinValue:        Order = -TcsCompare(A.Value, B.Value); break;
	case ETcsOverrideStrategy::MaxAbsValue:     Order = TcsCompare(std::abs(A.Value), std::abs(B.Value)); break;
	case ETcsOverrideStrategy::MinAbsValue:     Order = -TcsCompare(std::abs(A.Value), std::abs(B.Value)); break;
	case ETcsOverrideStrategy::HighestPriority: Order = TcsCompare(A.Priority, B.Priority); break;
	}

	if (Order != 0) { return Order > 0; }

	const int32 ByValue = TcsCompare(A.Value, B.Value);
	if (ByValue != 0) { return ByValue > 0; }

	// 0 不是来源；只在策略和值同时相等时比较归因。
	return A.OrderSeq != 0 && (B.OrderSeq == 0 || A.OrderSeq < B.OrderSeq);
}

// ── 工具一：按策略选出指定覆盖带里最强的那一条 ──────────────
static const FTcsAggregateEntry* SelectStrongestOverride(
    TConstArrayView<FTcsAggregateEntry> Entries,
    ETcsAggregateOp                     Op,
    ETcsOverrideStrategy                Strategy)
{
    const FTcsAggregateEntry* Winner = nullptr;
    for (const FTcsAggregateEntry& Entry : Entries)
    {
        if (Entry.Op != Op) { continue; }
        if (!Winner || IsStronger(Entry, *Winner, Strategy)) { Winner = &Entry; }
    }
    return Winner;
}

// ── 工具二：四带折叠。定序只为让结果与输入排列无关 ──────────
struct FTcsAggregateBands
{
    double SumAdd = 0.0, SumPercentAdd = 0.0, ProdMul = 1.0, SumFlatAdd = 0.0;
};

static FTcsAggregateBands FoldBands(TConstArrayView<FTcsAggregateEntry> Entries)
{
    // 浮点加法不满足结合律 ⇒ 先按 (OrderSeq, Value) 定序再累加
    // 排序走下标 + 内联分配，典型条目数（≤32）下零堆分配
    TArray<int32, TInlineAllocator<32>> Order;
    Order.Reserve(Entries.Num());
    for (int32 Index = 0; Index < Entries.Num(); ++Index) { Order.Add(Index); }
    Order.Sort([Entries](int32 A, int32 B)
    {
        const int32 ByOrder = TcsCompare(Entries[A].OrderSeq, Entries[B].OrderSeq);
        return ByOrder != 0 ? ByOrder < 0 : TcsCompare(Entries[A].Value, Entries[B].Value) < 0;
    });

    FTcsAggregateBands Bands;
    for (int32 Index : Order)
    {
        const FTcsAggregateEntry& Entry = Entries[Index];
        switch (Entry.Op)
        {
        case ETcsAggregateOp::Add:        Bands.SumAdd        += Entry.Value; break;
        case ETcsAggregateOp::PercentAdd: Bands.SumPercentAdd += Entry.Value; break;
        case ETcsAggregateOp::Mul:        Bands.ProdMul       *= Entry.Value; break;
        case ETcsAggregateOp::FlatAdd:    Bands.SumFlatAdd    += Entry.Value; break;
        default: break;   // 覆盖带不参与累加
        }
    }
    return Bands;
}

// 唯一求值内核。Out == nullptr 时不构造或写入任何明细。
static double EvaluateAggregatedCore(
	double BaseValue,
	TConstArrayView<FTcsAggregateEntry> Entries,
	ETcsOverrideStrategy Strategy,
	FTcsAggregateDetail* Out)
{
	// 入口按 §5.4 诊断非有限输入；此处省略诊断代码，不修正输入。
	if (const FTcsAggregateEntry* Winner =
		SelectStrongestOverride(Entries, ETcsAggregateOp::OverrideFinal, Strategy))
	{
		if (Out)
		{
			Out->Value = Winner->Value;
			Out->Override.Emplace(FTcsAggregateOverrideDetail{Winner->Op, Winner->OrderSeq});
			Out->Fold.Reset();
		}
		return Winner->Value;
	}

	const FTcsAggregateEntry* BaseWinner =
		SelectStrongestOverride(Entries, ETcsAggregateOp::OverrideBase, Strategy);
	const double EffectiveBaseValue = BaseWinner ? BaseWinner->Value : BaseValue;
	const FTcsAggregateBands Bands = FoldBands(Entries);
	const double Result = (EffectiveBaseValue + Bands.SumAdd)
		* (1.0 + Bands.SumPercentAdd) * Bands.ProdMul + Bands.SumFlatAdd;

	if (Out)
	{
		Out->Value = Result;
		Out->Override.Reset();
		if (BaseWinner)
		{
			Out->Override.Emplace(FTcsAggregateOverrideDetail{BaseWinner->Op, BaseWinner->OrderSeq});
		}
		Out->Fold.Emplace(FTcsAggregateFoldDetail{
			EffectiveBaseValue, Bands.SumAdd, Bands.SumPercentAdd, Bands.ProdMul, Bands.SumFlatAdd
		});
	}
	return Result;
}

double EvaluateAggregatedValue(
	double BaseValue,
	TConstArrayView<FTcsAggregateEntry> Entries,
	ETcsOverrideStrategy Strategy)
{
	return EvaluateAggregatedCore(BaseValue, Entries, Strategy, nullptr);
}

FTcsAggregateDetail EvaluateAggregatedDetail(
	double BaseValue,
	TConstArrayView<FTcsAggregateEntry> Entries,
	ETcsOverrideStrategy Strategy)
{
	FTcsAggregateDetail Detail;
	EvaluateAggregatedCore(BaseValue, Entries, Strategy, &Detail);
	return Detail;
}
```

### 3.1 单级互斥 ✅

**7 个策略互斥，没有隐藏的更高优先级规则。**

| 选「最大」时 | 一条 Priority=100 / Value=5 与一条 Priority=0 / Value=99 |
|---|---|
| 结果 | **99 赢**（Priority 完全不看） |

**理由**：使用者明确说了要按什么赢，就不该有另一条隐藏规则插队。

**后果（必须承认）**：`Priority` 只在 `HighestPriority` 策略下有意义；其余策略下它是死配置。处置见 §5.2。

### 3.2 施加序用 `uint64 OrderSeq`，不持有 `FTcsSourceHandle` ✅

**裁决**：条目上存 `uint64 OrderSeq`，它记的是**施加序**——这条修正器**首次被施加**的先后。

> **它不是「物理时间轴」。** 没有单位、与 `FTcsClock` 无关联、批量施加时同一时刻的 N 条也会拿到 N 个不同的号。

**值从哪来**：域侧持有 `FTcsSourceHandle`（撤销锚点 + UI 归因），构造条目时填 `Handle.Id`。**聚合器只接 `.Id`，不接整个句柄。**

**为什么降成 `uint64`**（三条判据）：

| # | 判据 | 说明 |
|---|---|---|
| ① | **只用 `.Id` 却持有整个句柄 = 过度耦合** | 聚合器需要的是「谁更早」这一个**序关系**；`IsValid()` / `operator==` / 进程唯一发号器的语义它一个都不用 |
| ② | **反射友好** | `FTcsSourceHandle` 是**非反射纯 C++ struct**（裸 `struct`，无 `USTRUCT`，见 [运行时实例](运行时实例.md) §1.3.1）。它出现在条目里就直接禁止 `FTcsAggregateEntry` 成为 `USTRUCT`。换成 `uint64` 后聚合器的类型**都可以**是反射类型 |
| ③ | **铁律 ④** | 注释只写当前契约。字段名叫 `Source` 而实际只读 `.Id`，读代码的人会以为聚合器在管身份 |

**`0` 是保留值 = 「无施加序语义」**：

| 域 | `OrderSeq` 填什么 | 为什么 |
|---|---|---|
| 属性 | `Handle.Id` | 有撤销锚点，施加序真实存在 |
| 参数 | `Handle.Id` | 同上 |
| **流程** | **`0`** | 流程域 MUST NOT 有 `Source` 字段（§4.3）——它没有施加序概念，也就不需要区分先后 |

> **`0` 这个保留值让 §4.3 的禁令与本节不再冲突**：流程域填 `0` 不是「有一个 Source」，而是「**不排施加序**」。`LatestApplied` / `EarliestApplied` 对全 `0` 的集合恒打平，落到 §5.1 的决胜级（按值比较）——**这正是流程域该有的行为**。覆盖带内不建议混用 `0` 与非 `0` 施加序；若发生混用，在 `LatestApplied` 与 `EarliestApplied` 下无施加序（`0`）一律弱于有施加序的非 `0` 条目，避免 `0` 在 `EarliestApplied` 下被误判为「最早施加」。

**三个「时序」MUST 分开**：

| 语义 | 该由谁承载 | `OrderSeq` 管不管 |
|---|---|---|
| **施加序**——首次挂上的先后 | `OrderSeq` | **管**，这就是它的全部含义 |
| **刷新序**——最近一次续命 | 需要它的域自己负责 | **不管**，也 MUST NOT 悄悄塞进来 |
| **物理时刻**——真实时间 | `FTcsClock` | **不管**，聚合器 MUST NOT 引入时间戳字段 |

> **Why Not 真的用物理时间**：要比真实时刻就得给 `FTcsAggregateEntry` 加 `FTcsClock` 时间戳——那是**另一个字段、另一个消费者**，而今天零个域需要「按真实时刻比较覆盖」。按铁律 ① 不建。

**刷新不改变 `LatestApplied` 判定，这是有意的**：

> 同源续命若只修改数值而不重新发号，`OrderSeq` 保持首次施加时的编号不变（具体刷新入口与重算时机由各领域自行裁决，不属聚合器）。

刷新是**续命**，不是**重新施加**。某域若需要「刷新后变得更『新』」，正确做法是**重发号**（= 显式重新施加），MUST NOT 被解释成 `OrderSeq` 的含义悄悄改变。

**同刻多条按发号序，即施加循环的顺序**：批量施加一次挂 N 条，会得到 N 个不同的号，先后 = 循环顺序。这是定义，不是缺陷——要「同刻无先后」就该换策略。

**可回放不新增要求**：`OrderSeq` 来自发号器，而发号器**不可重放**（`运行时实例.md` §1.2.4：「发号结果 MUST 进快照，或回滚区间内 MUST NOT 分配新号」）。聚合器只是引用这条既有裁决。

### 3.3 明细：只报告实际生效的计算 ✅

`EvaluateAggregatedDetail(BaseValue, Entries, Strategy)` 的 `Value` 与同输入的 `EvaluateAggregatedValue` 逐位一致。明细只报告聚合器计算或选出的结果，不重复输入条目，不提供逐条贡献或覆盖前的假设值。

| 路径 | `Value` | `Override` | `Fold` |
|---|---|---|---|
| 无覆盖 | 四带公式结果 | 缺省 | 原基值、四带实算汇总 |
| `OverrideBase` 生效 | 四带公式结果 | 基值覆盖类型与赢家序号 | 赢家基值、四带实算汇总 |
| `OverrideFinal` 生效 | 最终值覆盖的赢家值 | 最终值覆盖类型与赢家序号 | **缺省：没有执行公式** |

**缺省不等于单位元。** 公式执行了但某带没有条目，仍报告该带实际采用的单位元（加法 `0`、连乘 `1`）；没有执行公式就不返回这组字段。`Override` 是否有值才表示是否覆盖；`WinnerSeq == 0` 只表示该赢家不可追踪，不影响覆盖生效，覆盖数值为 `0` 同理。

例如，基值 `100`，条目为 `Add 20`、`PercentAdd 0.25`、`Mul 2`、`FlatAdd 5`：无覆盖得 `305`；增加 `OverrideBase 80` 得 `255`，明细仍有四带；再增加 `OverrideFinal 0` 则返回 `0`，且没有 `Fold`。

**成本与归属**：值入口返回 `double`，不构造明细；调用方有展示或诊断需求时才走明细入口。两者共用选优、定序和公式。明细是本地诊断 / 展示产物，不参与复制与快照。需要查看移除某条后会发生什么，应修改输入再调用同一内核，不在外层重写算术。

> 本节只说明各场景如何接入单值聚合，不定义领域 API、预筛策略、取值时刻或存储形态。领域未定的事项以各领域后续裁决为准。

### 4.0 一张总表

| | **属性** | **参数** | **流程属性** |
|---|---|---|---|
| **基值示例** | 当前属性的单一基值 | 参数行求值结果 | **0.0**（空集示例） |
| **条目来源** | 属性修正器实例 | 同键参数修正器实例 | 黑板该键的提交 |
| **条目数值** | 收集期求值 | 已解析值 | **读时**求值 |
| **预筛** | 无 | **竞争组选优** | 无 |
| **策略** | 属性定义侧配置 | 固定默认 | 固定默认 |
| **后续处理** | **值域收口**（clamp / wrap / custom） | 取整 + 下界 0 | **无** |
| **覆盖举例** | 换基值但保留修正，或直接锁最终值 | 直接锁本次参数求值的结果 | 用显式覆盖提交一个工作值 |

### 4.1 属性聚合

```text
遍历属性修正器实例
  → 求值（按需登记依赖边）
  → 摊平成同一属性的一组 FTcsAggregateEntry
→ EvaluateAggregatedValue(BaseValue, Entries, Strategy)
→ ApplyValueDomain(...)   // clamp / wrap / custom
```

**各属性的基值和条目由调用方准备。** 如果项目把基础量与额外量建模为不同属性，分别求各自的值，再按项目定义的派生关系得到总量；不要把两组条目交给同一次聚合并假定它们仍有不同作用范围。

**必须记住的分工**：

```text
条目收集（含求值、依赖登记）  →  聚合  →  值域收口
         不属于聚合器            聚合器     不属于聚合器
```

**属性域的刷新、批处理与重算时机归属性域后续裁决，不属聚合器**：聚合器是无状态纯函数，每次仅根据调用方传入的 `BaseValue`、摊平 `Entries` 与 `Strategy` 求值。属性域选择何时重算、是否提供批处理或同源原地改值接口，均以属性域正式裁决为准；唯一跨层约束是——若同源刷新希望保持原有 `LatestApplied` / `EarliestApplied` 位次，则沿用原 `OrderSeq`，若希望视为重新施加则重新发号（§3.2）。

**明细接线（§3.3）**：展示若需要解释某次结算，要把与该次值求值一致的 `BaseValue`、摊平 `Entries` 和 `Strategy` 交给 `EvaluateAggregatedDetail`。面板手里没有这些输入时，由属性侧提供；缓存、重收集与调用时点不由聚合器规定。明细解释的是聚合结果，不包含属性域之后的值域收口。

### 4.2 参数链

**它承担两件聚合器不做的事**：

**(a) 竞争组预筛**——同一竞争组内只让解析值最大的条目进聚合。

> 聚合本身顺序无关，但**「谁进聚合」不由聚合器管**。

**(b) 策略取默认值**——参数域没有「属性定义」这一层，所以不能有自己的策略配置。

**一个特殊场景**：`等级` 也走同一条聚合——

> 特殊之处在于**它改的是等级而不是参数表读数**，而不在于它另有一套算术。

所以 `Add +2` ⇒ 等级 3、`Mul 2` ⇒ 等级 6，与普通参数**逐字同式**。

### 4.3 流程属性

**特殊处理**：

- 基数**恒为 0.0**（流程黑板是「空集」语义，作用域值由调用方以 Override 提交写入）；
- **读时求值**（操作数保持提交态，提交时不求值）；
- 无覆盖优先级概念（`Priority` 恒 0）；
- **无值域收口**（流程工作值没有边界概念）。

**裁决**：

> **流程域 MUST NOT 有 `FTcsSourceHandle`。**

⇒ 流程域构造条目时：

| 字段 | 填什么 |
|---|---|
| `OrderSeq` | **`0`**（保留值 = 无施加序语义，§3.2） |
| `Priority` | **`0`**（无覆盖优先级概念） |

**这不再与 §3 的接口冲突**（2026-11-11 订正）：原裁决写「流程域 MUST NOT 有 `Source` 字段」，而 §3 的条目结构**强制**有一个 `Source`——流程域构造条目时无处可逃。改成 `uint64 OrderSeq` 后，填 `0` 是**合法且语义正确**的：它表达「我不参与施加序排序」，不是「我有一个我不该有的来源」。

⇒ 流程域因此**表达不了「后来者覆盖」**：`OrderSeq` 与 `Priority` 恒 0 ⇒ `LatestApplied` / `EarliestApplied` / `HighestPriority` 全部打平，落到 §5.1 决胜级按值比较，得到的是「大的覆盖小的」。

该语义是否需要，见族外 `未决-核心基线.md` §6；需要它时即触发让流程域开始填真实 `OrderSeq`，在此之前 MUST NOT 预留更多字段。

## 5. 比较器与决胜规则 ✅

### 5.1 覆盖选优与平局归因

```text
1) 按策略比较（7 选 1；在 LatestApplied / EarliestApplied 下，非 0 OrderSeq 恒强于无施加序的 0，同为 0 时策略级打平）
2) 若策略下打平 → 按有符号值比较（大的赢）
3) 若策略和值仍相同 → 只为归因：非 0 的 OrderSeq 优先；多个非 0 取最小值
```

> **Why Not 只比一级**：`MaxAbsValue` / `MinAbsValue` 必然打平——`+5` 与 `-5` 绝对值相同。

> **前两级决定覆盖数值，第三级只决定来源。** 例如两条覆盖都是 `100`、策略下也打平，`OrderSeq = 11` 与 `12` 选 `11`；若另一条是 `0`，仍选 `11`。两条都为 `0` 或同一个非 0 号，则数值与对外归因等价，无需再区分条目。

**比较一律用精确关系**（不等于 / 大于），不用近似相等：模糊相等不满足传递性，会破坏「顺序无关」。

**求值前的排序键与 `IsStronger` 共用同一套精确关系**（都用 `TcsCompare`）：MUST NOT 一处精确、一处近似——否则排序给出的定序与比较器认定的强弱会打架。

> **定序不是业务规则**：带内排序只固定浮点归约顺序；覆盖比较最后一级的 `OrderSeq` 只固定策略与数值打平时的归因，不改变原有策略的胜负。

> **`TcsCompare` MUST NOT 用减法实现**：`(A - B)` 在两个方向上都有溢出风险（`uint64` 尤甚，`LatestApplied`/`EarliestApplied` 直接用它），且减法只对整数成立。
> **`std::abs`** / **`std::signbit`** / **`std::is_floating_point_v`** 都是标准库符号，属语言 / 数学库，不是本框架定义。
> **`A != A`** 是识别 NaN 的标准手法（自比较为假），不需要额外函数。

### 5.2 Priority 的可见性 ✅

**问题**：`Priority` 只在 `HighestPriority` 策略下有意义，其余策略下是死配置。配置者填了没效果，比没填更糟。

**Why Not 条件显示（已评估，否决）**：声明式 `EditCondition` 的查找作用域是**被条件属性的所属 struct**（`EditConditionContext.cpp:130`；源码注释 `:190` 明写此假设），属性名不支持路径（只有函数名支持 `.` 全路径找静态函数，`:82`）。

| 试过的路子 | 为什么不行 |
|---|---|
| 声明式 `EditCondition` 引用另一结构体的 `Strategy` | 查不到——作用域就是本 struct |
| 函数库里一个 `static UFUNCTION` 判定 | 静态分支求值跑在**类的 CDO** 上（`:230-240`），看不到正在编辑的实例；且路径只传函数名，传不进参数 |
| 自定义 Details 面板（`IDetailPropertyRow::EditCondition`，`IDetailPropertyRow.h:217`） | **可行**，但为一个死配置的可见性要写一块编辑器代码 + customization 注册 |

> **跨对象是必然的，不是结构选择**：策略是「一个属性一份」，`Priority` 是「一条修正器一份」，这个层级差异不会随 Def 形态改变而消失。

**裁决**：在数据校验（`IsDataValid`）里报 **Warning**——十行代码拿到同样的告知效果。

### 5.3 不提供「带权数字」

**裁决**：运算带由 `Op` 枚举唯一确定，**不额外提供「带序权重」数值**。

**理由**：聚合器本身就是按 `Op` 分桶的，**根本不需要带权数字**。而一个「看起来能改变聚合顺序但实际上无消费者」的字段，只会诱导错误配置。

### 5.4 输入域与特殊值 ✅

> **条目 `Value` 与 `BaseValue` MUST 为有限值**（非 NaN、非 ±Inf）。非有限值是**上游缺陷**，聚合器 MUST NOT 试图修正它。

**为什么必须定这条**：`<` 对 NaN 两侧都为假、对 `±0` 两侧也都为假 —— 不打这条契约，比较器就**给不出全序**，赢家会取决于谁先被遍历到。

| 值 | 契约 | 比较器兜底（违约时仍成立） | 后果与边界 |
|---|---|---|---|
| **NaN** | MUST NOT 出现 | 视为**最小**；NaN 之间等价 | `MaxValue` 下 NaN 永不赢；`MinValue` / `MinAbsValue` 下会赢。违约传入多个不同载荷/符号位型的 NaN 时，只保证输出为 NaN，**不保证** NaN 位型逐位一致 |
| **±Inf** | MUST NOT 出现 | 无需特殊处理（序正常） | 但它会让 `ProdMul` 溢出成 Inf、再由 `Inf × 0` 产生 NaN，故一并排除 |
| **±0** | 允许 | `-0` 略小于 `+0` | 覆盖选优区分符号位（如 `MaxValue` 下 `+0` 胜 `-0`、`MinValue` 下 `-0` 胜 `+0`，`OverrideFinal(-0.0)` 保留 `-0.0`）；四带累加与连乘按定序后的 IEEE 754 算术执行（如 `(-0.0) + (+0.0) = +0.0`） |
| **有限输入运算溢出** | 入口只诊断非有限输入，不拦有限输入溢出 | — | 极端有限输入累加或连乘仍可能溢出为 `±Inf`（或进一步触发 `Inf × 0 = NaN`）；聚合器不做钳制或饱和，值域收口归调用方（§2.2） |

> **防御兜底不等于允许**：比较器给出全序，是为了让违约时**结果可复现**，而不是让违约变成可接受。求值入口 MUST 用 `ensureMsgf` 报一次违约——这个错误不可见（不崩、不报错、只让数据悄悄错），不加断言就没人知道。

### 5.5 两种覆盖的作用域 ✅

| 覆盖带 | 作用域 | 其余条目 |
|---|---|---|
| `OverrideBase` | 替换公式的基值 | 四个累加带照常参与 |
| `OverrideFinal` | 直接决定最终值 | 不选基值覆盖，也不执行四带公式 |

两种覆盖都可出现在同一次求值的条目中。策略只在**同一个覆盖带**内选优；一旦有最终值覆盖，不比较两个覆盖带之间的数值、优先级或施加序。同源配置的校验仍按 §6。

## 6. 同源多条 Override 的处置 ✅

> **在 Def 编辑器的数据校验里报 `Error`**（`EDataValidationResult::Invalid` + `Context.AddError`），**不是 `Warning`**。校验键为**「同源 + 同目标 + 同覆盖带（同为 `OverrideBase` 或同为 `OverrideFinal`）」**；判定逻辑随具体 `Def` 资产类型各自实现，本节不展开（同一来源若同时配置 `OverrideBase` 与 `OverrideFinal`，在聚合器层面按 §5.5 有确定语义，是否在配置侧禁止由对应领域 `Def` 校验裁决）。

**Why Not 聚合器自己解决**：这是**配置错误，不是求值歧义**——一次施加不可能在同一目标的同一覆盖带上同时给出两个覆盖值。

> **Why Not 用「比较器反正能算出个赢家」来兜底**：它确实算得出——策略打平后 §5.1 的**决胜级**会按值大小挑一条，`MaxValue` 一类更是直接就分出胜负。问题正在这里：那个胜负只是按 §5.1 的数值规则选出的，并不代表配置正确，拿它裁决语义错误，等于把配置错误**静默**变成一条看起来合法的结果。

| 同源、同目标、同覆盖带两条 Override | 比较器 | 后果 |
|---|---|---|
| **值不同** | 分得出（策略或决胜级） | 确定但**任意** ⇒ 正是要报的那一对 |
| **值相同** | 完全打平 | 两条值相同 ⇒ 输出一致，**实际无害** |

**为什么是 `Error` 而不是 `Warning`**：`Warning` 不产生失败判定，配置错误会一路活到运行期。**判定逻辑下放给各 `Def` 资产**——只有它知道自己有几行、行序与 `Source` 怎么来。

> **触发点（引擎事实）**：UE 数据校验的保存钩子在**保存完成之后**（`FDataValidationModule::OnPackageSaved` → `UEditorValidatorSubsystem::ValidateSavedPackage`），报出 message log 与 toast，**不阻断保存**。本项不要求「存不进去」，故不另挂 pre-save 钩子。

各 `Def` 资产的具体判定逻辑见族外：`Documents/tcs-remake-v2-drafts/未决-核心基线.md` §5。

## 10. 可推广到其它基线的四条

1. **数值本身不含方向**——任何「取最大 / 最小」的规则都要先问「这个字段的语义方向是什么」。
2. **把「谁和谁比」留在外面，把「怎么合」放在里面**——预筛、依赖登记、值域收口全部留调用方。
3. **封闭枚举 + 明确拒绝理由**，比开放扩展更能保护热路径的正确性。
4. **纯函数是理想的跨域单位**——没有状态，所以不产生生命周期问题；没有领域词汇，所以能跨语义完全不同的域。
