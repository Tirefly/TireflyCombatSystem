# 核心基线 · 数值聚合器（NumericAggregator）

> **定位**：V2 核心基线之一（Entity / Instance / Clock / EventBus / NumericAggregator / GameplayTag）。
> **回答什么问题**：**一堆修改怎么合成一个数**。

**审核状态图例**：✅ 已裁决并批准 ｜ ⚠️ 待审 ｜ ❓ 待调研

> **本文件的写法**：只写最终设计与已裁决的架构，不复述历史实现。

---

## 1. 它是什么

**一句话**：给定一个基数与一组「运算 + 数值」条目，求出一个数；**结果与条目顺序无关**（由固定累加顺序兑现，见 §2.3）。

**本质是一个纯函数**——零状态、零副作用、零领域词汇。

这也是它有资格成为核心基线的根本原因：它比池和堆更纯——只需要 `double`、一个枚举和一个来源句柄。

---

## 2. 算法

### 2.1 唯一的算法 ✅

```text
① 全局条目若含 OverrideGlobal：选出最强的一条，直接返回（一切作废）
② 逐段求值：
     段内若含 OverrideSegment：选出最强的一条，该段结果 = 该值（段内其他全部作废）
     否则：
         Base = 段内若含 OverrideBase ? 最强的一条的值 : 该段的 BaseValue
         Di   = (Base + ΣAdd) × (1 + ΣPercentAdd)
③ Final = (Σ Di) × (1 + ΣPercentAdd_全局) × ΠMul + ΣFlatAdd
```

**七个封闭的运算带，分两类**：

| 类 | 带 | 说明 |
|---|---|---|
| **累加** | `Add` / `PercentAdd` / `Mul` / `FlatAdd` | `Add`、`PercentAdd` 在段内；`Mul`、`FlatAdd` 在全局层；`PercentAdd` 两处都可用（段内 = 段百分比，全局 = 总加成） |
| **覆盖** | `OverrideBase` / `OverrideSegment` / `OverrideGlobal` | 覆盖范围由窄到宽，见 §5.5 |

**无 Custom 位。** 封闭枚举比开放扩展更能保护热路径的正确性。

**段数由调用方定，段序无语义。** 单段（`Segments` 只有一项、全局层为空）退化成 V2 初版的四带公式；要表达「基础值 / 额外值受不同百分比」这类 ARPG 公式就用两段。段之间是**求和**，编号只是标识，不含先后含义。

**Why Not 把乘区拆成多个独立的值容器**：另一种做法是给每个放大阶段各开一个容器，再由调用方把它们合成为一个数。

**这条路在 TCS 里有正当用途，但不在这一层**：它解的是「**多个不同的量**怎么串成一条管线」（例如「基础值 → 倍率 → 平坦加成 → 最终覆盖」那样一条链，链上每一步是不同的量、顺序有语义），而本文件解的是「**一个数**怎么由多个基值来源合成」。两者不是同一个问题的两个答案。

**真把它用在一个数上**，代价是：

| 代价 | 说明 |
|---|---|
| **乘区集合由代码产生** | 段由配置声明；容器要代码 `new` 出来 ⇒ 配置侧无法新增乘区 |
| **合成为被搬到调用方** | §2.1 的公式出现第二份实现——§2.3 的「单一实现」正是靠「只有一个地方知道怎么合成」兑现的 |
| **存储随乘区数线性增长** | 每个容器一份条目表 + 一份脏标记 + 一次独立折叠 |
| **容器间关系无契约** | 谁乘谁、谁在最后覆盖，全靠调用顺序约定，没有任何地方可校验 |

**一处必须承认的差异**：容器可以**异构**（某个只接受覆盖、某个基值恒为常量），而段是**同构**的——§5.5 的合法 `Op` 矩阵对所有段一视同仁，「第 1 段只许覆盖、第 2 段只许加法」这类**逐段不同**的约束今天表达不了。真有这种需求时，要扩的是 §5.5 的矩阵（按段位区分），**不是换成容器**。

**段级覆盖只在「段」这一层有意义**：`OverrideBase` 换的是某个段的基值，`OverrideSegment` 作废的是某个段——两者都以「存在多个段」为前提。所以**单段便捷重载**（一段 + 空全局层）的 `Entries` 只由**累加带 + `OverrideGlobal`** 构成，段级覆盖传进去会被 `FoldBands` 的 `default` 分支跳过。

> **这不是聚合器在偷懒**：单段重载的那「一段」没有可覆盖的对象，逐段覆盖在这里无意义。**合法性由调用方按 §5.5 矩阵自证**——聚合器不做预筛（§2.2），也不为越界条目报错。要段级覆盖就调分段版。

**Why Not 让属性域自己把几段拼起来**：看起来很省事——聚合器照旧只算单段，属性域每段调一次单段重载拿到 `Dᵢ`，再自己把 `Σ Dᵢ` 过一遍全局层。**它确实算得出**：每段传「该段条目 + 空全局层」时 `ΠMul=1`、`ΣFlatAdd=0`、`ΣPercentAdd_全局=0`，单段重载正好退化成纯段内公式 `(Base+ΣAdd)×(1+ΣPercentAdd)`，这一步没有歧义。

**代价落在全局层那一小段，但那一小段正是最难的部分**：属性域要拿 `ΣPercentAdd_全局` / `ΠMul` / `ΣFlatAdd`，就得自己遍历 `GlobalEntries`、按 `Op` 分流、把三个带各自累起来。表面上是三行代码，实际必须连同 §2.3 的**定序累加**一起重做——浮点加法不满足结合律，本条公式的「顺序无关」不是白来的，是靠「先按 `(OrderSeq, Value)` 升序排序再累加」兑现的（§3 `FoldBands`）。**谁累加，谁就得自带这把尺。**

**两份定序一旦分叉，就是两个数**：排序键少用一个字段、`±0` 的处理差一处（§5.4）、NaN 兜底写得不一样，同一个角色的数值在属性面板上和实际结算里就会不同，而且**不会崩、不会报错**。这正是 §2.3「单一实现」要防的形态——它防的不是「代码重复」，是「同一形状各写一遍之后悄悄走样」。

> **扩聚合器只多一个函数；让调用方自己拼则永久多一份实现**，且这份实现会随每次公式调整再分叉一次。

> 真正能替代这条设计的是**换模型**而不是换分工——§2.1 开头评估过「一乘区一容器」，结论是不采纳。

### 2.2 它不做什么（同等重要）✅

| 不做 | 谁做 |
|---|---|
| 不产生条目 | 调用方（各自的容器） |
| 不求值条目内的数值 | 调用方（收集期求值） |
| 不预筛条目（如竞争组） | 调用方 |
| 不做值域收口（clamp / wrap） | 调用方 |
| 不登记依赖边 | 调用方 |
| 不决定「谁该进聚合」 | 调用方 |

**一句话**：它只吃**已经摊平好的**条目；值入口吐出 `double`，另有一条**明细入口**吐出「这个数是怎么来的」（§3.3）。所有上下文相关的判断都在外面。

### 2.3 它保障的两件事

1. **顺序无关**——条目怎么排，结果都一样。这是确定性 / 可回放的地基。
   由**固定的累加顺序**兑现：求值前按 `(OrderSeq, Value)` 升序排序。**不靠浮点加法的结合律——它不成立。**
2. **单一实现**——三域共用同一份代码，不是「同一形状各写一遍」。

## 3. 接口形态（最终）✅

> **以下按依赖顺序排列**：任何被使用的类型都定义在使用点之前。

```cpp
// 外部符号（不属本文件）：
//   TConstArrayView / TArray / TInlineAllocator —— UE 视图与容器
//   std::abs / std::signbit（<cmath>）、std::is_floating_point_v（<type_traits>）—— 标准库
//
// 本文件**不引入 FTcsSourceHandle**——见 §3.2 的裁决。

enum class ETcsAggregateOp : uint8
{
    // ── 累加带（可并存，按位置折叠）──
    Add,              // 段内：线性加
    PercentAdd,       // 段内 = 段百分比；全局 = 总加成
    Mul,              // 全局：连乘
    FlatAdd,          // 全局：终值平坦加

    // ── 覆盖带（互斥，各自在自己的集合里按策略选赢家）──
    OverrideBase,     // 只覆盖「该段的 BaseValue」，段的 Add / PercentAdd 照常
    OverrideSegment,  // 覆盖「整个段」，段内其他条目全部作废
    OverrideGlobal,   // 覆盖「整个属性」，所有段 + 全局层全部作废
};

enum class ETcsOverrideStrategy : uint8
{
    LatestApplied,   // 施加序最大者胜（= 最近一次「首次施加」）。刷新不改变它，见 §3.2
    EarliestApplied, // 施加序最小者胜（= 最早一次「首次施加」）。刷新不改变它，见 §3.2
    MaxValue,        // 数值最大者胜（默认）
    MinValue,        // 数值最小者胜
    MaxAbsValue,     // 绝对值最大者胜
    MinAbsValue,     // 绝对值最小者胜
    HighestPriority, // Priority 最大者胜
};

struct FTcsAggregateEntry
{
    ETcsAggregateOp   Op       = ETcsAggregateOp::Add;
    double            Value    = 0.0;
    int32             Priority = 0;   // 仅 Override 带 + 仅 HighestPriority 策略时读
    uint64            OrderSeq = 0;   // 施加序（仅 Override 带 + 仅 LatestApplied/EarliestApplied 读）。
                                      // 0 = 「无施加序语义」（流程域用它，见 §4.3）
};

// 一段 = 一个基值 + 该段的条目（只用 Add / PercentAdd / OverrideBase / OverrideSegment）
struct FTcsAggregateSegment
{
    double                              BaseValue;
    TConstArrayView<FTcsAggregateEntry> Entries;
};

// 分段求值：段内各算各的，段结果相加，全局层再乘一次
// GlobalEntries 只用 PercentAdd / Mul / FlatAdd / OverrideGlobal
double EvaluateAggregatedValue(
    TConstArrayView<FTcsAggregateSegment> Segments,
    TConstArrayView<FTcsAggregateEntry>   GlobalEntries,
    ETcsOverrideStrategy                  Strategy = ETcsOverrideStrategy::MaxValue);

// 单段便捷重载：V2 初版四带公式的退化形态。OverrideGlobal 覆盖一切
// 对「只有累加带 + OverrideGlobal」的输入，与 V2 初版逐位相同；
// 混入段级覆盖（OverrideBase / OverrideSegment）时与分段版**不等价**——它们被忽略，见 §2.1 末注
double EvaluateAggregatedValue(
    double                              BaseValue,
    TConstArrayView<FTcsAggregateEntry> Entries,
    ETcsOverrideStrategy                Strategy = ETcsOverrideStrategy::MaxValue);

// ── 明细（§3.3）：与公式逐项对应，不合并层 ────────────────────

// 段级明细：对应「段值 = (Base + Σadd) × (1 + Σp)」的每一项
// 注意：段内没有 Mul / FlatAdd（§5.5 矩阵），故本结构只有两个累加带
struct FTcsAggregateSegmentDetail
{
    double           BaseValue     = 0.0;  // **实际使用的**基值（被 OverrideBase 换过则不是原 BaseValue）
    double           SumAdd        = 0.0;
    double           SumPercentAdd = 0.0;
    double           SegmentValue  = 0.0;  // 该段对「段值之和」的贡献

    // 该段生效的覆盖。MUST 给出**是哪一条**而不是 bool——界面要说「被【破甲】覆盖了」
    // 0 = 该段没被覆盖；此时 OverrideOp 无意义。
    // 域拿这个序号回查自己的账本即得来源句柄（明细是 UI 路径，O(n) 扫账本可接受，见 §3.3）
    uint64           OverrideWinnerSeq = 0;
    ETcsAggregateOp  OverrideOp        = ETcsAggregateOp::OverrideBase;  // 仅 OverrideWinnerSeq 有效时读
};

// 全局层明细 + 最终值
struct FTcsAggregateDetail
{
    double Value            = 0.0;  // 与值入口逐位相同
    double SumSegmentValues = 0.0;  // Σ 段值（中间量，便于核对）
    double SumPercentAdd    = 0.0;  // 全局层：总加成
    double ProdMul          = 1.0;
    double SumFlatAdd       = 0.0;

    // OverrideGlobal 命中时：整体不生效，Segments 留空
    bool   bOverridden          = false;
    uint64 OverrideWinnerSeq    = 0;   // 同 FTcsAggregateSegmentDetail::OverrideWinnerSeq

    TArray<FTcsAggregateSegmentDetail> Segments;
};

// 明细入口。代价由需要明细的调用点承担，值入口不受影响
FTcsAggregateDetail EvaluateAggregatedDetail(
    TConstArrayView<FTcsAggregateSegment> Segments,
    TConstArrayView<FTcsAggregateEntry>   GlobalEntries,
    ETcsOverrideStrategy                  Strategy = ETcsOverrideStrategy::MaxValue);
```

**实现形状**（**一律用精确关系，不用近似相等**——模糊相等不满足传递性，会破坏顺序无关）：

```cpp
// ── 比较器先定义：被下面的 IsStronger 与求值两处使用 ─────────────

// 三方比较：返回 -1 / 0 / +1，对浮点给出**全序**（含 NaN 与 ±0），不做减法
// 全序是「顺序无关」的实现前提：排序键与 IsStronger 共用这一把尺
template <typename T>
int32 TcsCompare(const T& A, const T& B)
{
    if (A < B) { return -1; }
    if (B < A) { return +1; }

    if constexpr (std::is_floating_point_v<T>)
    {
        // 走到这里只剩两种可能：真相等，或至少一侧 NaN
        const bool bANaN = (A != A);
        const bool bBNaN = (B != B);
        if (bANaN || bBNaN)
        {
            // 契约违约（§5.4），但仍给出全序：NaN 视为最小 ⇒ 结果可复现
            return bANaN ? (bBNaN ? 0 : -1) : +1;
        }
        // 有限且数值相等：±0 必须分开，否则位级结果仍依赖遍历顺序
        if (std::signbit(A) != std::signbit(B))
        {
            return std::signbit(A) ? -1 : +1;
        }
    }
    return 0;
}

// 两级比较：先按策略，打平再按有符号值（大的赢）——保证全序，结果与遍历顺序无关
bool IsStronger(const FTcsAggregateEntry& A, const FTcsAggregateEntry& B, ETcsOverrideStrategy Strategy)
{
    int32 Order = 0;   // A 对 B：正 = A 更强

    switch (Strategy)
    {
    case ETcsOverrideStrategy::LatestApplied:   Order = TcsCompare(A.OrderSeq, B.OrderSeq); break;
    case ETcsOverrideStrategy::EarliestApplied: Order = -TcsCompare(A.OrderSeq, B.OrderSeq); break;
    case ETcsOverrideStrategy::MaxValue:        Order = TcsCompare(A.Value, B.Value); break;
    case ETcsOverrideStrategy::MinValue:        Order = -TcsCompare(A.Value, B.Value); break;
    case ETcsOverrideStrategy::MaxAbsValue:     Order = TcsCompare(std::abs(A.Value), std::abs(B.Value)); break;
    case ETcsOverrideStrategy::MinAbsValue:     Order = -TcsCompare(std::abs(A.Value), std::abs(B.Value)); break;
    case ETcsOverrideStrategy::HighestPriority: Order = TcsCompare(A.Priority, B.Priority); break;
    }

    if (Order != 0) { return Order > 0; }
    return TcsCompare(A.Value, B.Value) > 0;   // 决胜级：有符号值大的赢
}

// ── 工具一：按策略选出指定覆盖带里最强的那一条 ──────────────
static const FTcsAggregateEntry* SelectStrongestOverride(
    TConstArrayView<FTcsAggregateEntry> Entries,
    ETcsAggregateOp                     Op,
    ETcsOverrideStrategy                Strategy)
{
    const FTcsAggregateEntry* Winner = nullptr;
    for (const FTcsAggregateEntry& Entry : Entries)
    {
        if (Entry.Op != Op) { continue; }
        if (!Winner || IsStronger(Entry, *Winner, Strategy)) { Winner = &Entry; }
    }
    return Winner;
}

// ── 工具二：四带折叠。定序只为让结果与输入排列无关 ──────────
struct FTcsAggregateBands
{
    double SumAdd = 0.0, SumPercentAdd = 0.0, ProdMul = 1.0, SumFlatAdd = 0.0;
};

static FTcsAggregateBands FoldBands(TConstArrayView<FTcsAggregateEntry> Entries)
{
    // 浮点加法不满足结合律 ⇒ 先按 (OrderSeq, Value) 定序再累加
    // 排序走下标 + 内联分配，典型条目数（≤32）下零堆分配
    TArray<int32, TInlineAllocator<32>> Order;
    Order.Reserve(Entries.Num());
    for (int32 Index = 0; Index < Entries.Num(); ++Index) { Order.Add(Index); }
    Order.Sort([Entries](int32 A, int32 B)
    {
        const int32 ByOrder = TcsCompare(Entries[A].OrderSeq, Entries[B].OrderSeq);
        return ByOrder != 0 ? ByOrder < 0 : TcsCompare(Entries[A].Value, Entries[B].Value) < 0;
    });

    FTcsAggregateBands Bands;
    for (int32 Index : Order)
    {
        const FTcsAggregateEntry& Entry = Entries[Index];
        switch (Entry.Op)
        {
        case ETcsAggregateOp::Add:        Bands.SumAdd        += Entry.Value; break;
        case ETcsAggregateOp::PercentAdd: Bands.SumPercentAdd += Entry.Value; break;
        case ETcsAggregateOp::Mul:        Bands.ProdMul       *= Entry.Value; break;
        case ETcsAggregateOp::FlatAdd:    Bands.SumFlatAdd    += Entry.Value; break;
        default: break;   // 覆盖带不参与累加
        }
    }
    return Bands;
}

// ── 分段求值：唯一实现体。Out == nullptr 时明细写入整段不存在 ──
static double EvaluateAggregatedCore(
    TConstArrayView<FTcsAggregateSegment> Segments,
    TConstArrayView<FTcsAggregateEntry>   GlobalEntries,
    ETcsOverrideStrategy                  Strategy,
    FTcsAggregateDetail*                  Out)
{
    // ① 全局覆盖：最外层，命中即整体作废
    if (const FTcsAggregateEntry* W = SelectStrongestOverride(GlobalEntries, ETcsAggregateOp::OverrideGlobal, Strategy))
    {
        if (Out)
        {
            Out->Value            = W->Value;
            Out->bOverridden      = true;
            Out->OverrideWinnerSeq = W->OrderSeq;
            Out->Segments.Reset();   // 整体不生效 ⇒ 段级留空（§3.3 语义表）
        }
        return W->Value;
    }

    if (Out) { Out->Segments.Reset(); Out->Segments.Reserve(Segments.Num()); }

    // ② 逐段求值
    double Sum = 0.0;
    for (const FTcsAggregateSegment& Seg : Segments)
    {
        double SegmentValue = 0.0;

        // 段覆盖：整段作废
        if (const FTcsAggregateEntry* W = SelectStrongestOverride(Seg.Entries, ETcsAggregateOp::OverrideSegment, Strategy))
        {
            SegmentValue = W->Value;
            if (Out)
            {
                Out->Segments.Add({ 0.0, 0.0, 0.0, SegmentValue,
                                    W->OrderSeq, ETcsAggregateOp::OverrideSegment });
            }
        }
        else
        {
            // 基值覆盖：只换 BaseValue，段内 Add / PercentAdd 照常
            double Base = Seg.BaseValue;
            uint64 BaseWinnerSeq = 0;
            if (const FTcsAggregateEntry* W = SelectStrongestOverride(Seg.Entries, ETcsAggregateOp::OverrideBase, Strategy))
            {
                Base = W->Value;
                BaseWinnerSeq = W->OrderSeq;
            }

            const FTcsAggregateBands Bands = FoldBands(Seg.Entries);
            SegmentValue = (Base + Bands.SumAdd) * (1.0 + Bands.SumPercentAdd);

            if (Out)
            {
                Out->Segments.Add({ Base, Bands.SumAdd, Bands.SumPercentAdd, SegmentValue,
                                    BaseWinnerSeq, ETcsAggregateOp::OverrideBase });
            }
        }

        Sum += SegmentValue;
    }

    // ③ 全局层
    const FTcsAggregateBands G = FoldBands(GlobalEntries);
    const double Result = Sum * (1.0 + G.SumPercentAdd) * G.ProdMul + G.SumFlatAdd;

    if (Out)
    {
        Out->Value            = Result;
        Out->SumSegmentValues = Sum;
        Out->SumPercentAdd    = G.SumPercentAdd;
        Out->ProdMul          = G.ProdMul;
        Out->SumFlatAdd       = G.SumFlatAdd;
    }
    return Result;
}

// ── 值入口：签名与成本都不变 ──────────────────────────────
double EvaluateAggregatedValue(
    TConstArrayView<FTcsAggregateSegment> Segments,
    TConstArrayView<FTcsAggregateEntry>   GlobalEntries,
    ETcsOverrideStrategy                  Strategy)
{
    return EvaluateAggregatedCore(Segments, GlobalEntries, Strategy, nullptr);
}

// ── 明细入口：代价由要明细的调用点承担（§3.3）────────────
FTcsAggregateDetail EvaluateAggregatedDetail(
    TConstArrayView<FTcsAggregateSegment> Segments,
    TConstArrayView<FTcsAggregateEntry>   GlobalEntries,
    ETcsOverrideStrategy                  Strategy)
{
    FTcsAggregateDetail Detail;
    EvaluateAggregatedCore(Segments, GlobalEntries, Strategy, &Detail);
    return Detail;   // NRVO
}

// ── 单段便捷重载：一段 + 空全局层，OverrideGlobal 覆盖一切 ──
//    Entries 只由累加带 + OverrideGlobal 构成；段级覆盖（OverrideBase /
//    OverrideSegment）在这一层没有意义，传入会被忽略（见 §2.1 末注）
//    对上述合法输入，与 V2 初版四带公式逐位相同；参数域 / 流程域用它
double EvaluateAggregatedValue(
    double BaseValue,
    TConstArrayView<FTcsAggregateEntry> Entries,
    ETcsOverrideStrategy Strategy)
{
    if (const FTcsAggregateEntry* W = SelectStrongestOverride(Entries, ETcsAggregateOp::OverrideGlobal, Strategy))
    {
        return W->Value;
    }
    const FTcsAggregateBands Bands = FoldBands(Entries);
    return ((BaseValue + Bands.SumAdd) * (1.0 + Bands.SumPercentAdd)) * Bands.ProdMul + Bands.SumFlatAdd;
}
```

### 3.1 单级互斥 ✅

**7 个策略互斥，没有隐藏的更高优先级规则。**

| 选「最大」时 | 一条 Priority=100 / Value=5 与一条 Priority=0 / Value=99 |
|---|---|
| 结果 | **99 赢**（Priority 完全不看） |

**理由**：使用者明确说了要按什么赢，就不该有另一条隐藏规则插队。

**后果（必须承认）**：`Priority` 只在 `HighestPriority` 策略下有意义；其余策略下它是死配置。处置见 §5.2。

### 3.2 施加序用 `uint64 OrderSeq`，不持有 `FTcsSourceHandle` ✅

**裁决**：条目上存 `uint64 OrderSeq`，它记的是**施加序**——这条修正器**首次被施加**的先后。

> **它不是「物理时间轴」。** 没有单位、与 `FTcsClock` 无关联、批量施加时同一时刻的 N 条也会拿到 N 个不同的号。

**值从哪来**：域侧持有 `FTcsSourceHandle`（撤销锚点 + UI 归因），构造条目时填 `Handle.Id`。**聚合器只接 `.Id`，不接整个句柄。**

**为什么降成 `uint64`**（三条判据）：

| # | 判据 | 说明 |
|---|---|---|
| ① | **只用 `.Id` 却持有整个句柄 = 过度耦合** | 聚合器需要的是「谁更早」这一个**序关系**；`IsValid()` / `operator==` / 进程唯一发号器的语义它一个都不用 |
| ② | **反射友好** | `FTcsSourceHandle` 是**非反射纯 C++ struct**（`TcsSourceHandle.h:20` 裸 `struct`，无 `USTRUCT`）。它出现在条目里就直接禁止 `FTcsAggregateEntry` 成为 `USTRUCT`。换成 `uint64` 后聚合器的类型**都可以**是反射类型 |
| ③ | **铁律 ④** | 注释只写当前契约。字段名叫 `Source` 而实际只读 `.Id`，读代码的人会以为聚合器在管身份 |

**`0` 是保留值 = 「无施加序语义」**：

| 域 | `OrderSeq` 填什么 | 为什么 |
|---|---|---|
| 属性 | `Handle.Id` | 有撤销锚点，施加序真实存在 |
| 参数 | `Handle.Id` | 同上 |
| **流程** | **`0`** | 流程域 MUST NOT 有 `Source` 字段（§4.3）——它没有施加序概念，也就不需要区分先后 |

> **`0` 这个保留值让 §4.3 的禁令与本节不再冲突**：流程域填 `0` 不是「有一个 Source」，而是「**不排施加序**」。`LatestApplied` / `EarliestApplied` 对全 `0` 的集合恒打平，落到 §5.1 的决胜级（按值比较）——**这正是流程域该有的行为**。

**三个「时序」MUST 分开**：

| 语义 | 该由谁承载 | `OrderSeq` 管不管 |
|---|---|---|
| **施加序**——首次挂上的先后 | `OrderSeq` | **管**，这就是它的全部含义 |
| **刷新序**——最近一次续命 | 需要它的域自己负责 | **不管**，也 MUST NOT 悄悄塞进来 |
| **物理时刻**——真实时间 | `FTcsClock` | **不管**，聚合器 MUST NOT 引入时间戳字段 |

> **Why Not 真的用物理时间**：要比真实时刻就得给 `FTcsAggregateEntry` 加 `FTcsClock` 时间戳——那是**另一个字段、另一个消费者**，而今天零个域需要「按真实时刻比较覆盖」。按铁律 ① 不建。

**刷新不改变 `LatestApplied` 判定，这是有意的**：

> 同源时**直接刷新实例内部的数值**，然后**立即结算**——**不重建条目、不重新发号、只改值**；重算在写侧完成（§4.1）。

刷新是**续命**，不是**重新施加**。某域若需要「刷新后变得更『新』」，正确做法是**重发号**（= 显式重新施加），MUST NOT 被解释成 `OrderSeq` 的含义悄悄改变。

**同刻多条按发号序，即施加循环的顺序**：批量施加一次挂 N 条，会得到 N 个不同的号，先后 = 循环顺序。这是定义，不是缺陷——要「同刻无先后」就该换策略。

**可回放不新增要求**：`OrderSeq` 来自发号器，而发号器**不可重放**（`运行时实例.md` §1.2.4：「发号结果 MUST 进快照，或回滚区间内 MUST NOT 分配新号」）。聚合器只是引用这条既有裁决。

### 3.3 明细：与公式同构，MUST NOT 合并层 ✅

**裁决**：提供一条**明细入口** `EvaluateAggregatedDetail`；**值入口的签名与成本都不变**。

**它解决的是两个正确性问题，不是便利性问题**：

| 问题 | 现象 |
|---|---|
| **覆盖不可见** | 一条 `OverrideSegment` / `OverrideGlobal` 赢了以后，其余条目**全部不生效**。调用方只拿最终值，界面上却仍列着「装备 +20、羁绊 +30%」——玩家一算对不上，只会以为是算错了 |
| **带合计无处可得** | 界面要显示「+40%」，而这个合计是 `ΣPercentAdd`。拿不到就只能在外层自己写一遍折叠 ⇒ **第二份实现**，违反 §2.3 |

#### 明细只放「调用方拿不到的量」

> **判据**：凡是调用方自己能从输入算出来的，明细 MUST NOT 重复给。

`FTcsAggregateSegment.Entries` 是调用方递进来的，逐条值多少它本来就知道。真正拿不回来的只有 `FoldBands` 肚子里那几样：

- 每段**实际使用的**基值（被 `OverrideBase` 换过之后，不再是 `Seg.BaseValue`）
- 每段的 `ΣAdd` / `ΣPercentAdd`
- 每段的**段值贡献**
- **哪个覆盖赢了**（句柄，不是 bool）

所以**不提供逐条贡献归因**（见本节末 Why Not）。

#### 明细结构 MUST 与公式逐项对应

§2.1 的公式有两层，**每段各有自己的乘数**，压成一组带是不可还原的：

```text
(B₁+A₁)(1+p₁) + (B₂+A₂)(1+p₂)   ≠   (B₁+B₂+A₁+A₂)(1+p₁+p₂)
```

代入 `B₁=100, p₁=50%, B₂=50, p₂=10%`：正确是 `150 + 55 = 205`；合并成「Add=0、Percent=60%」算出来是 `150 × 1.6 = 240`，**差 35**。

⇒ **段一层、全局层一层，各给各的。** 段内没有 `Mul` / `FlatAdd`，全局层没有 `Add`（§5.5 矩阵）——这个**不对称 MUST 原样体现在结构里**，否则结构会诱导下游按错的层去取。

#### 三种覆盖下的明细语义

| 覆盖作用域 | 段级 | 全局层 |
|---|---|---|
| **`OverrideBase`** | `BaseValue` = 赢家值；`SumAdd` / `SumPercentAdd` **照常**（真实生效）；`OverrideWinnerSeq` / `OverrideOp` 标出赢家 | 不受影响 |
| **`OverrideSegment`** | 段内两带置**单位元**（`SumAdd=0` / `SumPercentAdd=0`），`SegmentValue` = 赢家值 | 不受影响 |
| **`OverrideGlobal`** | **`Segments` 留空**（段整体不生效） | 三带置**单位元**（`SumPercentAdd=0` / `ProdMul=1` / `SumFlatAdd=0`），`Value` = 赢家值 |

> **单位元表示的「这一层不参与」与「本来就没有条目」不能靠数值区分**——所以 `OverrideWinnerSeq` / `OverrideOp` / `bOverridden` 是必需字段，不是锦上添花。
>
> **`ProdMul` 的单位元是 `1` 不是 `0`**：置 `0` 会让下游把「不参与」误读成「被乘成零」。

> **Why Not 同时给「覆盖前」的视图**：那会让每个字段成对出现，接口直接翻倍。要看「没被覆盖会是多少」，正确做法是**禁用那条覆盖再求一次**——求值是纯函数，重跑零副作用。

#### 成本：默认路径一分不付

返回含 `TArray` 的结构体必然走 sret（隐藏返回指针）+ 至少一次构造/析构。所以**值入口 MUST 保持返回 `double`**，明细由第二个入口承担；两者共用同一个实现体（`Out == nullptr` 时明细写入整段不存在，编译器可完全消除）。

> **单段便捷重载没有明细版**：参数域与流程域不消费明细（见下表）。需要单段明细时，按「一段 + 空全局层」自己组 `Segments` 调明细入口——不为它增加第二个重载。

> **Why Not 把值入口直接改成返回明细结构**：那让每一次求值都付 sret 与容器构造的成本，包括三域里所有根本不要明细的调用点。铁律 ① 的立场是「不建就不付」，不是「建了大家一起付」。

#### 谁消费（铁律 ①）

| 消费者 | 时机 | 约束 |
|---|---|---|
| **LAC 属性面板 / 装备 tooltip** | 战斗中（自走棋的构筑理解依赖它） | 单机，明细**不出机** |
| **宿主自己的调试显示** | 开发期 | 只在编辑器 / 非 Shipping 构建；**由宿主自己画**——本基线只给数据 |
| 幸存者战斗态（1000~5000 实体） | **不要** | 明细 MUST NOT 进热路径 |

> **MUST NOT 进网络复制**：明细是本地诊断 / 展示产物，不参与同步与快照。

> **Why Not 逐条贡献归因**（逐条记「这一条贡献了多少」）：**归因规则没有唯一解**。多条 `PercentAdd` 连乘时，「谁贡献了多少」取决于按顺序摊派还是按比例分摊；照顺序摊派的实现里，同一条的贡献值取决于它排第几——这与 §2.3 的「顺序无关」直接冲突。界面真要逐条，用**差分**：`带合计 − 移除这一条后的合计`，**复用同一个聚合器**，零新增实现。

## 4. 三个消费场景 ✅

### 4.0 一张总表

| | **属性** | **参数** | **流程属性** |
|---|---|---|---|
| **段数** | **N**（LAC = 2：基础 / 额外） | **1** | **1** |
| **基数** | 属性基础值（每段一个） | 参数行求值结果 | **恒 0.0**（空集语义） |
| **条目来源** | 属性修正器实例 | 同键参数修正器实例 | 黑板该键的提交 |
| **条目数值** | 收集期求值 | 已解析值 | **读时**求值 |
| **预筛** | 无 | **竞争组选优** | 无 |
| **策略** | 属性定义侧配置 | 固定默认 | 固定默认 |
| **后续处理** | **值域收口**（clamp / wrap / custom） | 取整 + 下界 0 | **无** |
| **哪几种覆盖有意义** | 三种都可用：`OverrideBase` / `OverrideSegment` / `OverrideGlobal` | 基本只有 `OverrideGlobal` | **基本无**（见 §4.3） |

### 4.1 属性聚合

```text
遍历属性修正器实例
  → 求值（按需登记依赖边）
  → 摊平成 FTcsAggregateEntry，并按「段」分桶（段的语义归属性域）
→ EvaluateAggregatedValue(Segments, GlobalEntries, 属性定义的策略)
→ ApplyValueDomain(...)   // clamp / wrap / custom
```

**段数是属性体系级的一次决定，不是逐属性配**：同一套属性体系里，同一条修正器的「落哪段」必须含义一致，否则一件装备无法同时作用于两段属性和单段属性。**LAC 采用两段**（基础 / 额外），参数域与流程域恒为单段。

**必须记住的分工**：

```text
条目收集（含求值、依赖登记）  →  聚合  →  值域收口
         不属于聚合器            聚合器     不属于聚合器
```

**同源刷新的语义**：**按来源定位 → 原地改值 → 立即重算**。

> **这条在 2026-11-11 订正**：原文写「标脏，重算归读路径（惰性）」，与 `Attribute.md` §2.2 的「写时重算、帧末派发」**直接冲突**。两份文档对同一件事给了相反的时机。
>
> **取值一致为「写时重算」**，理由见下。

由此需要一条专用入口。**它属属性域，不属聚合器**——聚合器是纯函数、零状态，改不了任何值：

```cpp
// 属性域入口。作用域 = 单个属性实例。
// 返回后该属性的值**已是最新**（写时重算，见下方契约 ④）
int32 UpdateMagnitudesBySource(
    FTcsAttributeInstance&  Attr,
    FTcsSourceHandle        Source,   // 属域侧类型；聚合器只接它的 .Id
    TConstArrayView<double> NewValues);
```

| # | 契约 | 说明 |
|---|---|---|
| ① | **作用域是单个属性** | 一次施加可在同一实体的多个属性上各挂条目，`(Entity, Source)` 定位不到是哪一组 ⇒ 签名 MUST 收属性，MUST NOT 收裸 `Entity` |
| ② | **顺序即标识** | `NewValues[i]` 对应「该来源在该属性上登记的第 `i` 条」；顺序 = 施加时写入的顺序（定义侧行序），实例生命周期内不变 ⇒ 不需要额外标识字段 |
| ③ | **原子** | 全部校验在写之前完成；来源不存在或数量不符 ⇒ 返回 `0`，**一条都不改**。不存在「部分失败」——半更新会让属性停在混合态，而这里没有事务可回滚 |
| ④ | **写成功后立即结算** | 顺序是「改值 → 登记受影响的求值节点 → 结算」。**不是标脏等读**——理由见 §4.1 末的 Why Not |
| ⑤ | **返回值** | 实际写入条数；`0` 表示什么都没做 |
| ⑥ | **数量不符要报** | 那是配置 / 代码错配，`ensureMsgf` 一次 |

**不变量**：同源条目集合本身稳定，只有值在变——这也是 ② 成立的依据。

**Why 写时重算，不惰性**（三条）：

| # | 理由 |
|---|---|
| ① | **链步骤是同步的** | `ApplyAttributeSet` → 触发行求值 → 行为链再入起链，全在同一帧同一调用栈内。重算若推迟到读时，**同一条链里「先写、后读」就会读到旧值**：例如「先给目标加 50 攻击力，紧接着按攻击力算伤害」，伤害会用加之前的攻击力 |
| ② | **读侧要保持纯内存返回** | `AttributeScaled` 会跨实体读（`Instigator` / `Target` 两侧），读时触发重算等于让一次读取连锁唤醒另一侧的求值，递归深度不可控；且 `Evaluate` 可能落到宿主源，宿主在回调里再读属性就会**求值中途重入** |
| ③ | **批已经能表达「这一批算一次」** | 惰性想解决的问题（多次写只算一遍）由 `BeginBatch` / `CommitBatch` 解决。不需要再造一套「攒到读时」的机制 |

> **惰性的唯一收益是「少算」，而它换来的代价是「可能读到旧值」**——对一个同步链式执行、要求「写完立即可读」的系统，这个交换不划算。

> **批内读到的是批开始前的值，这不是惰性的残留**：批的语义是「这一批改动要么一起生效、要么都还没生效」（`Attribute.md` §2.2），让外部读到「一半生效」的中间态只会让调用方更难推理。**批内不读，与「写时不重算」是两件事。**

**明细入口的义务（§3.3）**：明细所需的 `Segments` / `GlobalEntries` 由属性域在收集期摊平，面板手里没有。所以属性域 MUST 提供一条「按当前状态重新摊平 + 调 `EvaluateAggregatedDetail`」的入口，且**与缓存值走同一条收集路径**——否则面板显示的和实际算的是两个数。

> **它不是第二条求值路径**：重用同一个 `CollectLayerEntries`（`Attribute.md` §3.4），只是把摊平结果交给明细入口而不是值入口。

### 4.2 参数链

**它承担两件聚合器不做的事**：

**(a) 竞争组预筛**——同一竞争组内只让解析值最大的条目进聚合。

> 聚合本身顺序无关，但**「谁进聚合」不由聚合器管**。

**(b) 策略取默认值**——参数域没有「属性定义」这一层，所以不能有自己的策略配置。

**一个特殊场景**：`等级` 也走同一条聚合——

> 特殊之处在于**它改的是等级而不是参数表读数**，而不在于它另有一套算术。

所以 `Add +2` ⇒ 等级 3、`Mul 2` ⇒ 等级 6，与普通参数**逐字同式**。

### 4.3 流程属性

**特殊处理**：

- 基数**恒为 0.0**（流程黑板是「空集」语义，作用域值由调用方以 Override 提交写入）；
- **读时求值**（操作数保持提交态，提交时不求值）；
- 无覆盖优先级概念（`Priority` 恒 0）；
- **无值域收口**（流程工作值没有边界概念）。

**裁决**：

> **流程域 MUST NOT 有 `FTcsSourceHandle`。**

⇒ 流程域构造条目时：

| 字段 | 填什么 |
|---|---|
| `OrderSeq` | **`0`**（保留值 = 无施加序语义，§3.2） |
| `Priority` | **`0`**（无覆盖优先级概念） |

**这不再与 §3 的接口冲突**（2026-11-11 订正）：原裁决写「流程域 MUST NOT 有 `Source` 字段」，而 §3 的条目结构**强制**有一个 `Source`——流程域构造条目时无处可逃。改成 `uint64 OrderSeq` 后，填 `0` 是**合法且语义正确**的：它表达「我不参与施加序排序」，不是「我有一个我不该有的来源」。

⇒ 流程域因此**表达不了「后来者覆盖」**：`OrderSeq` 与 `Priority` 恒 0 ⇒ `LatestApplied` / `EarliestApplied` / `HighestPriority` 全部打平，落到 §5.1 决胜级按值比较，得到的是「大的覆盖小的」。

该语义是否需要，见族外 `未决-核心基线.md` §6；需要它时即触发让流程域开始填真实 `OrderSeq`，在此之前 MUST NOT 预留更多字段。

## 5. 比较器与决胜规则 ✅

### 5.1 两级比较

```text
1) 按策略比较（7 选 1）
2) 若策略下打平 → 按有符号值比较（大的赢）
```

> **Why Not 只比一级**：`MaxAbsValue` / `MinAbsValue` 必然打平——`+5` 与 `-5` 绝对值相同。

> **这条决胜规则是任意的，但又是必要的。** 补一级有符号值比较即得**全序**，结果与遍历顺序无关；否则同分打平会让赢家取决于谁先被遍历到。

**比较一律用精确关系**（不等于 / 大于），不用近似相等：模糊相等不满足传递性，会破坏「顺序无关」。

**求值前的排序键与 `IsStronger` 共用同一套精确关系**（都用 `TcsCompare`）：MUST NOT 一处精确、一处近似——否则排序给出的定序与比较器认定的强弱会打架。

> **两条比较都靠 `TcsCompare` 的全序，而不只是「精确」**：精确只保证不产生假相等；全序才保证「任何两条都有确定的强弱」。后者是「结果与遍历顺序无关」的充分条件——见 §5.4。

> **`TcsCompare` MUST NOT 用减法实现**：`(A - B)` 在两个方向上都有溢出风险（`uint64` 尤甚，`LatestApplied`/`EarliestApplied` 直接用它），且减法只对整数成立。
> **`std::abs`** / **`std::signbit`** / **`std::is_floating_point_v`** 都是标准库符号，属语言 / 数学库，不是本框架定义。
> **`A != A`** 是识别 NaN 的标准手法（自比较为假），不需要额外函数。

### 5.2 Priority 的可见性 ✅

**问题**：`Priority` 只在 `HighestPriority` 策略下有意义，其余策略下是死配置。配置者填了没效果，比没填更糟。

**Why Not 条件显示（已评估，否决）**：声明式 `EditCondition` 的查找作用域是**被条件属性的所属 struct**（`EditConditionContext.cpp:130`；源码注释 `:190` 明写此假设），属性名不支持路径（只有函数名支持 `.` 全路径找静态函数，`:82`）。

| 试过的路子 | 为什么不行 |
|---|---|
| 声明式 `EditCondition` 引用另一结构体的 `Strategy` | 查不到——作用域就是本 struct |
| 函数库里一个 `static UFUNCTION` 判定 | 静态分支求值跑在**类的 CDO** 上（`:230-240`），看不到正在编辑的实例；且路径只传函数名，传不进参数 |
| 自定义 Details 面板（`IDetailPropertyRow::EditCondition`，`IDetailPropertyRow.h:217`） | **可行**，但为一个死配置的可见性要写一块编辑器代码 + customization 注册 |

> **跨对象是必然的，不是结构选择**：策略是「一个属性一份」，`Priority` 是「一条修正器一份」，这个层级差异不会随 Def 形态改变而消失。

**裁决**：在数据校验（`IsDataValid`）里报 **Warning**——十行代码拿到同样的告知效果。

### 5.3 不提供「带权数字」

**裁决**：运算带由 `Op` 枚举唯一确定，**不额外提供「带序权重」数值**。

**理由**：聚合器本身就是按 `Op` 分桶的，**根本不需要带权数字**。而一个「看起来能改变聚合顺序但实际上无消费者」的字段，只会诱导错误配置。

### 5.4 输入域与特殊值 ✅

> **条目 `Value` 与 `BaseValue` MUST 为有限值**（非 NaN、非 ±Inf）。非有限值是**上游缺陷**，聚合器 MUST NOT 试图修正它。

**为什么必须定这条**：`<` 对 NaN 两侧都为假、对 `±0` 两侧也都为假 —— 不打这条契约，比较器就**给不出全序**，赢家会取决于谁先被遍历到。

| 值 | 契约 | 比较器兜底（违约时仍成立） | 后果 |
|---|---|---|---|
| **NaN** | MUST NOT 出现 | 视为**最小**；NaN 之间相等 | `MaxValue` 下 NaN 永不赢；`MinValue` / `MinAbsValue` 下会赢——只承诺**可复现**，不承诺合理 |
| **±Inf** | MUST NOT 出现 | 无需特殊处理（序正常） | 但它会让 `ProdMul` 溢出成 Inf、再由 `Inf × 0` 产生 NaN，故一并排除 |
| **±0** | 允许 | `-0` 略小于 `+0` | 二者数值相等但**位不同**；不分开则返回的位取决于遍历顺序，下游 `1/x` 会分叉成 `±Inf` |
| **结果溢出** | 不处理 | — | 归调用方的值域收口（§2.2「不做值域收口」；§4.0「属性 → clamp / wrap」） |

> **防御兜底不等于允许**：比较器给出全序，是为了让违约时**结果可复现**，而不是让违约变成可接受。求值入口 MUST 用 `ensureMsgf` 报一次违约——这个错误不可见（不崩、不报错、只让数据悄悄错），不加断言就没人知道。

### 5.5 三种覆盖的作用域与合法组合 ✅

| 覆盖带 | 作用域 | 覆盖后其他条目 |
|---|---|---|
| `OverrideBase` | **一个段的基值** | 该段的 `Add` / `PercentAdd` **照常参与** |
| `OverrideSegment` | **整个段** | 该段所有条目**全部作废** |
| `OverrideGlobal` | **整个属性** | 所有段 + 全局层**全部作废** |

**为什么三种都要**：`OverrideBase` 表达「基础值被重置但装备加成仍然算」；`OverrideSegment` 表达「这一段整体被锁定，任何修正都不再生效」；`OverrideGlobal` 表达「这个属性被整体接管」。三者是不同的策划语义，**由配置者显式选择**，MUST NOT 由实现代为推断。

**合法组合矩阵**（Def 校验直接查这张表）：

| 位置 | 允许的 `Op` |
|---|---|
| **段内条目** | `Add`、`PercentAdd`、`OverrideBase`、`OverrideSegment` |
| **全局条目** | `PercentAdd`、`Mul`、`FlatAdd`、`OverrideGlobal` |

矩阵外的组合 ⇒ `IsDataValid` 报 **Error**（与 §6 同款处理）。

> **冲突规则**：同一段内同时出现 `OverrideBase` 与 `OverrideSegment` ⇒ **配置错误**。两者都想控制这一段，但没有可比的大小关系——一个是「清空修正只留这个值」，一个是「只换基值、修正照常」。用策略在它们之间选赢家，等于替配置者编一条没人能解释的规则。

**段序无语义**：段之间是**求和**，编号只是标识。MUST NOT 假定「第 0 段先算」会带来任何顺序差异。

## 6. 同源多条 Override 的处置 ✅

> **在 Def 编辑器的数据校验里报 `Error`**（`EDataValidationResult::Invalid` + `Context.AddError`），**不是 `Warning`**。判定逻辑随具体 DefAsset 类型各自实现，本节不展开。

**Why Not 聚合器自己解决**：这是**配置错误，不是求值歧义**——一次施加不可能在同一属性上同时给出两个覆盖值。

> **Why Not 用「比较器反正能算出个赢家」来兜底**：它确实算得出——策略打平后 §5.1 的**决胜级**会按值大小挑一条，`MaxValue` 一类更是直接就分出胜负。问题正在这里：那个胜负来自一条**任意的**兜底规则（§5.1 原文：「这条决胜规则是任意的，但又是必要的」），拿它裁决语义错误，等于把配置错误**静默**变成一条看起来合法的结果。

| 同源两条 Override | 比较器 | 后果 |
|---|---|---|
| **值不同** | 分得出（策略或决胜级） | 确定但**任意** ⇒ 正是要报的那一对 |
| **值相同** | 完全打平 | 两条值相同 ⇒ 输出一致，**实际无害** |

**为什么是 `Error` 而不是 `Warning`**：`Warning` 不产生失败判定，配置错误会一路活到运行期。**判定逻辑下放给各 DefAsset**——只有它知道自己有几行、行序与 `Source` 怎么来。

> **触发点（引擎事实）**：UE 数据校验的保存钩子在**保存完成之后**（`FDataValidationModule::OnPackageSaved` → `UEditorValidatorSubsystem::ValidateSavedPackage`），报出 message log 与 toast，**不阻断保存**。本项不要求「存不进去」，故不另挂 pre-save 钩子。

各 DefAsset 的具体判定逻辑见族外：`Documents/tcs-remake-v2-drafts/未决-核心基线.md` §5。

## 10. 可推广到其它基线的四条

1. **数值本身不含方向**——任何「取最大 / 最小」的规则都要先问「这个字段的语义方向是什么」。
2. **把「谁和谁比」留在外面，把「怎么合」放在里面**——预筛、依赖登记、值域收口全部留调用方。
3. **封闭枚举 + 明确拒绝理由**，比开放扩展更能保护热路径的正确性。
4. **纯函数是理想的跨域单位**——没有状态，所以不产生生命周期问题；没有领域词汇，所以能跨语义完全不同的域。
