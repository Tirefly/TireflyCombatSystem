## 2. 为什么按「核心基线 → 领域」组织

### 2.1 文档的组织单位必须比实现更长寿

| 依据 | 会变吗 |
|---|---|
| 代码模块 | **会**——会合并、拆分、改名 |
| 代码文件夹 | **会**——会随重构移动 |
| **依赖方向**（谁是核心、谁是领域、谁是宿主契约） | **不会** |

⇒ 文档以**依赖方向**为单位，物理布局留给实现阶段决定。

### 2.2 判据

```
        核心基线（Core Baselines）
        Entity / Instance / Clock / EventBus / NumericAggregator
                        ↓  零领域词汇，被 ≥2 个域依赖
        ─────────────────────────────────────
                        ↓
        领域（Domains）
        Attribute / Parameter / State / Effect / Skill / Damage / Targeting
                        ↓  各自持有领域词汇
        ─────────────────────────────────────
                        ↓
        宿主契约（Host Contracts）
        由宿主实现、框架定义的注入面
```

> 一个设施**不含任何领域词汇**、**被 ≥2 个领域依赖** ⇒ 核心基线。
> 含领域词汇 ⇒ 属于那个领域。
> 实现方必须是宿主 ⇒ 宿主契约。

### 2.3 五项基线的复核

| 基线 | 含领域词汇？ | 被几个域依赖 | 判定 |
|---|---|---|---|
| Entity | 否（实体是本体，不是领域） | 全部 | ✅ 核心 |
| Instance | 否 | 4 个域 | ✅ 核心 |
| Clock | 否 | 4 个域 | ✅ 核心 |
| EventBus | 否（Tag 是通用路由） | 4 个域 | ✅ 核心 |
| NumericAggregator | 否（五带运算无领域语义） | 3 个域 | ✅ 核心 |

### 2.4 载体形态不预设

> **核心基线 MUST NOT 预设为独立模块。** 判据：内容彼此只通过少数接口耦合、且无领域词汇渗入 ⇒ 可提炼为独立模块；否则留作文件夹（[01](01-定位与判据.md) 铁律 2）。

### 2.5 这个名字什么时候会失效

- 某个域发展到**自己也需要一套核心机制** ⇒ 它升格为核心基线，或另立「次核心」层；
- 某个基线被证明**只有单一域使用** ⇒ 它降格进那个领域；
- 「各域系统就绪」若裁成**统一形态**（见族外 `未决-核心基线.md`）⇒ 它就是第 6 项候选，届时按 §2.2 同一判据复核；
- **实体本体若改判归框架**（见 [战斗实体](02-核心基线/战斗实体.md) §0）⇒ 实体载体的归属随之变更，`EntityComponent` 从宿主侧升为框架侧。这是架构变更，须重新裁决。
