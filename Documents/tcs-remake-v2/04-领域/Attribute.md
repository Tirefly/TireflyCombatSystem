# 领域 · Attribute（属性）

> **定位**：实体共享数值状态。管属性的身份、存储形态、当前值组成、边界与约束维护、变更操作、生命周期、求值依赖和通知。
> **回答什么问题**：某个实体的某个属性现在是多少、能不能读、可以怎样改、改了之后谁会知道。
> **依赖**：[数值聚合器](../02-核心基线/数值聚合器.md)（单值算术）、[战斗实体](../02-核心基线/战斗实体.md)（实体句柄与级联清理）、[运行时实例](../02-核心基线/运行时实例.md)（`FTcsSourceHandle` 撤销锚点）、[事件总线](../02-核心基线/事件总线.md)（通知派发）、[GameplayTag](../02-核心基线/GameplayTag.md)（属性身份）。

**审核状态图例**：✅ 已裁决并批准 ｜ ⚠️ 未定 ｜ ❓ 待调研

> **本文件的写法**：只写最终设计与已裁决的契约。裁决过程、比较方案和未决条目在族外[交接文档](../../tcs-remake-v2-drafts/未决-Parameter与Attribute-本轮重审交接.md)；正文的 ⚠️ 指向其 §5.5。各节对应的裁决条目编号见文末「已裁定（速查）」。
>
> 入口与类型名是已裁的符号；参数与返回类型的具体形态未定（⚠️ AR5）。

## 0. 定位与边界 ✅

### 0.1 与 Parameter 的分工 ✅

- Attribute 负责实体共享数值状态，以及同实体属性之间的派生随动。Parameter 负责技能等消费者的局部参数求值与独立修正。两域复用同一套聚合算术，不因此合并为一个领域，也不因此推出两套账本或两个代码模块。
- 单次值描述求值只完成本次计算：不建立持续依赖、不保存业务快照、不发布业务值变化通知。持续维护由 Attribute 负责。
- 值描述求值所需的属性读取能力由组织这次求值的维护者在本次调用中提供；求值本身不自行定位 Attribute 服务。
- 跨域只锁定三条契约：本次调用提供属性读取能力；自动随动描述在求值前报告完整的潜在属性读取集合（§6.2）；Def 中的描述自动导出依赖，编辑器校验与运行时读取守卫两者兼有（§8.3）。Parameter 的内部机制不受本文件约束。

### 0.2 不做什么 ✅

- **不内置业务语义。** 资源增减只是带符号的通用扣补；是否允许、操作量多少由业务先定。不内置 Damage / Heal、生命 / 法力等宿主词汇，不细分资源类别。
- **动态贡献不自带计时。** 到期由施加它的管理者撤销；属性 Disabled 不暂停外部管理的时长。
- **施加者销毁不自动撤销贡献。** 施加方来源不是贡献的生命期所有者，清理按撤销锚点进行（§4.3）。
- **不建帧末通知通道。** 通知在修改调用返回前送达（§7.3）。
- **不做跨实体持续随动。** 跨实体只按次读取（§6.2）。本轮不要求，并非永久禁止。
- **不做通用事务或历史回滚。** 整组原子性只覆盖文中写明的各个操作。
- **不改聚合器。** 边界钳制、依赖、可用性和非有限值检查都是领域在聚合前后完成的工作。

## 1. 身份与存储形态 ✅

### 1.1 身份 ✅

实体句柄 + 属性 GameplayTag 唯一确定一个已建立属性。同一实体同一 Tag 同时最多一份状态。外部按实体句柄 + Tag 定位属性，不为属性发运行时实例句柄。

### 1.2 存储形态：`ETcsAttributeStorage` ✅

`UTcsAttributeDef` MUST 显式声明存储形态，二选一：

| 形态 | 持久状态 | 当前值 |
|---|---|---|
| `Core` | `CoreValue`：持久核心基值 | 由聚合求出（§2.1） |
| `Resource` | `Amount`：持久存量，没有 `CoreValue` | 即存量（§2.4） |

- 这是形态声明，不是业务分类；不引入「基值 / 当前值」双字段模型。
- `Amount` 只由三件事改变：首次建立的初值（§5.1）、扣补（§4.1）、约束维护（§3.3）。
- 资源依赖的公式输入放在边界属性上。例：最大生命是 `Core` 型，成长表写在最大生命上；当前生命是 `Resource` 型，上界引用最大生命。

**命名理由**：`CoreValue` 不叫 `BaseValue`，因为 `BaseValue` 是聚合器公式的起点，可被 `OverrideBase` 替换，与持久的 core 不是同一个东西。`Amount` 不叫 `Current`，因为「当前值」是所有属性的求值结果；也不叫 `Pool`，以免与 `TTcsInstancePool` 撞名。

### 1.3 运行态 ✅（持有者 ⚠️）

| 类型 | 含义 |
|---|---|
| `FTcsAttributeInstance` | 一个 `UTcsAttributeDef` 在某实体上的运行时对应物。不入 `TTcsInstancePool`，在实体的属性集合内按 Tag 查找 |
| `FTcsEntityAttributes` | 一个实体的全部属性运行态 |

`FTcsEntityAttributes` 由谁持有、挂在哪里：⚠️ AR1。

## 2. 当前值组成 ✅

### 2.1 `Core` 型：`BaseValue` 恒为 `CoreValue` ✅

当前值 = 聚合器单值公式（`BaseValue = CoreValue`，条目 = 定义内派生贡献 + 未撤销的动态贡献），再按 §3.2 钳制。

不设基值公式，也不设「派生落在基值还是运算带」的位置枚举。派生一律经运算带进入聚合（§2.2）。

### 2.2 定义内派生贡献 `DerivedAttrMods` ✅

- `UTcsAttributeDef` 的 `DerivedAttrMods` 声明随属性一同建立的派生贡献，每项落在一个运算带，受该带及覆盖规则的正常语义约束。例：core 100、由力量派生 Add 20，当前值 120；`OverrideBase` 200 生效时为 220，力量变化后仍随动。
- 派生不改写 `CoreValue`。需要「完全由其他属性算出」的属性，`CoreValue` 配 0。
- **同实体随动**：派生或贡献读取的同实体属性变化后，Attribute 维护受影响的当前值，调用者无需刷新。随动输入只能是 Attribute 可掌握的变化：固定配置、自身 `CoreValue`、同实体其他属性的当前值。其他外部变化须先显式写入某个属性，才能参与随动。
- 定义内派生贡献不接受普通动态撤销；Disabled 与唤醒都保留它们。

### 2.3 动态贡献 `FTcsAttrModInstance` ✅

- **粒度**：一个 `UTcsAttrModDef` 只修改一个属性，即一个目标 Tag、一个运算带、一个数值或计算描述，对应一条 `FTcsAggregateEntry`。施加后对应一个 `FTcsAttrModInstance`。多属性效果用多个 Def 表达，不设 Entry 类型。
- **成组**：一次施加的多个 `FTcsAttrModInstance` 共享一个撤销锚点（`FTcsSourceHandle`），组成一整组；这一层不建类型。施加方来源与撤销锚点是两种角色（[运行时实例](../02-核心基线/运行时实例.md) §1.3.3）。
- 多来源贡献并存、各自独立撤销；施加与撤销的时机由宿主决定。
- 计算描述读取同实体属性时自动随动（§2.2）。

### 2.4 `Resource` 型当前值 ✅

启用且必需边界可读时，当前值就是 `Amount`。`Resource` 型不接受任何贡献：不能「30 秒内当前生命 +300」，可以「30 秒内最大生命 +300」。

### 2.5 Why Not ✅

- **基值公式 / 派生位置枚举**：派生位于基值或 Add 带，都会被 PercentAdd / Mul 放大；两者差别只在 `OverrideBase` 是否一并覆盖派生、明细里归为基值还是贡献，后者没有真实消费者。
- **「只作用于基础部分」的百分比**（如额外攻击力、基础攻击光环）：放在任何位置都做不到。做法是属性分层：声明独立属性，再派生到目标属性。
- **Segment / 两段**：聚合器已裁定单值聚合；需要独立建模的数值用独立属性表达。

## 3. 边界与约束维护 ✅

### 3.1 边界声明 ✅

- 每个属性可以声明 `LowerBound` 和 `UpperBound`。每一侧的种类为 `ETcsAttributeBoundKind`：

| 值 | 含义 |
|---|---|
| `Unbounded` | 无界 |
| `Constant` | 常量 |
| `Attribute` | 同实体另一属性的当前值 |

- `Core` 型未声明的一侧即无界。
- `Resource` 型未声明下界时，契约默认下界为常量 0；可以声明其他下界，也可以显式声明 `Unbounded`。上界不强制。
- 边界引用的属性纳入依赖无环检查（§6.2）。

### 3.2 `Core` 型：聚合后钳制可见值 ✅

- 聚合后按有效区间钳制对外的当前值；不改 `CoreValue`，也不改贡献。`OverrideFinal` 不能绕过边界。
- 非有限结果在钳制前失败，不靠边界变成伪成功的有限值，也不做静默饱和。
- 边界不可读或有效区间为空时，当前读失败。

### 3.3 `Resource` 型：持久维护 ✅

边界对存量的影响 MUST 真实写入 `Amount` 并持久保留，不能只在读取时临时钳制：

| 情况 | 对 `Amount` 的效果 |
|---|---|
| 上界下降到存量以下 | 截断并保留。800 / 1000，上界降到 600 → 600；上界再升也不返还 |
| 上界上升 | 不补 |
| 下界上升到存量以上 | 永久补高。20，下界升到 30 → 30；下界再降也不扣回。这是约束维护，不是补充 |
| 必需边界不可读 | 当前读失败，扣补失败，`Amount` 原样保留，不当作 0、不清零 |
| 有效区间为空（如下界 0、上界 -10） | 同上；不隐式抬高上界 |
| 边界恢复可读 | 按当时的有效边界维护 `Amount`，只发可用性恢复通知。例：存量 800，故障期间上界变为 600，恢复时为 600 |
| 属性 Disabled 期间 | 边界变化不维护 `Amount`；唤醒时按当时的有效边界维护（§5.3） |

已合法接纳的边界修改不因下游故障自动回滚。

## 4. 变更操作 ✅

三种变更语义互不替代：资源扣补改 `Amount`，core 更新改 `CoreValue`，动态贡献可撤销。

### 4.1 资源扣补：`ModifyResourceAmount` ✅

- `ModifyResourceAmount(Tag, Delta)`：`Delta` 带符号，作用于已建立的 `Resource` 型属性，返回实际生效的变化量。
- **按最终可见量计量**：可见 200 扣 30 得 170；不逆解聚合公式，不暗加 `OverrideFinal`。
- **部分生效**：补充可部分生效到上界（800 / 1000 补 300，实际 +200）；扣减可部分生效到下界（10 扣 30、下界 0，实际 -10）。部分生效不等于足额支付；是否允许施法、是否足额由业务先行判断。请求量不等于实际变化量。
- **失败**（`Amount` 不变）：属性 Disabled；必需边界不可读；有效区间为空；结果非有限。Disabled 期间失败的请求不在唤醒时补执行。

### 4.2 core 更新：`SetCoreValues` 与四类导入 ✅

| 入口 | 来源 |
|---|---|
| `SetCoreValues` | 调用方直接给出一组目标与值 |
| `ImportCoreValuesFromJson` / `ImportCoreValuesFromCsv` / `ImportCoreValuesFromDataTable` | 每条一属性：记录标识 + 属性 Tag + core 值；同一记录是一组 |
| `ImportCoreValuesFromCurveTable` | 行名即属性 Tag，一张表是一组；求值输入由调用方明确给出 |

- 采用 TCS 约定格式，宿主不需要为这四类来源重写读取器；不支持任意宿主布局映射，不自动绑定等级成长。成长流程显式调用这些入口。
- 只更新明确列出的目标，未列出的保持不变；不隐式建立属性。
- **合法性**：目标已建立；目标是 `Core` 型（列出 `Resource` 型目标即整组拒绝，core 导入不能当作设置存量的入口）；值有限；同一记录内同一属性不重复（值相同也不行；不同记录出现同一属性正常）。任一不满足 → 整组拒绝，无部分写入、无副作用、无通知。
- **整组原子，合法即接纳**：通过合法性校验的一组写入整体生效。若新状态令派生、边界或约束维护失败，本次写入不回滚，相关属性按 §6.1 的失败状态表现，可用性变化另行通知。
- Disabled 属性可写 `CoreValue`，写入不启用它；唤醒时使用新值。

### 4.3 动态贡献：`ApplyAttrMods` / `RemoveAttrMods` / `UpdateAttrMods` ✅

三个入口都以撤销锚点定位，不为单条贡献建句柄。

**`ApplyAttrMods`**：以一个撤销锚点施加一组贡献。

- 任一请求不合法（目标未建立、目标不接受贡献、潜在依赖成环等）→ 整组拒绝，无部分修改、无通知。
- 已有属性的合法贡献，即使施加后当前值求不出也照常接纳；接纳成功与当前值可用是两回事。
- Disabled 目标可接纳合法新贡献，不因此启用；唤醒时使用仍未撤销的贡献。

**`RemoveAttrMods`**：撤销该锚点下的全部贡献。锚点未命中（已撤销、已被级联清理或从未施加）时无操作，返回未命中，不报错、不发通知。Disabled 属性上的贡献照常可撤销。

**`UpdateAttrMods`**：对该锚点的整组做原子替换，只允许同形替换。

- 新旧两组按组内序号一一对应，目标和运算带不变，只换数值或计算描述；保留施加身份和全部 `OrderSeq`。
- 形状不符、新描述引入非法依赖、锚点未命中 → 失败，旧组不变；未命中不隐式变成一次新施加。
- 要改变形态，先撤销，再用新锚点施加。
- 按替换后的整组结果维护派生、边界和通知，不产生组内中间态。例：基础最大值 700 + 旧贡献 300 = 1000，当前 800；替换为新的 300 后当前仍为 800。若先撤后加，会被截到 700 且不返还。
- 新组合法即接纳，下游失败不回滚（同 §4.2）。

**锚点范围**：一个撤销锚点只属于一个目标实体。批量清理由宿主传入一组锚点逐个撤销；整组原子性只在单实体内成立，不提供跨实体事务。

定义内派生贡献不在这三个入口的操作范围内。

### 4.4 三种变更对照 ✅

core 100 + Add 20 = 120。`SetCoreValues` 把 core 改为 105 后当前值 125；随后撤销 Add 20，当前值 105。

## 5. 生命周期 ✅

### 5.1 首次建立：`AddAttributes` ✅

- 显式成组建立，按完整候选状态校验；任一非法 → 整组拒绝，无部分新属性。同组内的无环依赖与声明顺序无关。
- 对已启用的同 Tag 重复建立失败：不重置、不更新、不做引用计数。组内重复同样拒绝。
- 初始当前值和必要约束全部可用，整组才建立成功。失败时没有新属性、没有本次持久副作用、不发通知；不回滚此前独立完成的其他状态变更。
- **`Core` 型初值**：`CoreValue` 取 Def 配置的 core 初值。
- **`Resource` 型首次满值**：存在有效上界时取上界；没有有效上界时取 max(0, 有效下界)，未声明下界时下界为 0，显式无下界时按 0 计。例：护盾类资源默认下界 0、无上界，首次值为 0。初值不由宿主显式传入；关卡特殊规则在建立之后执行。
- 建立成功发一次可用性通知（不可读 → 可读），不发数值通知。

### 5.2 停用：`DisableAttributes` ✅

- 实体存活期间属性不直接移除，只标记 Disabled。
- 停用会破坏某个启用属性的必需依赖时拒绝，状态不变；检查按完整潜在计算与维护关系进行，不因本次分支未读取而放行。不自动级联停用；须先停用依赖者，再停用被依赖者。
- Disabled 属性：普通当前读失败（不返回 0 或旧值）；保留 `CoreValue`、`Amount` 与全部未撤销贡献；资源扣补失败；可写 `CoreValue`；可接纳合法新贡献；贡献可正常撤销；边界变化不维护 `Amount`。
- 停用成功发可用性通知（可读 → 不可读）。

### 5.3 唤醒 ✅

- 对 Disabled 的同 Tag 调用 `AddAttributes` 即唤醒原运行态，不重新初始化。core 已成长到 120 不回到配置的 100；`Amount` 不重新补满，600 唤醒时有效上界为 500 则维护为 500。
- 求值与必要约束维护成功后唤醒才生效。失败时继续 Disabled，不留本次的 core、存量或贡献副作用，不发通知；不撤销此前独立完成的操作。
- 不复活停用期间已撤销的贡献，也不要求仍有效的来源重新施加；不自动唤醒未列出的依赖。
- 同一组可以混合首次建立与唤醒，按整体候选状态校验，一起生效；任一失败，本次新建、唤醒和存量都不留副作用。
- 唤醒成功发可用性通知。

### 5.4 实体销毁 ✅

属性随实体清除（[战斗实体](../02-核心基线/战斗实体.md) §2.2 级联清理）。这不是属性的可用性跃迁，不发任何通知，以免在级联清理中重入。订阅者依据实体层或宿主信号配对注销。

## 6. 求值与依赖 ✅

### 6.1 当前值读取 ✅

- 运行时计算动词统一用 `Evaluate`，与 `EvaluateAggregatedValue` / `EvaluateAggregatedDetail` 一致：每次真算、只返回值、不写入、可能失败，所以不用 `Get`。
- 必需读取失败即本次明确失败，不隐式用 0 或历史值。外层需要回退时自行组织。
- 所有已配置的计算描述（定义内派生与动态贡献）都成功，当前值才可用。被 `OverrideFinal` 遮住的计算失败，属性仍不可用；覆盖不能遮蔽失败，潜在依赖也不因覆盖而消失。
- 失败不回退到旧的成功缓存。内部可以保留旧缓存，但不能当作成功的当前值交付。
- 修改完成后，普通读取即反映该修改及其派生影响，调用者无需额外刷新。
- 属性不可读的情形：Disabled；必需边界不可读；有效区间为空；计算失败（含越声明读取）；结果非有限。
- 失败的错误表示与诊断细节：⚠️ AR5。

### 6.2 依赖 ✅

- 依赖只来自 Def 和贡献中的计算描述与边界引用，自动导出，不手填依赖清单。
- 计算关系与约束维护关系合并后，绑定后的潜在依赖 MUST 无环，包括本次不执行的读取。新建或变更引入环即拒绝；不采用执行到环才报错的规则，不迭代求解，不规定存图算法。
- 编辑器先验证可分析的部分；运行期读取超出声明集合时本次失败并诊断，不靠实际执行补全依赖。
- 自动随动限同实体。值描述可以跨实体按次读取，不能由此推出跨实体持续维护。

### 6.3 与 Parameter 的接合 ✅（结果持有 ⚠️）

属性读取能力由本次调用提供（§0.1）。消费者可选择实时求值，或在指定时点求值并保留结果。指定时点的结果由谁持有，属于 Parameter 的暂停项（交接文档 §5.2），不在本域裁定。

### 6.4 计算描述的类型 ⚠️

计算描述的表达式类型、是否与 Parameter 共用：⚠️ AR3。

## 7. 通知 ✅

### 7.1 两类通知 ✅

| 类别 | 何时发 |
|---|---|
| 可用性通知 | 已建立属性在可读与不可读之间跃迁。原因无关：首次建立、故障、恢复、Disabled、成功唤醒都用同一种信号 |
| 数值通知 | 属性变化前后都可读，且当前值实际改变 |

- 只发当前值的实际变化。输入变了而当前值不变时不发，例如 `OverrideFinal` 200 生效时 core 从 100 改为 105。
- 判等为精确数值相等，无容差，正负零相等。需要过滤微小变化的消费者自行处理。
- 可用性变化不当作「变为 0」，也不等消费者下次读取才发现。
- 同一轮里同一属性最多出现在一类通知中：数值通知要求前后都可读，可用性通知要求有一侧不可读。

### 7.2 载荷 ✅

| 类型 | 字段 |
|---|---|
| `FTcsAttributeAvailabilityChangedPayload` | `Entity`、`AttributeTag`、`bAvailable` |
| `FTcsEntityAttributesValueChangedPayload` | `Entity`、`Changes` |
| `FTcsAttributeValueChange` | `AttributeTag`、`OldValue`、`NewValue` |

载荷记录历史变化，不冻结当前状态，不表达受伤、治疗等业务因果；回调中再读可能看到更后的状态。两类事件的频道 Tag：⚠️ AR4。

### 7.3 时机与顺序 ✅

- 本次关联维护全部完成后才通知。回调读到的是更新后的当前值或明确失败，看不到维护到一半的状态。
- 普通独立修改在返回前送达通知。多项 core 导入按整组通知，不逐项提前。不延到帧末。
- 可用性通知逐属性立即分发，不合并。
- 数值通知按通知轮发出：每轮每个实体一个数值事件，包含本轮全部变化属性，按属性 GameplayTag 全名稳定排序（不本地化，不按依赖拓扑或注册顺序）。顺序在进入该轮前确定，回调重入不重排当前轮。
- 同一轮内先发逐属性的可用性通知，再发实体数值事件。
- 跨实体的通知顺序：⚠️ AR6。

### 7.4 重入 ✅

- 回调可以同步发起新的修改。重入修改立即生效，其通知延到当前通知轮结束后发送，仍在最外层修改调用返回前全部送完。因此重入调用自己返回时，它引起的通知可能尚未送达。
- 依赖无环不保证业务回调链终止。无限连锁的责任归宿主；实现可以在开发构建中诊断嵌套深度，但这不属于契约，也不改变操作成败。

### 7.5 订阅 ✅

| 入口 | 目标 |
|---|---|
| `SubscribeAttributeAvailability(Entity, AttributeTag)` | 单个属性的可用性 |
| `SubscribeAttributesValueChanged(Entity)` | 该实体的数值事件；需要筛选属性时读载荷的 `Changes` |

- 实体 MUST 存活，否则订阅失败。可用性订阅不要求属性已建立：未建立、Disabled、已建立的属性都可以订阅。
- 实体注销后不再派发。
- 订阅者配对注销，未命中时无操作（[事件总线](../02-核心基线/事件总线.md) §1.1.4、§1.1.9）。
- Tag 写错的订阅永远收不到派发，由编辑器校验发现。

### 7.6 不发通知的情况 ✅

- 非法请求被整组拒绝；首次建立失败；唤醒失败。
- 当前值未实际改变。
- 跨越不可用区间的数值变化：120 → 不可用 → 150，恢复时只发可用性恢复，不补发 120 → 150。
- `RemoveAttrMods` 锚点未命中。
- 实体销毁。

## 8. Def 与校验 ✅

### 8.1 `UTcsAttributeDef` ✅

| 内容 | 说明 |
|---|---|
| 属性 GameplayTag | 身份（§1.1） |
| 存储形态 `ETcsAttributeStorage` | 必填，`Core` / `Resource`（§1.2） |
| core 初值 | 仅 `Core` 型（§5.1） |
| `DerivedAttrMods` | 定义内派生贡献（§2.2） |
| `LowerBound` / `UpperBound` | 可选，种类 `ETcsAttributeBoundKind`（§3.1） |

没有正式命名的字段，其拼写不影响契约（⚠️ AR5）。运行中替换定义：⚠️ AR7。

### 8.2 `UTcsAttrModDef` ✅

一个目标 Tag、一个运算带、一个数值或计算描述（§2.3）。`Priority` 的可见性与同源多条 Override 的 Def 校验遵循[数值聚合器](../02-核心基线/数值聚合器.md) §5.2、§6。

### 8.3 编辑器校验 ✅

- 由专门的 EditorSubsystem 通过 `IAssetRegistry` 取得 **TCS 的所有 Def** 集中校验，不限于属性 Def。
- 每个 Def 通过自己的 `IsDataValid` 做自身校验。
- 计算描述是依赖来源，编辑期校验与运行时守卫兼有，不是二选一。
- 编辑器只能发现可分析的问题，不保证动态贡献组合、上下文绑定与运行时数值永远不会导致空区间、失败或成环；运行时规则不能因此删除。
- 子系统名称、发现范围细则、调用时机、诊断载荷与算法：⚠️ AR2。
