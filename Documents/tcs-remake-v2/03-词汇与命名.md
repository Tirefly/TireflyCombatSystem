# 词汇与命名

> **定位**：跨全族的**词汇纪律**与**命名规约**。与 [01-定位与判据](01-定位与判据.md) 同级——那份管「怎么写文档」，本文件管「怎么给东西取名」。
> **为什么单列一册**：这些规约不属于任何一个域——`Instance` 裸词禁令对 Attribute / Skill / State / Action 同等有效，`Def` 后缀横跨五个域的资产类。塞进任一域文档，其余域就看不到。

**审核状态图例**：✅ 已裁决并批准 ｜ ⚠️ 未定 ｜ ❓ 待调研

---

## 1. `Instance` MUST NOT 作裸词 ✅

> **`Instance` MUST NOT 作裸词出现；书写时 MUST 带种类前缀**（`BuffInstance` / `SkillInstance` / `ChainInstance`）。
> 核心基线那一层讲的是**通用池机制**，英文简称统一写作 `RuntimeInstance`，不叫裸词「Instance」。

**理由**：`ChainInstance` / `BuffInstance` 在机制上是同一种东西——**都是 `TTcsInstancePool` 里的池元素本体**（池存 `TArray<TInstance>` 本体、不存句柄，见 [运行时实例](02-核心基线/运行时实例.md) §1.2.1）。带种类前缀不是引入新概念，而是把「它们共用同一套池机制」说清楚而不混淆。

**真正要防的不是「两个 Instance」，是「裸词 Instance」**：

| 说法 | 判定 |
|---|---|
| `BuffInstance` / `SkillInstance` / `ChainInstance` | ✅ 带前缀，分得清 |
| 裸说「Instance」指代核心基线那一层 | ❌ MUST NOT |

### 1.1 连带：成员名同样适用

子系统里持有池的成员 MUST NOT 叫 `InstancePool`——那会与通用模板 `TTcsInstancePool` 撞名。必须带种类前缀，如 `ChainInstancePool`。

## 2. 定义资产一律 `Def` 后缀 ✅

| 资产类 | 写法 |
|---|---|
| 状态定义（基类） | `UTcsStateDef` |
| 技能定义 | `UTcsSkillDef` |
| Buff 定义 | `UTcsBuffDef` |
| 链定义 | `UTcsActionChainDef` |
| 触发条件定义 | `UTcsActionTriggerDef` |
| 属性定义 / 属性修正器定义 | `UTcsAttributeDef` / `UTcsAttrModDef` |

**判据**：`Def` 已经是基类与多数派的写法；`DefAsset` 既与基类 `UTcsStateDef` 不一致，也不表达任何额外含义（`Def` 本身就是资产）⇒ **MUST NOT 用 `DefAsset` 后缀**。

> **非资产的结构体与资产类只差 `U` / `F` 前缀不算撞名**：`FTcsActionTriggerDef`（结构体）与 `UTcsActionTriggerDef`（资产）并存是 UE 常规。

---

## 3. 域名词：`Action` ✅

**判据**：`Action` 覆盖这个域装的东西——**被触发、按步骤执行、产生后果**。`Effect` 只覆盖「后果」那一段，把「触发」与「步骤」排除在外；且它与「表现效果」同音，讨论中会不断被误读为 VFX。域名词要能一句话说清「这里装什么」，`Action` 能，`Effect` 不能。

| 名 | 说明 |
|---|---|
| `UTcsActionSubsystem` | 世界子系统 |
| `FTcsActionChain` | 链本体 |
| `UTcsActionChainDef` | 链定义资产 |
| `FTcsActionStep` | 步骤基类 |
| `FTcsActionStepExecutorRegistry` | 步骤执行器注册表 |
| `FTcsActionStepExecutorRegistrar` | 静态自注册器 |
| `FTcsActionContext` | 步骤间传递的上下文（非反射） |
| `FTcsActionTriggerDef` | 触发条件定义（结构体） |
| `UTcsActionTriggerDef` | 触发条件定义（资产，见 §2） |
| `FTcsActionTriggerInstance` | 触发条件实例 |
| `FTcsActionTriggerHandle` | 触发条件句柄 |
| `UTcsActionStepExecutor` | `UObject` 步骤执行器插槽 |

**为什么步骤执行器是 `UObject` 插槽而不是纯 `USTRUCT`**：宿主必须能**定义新种类的步骤并携带自己的状态**。若步骤全是 `USTRUCT`、注册表键是 `UScriptStruct*`，蓝图与反射脚本造不出新种类——它们只能「借壳」已有步骤再按参数分发；宿主自写带状态的复杂逻辑也无处安放（蓝图不能定义新类型，自定义状态只能住 `UCLASS` 的变量里）。

---

## 4. 状态名词：`Instance`，不用 `Run` ✅

| 名 | 说明 |
|---|---|
| `FTcsChainInstance` | 链本体 |
| `FTcsChainInstanceHandle` | 链句柄 |
| `FTcsChainInstanceTag` | 链标签 |
| `ChainInstancePool` | 子系统持有的链池成员 |

**判据**：池元素本体统一叫 `Instance`（§1），与通用模板 `TTcsInstancePool` 同系；`Run` 同时是动词与名词，在「运行一次」与「运行态本体」之间反复歧义。

---

## 5. 波及面 ✅

V2 从零编写，名字起手就是最终名 ⇒ **不存在改名任务**：没有待改的代码标识符，没有待改的 `.uasset` 资产。

唯一需要留意的是**示例里的领域符号**：[00-跨基线时序](02-核心基线/00-跨基线时序.md) 用到若干领域符号，其字段、时刻与语义由对应领域裁，本文件不保证；其中的**函数名**在对应领域开文档时定稿，在那之前它们是占位符号，不构成契约。
