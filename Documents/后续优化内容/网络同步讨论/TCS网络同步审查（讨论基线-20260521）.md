# TCS 网络同步审查（讨论基线）

> 自 2026-05-25 起，本文档已从原“网络同步与性能优化审查”系列提纯并改名；已实现的本地性能 / 流程优化内容已抽离归档至 [归档：TCS 既有优化落地记录（2026-05-25）](<./_archive/TCS既有优化落地记录（2026-05-25）.md>)。本文只保留后续 `TCS` 网络同步讨论基线。

## 1. 文档目的

本文档用于整理当前 `TireflyCombatSystem` 插件中，与以下主题直接相关的代码事实、风险判断和讨论入口：

1. 哪些当前设计可能影响网络同步正确性。
2. 哪些当前运行时结构不适合作为未来直接同步边界。
3. 哪些本地 Tick / 生命周期路径后续必须收敛到服务器权威推进。
4. 后续网络同步实现还需要确认哪些预测、配对与客户端重建边界。

本文档不是最终实施方案，也不是 OpenSpec proposal。
本文档的用途是先建立一份可讨论、可质疑、可逐项确认的网络同步技术基线，后续再根据确认结果拆成具体实现方案。

关于预测分层、`Predictable / AuthorityOnly` 契约、`AttributeModifierDef` 白名单和回滚链等更细的讨论，现以 [TCS网络同步审查（扩展：GAS预测边界与TCS预测分层-20260522）](<./TCS网络同步审查（扩展：GAS预测边界与TCS预测分层-20260522）.md>) 为最新讨论基线；本文只同步回写那些已经影响总体判断、待确认决策和讨论顺序的结论。

另外，历史上已经完成实现的本地性能与流程优化内容，现已统一移入 [归档：TCS 既有优化落地记录（2026-05-25）](<./_archive/TCS既有优化落地记录（2026-05-25）.md>)，不再继续留在本文中跟踪落地状态。

## 2. 当前结论摘要

基于当前源码和后续讨论收敛结果，先给出四个初步判断：

1. `TCS` 当前实现层面仍更接近“尚未完成联机化落地的本地权威运行时框架”，但联机讨论方向已经从开放问题收敛为：`服务器权威真值 + 客户端窄预测 + 分支清理 / 权威重建`。
2. 当前运行时容器和工作结构并不适合直接作为未来同步边界；更合理的方向仍然是“服务器运行时结构 + 客户端消费的权威快照 / 紧凑结果”。
3. 本地时间戳参与排序、本地 Tick 推进 `StateTree / Buff` 生命周期、以及本地工作集容器与权威结果耦合过深，仍然是当前最值得优先澄清的联机分叉风险。
4. 预测扩展层面当前真正还需要继续细化的，是 `Predictable / AuthorityOnly` 契约、`Apply-P / Apply-S / Apply-R` 边界、`AttributeModifierDef` 局部预测白名单，以及 `State / Buff / Attribute / Skill` 的最小快照粒度与客户端重建边界。

## 2.1 当前文档会频繁出现的 `Apply` 三段缩略语

为了避免后文先使用缩略语、后解释缩略语，这里先把 `Apply-P / Apply-S / Apply-R` 的意义前置说明。

需要先明确：

1. 这三个名字描述的是**同一次 `StateInstance Apply` 在网络预测模型中的语义三段**。
2. 它们不是在要求当前代码里必须已经拆成三个独立函数。
3. 后文如果再次使用这三个缩略语，默认都按这里的含义理解；更细的展开说明见后文 `D1.1`。

### Apply-P

`Apply-P` = `Predictive Apply`

它指的是：

客户端为了先给本地玩家即时反馈，而先进入的一段预测性 `Apply` 前奏逻辑。

当前基线下，它主要承载：

1. 预测分支启动。
2. 允许先执行的 `Predictable Task`。
3. 本地临时激活标记。
4. 本地 `Montage`、镜头、音效、UI、目标预览等前奏或表现逻辑。
5. 非常有限的自体局部预测。

### Apply-S

`Apply-S` = `Server Apply`

它指的是：

服务器对同一条语义请求执行权威 `Apply`，并产出最终真值结果的主段。

当前基线下，它主要承载：

1. 最终 `State` / 槽位激活结果。
2. 最终 `Buff` 生命周期与堆叠真值。
3. 最终 `Attribute` 真值写入与复杂计算链。
4. 冷却、移除、跨目标效果、强控制、强免疫等服务器战斗责任结果。

### Apply-R

`Apply-R` = `Reconcile Apply`

它指的是：

服务器结果返回后，本地对预测分支与权威结果做确认、回滚、修正与重建的收敛段。

当前基线下，它主要承载：

1. 预测成功后的配对与确认。
2. 预测失败后的 `RequestRemoval`、退出清理与分支丢弃。
3. 局部预测和服务器结果不一致时的清理与重建。

## 3. 当前代码事实

### 3.1 网络同步相关事实

1. 当前插件源码中，没有形成完整的 `Replication / RepNotify / RPC` 主链。
2. `State`、`Buff`、`Attribute` 的核心入口目前仍然是本地直接调用的运行时函数，而不是显式区分 `Authority` 和 `Remote` 的网络入口。
3. `FTcsSourceHandle` 已实现 `NetSerialize`，说明来源句柄已为网络传输做过准备，但这不等于 `State / Buff / Attribute` 已有完整同步方案。
4. `State` 和 `Attribute Modifier` 的部分排序/合并决策依赖本地时间戳，而不是依赖服务器统一序号或统一网络时钟。
5. `StateTree`、`Buff Period`、`State 生命周期` 当前都基于本地 Tick 推进。

### 3.2 运行时容器相关事实

1. `UTcsStateComponent` 内部核心容器包括：
   - `FTcsStateInstanceIndex StateInstanceIndex`
   - `FTcsStateTreeTickScheduler StateTreeTickScheduler`
   - `TMap<FGameplayTag, FTcsStateSlot> RuntimeStateSlots`
2. `UTcsAttributeComponent` 内部核心容器包括：
   - `TMap<FName, FTcsAttributeInstance> Attributes`
   - `TArray<FTcsAttributeModifierInstance> AttributeModifiers`
   - `TMap<int32, TArray<int32>> SourceHandleIdToModifierInstIds`
   - `TMap<int32, int32> ModifierInstIdToIndex`
3. 这些运行时结构非常适合本地查找、排序和增删改，但并不适合直接按当前形态做网络复制。

### 3.3 Tick 与调度相关事实

1. `UTcsStateComponent::TickStateTrees()` 会逐帧调度运行中的 `StateTree` 实例。
2. `UTcsBuffComponent::TickBuffLifecycles()` 会逐帧推进有限时长 Buff 的剩余时间。
3. `FTcsSTTask_BuffPeriodDriver::Tick()` 会在 Buff 实例树里逐帧累计时间，并按周期发出 `Event.Buff.PeriodTick`。
4. `UTcsSkillComponent` 当前虽然开启了 Tick，但目前逻辑非常轻，仅保留了 `0.1s` 间隔的空框架。
5. `FTcsSTEvaluator_SlotDebug::Tick()` 会定期生成调试字符串快照，这是开发期成本，不是业务语义成本。

## 4. 网络同步风险清单

## 4.1 未建立明确的联机权威边界

### 当前代码事实

1. `State` 的应用入口仍然是 `UTcsStateComponent::TryApplyState()`。
2. `Buff` 的应用入口仍然是 `UTcsBuffComponent::ApplyBuff()`，其内部继续转向 `StateComponent->TryApplyState()`。
3. `Attribute` 的增删改和 Modifier 应用也都是本地组件方法直接执行。

### 风险判断

如果未来客户端既直接运行这些入口，又没有明确拆出“预测分支 / 服务器权威真值 / 权威回灌重建”的边界，那么：

1. 预测路径和真值路径会混在一起，本地状态先分叉后难以稳定收敛。
2. 同一效果在服务端和客户端的排序、合并、时序结果可能不同。
3. 后续每个模块都会被迫补大量“同步补丁”，而不是从一开始就站在统一的服务器真值 + 窄预测模型上。

### 当前建议（已讨论确认）

下面这组内容虽然仍保留在“当前建议”栏下，但它们已经不是未定方向，而是已讨论确认的当前基线：

这条问题本身已经不应再继续停留在“要不要服务器权威”这种总问上。

当前更合适的基线是：

`服务器权威真值 + 客户端窄预测 + 分支清理 / 权威重建`

后续真正需要继续细化的是：

1. `StateInstance Apply` 的 `Apply-P / Apply-S / Apply-R` 边界。
2. `Predictable / AuthorityOnly` Task 的执行与退出清理契约。
3. 哪些路径只能服务器推进，哪些路径只允许客户端做局部预测或纯表现先行。

## 4.2 本地时间戳参与排序和合并

### 当前代码事实

1. `UTcsStateComponent::CreateStateInstance()` 会给 `StateInstance` 写入 `ApplyTimestamp`。
2. `UTcsAttributeComponent::ApplyModifier()` 和 `HandleModifierUpdated()` 会写入 `ApplyTimestamp / UpdateTimestamp`。
3. `State` 的同优先级策略 `UseNewest / UseOldest` 会依赖 `ApplyTimestamp`。
4. `BuffMerger_UseNewest / UseOldest / StackByInstigator` 会依赖 `ApplyTimestamp`。
5. `Attribute Modifier Merger_UseNewest / UseOldest` 会依赖 `ApplyTimestamp / UpdateTimestamp`。

### 风险判断

这些时间戳当前是本地 `UTC ticks`，在单机环境中合理，但在联机环境中会带来两个问题：

1. 服务端和客户端即使收到“逻辑上相同”的事件，时间戳也不会完全一致。
2. 同步重放时，合并结果和排序结果可能因为时间戳不同而发生分叉。

### 当前建议（已讨论确认）

下面这组内容已经属于当前讨论确认的基线：

1. 这些时间戳在后续进入网络同步实现时，应归入服务器权威配置与验证体系。
2. 本地客户端可以保留自己的时间戳或本地时序信息，用于预测分支、本地显示或调试，但它们不应作为权威验证依据。
3. 如果后续这些时间戳仍要继续参与排序或合并决策，更稳妥的方向仍然是改成“服务器分配的单调序号”或同等级别的服务器权威排序键。
4. 也就是说，后续应显式拆开“本地时间信息”和“服务器权威排序依据”，不要再让客户端本地时间戳承担权威验证责任。

## 4.3 本地 Tick 推进状态树与 Buff 周期

### 当前代码事实

1. `StateTree` 实例 Tick 由 `UTcsStateComponent::TickStateTrees()` 在组件侧统一推进。
2. `Buff` 周期事件由 `FTcsSTTask_BuffPeriodDriver::Tick()` 在实例树内按 `ElapsedTime` 发射。
3. `UTcsBuffComponent::TickBuffLifecycles()` 会直接扣减 `RemainingDuration`。

### 风险判断

只要客户端也把这些逻辑当成真值持续推进，而不是仅在受控预测分支内处理局部前奏或表现，就可能出现：

1. 时长不同步。
2. 周期事件触发帧不同步。
3. 生命周期结束帧不同步。

### 当前建议（已讨论确认）

下面这组内容已经属于当前讨论确认的基线：

1. `UTcsStateComponent::TickStateTrees()` 当前虽然是本地运行时 Tick 入口，但后续联机语义里，它所驱动的状态槽更新与状态真值收敛，应以服务器权威结果为准。
2. 本地客户端可以对 `StateTree` 做受限制的预测执行，但这种执行只能属于受控预测分支，最终仍受服务器裁决与修正。
3. `UTcsBuffComponent::TickBuffLifecycles()`、`FTcsSTTask_BuffPeriodDriver::Tick()` 这类 `Buff` 生命周期、周期推进与到期判定路径，当前应整体视为不可预测内容，统一由服务器权威执行和判定。
4. 也就是说，`State` 的本地预测 Tick 未来最多只应承担有限前奏或局部预测责任，而 `Buff` Tick 主链当前不应进入客户端真值预测范围。
5. 最终结果仍需要通过紧凑快照或服务器权威 `Apply` 结果回灌客户端。

## 4.4 当前运行时结构不适合直接复制

### 当前代码事实

1. `RuntimeStateSlots` 是 `TMap<FGameplayTag, FTcsStateSlot>`，槽位内还保存状态实例数组和运行时 Gate 状态。
2. `StateInstanceIndex`、`StateTreeTickScheduler`、`ModifierInstIdToIndex`、`SourceHandleIdToModifierInstIds` 都是为了本地高效访问而设计的辅助结构。
3. 这些容器的维护逻辑依赖大量本地对象指针、索引和运行时调度状态。

### 风险判断

如果未来试图“直接复制整个运行时容器”，大概率会遇到：

1. 复制数据量大。
2. 脏数据判断复杂。
3. 本地辅助索引与网络同步数据耦合过深。
4. 后续维护成本高于收益。

这里还必须补一条引擎层前提：按 UE 5.7 当前 `UPROPERTY` 复制链路，replicated `map / set` 本身并不是可直接落地的通用方案。引擎源码里的 `UHT` 对 replicated map / set 会直接报 `Replicated maps are not supported.`、`Replicated sets are not supported.`；属性复制路径里也有 `Replicated TMaps are not supported.`、`Replicated TSets are not supported.` 的明确错误日志。

所以，这一节的问题不能再被表述成“只是我们主观上不喜欢复制 `TMap / TSet`”。更准确的说法是：一方面，当前这些容器本来就混有大量本地工作结构；另一方面，UE 当前复制链路也不支持把它们直接当普通 `Replicated` 变量落地。真正需要讨论的，是当某些必须同步的权威语义当前寄存在这些容器里时，后续应如何只把那部分必要语义抽出来。

另外，这里还有一个很容易走偏的方向，也需要提前排除：

不要把“后续可能需要网络同步”直接理解成“当前所有带容器的运行时结构，都应该原地改造成自带序列化/反序列化函数的通用网络结构”。

原因是当前这些运行时结构里，混杂了几类本质不同的数据：

1. 真正有网络意义的权威状态。
2. 可以从主数据重建的本地索引或优化缓存。
3. 依赖本地对象指针、调度状态、运行时引用关系的工作集数据。

如果把这三类数据强行混在同一个“统一可序列化结构体”里，后续很容易把网络同步层和本地运行时实现细节绑死在一起。

### 当前建议

这一节当前仍应保留为预研判断，而不应误写成“已经决定后续一定怎么同步”。

也就是说：

1. 现阶段 `TCS` 还没有进入具体网络同步实现，这里先只记录“当前运行时结构直接复制风险较高”这一点。
2. 至于后续到底是走紧凑结果复制、半结构化快照，还是别的同步组织方式，应该等真正开始实现网络同步时再做正式设计决定。
3. 当前可以先保留一个倾向性判断：相比直接复制整个运行时内部结构，紧凑结果或紧凑快照更值得优先考虑，但这还不是本阶段的已确认实现结论。
4. 如果未来真的进入实现阶段，更合理的方向不是“给所有运行时容器本体加序列化”，而是：
   - 只为未来确实需要服务器同步的那部分语义，设计 `State / Buff / Attribute / Skill` 各自专门的**权威快照结构体**或显式同步字段。
   - 由这些快照结构体负责序列化与反序列化。
   - 运行时组件、实例和本地优化容器继续按运行时职责组织；必要时由快照导入、导出或重建它们。
5. 也就是说，后续如果要包装成结构体，优先应该包装的是“网络同步边界上的快照数据”，而不是“所有当前带容器的运行时工作结构”。
6. 基于当前讨论，为了避免后续性能优化阶段给未来联机埋坑，**现在有必要先确认哪些内容未来可能需要服务器同步给客户端**；但这个确认应按“语义边界”进行，而不是按“是不是 `TMap / TSet`”进行。
7. 仅仅因为某个数据当前放在 `TMap / TSet` 里，就提前把它整体改成结构体，并不能自动解决未来同步问题；反过来，因为 UE 当前复制链路不支持直接 replicated `TMap / TSet`，真正需要同步的也更应该被拆成最小语义字段，而不是把整个容器迁移成另一个“看起来可序列化”的大结构。
8. 因此，当前更合理的预研动作应该是先做一轮“未来权威快照候选数据”和“明确不应直接同步的本地容器”的分类，而不是立刻对所有相关容器做结构性改造。

### 4.4.1 现阶段值得先确认的“未来权威快照候选数据”

下面这些内容，当前更值得先在讨论层面确认“未来是否需要服务器同步给客户端”：

1. `Attribute`：`UTcsAttributeComponent::Attributes` 当前是最明显的候选来源；未来更值得进入权威快照的，通常是 `AttributeDefId / AttributeInstId / BaseValue / CurrentValue` 这类最终属性状态，而不是把整个运行时 `TMap` 原样当同步对象。当前实践方向已经可以进一步收紧为：服务器继续使用运行时 `TMap` 管理 Attribute 实例，客户端长期持有拍平后的属性快照数组；如果该快照集合长期存在并频繁变更，优先考虑 `FFastArraySerializer`。
2. `Attribute`：`FTcsAttributeModifierInstance` 当前不应作为客户端长期同步对象。对于伤害归因、击杀归因、结算显示这类需求，更合理的方向是基于 `SourceHandle` 设计独立事件结构或汇总结构，而不是直接复制 Modifier 容器或长期保留 Modifier 快照。
3. `State`：`UTcsStateComponent::RuntimeStateSlots` 当前是状态槽语义的集中承载点，但未来更值得同步的应是 `SlotTag / bIsGateOpen / 最终激活状态结果` 这类槽位最终语义，而不是把整个 `FTcsStateSlot` 运行时结构整体当作同步对象。
4. `State`：`UTcsStateInstance` 当前更像状态实例快照候选来源；其中更值得优先确认的字段包括 `StateDefId / StateInstanceId / SourceHandle / Stage / Level`，以及那些确实会影响客户端显示、预测或收敛的运行时参数映射，例如 `NumericParameters / BoolParameters / VectorParameters` 及其 Tag 版本。
5. `Buff`：`UTcsBuffInstance` 当前更像 Buff 快照候选来源；其中 `TotalDuration / RemainingDuration / Period / MaxStackCount / StackCount` 这类服务器裁决后的生命周期与叠层结果，明显比 `DurationTracker` 这类 Tick 工作结构更适合作为未来快照字段。
6. `Skill`：当前 `UTcsSkillComponent / UTcsSkillInstance` 还是轻量框架，暂时没有像 `State / Buff / Attribute` 那样明确的运行时容器负担；但如果后续联机化，技能激活状态、冷却真值和必要的 `SkillInstance` 可见状态，仍值得单独列为未来候选同步边界。

基于这轮代码检查，当前更明确的结论是：

1. 现在有必要先确认这些“未来权威快照候选字段”。
2. 但还没有必要因为它们当前落在 `TMap / TSet` 里，就立刻把现有运行时容器整体改造成结构体。
3. 更合理的后续落地方向，仍然是单独设计 `Attribute / State / Buff / Skill` 的快照项结构，而不是直接改写当前运行时工作结构。

### 4.4.2 当前更像本地缓存 / 索引 / 调度结构的对象

按当前代码事实，下面这类对象更像本地运行时工作结构，不应因为未来可能做联机，就先默认视为权威同步对象：

1. `SourceHandleIdToModifierInstIds`、`ModifierInstIdToIndex` 这类可从 `AttributeModifiers` 主数据重建的本地索引。
2. `StateInstanceIndex`、`StateTreeTickScheduler` 这类本地索引或调度结构。
3. `Mapping_StateSlotToStateTreeStateName`、`CachedActiveStateNames`、`PendingSlotActivationUpdates` 这类状态槽刷新辅助结构。
4. `FTcsStateSlot` 内部的 `BuffMergeGroups`、`DirtyBuffMergeStateDefIds`、`bBuffMergeRequiresFullRebuild` 这类 Buff merge 运行时缓存与脏标记。
5. `DurationTracker` 这类本地 Tick 跟踪结构。
6. `Owner / Instigator / 组件引用` 这类运行时对象引用、缓存句柄和工作集引用关系，也不应直接被当成未来权威快照字段本体。

这些对象后续当然可能需要为联机化做配套改造，但更合理的方向通常是：

1. 让它们继续作为本地运行时结构存在。
2. 由服务器权威快照驱动它们的导入、重建或刷新。
3. 而不是把它们直接当成网络传输边界本身。

## 6. 待确认决策清单

## D1. TCS 联机主模型的剩余细化点

当前不再把“是否采用服务器权威模型”当成开放式总问题。基于扩展文档，当前已收敛的方向是：

`服务器权威真值 + 客户端窄预测 + 分支清理 / 权威重建`

这里还需要把 `StateInstance Apply` 的三段语义再细化一下，避免后续讨论时把它误读成一句口号。

### D1.1 `Apply-P / Apply-S / Apply-R` 的当前含义

需要先明确：

1. 这里的 `Apply-P / Apply-S / Apply-R` 是**语义三段**，不是要求当前代码里必须已经拆成三个独立函数。
2. 这三段描述的是“同一次 `StateInstance Apply` 相关语义在网络预测模型里的职责分层”，不是说现有调用链已经天然长成这个结构。

#### Apply-P：预测性 Apply 与前奏段

这一段的核心意思是：

客户端为了先给本地玩家即时手感，可以先进入一次预测性的 `Apply`，并启动那部分被允许先跑的本地逻辑。

按当前讨论，`Apply-P` 更适合承载：

1. 创建预测分支记录。
2. 启动允许客户端先执行的 `Predictable Task`。
3. 写入短生命周期的本地临时标记，例如“施法中 / 预测中 / 激活中”。
4. 播放本地 `Montage`、镜头、音效、UI 提示、目标预览等前奏或表现逻辑。
5. 执行非常有限的自体局部预测，例如少量资源预估扣减。

而下面这些内容不应默认落在 `Apply-P`：

1. `Buff` 的周期、到期、移除。
2. 复杂 `Attribute` 真值链。
3. 对他体产生强战斗责任的真值效果。
4. 任何长期持续、难以整体回收的真值路径。

#### Apply-S：服务器权威 Apply 与主段

这一段的核心意思是：

服务器执行同一条语义请求，并负责产生最终有效的真值结果。

按当前讨论，`Apply-S` 更适合承载：

1. 最终决定 `State` / 槽位激活结果。
2. 最终注册 `Buff` 生命周期与堆叠真值。
3. 最终写入 `Attribute Modifier` 并推进复杂计算、合并、排序与约束传播。
4. 最终决定冷却、移除、跨目标影响、强控制、强免疫等战斗责任结果。
5. 决定哪些客户端预测内容被确认，哪些需要否决或修正。

#### Apply-R：修正段

这一段的核心意思是：

服务器结果回来后，本地需要把预测分支和权威结果收敛成一个最终一致状态。

按当前讨论，`Apply-R` 至少要覆盖三种情况：

1. **确认成功**：预测分支与服务器结果配对成功，预测结果升级为正式状态，或被服务器结果平滑接管。
2. **确认失败**：本地通过 `RequestRemoval` 终止预测分支，触发 `Predictable Task` 的退出清理，再丢弃该分支结果。
3. **确认部分分歧**：先清理本地预测结果，再用服务器快照或服务器权威 `Apply` 结果重建本地状态。

对当前基线而言，最重要的不是立即把这三段实现成代码结构，而是先把职责边界说清：

1. `Apply-P` 负责“允许先跑的本地前奏与窄预测”。
2. `Apply-S` 负责“服务器真值裁决”。
3. `Apply-R` 负责“预测分支与服务器结果的收敛”。

后续真正需要继续细化的是：

1. `StateInstance Apply` 的 `Apply-P / Apply-S / Apply-R` 边界如何落实到 `State / Buff / Skill` 路径。
2. `Predictable / AuthorityOnly` Task 的执行边界、退出回滚责任和最小校验/调试支撑如何定义。
3. `PredictionBranchId / PredictionTransactionId` 何时进入正式设计，以及它们为什么不作为当前阶段的阻塞项。

## D2. 联机同步粒度与客户端重建边界

需要确认：

1. 延续当前方向，是否继续优先同步紧凑结果，而不是运行时内部结构。

3. `State / Buff` 的紧凑实例快照最小需要包含哪些字段，以及它们如何与本地预测分支配对或重建。

3. 是否拆分“调试时间戳”和“业务排序键”。

## 7. 建议讨论顺序

如果要逐项讨论，我建议按下面顺序推进：

1. 先以扩展文档确定的 `服务器权威真值 + 客户端窄预测 + 分支清理 / 权威重建` 作为当前联机总方向。

4. 再确认联机同步粒度，以及 `State / Buff / Attribute` 的客户端重建边界。
5. 再讨论时间戳是否继续参与业务排序，以及是否改成服务器统一序号。
