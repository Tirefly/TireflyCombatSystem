# TCS 网络同步审查（扩展：GAS 预测边界与 TCS 预测分层）

> 自 2026-05-25 起，本文档已从原“网络同步与性能优化审查”系列提纯并改名；已实现的本地性能 / 流程优化内容已抽离归档至 [归档：TCS 既有优化落地记录（2026-05-25）](<./_archive/TCS既有优化落地记录（2026-05-25）.md>)。本文只保留后续 `TCS` 网络同步与本地预测边界讨论。

## 1. 文档定位

本文档是 [TCS网络同步审查（讨论基线-20260521）](<./TCS网络同步审查（讨论基线-20260521）.md>) 的扩展讨论文档。

本文档补充两类内容：

1. `GAS` 中“哪些内容可以预测、哪些内容不可以预测”的边界整理。
2. 把这条边界翻译到当前 `TCS` 架构上，形成一份可讨论的预测分层和白名单矩阵。

本文档不是最终实现方案，也不是最终 OpenSpec proposal。
本文档的作用仍然是建立讨论基线，帮助后续确认：

1. `TCS` 应该预测什么。
2. `TCS` 不应该预测什么。
3. `TCS` 的 `StateInstance Apply / StateTreeTask / Buff / Attribute` 应该如何分层。

## 2. 先给出一句总判断

基于 `GAS` 的成熟经验，当前更稳的方向不是“把整条技能语义、整条 StateTree 语义都做成可预测可回滚”，而是：

1. 服务器负责真实状态与真实结算。
2. 客户端只预测手感收益高、且容易修正的局部路径。
3. 回滚单位优先设计成“预测分支 / 预测事务”，而不是要求每个 `Task` 都提供通用逆操作。

对应到当前 `TCS`，我更倾向的方向仍然是：

`服务器权威真值 + 客户端窄预测 + 分支清理 / 权威重建`

而不是：

`整套 State / Buff / Attribute / Task 全量语义预测`

## 2.1 需要先锁定的当前架构硬约束

结合当前 `TCS` 现有框架，需要先把下面两条当作后续讨论的硬前提：

1. 一个技能的所有表现逻辑，只可能直接写在 `StateTreeTask` 中，或者不由 `StateTreeTask` 直接实现，但仍然由 `StateTreeTask` 调用。
2. 无论入口是 `Buff` 还是 `Skill`，只要要触发对应的 `StateTree` 执行，就必须先走一次 `StateInstanceApply` 流程。

这两条约束带来的直接结论是：

1. 后续讨论“客户端预测”时，不能再默认假设存在一条正式的“绕过 `StateTreeTask` 的技能表现主链”。
2. 后续讨论“客户端预测”时，也不能再默认假设存在一条正式的“绕过 `StateInstanceApply` 的技能启动主链”。
3. 真正需要讨论的不是“要不要经过 `Apply`”，而是“客户端是否也要执行一次预测性的 `Apply`，以及这次 `Apply` 启动后的 `StateTreeTask` 链里，哪些逻辑允许先跑，哪些逻辑必须留给服务器真值层”。

## 3. GAS 预测边界摘要

## 3.1 GAS 明确支持或默认支持预测的内容

结合 `GameplayPrediction.h` 的公开整理、Epic 官方文档和社区成熟实践，`GAS` 当前明确支持或默认支持预测的内容主要包括：

1. `GameplayAbility` 激活。
2. `Triggered Events`。
3. `GameplayEffect` 的施加，但主要限于 `Modifier` 路线。
4. `Attribute` 改值，但核心前提仍然是 `Modifier / MMC` 这一类声明式改值。
5. `GameplayTag` 的施加。
6. `GameplayCue` 事件。
7. `Montage` 播放。
8. 依赖 `CharacterMovement` / `RootMotionSource` 的移动路径。
9. 目标选择与 `TargetData` 生产。
10. `Cost` 的本地提交，只要当时仍处于有效预测窗口。

这里有一个很重要的限制：

`GAS` 支持的不是“任意用户逻辑都能预测”，而是“Ability 框架已经知道怎么配对、怎么跳过 redo、怎么在服务器回来后校正”的那部分逻辑。

## 3.2 GAS 明确不支持，或官方明显不建议依赖预测的内容

`GAS` 当前明确不支持，或者实践上明显不建议依赖预测的内容主要包括：

1. `GameplayEffect` 的移除。
2. `GameplayEffect` 的周期效果，也就是 `Periodic` 路径。
3. `GameplayEffectExecutionCalculation`，即 `ExecCalc`。
4. 真正意义上的冷却结束时刻。
5. 复杂伤害结算、暴击、吸血、死亡这类强语义结果。
6. 任意带真实玩法责任的 `Actor` 生成，例如真实 projectile 命中责任链。
7. 跨越长生命周期、跨多个 latent 回调、又没有新预测窗口的能力语义链。
8. 任意客户端自造的“服务器本来不会主动做”的预测行为。

其中最关键的三个限制是：

1. `ExecCalc` 不可预测。
2. `GE Removal` 不可预测。
3. `Periodic GE` 不可预测。

这三个限制几乎直接决定了：

1. `GAS` 不适合把持续效果完整地做成全量预测。
2. `GAS` 不适合把复杂伤害与死亡做成强预测。
3. `GAS` 的冷却只能做“局部表现预测”，不能做完全无误差的真值预测。

## 3.3 GAS 对冷却、伤害、周期效果的实际处理态度

从公开资料看，`GAS` 在下面几个点上是非常克制的：

### 冷却

1. 本地可以先出现“开始冷却”的 UI 反馈。
2. 但真实冷却是否结束，仍取决于服务器的 `Cooldown GE`。
3. 因为 `GE Removal` 不能预测，所以冷却结束天然不可靠。
4. `Fortnite` 对高频武器没有完全依赖通用 `Cooldown GE`，而是自己做额外 bookkeeping。

### 伤害

1. 理论上可以尝试预测。
2. 但成熟实践普遍偏向不预测，尤其不预测死亡。
3. 原因是误判时观感非常差，例如血量回弹、死亡回滚、ragdoll 复活。

### 周期效果

1. `Periodic GE` 不可预测。
2. 这意味着 `DOT / HOT / 周期回能 / 周期回蓝 / 周期触发` 等路径，本质都更适合放在服务器真值层。

## 4. GAS 为什么只预测这一小层

`GAS` 的预测设计，并不是能力不足，而是一种非常明确的取舍。

## 4.1 Epic 的方法论是“只预测你能承担后果的东西”

公开材料里，Epic 的核心态度可以压缩成一句话：

不是“预测一切”，而是“预测你能安全预测、而且值得预测的最小集合”。

也就是说：

1. 如果预测失败后，修正代价小、观感可接受，就可以考虑预测。
2. 如果预测失败后，修正代价大、观感很差、作弊面太宽，就不应该轻易预测。

## 4.2 GAS 的预测窗口是“原子窗口”，不是“整条长期语义链”

`GAS` 的 `PredictionKey` 和 `Scoped Prediction Window` 本质上都在表达同一件事：

1. 预测适用于一小段原子指令窗口。
2. 这个窗口外的 latent 回调，不会天然继续持有预测资格。
3. 如果要继续预测，必须显式创建新的预测窗口。

这说明 `GAS` 天然更适合：

1. 激活。
2. 确认。
3. 施加。
4. 局部表现反馈。

而不是适合：

1. 长时间运行的通用行为图。
2. 任意跨帧状态机。
3. 任意持续逻辑的自动回滚。

## 4.3 GAS 的“回滚”也不是任意用户逻辑级的通用回滚

从公开资料看，`GAS` 能处理的是：

1. 已知类型的 `GameplayEffect` 预测配对。
2. 已知类型的 `GameplayCue` 重做与跳过。
3. 服务器确认或否决后的框架级校正。

它并没有提供“任意 Ability 图、任意用户逻辑、任意自定义 Task 都自动可回滚”的通用机制。

这和当前我们讨论 `TCS` 时的核心判断是一致的：

不要默认把“用户写的所有 `StateTreeTask`”都视为天然可回滚对象。

## 5. GAS 对当前 TCS 的直接启示

## 5.1 不要把 `StateInstance Apply` 看成一个必须整体预测的黑盒

如果完全照 `GAS` 的思路理解，当前 `TCS` 更合理的做法不是：

“客户端把 `StateInstance Apply` 整套完整执行一遍，然后所有副作用都能回滚。”

更合理的理解应该是：

“如果客户端为了技能手感也要先出表现，那么它仍然需要进入一次预测性的 `StateInstanceApply -> StateTreeTask` 链，只是这条链里的内容不能被默认视为全部都可预测、全部都可回滚。”

也就是说，`Apply` 不是非黑即白，而应该拆层。

## 5.2 不要把 `Buff` 生命周期完整塞进预测层

结合 `GAS` 的边界，下面这些内容都不适合天然进入预测主链：

1. `Buff` 周期 Tick。
2. `Buff` 到期移除。
3. `Buff` 剩余时长作为真值状态。
4. 依赖堆叠、优先级、时间戳合并策略的 `Buff` 真值结果。

这意味着：

1. `Buff` 的“开始表现”可以预测。
2. `Buff` 的“真实生命周期”更适合服务器推进。

## 5.2.1 状态类 Buff 不能只按“是否加了一个状态”来判断能不能预测

这里需要把一类很容易误判的 Buff 单独拿出来：

`无敌 / 眩晕 / 沉默 / 定身 / 霸体 / 缴械 / 禁疗 / 禁用技能槽`

这类 Buff 虽然表面上常常只是“给目标加一个状态标记”，但网络语义上它们不是普通标签，而是强语义战斗状态。

原因是它们通常会直接改变：

1. 伤害是否成立。
2. 技能是否允许激活。
3. 输入是否允许继续生效。
4. 移动是否允许继续执行。
5. 行为树或状态树中的执行分支是否被打断、阻塞或豁免。

因此，这类 Buff 不能仅仅因为“实现形式上只是加状态”，就直接归入“适合预测”的范围。

## 5.2.2 状态类 Buff 的预测边界

结合 `GAS` 的边界和当前 `TCS` 的实现约束，这类状态型 Buff 更适合按下面方式理解：

1. 可以预测的，通常只是“开始表现”或“局部反馈”。
2. 不适合预测的，通常是“战斗真值”和“强控制结果”。

更具体一点：

### 自体状态

像“自己给自己加无敌、霸体、施法保护”这类状态，如果是本地玩家主动发起，客户端可以有限地预测它们的开始阶段。

但这里的“可以预测”，仍然只应该理解成：

1. 客户端可以先进入预测性的 `StateInstanceApply -> StateTreeTask` 链。
2. 可以先播放本地表现、UI、镜头、提示。
3. 如果需要，也可以先写入非常短暂的本地预测标记。

而下面这些仍应保留给服务端真值：

1. 伤害是否真的被豁免。
2. 霸体是否真的阻止了打断。
3. 状态何时真正结束。
4. 状态结束后引发的后续战斗语义。

### 对他体施加的控制或免疫状态

像“把别人打晕、沉默、定身、缴械、禁疗，或者给别人套无敌”这类状态，不建议做客户端真预测。

更准确地说：

1. 可以预测命中反馈、受击表现、图标提示、局部视觉反馈。
2. 不建议预测“目标真的已经进入眩晕/无敌/沉默真值状态”。

因为一旦预测失败，回滚代价非常高：

1. 目标明明还可以行动，却在本地先被锁住。
2. 目标明明没有无敌，却在本地先被判成免疫伤害。
3. 目标已经出现了受控表现，但服务端随后否决。

这种错误会直接伤害战斗正确性和观感稳定性。

## 5.2.3 当前更稳的默认结论

如果后续没有特化案例，我建议当前先把状态类 Buff 默认分成三类：

1. 纯表现状态：可预测。
2. 自体软状态：可有限预测，但仍要服务端验证。
3. 强权威硬状态：默认服务端权威。

在这个分类下：

1. `无敌` 默认按强权威硬状态处理。
2. `眩晕` 默认按强权威硬状态处理。
3. `沉默 / 定身 / 缴械 / 禁疗 / 禁用技能` 默认也都按强权威硬状态处理。

如果未来某个具体状态确实必须扩大预测面，也应该视为专项设计，而不是默认策略。

## 5.3 不要把 `Attribute` 真值计算链完整塞进预测层

结合当前 `TCS` 代码事实，`Attribute` 模块最复杂的部分不是“加一个数”，而是：

`Modifier -> Recalculate -> Clamp -> Constraint Propagation`

如果这一整条链都放进客户端预测，就会同时引入：

1. 计算热点。
2. 回滚热点。
3. 分叉热点。
4. UI 跳变热点。

所以更合理的方向是：

1. 允许客户端预测非常有限的、自身的、短窗口的、声明式属性变化。
2. 把复杂约束传播、跨属性收敛、最终真值维持在服务器侧。

## 5.3.1 对 Attribute 局部预测的建议：不要继续用“简单 / 短窗口”做口头判断

你前面提到的困难是对的：

`简单`
`短窗口`

这两个词在实现上都太主观，后续很容易越讨论越散。

我更建议把 `Attribute` 局部预测改成“显式白名单条件”，而不是抽象描述。当前更稳的筛选条件可以是：

1. **只允许自体属性**：只能预测本地玩家自己身上的属性，不预测他体属性真值。
2. **只允许激活窗口内变化**：只能发生在一次预测性 `Apply` 或其紧邻的确认窗口内，不允许进入长期持续更新。
3. **只允许单属性直接变化**：优先只允许单属性的直接加减，不允许依赖多属性联动得出最终结果。
4. **不能触发复杂约束传播**：只要会进入 `Constraint Propagation`、动态范围联动、跨属性收敛，就默认排除。
5. **不能依赖复杂排序与合并**：只要强依赖 Modifier 合并顺序、时间戳、Merger 策略，就默认排除。
6. **预测失败后只影响本地手感**：如果预测错了，只能带来 UI 或局部表现修正，不能改变他人的战斗真值。
7. **必须能被预测分支整体回收**：一旦服务器否决，能够通过分支销毁或快照覆盖直接收掉。

按这套条件看，当前最适合作为局部预测候选的，一般会是：

1. 自体资源消耗，例如蓝量、能量、体力的即时扣减。
2. 自体短时移动相关属性预估，例如冲刺前的速度预估、瞄准减速预估。

而下面这些我建议继续默认排除：

1. 会触发范围联动的属性。
2. 会改写其他属性上限/下限关系的属性。
3. 会进入复杂 Modifier 合并链的属性。
4. 会影响他体战斗结果的属性。

如果后续真要工程化，我建议当前第一落点优先放在 `AttributeModifierDef`，不要继续停留在口头约定；但这里也不要过早假设“永远只需要 Modifier 一层就够了”。更稳妥的收敛方式可以是：

1. 在 `AttributeModifierDef` 上显式标记“允许预测性本地应用”。
2. 只有带这个标记、且没有被上层规则否决的 Modifier，才允许进入预测白名单。
3. 如果后续发现某些 Attribute 本身具有强权威语义，再补 `AttributeDef` 级别的上层 veto / policy，而不是反过来让 Modifier 单方面决定一切。

## 5.4 高频射击、短 CD、连招窗口不要完全压在通用持续效果真值上

这是 `GAS` 给 `TCS` 非常重要的一条启示。

如果未来 `TCS` 既想支持：

1. `ARPG`
2. 射击
3. 格斗
4. 回合外实时连招

又想保留统一的 `State / Buff` 语义层，那么：

高频输入窗口、射速、极短 CD、连招衔接窗口

最好不要完全寄托在“通用 Buff 时长移除”或“通用 State Duration 结束”这类路径上，否则延迟公平性问题会非常明显。

不过结合你刚确认的设计边界，这里也要做一个收口：

1. 技能 `CD` 本身不归具体 `Buff / StateDuration` 管，而是归 `SkillInstance` 自己负责。
2. 连招窗口也不归 `Buff` 管，后续更适合作为独立机制，或者放进动作游戏扩展插件里做专项实现。

因此，对当前 `TCS` 来说，这里的真正重点已经不再是“要不要把技能 CD 和连招窗口继续塞回通用 Buff 语义”，而是：

高频技能链路里的 `StateTreeTask` 行为，后续是否需要批处理能力。

不过这里的“批处理”不能理解成把所有高频 Task 粗暴并帧或合并执行。更合理的方向应该是“高频同构语义的受控批处理”，例如：

1. 连续射击里的重复预备逻辑。
2. 高频命中预览或目标采样前的重复本地准备逻辑。
3. 高频纯表现派发。

如果现阶段只举一个更具体的优先分析例子，那么：

`Montage` 播放请求可以作为高频批处理分析的优先入口之一。

但这里必须把边界说清楚：

1. 这不等于“把 Montage 状态推进本身整体做成批处理”。
2. 也不等于“把 Section 切换、Notify 责任链、打断语义统一合并执行”。
3. 更合理的切入点是：先看高频场景下重复的本地播放请求派发、参数整理、纯表现广播，哪些可以受控合批。

而下面这些不应默认进入批处理：

1. 顺序敏感的 Task。
2. 直接改写服务器真值责任的 Task。
3. 强依赖随机结果或跨目标副作用的 Task。

## 6. TCS 预测分层建议

下面这套分层，不是最终代码结构，而是当前讨论阶段更适合的职责划分。

需要特别说明的是：

1. 这里的“分层”首先是语义分层，不等于调用栈可以天然拆开。
2. 对当前 `TCS` 而言，凡是属于 `Skill / Buff` 主链的正式表现逻辑，承载位置仍然只能是 `StateInstanceApply` 启动后的 `StateTreeTask` 或其调用逻辑。
3. 因此 `P0 / P1` 并不等于“在 `StateTreeTask` 外另起一条技能表现链”，而是指“进入预测分支后，哪些 `Task` 与副作用允许客户端先执行”。

## 6.1 P0：客户端即时反馈层

这一层的目标只有一个：

让玩家输入后立即得到反馈。

这一层适合放：

1. 输入接收。
2. 本地瞄准预览。
3. 本地范围预览。
4. `Montage`、镜头、音效、UI 提示。
5. 纯表现 `GameplayCue` 等价物。
6. 不承担真值责任的本地临时提示状态。

这一层的特点是：

1. 可以先执行。
2. 即使被打断，也不应该造成世界真值分叉。
3. 本质是“表现先行层”。

## 6.2 P1：受控语义预测层

这一层才是真正意义上的“窄预测层”。

它只适合放满足下面条件的逻辑：

1. 由本地玩家主动发起。
2. 服务器会执行同一条语义请求。
3. 只影响自身，或影响范围极小。
4. 不依赖 `Periodic`、移除、长期调度。
5. 不依赖复杂排序、复杂合并、复杂随机结果。
6. 预测失败时，可以通过整段分支清理来修正。

## 6.3 S0：服务器权威真值层

这一层负责：

1. 真实状态插入与真实移除。
2. 真实 `Buff` 生命周期。
3. 真实 `Attribute` 最终值。
4. 真实伤害、治疗、暴击、死亡。
5. 真实冷却结束。
6. 真实 projectile / summon / world actor 玩法责任。

这一层的原则是：

1. 允许慢一点。
2. 不允许错。
3. 不能把长期一致性交给客户端碰运气。

## 6.4 C0：客户端消费与显示层

这一层负责消费服务器的真值结果并做显示整理，例如：

1. 用服务器同步结果更新 UI。
2. 平滑显示血条、冷却、剩余时间。
3. 驱动远端角色的表现回放。

这一层不应该负责重新决定真值。

## 7. TCS 白名单矩阵

本节的“白名单矩阵”不是最终协议，而是目前更稳的默认建议。

## 8. 对 `StateInstance Apply` 的拆分建议

如果后续 `TCS` 真要支持本地预测，讨论重点不应该再是“能不能绕过 `StateInstanceApply`”，因为按当前架构，`Buff / Skill` 只要要触发 `StateTree` 执行，就必须先经过一次 `Apply`。

更合理的方式是：

1. 承认客户端若要先出正式技能表现，也需要执行一次“预测性的 `Apply`”。
2. 把一次 `Apply` 启动后的整条语义链拆成三段职责，而不是把 `Apply` 本身理解成可以被绕开的入口。

## 8.1 Apply-P：预测性 Apply 与前奏段

这一段可以允许客户端先执行的内容包括：

1. 客户端发起一次预测性的 `StateInstanceApply`，并创建预测分支记录。
2. 启动承载技能表现的预测 `StateTreeTask` 链。
3. 写入本地临时激活标记。
4. 播放本地动画与局部特效。
5. 产生目标预览。
6. 进行非常有限的自体资源预估扣减。

这里还需要把一个实现边界再说得更硬一点：

1. 在当前 `TCS` 架构下，如果本地预测真的发生，它的正式执行载体只能是“客户端先启动的一条预测性 `StateInstanceApply -> PredictableTask` 分支”。
2. `StateTreeTickScheduler` 只是这条本地预测分支派生出来的本地调度器，不属于需要同步给客户端的权威状态。
3. 换句话说，客户端不是“拿到服务器的 scheduler 再开始预测”，而是“本地先有预测 `StateInstance` 分支，分支进入 Running/Active 后，自然注册进本地 scheduler”。

## 8.2 Apply-S：服务器权威 Apply 与主段

这一段应该由服务器掌握真值，包括：

1. 服务器执行对应的权威 `StateInstanceApply`。
2. 真正决定槽位最终激活结果。
3. 真正注册 `Buff` 生命周期。
4. 真正写入 `Attribute Modifier`。
5. 真正执行复杂计算、合并、排序、约束传播。
6. 真正决定冷却、到期、移除与跨目标效果。

## 8.3 Apply-R：修正段

这一段负责处理服务器回来后的三种情况：

1. **确认成功**：预测分支升级为正式状态，或与服务器权威 `Apply` 产物配对。
2. **确认失败**：整体清理预测分支副作用。
3. **确认部分分歧**：清掉预测结果，再用服务器快照重建本地状态。

这比“让每个 `Task` 都自己写逆操作”更现实，也更符合 `GAS` 的实际边界。

## 8.4 可以把 `StateTreeTask` 的退出回调作为预测回滚基础

基于你刚确认的现有框架事实，这里有一个很关键的正面条件：

`TCS` 的 `StateTreeTask` 在 `StateTree` 结束时，可以自动执行类似 `OnQuitState` 的退出事件。

这意味着，后续如果要做窄预测，完全可以把这套退出回调机制作为 `StateTreeTask` 预测回滚的基础设施。

我更建议把它理解成：

1. **不是给每个 Task 设计通用逆操作接口**。
2. **而是要求可预测 Task 在退出回调里清理自己的预测性副作用**。

按这个思路，后续可以形成一条比较自然的回滚链：

1. 客户端启动预测性 `Apply`。
2. 预测分支中的 `Predictable Task` 开始执行。
3. 如果服务器否决，直接终止预测分支对应的 `StateTree`。
4. `Predictable Task` 在退出回调中清理本地预测副作用。
5. 再由服务器快照或服务器权威 `Apply` 结果重建最终本地状态。

这条路径的好处是：

1. 它符合当前 `TCS` 已有的 `StateTreeTask` 生命周期结构。
2. 它不要求所有 Task 都会“反向运算”。
3. 它更接近“分支销毁 + 权威重建”，而不是“任意逻辑级精细逆操作”。

同时也要把另一个经常混淆的点明确写出来：

当前不需要同步的，是 `StateTreeTickScheduler` 这种本地派生调度结构；当前真正需要设计清楚的，是“客户端是否允许创建预测 `StateInstance` 分支，以及哪些 `Task` 允许挂在这条分支里执行”。

当然，这里也有一个前提：

只有被标记为 `Predictable` 的 `Task`，才应该被要求具备这类退出清理能力；`AuthorityOnly` 的 `Task` 本来就不应该在客户端预测分支里执行。

结合这轮讨论，当前可以先把 `Predictable Task / AuthorityOnly Task` 的职责契约收敛成下面几条：

1. `StateTreeTask` 仍按正常业务逻辑编写，不额外要求作者拆两套完全不同的主体实现。
2. 当某个 `Task` 被配置为 `Predictable` 时，本地客户端在预测分支中允许执行其内部逻辑。
3. 当某个 `Task` 被配置为 `AuthorityOnly` 时，本地客户端在预测分支中必须直接绕过，不执行其主体逻辑。
4. 被配置为 `Predictable` 的 `Task`，必须在自己的结束逻辑中实现预测副作用清理。
5. 一旦 `StateInstance Apply` 被服务器否决，本地分支会进入 `RequestRemoval` 流程，并借由 `StateTreeTask` 的退出链自动触发这些清理逻辑。

### 8.4.1 当前仓库中已有 `StateTreeTask` 的建议分类

当前 `TCS` 仓库里实际用于讨论的 C++ `StateTreeTask` 很少，所以这里先只给“建议分类”，不把它们误写成已经完全定死的实现结论：

| Task | 当前职责 | 建议分类 | 原因 / 备注 |
| --- | --- | --- | --- |
| `FTcsStateChangeNotifyTask` | 在 `EnterState / ExitState` 时回调 `UTcsStateComponent::OnStateTreeStateChanged()`，驱动状态槽位与阶段联动 | 默认 `AuthorityOnly` | 它已经碰到 `StateComponent` 级状态联动，不像纯表现任务。除非后续把其中的“本地可预测通知”与“权威状态联动”进一步拆开，否则不应默认放进客户端预测分支 |
| `FTcsBuffPeriodDriverTask` | 按周期累计时间并发出 `Event.Buff.PeriodTick` | `AuthorityOnly` | Buff 周期、到期、移除当前已明确排除出预测层；该任务本身又是跨帧周期驱动，因此不应进入客户端预测分支 |

这张表当前的意义主要是两点：

1. 它先把“默认保守分类”写清楚，避免后面把现有 Task 误读成天然可预测。
2. 等后续真正出现更多 Gameplay `StateTreeTask` 时，再按“是否触碰权威状态写入 / 是否具备退出清理能力 / 是否只是局部可回收副作用”继续扩展这张表。

不过这里必须把一个风险写清楚：

如果这套契约长期完全依赖作者自觉，而没有任何最低限度的系统校验，那么它不是“完全没问题”，而是“前期可用、后期高风险”。

原因很直接：网络预测里最难排查的错误，往往就来自下面这类问题：

1. 某个本应 `AuthorityOnly` 的 `Task` 被错误标成了 `Predictable`。
2. 某个 `Predictable` 的 `Task` 执行了不该在客户端先跑的副作用。
3. 某个 `Predictable` 的 `Task` 虽然实现了退出逻辑，但没有把预测副作用清理干净。

所以当前更严谨的说法应该是：

1. 在设计收敛阶段，可以先把它视为“规范驱动的作者契约”。
2. 一旦真正进入实现阶段，至少要补最小校验或调试支撑，例如标记校验、运行时断言、分支日志，而不是永久完全依赖人工自觉。

对当前文档阶段，还可以再补一句边界：

这套“最小系统校验 / 调试支撑”目前只需要先作为明确待办写进讨论基线，不需要在尚未正式开始网络同步扩展时就把实现机制全部定死。

## 9. 当前已确认的结论与剩余问题

## 9.1 当前已确认的结论

到目前为止，这份文档里已经可以先视为确认的点包括：

1. `TCS` 的预测层明确限定为窄预测。
2. `StateInstance Apply` 可以按“预测性 Apply / 服务器权威 Apply / 修正段”拆分理解。
3. `StateTreeTask` 暂时更适合划成 `Predictable / AuthorityOnly` 两类，不继续引入 `CosmeticOnly` 这一层分类。
4. 当 `Task` 被配置为 `Predictable` 时，本地客户端允许执行其内部逻辑；当其被配置为 `AuthorityOnly` 时，本地客户端在预测分支中应直接绕过。
5. 被配置为 `Predictable` 的 `Task`，必须在自身结束逻辑里实现预测副作用清理；一旦服务器否决 `Apply`，本地可通过 `RequestRemoval` 流程触发这条回滚链。
6. 如果本地预测真的发生，它的正式执行载体只能是“预测性 `StateInstanceApply -> PredictableTask` 分支”；`StateTreeTickScheduler` 只是该分支本地派生出来的调度器，不属于同步边界。
6. `Buff` 的周期、到期、移除统一排除出预测层。
7. 复杂 `Attribute` 真值链统一保留在服务器权威层。
8. `Attribute` 局部预测白名单的当前首选落点是 `AttributeModifierDef`，但后续应保留 `AttributeDef` 级上层 veto / policy 的扩展空间。
9. `PredictionBranchId / PredictionTransactionId` 这类统一预测标识值得引入，但详细生命周期与配对设计可以延后到真正进入网络同步扩展阶段时再定。
10. 技能 `CD` 归 `SkillInstance` 自己管理，不归通用 `Buff / StateDuration` 管。
11. 连招窗口后续更适合作为独立机制，或者放入动作游戏扩展插件中专项实现。
12. 高频技能链路里的 `StateTreeTask` 行为，大概率需要支持受控批处理机制，但要结合具体实现再定范围。
13. 当前仓库里已存在的 `FTcsStateChangeNotifyTask` 与 `FTcsBuffPeriodDriverTask`，都更适合先按保守口径视为 `AuthorityOnly`，而不是默认纳入客户端预测分支。

## 9.2 当前剩余的核心问题

基于当前已经确认的边界，后续真正还需要细化的，主要剩下面几个问题：

1. `Predictable Task` 的作者契约虽然已经有方向，但进入实现阶段后最低限度要加哪些系统校验与调试支撑，还需要细化；当前阶段只先把这件事记为明确待办，不阻塞现阶段讨论。
2. `AttributeModifierDef` 上的局部预测白名单具体要落哪些字段、如何判定，以及是否保留 `AttributeDef` 上层 veto，还需要进一步收敛；当前已确认首选落点是 `AttributeModifierDef`。
3. 高频技能链路里的 `StateTreeTask` 行为，哪些适合做受控批处理、哪些必须保持逐个执行，仍需要结合具体实现分析；`Montage` 播放请求可以作为优先分析入口，但不能把整个 Montage 语义粗暴视为可合批对象。
4. `PredictionBranchId / PredictionTransactionId` 的详细生命周期、配对规则和失效规则可以暂时延后，不作为当前讨论阶段的阻塞项。

## 10. 当前建议的下一步

如果继续沿这条线往下走，我建议下一步先把下面四件事细化成更具体的设计条目：

1. 先把 `Predictable / AuthorityOnly` 的作者契约保留在当前讨论文档里，等真正开始扩展网络同步时，再补最小系统校验与调试支撑的具体方案。
2. 先把 `AttributeModifierDef` 上的局部预测白名单规则具体化，并决定是否同步预留 `AttributeDef` 上层 veto。
3. 先评估高频技能场景下哪些 `StateTreeTask` 适合受控批处理，哪些不适合；如果要先举具体例子，优先分析 `Montage` 播放请求相关的高频纯表现派发路径。
4. 等真正开始扩展 `TCS` 的网络同步与本地预测时，再细化 `PredictionBranchId / PredictionTransactionId` 的结构与配对语义。

这四件事细化后，再继续往下推：

1. 预测分支数据结构。
2. `StateTreeTask` 两分类约束。
3. 同步快照粒度。
4. 高频技能链路中的预测支撑与权威边界方案。
