# 借鉴 02：一切皆为持续效果的统一思维

## 概述

AbilityKit 在 `Docs/游戏效果系统统一抽象.md` 提出"**Buff、主动技能、被动技能、引导技能、光环效果……本质上都是同一种东西，只是配置参数不同**"。所有持续效果使用完全相同的配置结构，只是参数值不同，统一由一个 `EffectRegistry` 管理生命周期。

本借鉴对 TCS 是"思维校准"而非"架构重写"：TCS 已有共享基类 `UTcsStateDefinition`，方向接近；可进一步评估光环、Toggle 被动、持续区域效果是否可建模为"持续 State"的统一配置变体。

## AbilityKit 设计思想与架构实践

### 打破类型壁垒

AbilityKit 明确反对"为每种效果写专门系统"（`游戏效果系统统一抽象.md:7-43`）：

```
传统思维：Buff / 技能 / 被动 / 光环 = 四种东西 → 四套系统
统一思维：它们都是同一个东西的不同配置 → 一套系统
```

核心理念是"**配置即类型**"：
- 主动技能 = `Trigger=Active, Duration=0`
- 被动 = `Trigger=Passive, Condition=OnDamaged`
- Buff = `Trigger=Passive, Duration=5s`
- 光环 = `Trigger=Aura, Duration=Infinite, Range=10m`

### 统一配置模型

`EffectConfig` 接口把四维抽象都收进同一结构（`游戏效果系统统一抽象.md:50-73`）：

```csharp
public interface IEffectConfig
{
    // ===== WHO - 目标 =====
    TargetSelector Target { get; }
    RangeShape Range { get; }
    float RangeValue { get; }

    // ===== WHEN - 时机 =====
    TriggerMode TriggerMode { get; }        // Active/Passive/Aura/Toggle
    TriggerCondition TriggerCondition { get; }
    float Cooldown { get; }

    // ===== WHAT - 效果 =====
    IReadOnlyList<Effect> Effects { get; }
    GameplayTagContainer Tags { get; }
    ModifierData[] Modifiers { get; }

    // ===== HOW - 执行方式 =====
    ExecutionMode ExecutionMode { get; }    // Immediate/Delayed/Continuous/Phased/Channeled
    float Duration { get; }
    float Interval { get; }
    bool Interruptible { get; }
}
```

### 统一注册表

所有效果用 `EffectRegistry.Start(config, ctx)` 统一启动，按 TriggerMode 内部分流（`游戏效果系统统一抽象.md:280-316`）：

```csharp
public ContinuousHandle Start(IEffectConfig config, EffectContext ctx)
{
    var instance = CreateInstance(config, ctx);
    switch (config.TriggerMode)
    {
        case TriggerMode.Active:    return StartActiveEffect(instance);
        case TriggerMode.Passive:   return RegisterPassiveEffect(instance);
        case TriggerMode.Aura:      return RegisterAuraEffect(instance);
    }
}
```

所有效果用同一 `End(handle, reason)` 统一清理：移除 Modifier、移除 Tag、取消调度、通知结束（`游戏效果系统统一抽象.md:306-316`）。

### 统一生命周期的收益

AbilityKit 列出统一的好处（`游戏效果系统统一抽象.md:402-457`）：

1. **代码复用**：一套生命周期管理覆盖所有效果类型，而非 BuffSystem/SkillSystem/PassiveSystem/AuraSystem 四套。
2. **统一查询**：`GetActiveEffects` / `GetByTag("Unpurgable")` / `InterruptByTag("Stun")` / `GetByTarget(targetId)` 跨类型查找。
3. **统一持久化**：所有效果走同一 `EffectSaveData` 序列化格式。
4. **统一调试**：所有效果走同一事件日志 `EffectStarted/Tick/Ended`。

### 设计三原则

AbilityKit 给出三条设计原则（`游戏效果系统统一抽象.md:461-517`）：

1. **配置驱动，非代码驱动**：用配置描述效果，代码统一处理，而非为每种效果写专门类。
2. **参数化，非特殊化**：用参数区分，都是效果的不同配置，而非用特殊类型区分。
3. **接口组合，非继承**：特性以可选接口组合（ITagRequirementsSource/IModifierSource/IEffectSource/ITagSource），而非继承树。

## 与 TCS 现状的对比

### TCS 已有的共享抽象

TCS 已有 `UTcsStateDefinition`（抽象共享契约，`UCLASS(Abstract, BlueprintType, Const)`），承载所有运行时状态共享字段：StateDefId/StateTag/StateSlotType/Priority/CategoryTags/FunctionTags/StateTreeRef/TickPolicy/ActiveConditions/Parameters/LevelParamTag。

派生关系：
- `UTcsBuffDefinition : UTcsStateDefinition`，承载 Buff 专属：DurationType/Duration/Period/MaxStackCount/MergerType/OnStackIncrease/OnDurationExpired/BuffInstanceClass。
- `UTcsSkillDefinition : UTcsStateDefinition`，承载 Skill 专属：SkillInstanceClass/SkillEntryClass/CooldownParamTag/CooldownParam。

两者共享生命周期：`Inactive → Active → HangUp/Pause → Expired`，共用 `FinalizeStateRemoval` 八步移除。

证据：`E:\Projects_Unreal\TireflyGameplayUtils\Plugins\TireflyCombatSystem\Source\TireflyCombatSystem\Public\State\TcsStateDefinition.h:22-155`；`TcsBuffDefinition.h:84-198`；`TcsSkillDefinition.h:22-94`；`specs/state-management/spec.md:39-50`。

### 相似点

TCS 的"共享基类 + 派生挂接"与 AbilityKit 的"统一配置 + 参数化"在精神上接近：
- 都共享生命周期管理（TCS 的八步移除 vs AbilityKit 的统一 End）。
- 都共享字段（TCS 的 StateDefId/StateTag/Priority vs AbilityKit 的 TriggerMode/Tags/Duration）。
- 都反对为每种效果写独立系统。

### 差异点

- **统一程度**：AbilityKit 走到极致，单一 `EffectRegistry`；TCS 保留类型化分层，Buff/Skill 各自 Definition 派生类。
- **光环/Toggle 被动**：TCS 目前没有显式 Aura 或 Toggle 状态类型，缺乏这一类持续效果的统一建模。
- **跨类型查询**：TCS 目前没有"跨所有状态类型查询"的统一 API，状态查询绑定在 `StateComponent` 的 `StateInstanceIndex` 上（`specs/state-management/spec.md:110-128`）。

## 借鉴建议

### 1. 评估"持续 State"统一变体

TCS 可在 `UTcsStateDefinition` 基类基础上评估引入"持续效果变体"枚举或字段：

```cpp
// 仅作设计示意，非最终实现
enum class ETcsEffectVariant : uint8
{
    OneShot,      // 一次性 State（瞬时）
    Continuous,   // 持续 State（Buff 类）
    Aura,         // 光环 State（持续 + 范围目标）
    Toggle,       // 开关 State（手动切换、永久持续）
    Channeled     // 引导 State（持续 + 可打断）
};
```

变体作为 Definition 层字段，决定生命周期与 TickPolicy 默认值，不破坏现有 Buff/Skill 派生分层。

### 2. 引入跨类型统一查询

TCS 目前状态查询绑定 `StateTag` / `StateSlotType`。可评估在 `UTcsStateComponent` 上增加按 EffectVariant / FunctionTags 的统一查询入口，作为高阶便利 API，不替代现有 `StateInstanceIndex`。

### 3. 评估光环（Aura）作为统一持续 State

TCS 目前没有光环建模。光环本质是"持续 State + 范围目标选择 + 周期 Tick"。可在 `UTcsStateDefinition` 层引入 `TargetSelector` + `RangeShape` + `Interval`，让光环成为"持续 State 的 Aura 变体"，而不是独立系统。

### 4. 评估 Toggle 被动作为统一持续 State

Toggle 被动（防御姿态、潜行、形态切换）本质是"持续 State + 手动切换 + 永久 Duration"。可建模为 `Continuous` 变体 + `DurationType=Infinite` + 手动 `RequestStateRemoval`。

## 风险与前置条件

- **风险：低到中**。统一变体是 Definition 层增量字段，不破坏现有 Buff/Skill 类型化分层。
- **前置条件**：
  - TCS 目前 State/Buff 完成度 90%+，是引入统一变体的有利时机（`project.md:210-218`）。
  - 需评估现有 `UTcsBuffDefinition` 的 DurationType/Period/MaxStackCount 等字段是否可上提到基类作为"持续变体通用字段"，避免重复。**注意**：上提会扩大基类表面积，需 spec 评审确认。
- **落地形式**：
  1. 先在 `Documents/` 下做一次"光环/Toggle 在 TCS 中的建模"专题分析（无代码）。
  2. 若结论可行，创建 OpenSpec capability `add-effect-variant-aura-toggle`，评审 Definition 层字段方案。
  3. 运行时增量实现，不破坏现有八步移除与 StateSlot 机制。

## 不建议的做法

- **不要**走向 AbilityKit 式单一 `EffectRegistry`，废弃 TCS 的 `StateComponent` / `StateInstance` 类型化分层。TCS 的强类型与编辑器 authoring 价值高于"极致统一"。
- **不要**把 Buff/Skill 的专属字段（如 Buff 的 StackCount/Skill 的 SkillEntry）强行上提到基类。"持续变体"只承载持续效果通用字段（Duration/Interval/Target/Range），专属字段留在派生类。
- **不要**一次性把所有现有 Buff/Skill 资产改造为"统一变体"。TCS 目前确认无 Blueprint 资产引用（`project.md:17-21`），可只在新设计的光环/Toggle 上使用，老资产保持不变。
