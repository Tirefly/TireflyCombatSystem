# 借鉴 08：原生网络分层蓝本

## 概述

AbilityKit 把网络同步作为框架一等公民，构建完整的分层模型：**Host/Session → 帧数据层 + 快照路由层 → 状态同步与客户端预测 → 战斗传输层 → 游戏应用层**，并实现 FrameSync（帧同步）与 StateSync（状态同步）两种同步风格，混合同步能力。

TCS 当前网络完成度 0%，仅有 `runtime-network-identity` 设计约束，无实现。当 TCS 启动网络实现时，AbilityKit 的分层是现成参考蓝本。

## AbilityKit 设计思想与架构实践

### 网络同步架构分层

AbilityKit 给出明确分层（`README.md:599-628`）：

```
游戏应用层            （MOBAGame / FPSTest / RPGDemo）
战斗传输层            IBattleLogicTransport ← NetworkTransport  (game.battle)
状态同步与客户端预测   IClientPredictionModule / IPredictionCoordinator  (world.statesync)
   帧数据层              FramePacket / Buffer                  (networkfragments)
   快照路由层            FrameSnapshotDispatcher                (world.snapshot)
Host / Session           FramePacketNetAdapter                  (host.extension)
网络层                  INetworkClient / Orleans                (network.runtime)
```

### 三种同步风格

AbilityKit 明确区分三种同步风格（`README.md:631-637`）：

| 风格 | 推荐游戏 | 特点 |
|------|----------|------|
| 帧同步 FrameSync | MOBA、格斗、RTS | 服务器统一驱动，每帧输入同步，客户端本地计算 |
| 状态同步 StateSync | MMORPG、大型多人、FPS | 服务器权威，客户端接收快照，可选预测回滚 |
| 混合同步 Hybrid | FPS+技能 | 移动帧同步，伤害状态同步 |

### 核心模块

#### 客户端预测与回滚

`com.abilitykit.world.statesync`（`README.md:241`、`AbilityKit_vs_GAS_Comparison.md:887-959`）：

- `ClientPredictionRunner`：`TickPredicted(frame)` / `ForceReconcile()`。
- `IRollbackStateProvider`：`Export(frame)` / `Import(frame, payload)`。
- `RollbackCoordinator`：保存 / 恢复 `WorldRollbackSnapshot`。
- `RollbackSnapshotRingBuffer`：环形缓冲。

#### 帧同步与帧数据

`com.abilitykit.world.framesync`（`README.md:238`）：

- FrameSync、Rollback、ClientPrediction、输入历史。
- `RemoteFrameBuffer` / `RemoteFrameAggregator`。

#### 快照路由

`com.abilitykit.world.snapshot`（`README.md:239`）：

- 按 opCode 解码并分发到处理器，与网络解耦。
- `FrameSnapshotDispatcher`。

#### 录像回放

`com.abilitykit.record`（`README.md:242`）：

- Session、Container、Track，支持输入录制与状态哈希采样。

### Session 装配层

`com.abilitykit.coordinator`（`README.md:176-212`）位于运行时装配层，把不同运行环境提供的 Host / Transport / View 统一装配成可运行战斗会话：

```
ISessionCoordinatorHost → SessionConfig → SessionCoordinator
  → WorldHost / IWorldHost → Logic World
  → SyncAdapterFactory → LocalSyncAdapter / RemoteSyncAdapter / HybridSyncAdapter
  → SubFeatures / ViewTimeline
```

业务工程只实现 `ISessionCoordinatorHost`，提供 WorldHost 创建、WorldCreateOptions、服务注册、配置加载、出生数据。

### 框架价值

AbilityKit 的核心价值是把"同一套战斗逻辑"放到不同运行环境复用：
- 本地 Demo → `LocalSyncAdapter`。
- 远程状态同步 → `RemoteSyncAdapter`。
- 带客户端预测多人 → `HybridSyncAdapter`。
- 测试与 Console → 复用纯 C# World 与同一套会话生命周期。

## 与 TCS 现状的对比

### TCS 当前的网络设计

TCS 网络完成度 0%（TCS 子代理报告 §3.7）。仅有 `runtime-network-identity` spec 作为后续设计约束。

#### 设计约束

`runtime-network-identity/spec.md:8-62`、`design.md:1-42` 规划身份分层：

- `DefId`：定义级身份（Definition 的稳定标识）。
- 实例级权威身份：`StateInstId` / `AttrModInstId` / `SkillModInstId`。
- `SourceHandle`：效果施加归因。
- 未来 `PredictionKey`：预测键。

#### 已有网络能力

`FTcsSourceHandle` 已实现 `NetSerialize` 与 `WithNetSerializer`（`TcsSourceHandle.h:108-150`），但只是结构序列化能力，不等于完整网络同步实现。

### 差异点

- **完成度**：AbilityKit 网络完整实现；TCS 仅设计约束。
- **分层**：AbilityKit 有明确分层与适配器工厂；TCS 尚未设计。
- **同步风格**：AbilityKit 支持三种；TCS 未选型。
- **装配**：AbilityKit 有 SessionCoordinator 装配层；TCS 仅有 `TcsRuntimeBootstrapSubsystem`（TCS 子代理报告 §3.8），方向接近但未做网络分歧。

### 相似点

- 两者都把"身份"作为网络同步一等公民。
- 两者都强调"服务器权威 / 客户端预测"的分层考虑。
- TCS 的 `RuntimeBootstrap` 与 AbilityKit 的 `SessionCoordinator` 在"装配"职责上类似。

### TCS 缺口

- 未选型：FrameSync / StateSync / Hybrid？
- 无预测回滚框架：`ClientPredictionRunner` / `RollbackCoordinator` 等价物缺失。
- 无快照路由层。
- 无战斗传输层抽象。
- 无录像回放。

## 借鉴建议

### 1. 当 TCS 启动网络实现时，借鉴 AbilityKit 分层蓝本

建议在 TCS 网络 capability 启动时，参照 AbilityKit 分层做架构 design：

```
游戏应用层            （Gameplay）
战斗传输层            IBattleLogicTransport ← NetworkTransport
状态同步与预测        TcsClientPredictionModule / TcsPredictionCoordinator
  快照层              TcsSnapshotDispatcher
Host / Session       TcsSessionAdapter
网络层               UE OnlineSubsystem / custom
```

### 2. 不要照抄纯 C# 实现，要适配 UE 网络栈

UE 已有完善网络栈：
- `UNetDriver` / `UChannel` / `Bunch`。
- `AActor::Replication` / `UActorComponent::Replication`。
- `IAbilitySystemComponent` 风格的 GAS 同步参考。
- `GameplayPrediction` 模块。

TCS 的网络应该：
- 优先复用 UClass 属性同步与 RPC，而非另起一套"快照路由"。
- 但 AbilityKit 的"分层思路"可吸收为概念蓝图。

### 3. 选型决策

TCS 需要先做 OpenSpec 提案决定同步风格。可能选项：

- **StateSync（推荐）**：UE 原生 Actor 复制最契合，适合 ARPG/MMO。
- **FrameSync**：需要状态哈希与确定性模拟，对 StateTree 不友好（StateTree 不保证帧内确定回放）。
- **Hybrid**：移动用帧同步、伤害用状态同步——复杂度高，谨慎。

建议先以 StateSync 为主线启动，FrameSync/Hybrid 作为后续可选扩展。

### 4. 分阶段推进

- **阶段 A**：完成 `runtime-network-identity` 设计，把 DefId / StateInstId / SourceHandle / PredictionKey 分层落到代码。
- **阶段 B**：选定同步风格（建议 StateSync），实现 SourceHandle 与 StateInstance 的属性复制。
- **阶段 C**：引入预测回滚框架，借鉴 `RollbackCoordinator` 思路实现 State 快照保存 / 恢复。
- **阶段 D**：快照路由与回放。

### 5. 测试蓝本

AbilityKit 的"纯 C# 验收矩阵 + 战斗回放 + 状态哈希"（`README.md:83`）可作为 TCS 网络验收蓝本：

- 状态哈希采样用于客户端 / 服务器一致性校验。
- 战斗回放用于权威性验证。
- 验收矩阵支持自动回归（结合 TCS `TireflyCombatSystemTests` 模块）。

## 风险与前置条件

- **风险：待时机**。网络是大型工作，启动前需用户明确确认进入网络实现阶段。
- **前置条件**：
  - `runtime-network-identity` spec 需先从"设计约束"推进为"可实现 spec"。
  - State/Buff 完成度 90%+，是启动网络的稳定基础。
  - Skill 系统完成度 35%，网络实现可能伴随 Skill 主路径收敛同步推进。
- **落地形式**：
  1. 用户确认启动网络实现后，创建 OpenSpec capability `add-network-sync-foundation`。
  2. 先做 design.md 评估同步风格、UE 网络栈复用范围。
  3. 分阶段落地（A→D）。
  4. 不照抄 AbilityKit 纯 C# 实现，做 UE 原生适配。

## 不建议的做法

- **不要**照抄 AbilityKit 的纯 C# 网络实现。UE 有成熟网络栈，强行另起一套会冲突。
- **不要**在 State/Buff/SourceHandle 这些基础稳定性不足时启动网络。先完成现有活动 change 验证。
- **不要**默认选 FrameSync。StateTree 不是为确定性帧回放设计的，FrameSync 风险高。
- **不要**把 AbilityKit 的模块边界（framesync / statesync / snapshot / networkfragments）原样移植为 UE 插件模块。TCS 的模块边界应保持 Runtime/Editor 双模块。
