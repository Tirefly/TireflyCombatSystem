# 文档：DefMgrSubsystem 对热更新与创意工坊 UCG 导入的后续影响分析

> 文档日期：2026-07-01  
> 适用范围：TireflyCombatSystem（TCS）插件后续优化讨论  
> 目的：记录未来若项目需要支持“运行中热更新 Def 内容”或“游戏内导入创意工坊 / UGC 内容”时，`UTcsDefinitionManagerSubsystem` 可能受到的影响、风险点与可选优化方案。

---

## 1. 结论先行

当前 TCS 的 `UTcsDefinitionManagerSubsystem` **不应**在基础契约中直接引入通用 `RuntimeRefresh` 语义。

原因不是“未来永远不需要”，而是：

1. 当前主目标是建立**干净、稳定、可验证**的运行时 Definition 管理层；
2. “热更新 / UCG 导入”属于**额外能力**，不是所有项目的基础运行时事实；
3. 一旦把通用 `RuntimeRefresh` 提前写进基础契约，就会把大量“一致性重收敛”问题提前绑定到所有项目，明显扩大系统复杂度；
4. 真正困难的部分不在“重新扫描 Definition 资源”，而在“运行中的 Skill / Buff / State / Modifier 实例如何与新旧 Definition 对齐”。

因此，更合理的方向是：

- **当前阶段**：DefMgrSubsystem 只承担稳定的运行时 Definition 解析、缓存、查询职责；
- **未来阶段**：如果某个具体项目确实需要运行中内容变更，再以**新增 capability / 新 proposal**的形式，为该项目引入专门的 refresh / snapshot / 内容源切换机制。

---

## 2. 本文讨论的问题边界

本文讨论的是未来某些项目可能出现的需求，例如：

- 游戏运行过程中挂载新的 DLC / 热更新内容包；
- 玩家在游戏内导入创意工坊内容；
- UCG 系统在游戏进行中生成一批新的 Definition 数据或规则集；
- 宿主 / 服务器在不中断运行的情况下切换规则配置集。

本文**不讨论**以下内容：

- 当前 TCS 基础提案中的 runtime Definition 主路径改造；
- 编辑器期 `UTcsDefinitionRegistrySubsystem` 刷新逻辑；
- 单纯的编辑器 authoring 便利性；
- 没有运行时内容变更事实时，凭空设计一套“通用 refresh 生命周期”。

---

## 3. 什么时候才真正需要 RuntimeRefresh

只有当项目同时满足下面三个条件时，才值得认真设计 `RuntimeRefresh`：

1. **运行中的内容源会变化**  
   例如新 Def 包、工坊内容、远程规则集、运行时导入文件。

2. **变化必须在当前会话立即生效**  
   不是“重开关卡 / 重新进局 / 重启游戏后生效”，而是当前会话内立即可见。

3. **系统愿意承担运行中一致性收敛成本**  
   即项目接受“旧实例怎么处理、新旧 Def 如何切换、同步和存档如何对齐”等额外设计成本。

如果缺少其中任意一条，就不应该轻易引入 `RuntimeRefresh`。

### 3.1 其实很多项目并不需要

很多项目的真实需求只是：

- 游戏启动时扫描本地内容；
- 进入某个会话前加载所需 Def；
- 新内容在下次进局或重启后生效。

这种情况下，**完全没有必要**设计运行中 refresh。强行加进去只会污染基础架构。

---

## 4. 真正的难点不在“重新加载资源”

如果未来某个项目要支持运行中内容变更，表面上看像是在问：

> “DefMgrSubsystem 能不能重新扫一遍 Definition？”

但真正棘手的问题其实是下面这些：

### 4.1 SkillEntry 的身份与快照问题

- 已学会的 `UTcsSkillEntry` 以哪个版本的 `SkillDef` 为准？
- 如果 `SkillDefId` 相同但内容已替换，旧 Entry 是否自动切到新 Def？
- `SkillDefinition*` 缓存是否立即失效？
- 运行中的 Skill cooldown、level param、snapshot 配置是否需要重算？

### 4.2 Buff / State 实例的存量一致性

- 已存在的 StateInstance 是否继续绑定旧 Definition 快照？
- 如果新 Def 改了 duration、param evaluator、slot policy，旧实例是否也要被迁移？
- 是否允许“新实例走新 Def，旧实例继续跑旧 Def”？

### 4.3 SkillModifier / AttributeModifier 的链式副作用

- 已写入参数实例链的 runtime modifier 是否需要重建？
- 旧 modifier entry 是否要清空后重算？
- 如果 refresh 发生在中途，会不会出现参数链前半段旧、后半段新？

### 4.4 存档 / 联机 / 回放一致性

- 客户端与服务器若加载到不同版本的 Def，会怎样？
- 旧存档恢复时，DefId 指向的新内容与旧内容不兼容怎么办？
- 战斗回放、determinism 或日志复盘是否需要绑定 Definition 版本号？

### 4.5 内容卸载与删除

- 新内容可以导入，但能不能在会话中卸载？
- 若某 Def 被移除，而已有实例仍在引用它，该如何处理？
- 是拒绝卸载，还是保留僵尸快照，还是强制移除相关实例？

结论很直接：

> **“重新解析 Definition”只是最容易的一步；真正昂贵的是运行中对象的一致性治理。**

---

## 5. 对 DefMgrSubsystem 可能带来的影响

如果未来确实要支持热更新 / 创意工坊 / UCG 运行中导入，那么 `UTcsDefinitionManagerSubsystem` 可能至少会受到以下影响。

### 5.1 从“静态来源管理”升级为“动态来源管理”

当前更合理的基础契约是：

- 运行时存在一组稳定的 Definition 来源；
- DefMgrSubsystem 从这些来源解析与缓存；
- 主路径按 `DefId` 查询并失败即失败。

如果支持运行中导入，就必须再处理：

- 内容源新增；
- 内容源替换；
- 内容源移除；
- 内容源优先级冲突；
- 同名 `DefId` 覆盖关系。

### 5.2 需要显式“版本”或“快照”概念

一旦运行时内容可能变化，单纯的 `DefId -> Definition*` 映射通常就不够了。

后续可能需要：

- `DefId + Version`；
- 或 `DefId + SnapshotHandle`；
- 或“当前活动 Definition 集合”的显式快照对象。

否则系统无法可靠表达：

- 当前实例到底绑定的是哪一版 Definition；
- 为什么两个同 `DefId` 的对象表现不同；
- 为什么旧存档和新内容不兼容。

### 5.3 需要明确“refresh 的影响边界”

如果未来引入 refresh，必须先回答：

- refresh 只影响**后续新建实例**？
- 还是也影响**当前已存在实例**？
- 已存在实例是自动迁移、延迟迁移，还是永不迁移？
- refresh 是原子切换，还是增量修补？

这部分如果不先写清楚，任何 `RuntimeRefresh` 都会变成高风险入口。

### 5.4 失败语义会进一步复杂化

当前基础提案里，失败类别至少区分：

- 未注册
- 类型不匹配
- 加载失败

如果未来支持动态内容变更，失败类别可能还要扩展，例如：

- 内容源冲突
- 快照已过期
- 引用中的 Definition 已卸载
- 当前会话不允许切换活动快照
- 运行中实例阻止 refresh 生效

也就是说，未来的动态内容能力很可能要求更完整的错误码或诊断体系。

---

## 6. 可选优化方案

下面列出的不是“现在就应该上”的内容，而是未来项目真有硬需求时，可以考虑的方向。

---

### 方案 A：不做 RuntimeRefresh，只支持“新会话生效”

**做法**
- 游戏运行中允许导入新内容包或工坊内容；
- 但当前会话不刷新 DefMgrSubsystem；
- 新内容只在下一次进局 / 重开 / 重启后生效。

**优点**
- 复杂度最低；
- 不污染当前 runtime contract；
- 不需要处理存量实例迁移。

**缺点**
- 用户体验不够“即时”；
- 某些 UCG 场景下不够灵活。

**适用场景**
- 大多数内容型项目；
- 不要求“导入后立刻在当前战局生效”的项目。

**总体评价**
- 这是最保守、也最稳的方案。
- 如果未来没有非常明确的即时生效需求，优先考虑这个方案。

---

### 方案 B：内容源变更后，生成新快照，但只影响后续新建实例

**做法**
- DefMgrSubsystem 接收到明确的“内容源更新”指令；
- 生成新的 Definition Snapshot；
- 后续新建的 Skill / Buff / State / Modifier 使用新快照；
- 已存在实例继续绑定旧快照，不自动迁移。

**优点**
- 比全量 runtime refresh 安全很多；
- 不需要强制迁移所有存量实例；
- 适合渐进式支持热更新能力。

**缺点**
- 同一会话内可能同时存在“旧快照实例”和“新快照实例”；
- 需要额外设计 snapshot 标识和兼容性边界。

**适用场景**
- 允许“一次导入，只影响之后新生成内容”的项目；
- 愿意接受会话内多快照并存的项目。

**总体评价**
- 这是未来如果要扩展，我最推荐优先评估的方案。
- 它比“原地刷新全部实例”现实得多。

---

### 方案 C：显式 RuntimeRefresh，但只允许原子切换到新快照

**做法**
- 内容源更新后，先构建完整新快照；
- 通过一个显式、受控的 refresh/swap 点，将“当前活动快照”原子切换到新快照；
- 同时明确规定：
  - 哪些实例继续使用旧快照；
  - 哪些实例必须重建；
  - 哪些系统在切换期间暂停。

**优点**
- 比零散刷新更可控；
- 能避免“边查边改”的半刷新状态。

**缺点**
- 设计复杂度高；
- 实现成本高；
- 对联机、存档、实例迁移、日志追踪要求都更高。

**适用场景**
- 强规则型游戏；
- 需要明确内容切换点的项目；
- 有能力承担较高工程成本的项目。

**总体评价**
- 这是一个可以做，但必须单独立项的能力。
- 不应混在当前基础 DefMgrSubsystem 提案里偷带进去。

---

### 方案 D：允许运行时导入，但 DefMgrSubsystem 不直接承担导入逻辑

**做法**
- 单独设计一个“内容导入 / 内容挂载 / 工坊资源管理”上层系统；
- 由它把已经验证完成的 Definition 集合作为输入提供给 DefMgrSubsystem；
- DefMgrSubsystem 只承担“消费已确认的 Definition 来源”这一职责。

**优点**
- 职责分离清晰；
- 避免 DefMgrSubsystem 既做运行时查询，又做文件导入、校验、冲突解决。

**缺点**
- 需要额外系统配合；
- 初期看起来比“都塞进 DefMgrSubsystem”更麻烦。

**适用场景**
- 有创意工坊、模组、UCG 内容挂载需求的项目。

**总体评价**
- 如果未来真走工坊 / UCG 导入路线，这个方向几乎是必须的。
- 否则 DefMgrSubsystem 很快会职责爆炸。

---

## 7. 后续若真要支持，应新增哪些能力

如果未来某项目明确要支持运行中热更新或 UCG 导入，建议单独新建 proposal，并至少覆盖以下能力：

### 7.1 内容源管理
- 定义内容源注册、卸载、优先级、冲突解决策略；
- 明确本地包、远程包、工坊内容、临时生成内容的来源差异。

### 7.2 Definition Snapshot / Versioning
- 明确 `DefId` 是否需要版本；
- 明确运行时实例与快照的绑定关系；
- 明确旧快照何时释放。

### 7.3 运行中实例一致性策略
- SkillEntry 如何迁移；
- Buff / StateInstance 如何迁移；
- SkillModifier / AttributeModifier 链如何重建。

### 7.4 存档 / 联机兼容策略
- 存档记录的是 `DefId` 还是 `DefId + Version`；
- 客户端与服务器如何保证 Definition 集一致；
- 内容缺失时如何降级或拒绝加载。

### 7.5 诊断与工具支持
- 更强的错误码 / 失败分类；
- 当前活动快照、实例绑定快照、内容源冲突的调试可视化；
- 导入成功但未激活、已激活但旧实例仍绑定旧快照等状态提示。

---

## 8. 对当前 TCS 提案的建议

基于当前阶段目标，建议保持如下边界：

1. 当前 `UTcsDefinitionManagerSubsystem` **不提供**通用 `RuntimeRefresh`；
2. 当前 runtime contract **不假定** DefAsset 运行中增删改查；
3. 当前 proposal 只解决：
   - Definition 运行时归口；
   - DefId 主路径；
   - 统一失败语义；
   - 与 editor registry 的强解耦；
4. 未来若某项目确实有热更新 / 工坊 / UCG 运行中导入需求，再单独做新的 capability 和 proposal。

这条边界必须守住。否则当前提案会被未来假设拖垮，基础层会在落地前就变成一个过度设计的大系统。

---

## 9. 推荐的后续策略

如果未来真的出现相关项目需求，建议按以下顺序推进：

### 第一阶段：先确认是否真的需要“当前会话立即生效”
如果不需要，优先使用“新会话生效”策略，避免 runtime refresh 复杂度。

### 第二阶段：若必须立即生效，优先做“新快照只影响新实例”
先不要尝试全量迁移所有存量实例。

### 第三阶段：只有在项目明确需要时，才评估原子切换或受控 refresh
这一步必须单独立项，不应作为 DefMgrSubsystem 的默认能力自动存在。

---

## 10. 最终建议

一句话总结：

> **未来某些项目可能需要热更新或游戏内导入 UCG 内容，但这并不意味着当前就应该把通用 `RuntimeRefresh` 写进 DefMgrSubsystem 的基础契约。**

当前更正确的做法是：

- 先把 DefMgrSubsystem 做成干净、稳定的 runtime definition 管理层；
- 将“动态内容源 / snapshot 切换 / 运行中一致性收敛”视为未来按需扩展能力；
- 到真正有项目需求时，再以独立 proposal 的方式处理。
