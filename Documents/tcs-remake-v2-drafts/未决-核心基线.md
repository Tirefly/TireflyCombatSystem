## 1. 哪些运行期类型需要句柄

**已裁**：Buff 实例 / Skill 实例 / Skill 账本条目**需要句柄**（跨容器引用 + 槽位复用双条满足）。

**未裁**：其余类型的取舍。

| 类型 | 当前无句柄的理由 | 需要重新审视吗 |
|---|---|---|
| 属性实例 | 属性表内按 `Attr` tag 查，不退槽 | 若需要跨系统按句柄引用（如网络复制、外部监听）则要 |
| 属性修正器实例 | 挂在父属性内，按 `Source` 级联摘除 | 若要单独摘除某一条（不按来源）则要 |
| 参数快照条目 | 快照内按 tag 查；快照本身随实例销毁 | 若要跨快照引用则要 |
| 参数修正器 | 参数链内形参传入，无持久容器 | 若参数链产生持久化运行态则要 |
| Skill 修正器实例 | 类型当前不存在 | 待该能力落地时判 |

**缺什么裁决**：每个类型是否出现「① 跨容器 / 跨调用边界被引用 ② 槽位会复用」这两条。在任一类型出现真实消费者前，**MUST NOT** 为它建句柄。

## 2. 各域系统就绪判据（`IsSystemReady`）

**语义**：某个域（Attribute / Buff / Skill / …）自己的系统初始化是否已经执行结束。问的是**系统**，不是实体。

| 疑点 | 说明 |
|---|---|
| 作用域 | 每域各一个，还是整个 TCS 一个？（各域初始化完成时机不同） |
| 可逆性 | 一次性置位，还是可回退（世界拆解、热重载）？ |
| 载体 | 各域子系统方法，还是统一的「就绪聚合面」？ |
| 通知形态 | 需要「就绪」事件（订阅者在回调里才安全），还是只需轮询？ |

**缺什么裁决**：每个域各自定义，还是框架给统一形态。若是后者，它够格成为第 6 项核心基线（判据见 [INDEX](../tcs-remake-v2/INDEX.md) §2.2）。

**已知的坑**：

| 坑 | 说明 |
|---|---|
| 粒度三层 | 实体级 / 域级 / 世界级完成时机、可逆性、消费者都不同，用同一个名字会造成「同名不同义」 |
| 域边界未定 | 「每域一个」假设了域边界固定，而模块合并尚未决定；若合并，它可能退化成三个布尔字段复用一个「系统」 |

## 3. 受击反馈强度从哪来

`TcsHitReaction` 这类下游插件要靠事件知道「该做什么反馈」。现有事件能给：实体句柄、伤害数值、来源句柄、伤害类型 Tag。

**但「受击强度」这个数没有来源**：

| 候选来源 | 否决理由 |
|---|---|
| 伤害数值本身 | 10 点暴击可能要重反馈，1000 点 DoT 可能要轻反馈 |
| 伤害类型 Tag | 只能表达「火焰 / 物理」，表达不了「这一下打得多狠」 |
| 由 TCS 某机制算出 | 那就等于 TCS 定义了一种「反馈强度」的语义 |

**缺什么裁决**：事件载荷是否需要带一个宿主可写的附加面。属**效果执行**域，不是实体层。

## 4. 千级实体下的路由结构（事件总线）

当前形态是「一个频道 → 一个槽位数组」。需要回答：

| 问题 | 影响 |
|---|---|
| 是否需要「按实体过滤」的快路径 | 千级实体下，通知全体再逐个丢弃是浪费 |
| 频道分桶的粒度 | 是否要为高频频道单独优化 |

**缺什么**：压测数据。**在拿到数据前 MUST NOT 预设结构。**

**为什么要压测而不是推理**：当前形态的每一次派发都是「锁长度 + 线性扫槽位」，成本 = 订阅者数 × 派发深度。千级实体下订阅者可能上千，但**实际匹配频道的可能只有几十个**——要不要为这个比值做结构，取决于真实比值，不取决于想象。

## 5. 同源多条 Override 的 Def 校验规则（数值聚合器）

一个来源可以有多行修正器指向同一属性且同为 Override 带，此时它们的 `Source` 相同：

| 条目 | Source | Op | Value |
|---|---|---|---|
| 来源 A 第 1 行 | **7** | Override | 100 |
| 来源 A 第 2 行 | **7** | Override | 200 |

⇒ **七个策略其实都分得出胜负**：策略级打平后，`§5.1` 的**决胜级**（按 `Value` 比大小）会接管，上例的 `200` 恒赢。
（原先此处的「`Latest` / `Earliest` / `HighestPriority` 都无法分出胜负」是**事实错误**，2026-11-03 订正。）

**已裁方向**（2026-11-03 用户确认，此前误记为未裁）：

1. **报 `Error`，不是 `Warning`**——`IsDataValid` 返回 `EDataValidationResult::Invalid` + `Context.AddError`。`Warning` 不产生失败判定，配置错误会一路活到运行期。
2. **判定逻辑下放给各 DefAsset**——不同 DefAsset 有各自的判定方式与逻辑，只有它知道自己有几行、行序与 `Source` 怎么来。
3. **用引擎默认行为，不另挂 pre-save 钩子**——UE 数据校验的保存钩子在**保存完成之后**（`FDataValidationModule::OnPackageSaved` → `UEditorValidatorSubsystem::ValidateSavedPackage`），报 message log 与 toast，**不阻断保存**。

**未裁**：各 DefAsset 的**具体判定逻辑**（本表上例的「值不同」才需要报，「值相同」输出一致、实际无害）——逐资产落地时再定。

## 6. 流程域要不要「后来者覆盖」（数值聚合器）

流程步骤是**顺序执行**的，语义上「后写的覆盖先写的」更自然；而聚合器当前给的是「大的覆盖小的」（`Priority` 恒 0 ⇒ 同优先级取最大值）。

| 方案 | 代价 |
|---|---|
| 流程黑板提交带 `Source` | `Source` 是原子递增序号，能天然表达「后来者」；但流程域的每个提交都要发号 |
| 给提交加独立序号 | 多一层「新序号与 `Source` 不同源」，两者不一致时无法判定谁赢 |
| 维持现状 | 流程域表达不了「后来者覆盖」；这类需求只能由调用方自己在提交时不写第二条 |

**缺什么裁决**：流程域是否存在真实消费者需要「后来者覆盖」。**在出现该消费者前 MUST NOT 加 `Source` 或任何序号字段。**

## 7. `uint64` 反射限制的真实边界（运行时实例）——**已解决（2026-11-02）**

`运行时实例.md` §1.3.1 原写：「实体句柄与实例句柄要进反射，MUST 用 `int64`（**UHT 不支持 `uint64` 作属性类型**）」。

**这一句的理由未经核实，且初步证据指向它不成立。**

### 已查到的事实（UE 5.8）

| # | 事实 | 位置 |
|---|---|---|
| 1 | UHT **有** `uint64` 属性关键字 | `EpicGames.UHT/Types/Properties/UhtUInt64Property.cs:70` |
| 2 | 该属性映射到引擎类 `UInt64Property`，`CodeGenParamsStruct = FUInt64PropertyParams` | 同文件 `:16` `:26` |
| 3 | 蓝图 schema 里**没有** `uint64` 的 pin 类型 | `EdGraphSchema_K2.h` 只有 `PC_Int64`，无 `PC_UInt64` |
| 4 | 蓝图 pin 转换里**没有** `FUInt64Property` 分支 | `EdGraphSchema_K2.cpp` `ConvertPropertyToPinType` 只处理 `FInt64Property → PC_Int64` |

⇒ 初步判断：**限制在「蓝图」，不在「UHT」**。两者适用范围完全不同——前者只管蓝图暴露，后者管所有反射。

### 受影响的只有理由，不涉及结论

| 项 | 是否会变 |
|---|---|
| `FTcsCombatEntityHandle` / 实例句柄用 `int64` | **不变**——它们要 `BlueprintType`、要进事件载荷与蓝图 |
| `FTcsSourceHandle` 用 `uint64` | **不变**——它非反射，两种宽度都对它无所谓 |
| 上面那句「为什么不同宽」的理由 | **要改**（若查实） |

### 缺什么

| 问题 | 要查什么 |
|---|---|
| `uint64` 属性能否通过 UHT 全流程（含 `UPROPERTY(BlueprintReadOnly)` 的组合） | 实际编译一个带 `uint64` 属性且标 `BlueprintReadOnly` 的 `USTRUCT` |
| 若 UHT 放行，蓝图侧是报错还是静默降级 | 同上，看编辑器与编译日志 |
| 非蓝图（纯 C++ 反射）路径下 `uint64` 是否无限制 | 反射遍历 / 序列化路径 |

**为什么不用 grep 直接定论**：`UhtUInt64Property.cs` 的存在只证明「关键字被识别」，不证明「`BlueprintReadOnly` 组合能过 UHT 校验」。**按 5.7，读到的源码必须能覆盖到被判定的那条路径。**

**处置**：族内该句已标 ⚠️ 待查并指向本节；**在查实前 MUST NOT 据此理由改动任何句柄宽度**。

### 结论（2026-11-02）

**问题问错了对象。** 本节的三个「缺什么」全都在问 **UHT** 放不放行——但结论不依赖那个问题的答案：

| 分支 | 结果 |
|---|---|
| UHT 放行 `uint64` + `BlueprintReadOnly` | 蓝图侧没有 `uint64` 引脚映射（`EdGraphSchema_K2` 对 `FUInt64Property` 零分支），**句柄在蓝图里用不了** |
| UHT 报错 | `uint64` 属性根本建不出来 |

⇒ **两条分支都指向同一结论：蓝图可见的句柄 MUST 用 `int64`。** 所谓「待查」只影响「失败发生在编译期还是暴露期」，不影响判据。

**已核实的定位点**：`EdGraphSchema_K2.cpp:3516` 处理 `FInt64Property`；全 `BlueprintGraph` 模块对 `UInt64` 零命中。

**族内已改为不带待查标记的表述**（`运行时实例.md` §1.3.1），理由从「UHT 不支持」改为「蓝图侧没有 `uint64` 引脚」。

**仍然建议做的一次实证**（不阻塞任何结论）：编译一个带 `uint64` + `BlueprintReadOnly` 的 `USTRUCT`，确认失败发生在编译期还是暴露期——这只影响报错体验，不影响宽度选择。

## 8. 伤害记录的形状与事件（Damage 域）

**已裁的大方向（2026-11-11，D35）**：「游戏结算统计」拆两层——**机制归插件**（事件 + 记录形状 + 读取路径），**业务口径归宿主**（什么值得统计、报表口径、上报目标与频率）。

> **注意**：**统计口径本身已裁为「不建」**，写在 [01-定位与判据 §1.2](../../tcs-remake-v2/01-定位与判据.md) 非目标清单 ③。本节只管**插件该给的那一半**——记录形状与投递事件。

**未裁的部分**（归 Damage 域）：

| # | 问题 | 说明 |
|---|---|---|
| ① | 伤害记录结构的形状 | 哪些字段、是否扁平可反射 |
| ② | 伤害记录事件的 **Tag 名** | 本轮**MUST NOT** 钉死；写作时用「伤害记录事件（名称归 Damage 域裁）」 |
| ③ | 是否由插件提供环形缓冲 | 还是宿主自建；若要给，容量与满了怎么办 |
| ④ | 记录是否带「每键修改器贡献清单」 | **已有反向判据**：千人战场是量灾难；「这个数怎么算出来的」走聚合器的明细入口，不靠记录 |

> **③ 的边界**：插件给环形缓冲**不算猜宿主词汇**（缓冲是载体，不是口径）；但**带过滤条件的查询口**算。这一条本身仍待裁。

> **V1 参照形态（**V1 名**，不是 V2 契约）**：`FTcsDamageRecord`（`Source/TcsDamage/Public/Flow/TcsDamageRecord.h`）扁平可反射，含 `FlowId` / `Source` / `Target` / `Base` / `Final` / `Executed` / `Absorbed` / `bKill` / `Sequence` / `Timestamp`；事件经总线立即通道同步派发。

> **一条已有的硬边界**：统计需要「保存」，而 EventBus **MUST NOT 保存、缓存或重放任何载荷**（[事件总线 §0.1](../../tcs-remake-v2/02-核心基线/事件总线.md)）。⇒ 要留存就必须有独立的消费端缓冲，不能指望总线代劳。

## 9. V2 没有事件 Tag 的命名公约

**这是一个既有欠账。**

| 出处 | 写法 |
|---|---|
| V1 全仓 | `TcsEvent.<域>.<事件名>`（点分，走 `UE_DEFINE_GAMEPLAY_TAG_COMMENT`） |
| V2 [00-跨基线时序](../../tcs-remake-v2/02-核心基线/00-跨基线时序.md) | `Event.Skill.Cast`（点分，**无** `Tcs` 前缀） |
| V2 [Attribute.md](../../tcs-remake-v2/04-领域/Attribute.md) | `Event.Attribute.Changed` / `Event.Attribute.Presence`（同上） |

⇒ **两处写法已经不一致**，而 `03-词汇与命名.md` 无此条。

**为什么现在不能顺手钉死**：这三处出现的都是**领域占位符号**（`00-跨基线时序.md` §0 已声明「不构成本文件的机制」），不是契约。若此刻按其中一处定公约，另一处就要跟着改，而定公约的时机应当是**事件命名真正开始被消费**的时候。

**缺什么裁决**：

| # | 问题 |
|---|---|
| ① | 前缀用不用 `Tcs`（V1 用，V2 现有写法不用） |
| ② | 段数固定几段：`<域>.<事件>` 还是 `<域>.<子域>.<事件>` |
| ③ | 这条公约住哪——`03-词汇与命名.md` 还是 [GameplayTag](../../tcs-remake-v2/02-核心基线/GameplayTag.md) |
| ④ | 与本项目的 tag 治理规范如何对齐 |

> **MUST NOT 改动任何一处现有写法**——等公约裁了一起改。
