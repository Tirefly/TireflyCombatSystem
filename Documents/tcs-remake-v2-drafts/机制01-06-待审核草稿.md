## 机制 1｜实例池 `TTcsInstancePool`

| 字段 | 内容 |
|---|---|
| **1 机制** | 稠密数组 + FreeList 复用 + 代际防悬空的泛型实例池。把「是否在册」编码进代际奇偶位（奇 = 已分配 / 偶 = 空闲），于是 `ForEach` 与 `IsValid` 都不需要额外位图。 |
| **2 设计原因** | **出处：`LOG-00-core` D0-2 / D0-4 + `spec/01-module-m0-core.md` §2.1**。<br>D0-2 原文给出三方案：A `FGuid`（无池定位能力）/ **B 索引+代际（推荐）** / C TCS 现状式（`UObject` + 弱引用 + 单调 int32）。选 B 的理由：「O(1) 池定位，代际校验捕获悬空引用，是「USTRUCT+句柄+池」既定裁决的自然实现」，并明确标注「**净新增设计，TCS 无先例**」。<br>D0-4 原文：A 线程安全池（为未来多线程留路）/ **B 单游戏线程假设 + 断言（推荐）**——「不加锁成本；越界即断言失败暴露架构违规。真需要并行时再升级」。<br>附加约束（D0-2）：**每实例类型独立强类型句柄**，禁止通用句柄互串。 |
| **3 业务需求** | **LAC**：强。Buff 实例进出频繁，回合间大量创建/销毁。<br>**动作游戏**：强。技能实例与链运行态高频分配。<br>**幸存者**：**最强**。千级实体 × 十几个 Buff，分配器不稳就会碎片化。 |
| **4 消费者现状** | **真实 5 处**：`FTcsExpiryHeap`（条目池）、`FTcsEventBus`（订阅池）、`TcsEffect`（`RunPool`）、`TcsSkill`（`SkillInstances`）、`TcsState`（per-entity 桶）。<br>`TcsCoreStats.cpp:67` 的 `FAnchorInstance` 是**编译锚点**，不算消费者。 |
| **5 消费者归属** | **框架机制决定**——五个消费者都是框架自己的运行时容器，不由宿主决定时机。 |
| **6 是否重构** | **改造**。池本身是对的，但**它同时承担了两件不同的事**：① 池化复用；② 代际身份。<br>证据：per-entity 桶为了复用这套代码，不得不注入**进程级发号器**（`FTcsStateGenerationIssuer`）。`TcsInstancePool.h` 头注原文说明原因：各桶各自从 1 发号会导致「跨桶扫描式解析**命中错实体**」。<br>⇒ **句柄的生成规则**与**槽位复用规则**是两件事，被强行塞进同一个模板参数。 |
| **7 V2 处置** | 池保留；**把代际发号从模板参数里抽出来**，做成独立的句柄生成器。per-entity 桶不再需要注入特殊策略。<br>「零策略纪律」（`Free` 不清零内容、`Reset` 不逐槽清理）保留——它把资源清理责任显式留在调用方，是对的。 |

**要带走的精华**：代际奇偶簿记。零位图、零额外内存，且「是否为良构句柄」可静态判断。

## 机制 2｜到期堆 `FTcsExpiryHeap`

| 字段 | 内容 |
|---|---|
| **1 机制** | 最小堆 + 池化条目 + 惰性取消。**先换出当前到期集，再逐项回调**——回调内新入堆的条目归下一次 `AdvanceTo`。 |
| **2 设计原因** | **出处：`LOG-00-core` 的 M3 部分 + `spec/01-module-m0-core.md` §2.3 + `spec/03-module-states.md:114`**。<br>原文：「`FExpiryHeap`：按到期时间排序的最小堆；惰性删除 + 代际校验；**帧成本 = 到期项数**。服务 M3 到期、M4 定时步骤、M5 冷却。」<br>「先换出再回调」的纪律与事件总线的帧末冲洗同源（见机制 5），目的是**帧成本有界 + 防自激**。 |
| **3 业务需求** | **LAC**：强。Buff 持续时间、技能冷却、回合结束判定。<br>**动作游戏**：强，**但不够**——需要帧对齐（动画通知）与取消窗口，而当前只有「绝对时刻到期」。<br>**幸存者**：强。千级实体同时挂 Buff，到期量巨大。 |
| **4 消费者现状** | **6 处**：`TcsBuff`（寿命 `ExpiryEntry` + 周期 `PeriodEntry`）、`TcsEffect`（`StepWaitDelay` / `StepWaitEvent` 超时）、`TcsSkill`（冷却 + 相位）。 |
| **5 消费者归属** | **框架机制决定**。 |
| **6 是否重构** | **保留结构，改造回调签名**。<br>`OwnerId` 是 `uint64`，注释写「堆零领域词汇——回调按 OwnerId 归还归属」。这是刻意的去领域化，但代价是**到期时只能拿到一个数字**。`TcsCastOps_Phase.cpp` 为此写了专门的「重查」逻辑（含约 60 行注释解释为什么必须重查）。<br>⇒ 每个消费者各写一遍「这个数字现在还是谁」是可预见的成本。 |
| **7 V2 处置** | 「先换出再回调」纪律**原样保留**（这是本项最有价值的资产）。<br>`OwnerId` 改为**强类型句柄**，并配一条契约：到期回调必然拿到有效句柄，或明确拿到「已失效」信号——**不让每个消费者各自实现重查**。<br>帧对齐需求（动作游戏）不在 V2 第一版做，但**不要用「绝对时刻」把结构堵死**。 |

**要带走的精华**：先换出、再回调。帧成本有界，且回调内入堆天然归下一拍。

## 机制 3｜战斗时钟与泵（`FTcsClock` + `UTcsClockSubsystem`）

| 字段 | 内容 |
|---|---|
| **1 机制** | 全插件唯一取时入口（帧号 + 累计 ScaledDt + 本帧步长）。世界级子系统在 `FWorldDelegates::OnWorldTickStart`（`UWorld::Tick` 头部）驱动**固定四步泵序**：① 时间源取步长 → ② 时钟推进 → ③ 总线帧末冲洗 → ④ 到期堆 `AdvanceTo`。 |
| **2 设计原因** | **出处：`LOG-00-core` D0-5 + `decisions/dec-2026-08-31-tick-pump.md` 全文 + `log/log-04-integration-m6.md` D6-5**。<br>**D0-5 原文**：A 各组件自行 Tick（「回到 TCS 模式，时序散乱」）/ **B 单一 `UTickableWorldSubsystem` 泵 + `FCombatClock` 封装（推荐）**——「内部默认 `World DeltaSeconds × TimeDilation`，**时间源做成可注入接口（`ITimeSource`），宿主项目可替换（如回合制注入「回合数即时间」）**」。<br>**tick-pump 决策（裁决 2b）** 给出更完整的三层职责划分：TickableWorldSubsystem 管秩序（泵序 / ScaledDt 供给 / 暂停变速 / Tickable 注册表 / 总线帧末泵）｜ActorComponent 管状态与本地执行（持 Buff 容器 / 技能游标，`TickCombat` 内处理本地到期）｜词汇类管逻辑。防止的坏事是**上帝对象**：「每加一种行为都要改集中式执行器 switch」。<br>**D6-5** 追加：「**全部战斗组件不自 `TickComponent`**（TCS 各组件自 Tick 的反面）——M0 时钟泵唯一驱动」。 |
| **3 业务需求** | **LAC**：强。回合制下「时间」是抽象推进；当前**用真实帧时间跑回合制**，两者并不冲突。<br>**动作游戏**：强。帧级，需要与动画蒙太奇对齐。<br>**幸存者**：强。实时 tick，当前设计直接可用。 |
| **4 消费者现状** | `GetClock()` **插件内 12 处 + 宿主 3 处**。泵本身只服务时钟、总线、到期堆三者。 |
| **5 消费者归属** | **框架机制决定**——时钟是机制底座，不归宿主。 |
| **6 是否重构** | **泵保留，但发现一处重大形态漂移**。<br>**决策文档里的设计形态**（`dec-2026-08-31-tick-pump.md` §5–§7）是：`ICombatTicker` 接口 + `Tickables` 注册表 + 每组件 `TickCombat(ScaledDt)` + **帧结构三拍**（泵组件 → 总线 Flush → 本地清扫）。<br>**实测落地**：`ICombatTicker` / `TickCombat` 在整个 `Source/` **0 命中**。落地的形态是「**没有任何 per-component tick**」——所有周期行为改由到期堆（时间维度）与事件总线（事件维度）驱动。<br>组件头注释写的是「不自 `TickComponent`（D6-5：M0 泵唯一驱动）」，**它兑现的是 D6-5 的字面，而不是裁决 2b 的形态。** |
| **7 V2 处置** | **泵序保留**（四步顺序有明确理由：时钟必须先推进，帧末冲洗须早于到期堆）。<br>**形态漂移必须记为 V2 的正向结论**：取消 per-component tick 比原设计的「pump 逐组件调 `TickCombat`」更好——后者在千级实体下就是 1000 次虚调用/帧，而到期堆是「帧成本 = 到期项数」。<br>⇒ **V2 明确采纳「无 per-component tick」**，并把 `ICombatTicker` 这一层设计从总纲里划掉。 |

**要注意的一条**：这是本轮发现的第一处「**决策文档写得比落地更复杂，而落地更简单也更好**」。它说明 `combat-system-design/` 里的部分「已定」内容其实从未落地，且**没落地是对的**。

## 机制 4｜事件总线（`FTcsEventBus` + `UTcsEventBusSubsystem`）

| 字段 | 内容 |
|---|---|
| **1 机制** | Tag 路由 + 订阅表（`TMultiMap<FGameplayTag, Handle>`）+ 池化订阅记录 + 共享 Handler UObject。派发前快照同 Tag 订阅句柄，逐目标校验代际；失效订阅惰性摘除。 |
| **2 设计原因** | **出处：`decisions/dec-2026-08-31-event-bus.md` 全文（裁决 2a）+ `LOG-00-core` D0-3**。<br>起因是一个真问题：裁决 2 选定 RuntimeInstance = USTRUCT + 句柄 + 容器后，**UStruct 无法监听 UE Delegate**（`AddUObject` 需要对象身份）。<br>决策文档的答案是「监听的是**共享 Handler 类**，实例作为视图参数被路由」——逻辑住在永生 Handler UClass 上，状态住在短命 struct 实例里。**短命实例永远不做 `AddUObject`**。<br>三条纪律：① 生命周期闭合（Apply/Remove 时同步注册/注销）；② **事件分级**（查询类立即、状态类帧末）；③ 溢出策略自定。<br>§8「这笔 rent 换回什么」列了四条收益：生命周期安全 / 顺序与确定性 / 单点可观测 / 同构红利。 |
| **3 业务需求** | **LAC**：强。跨实体联动（Buff 连锁、伤害触发）必须有序且可回放。<br>**动作游戏**：强。<br>**幸存者**：**需重新评估**——千级实体 × 高频事件下，Tag→MultiFind→遍历 的成本需要实测。 |
| **4 消费者现状** | **发布 11 处**（Attribute 1 / Buff 2 / Damage 2 / Skill 4 / Effect 2）。<br>**订阅 3 处**：`TcsChainEventWaitRegistry`、`TcsTriggerRegistry`（均在 `TcsEffect`）、`TcsBuffBehaviorRegistry`（`TcsBuff`）。 |
| **5 消费者归属** | **框架机制决定**（三个订阅者都是框架自己的机制）。 |
| **6 是否重构** | **改造，两处硬伤**。<br>**硬伤 A｜注册口形状错**：`Subscribe(Tag, UTcsEventHandler*, Dispatch)` 只收 `UObject*`，传不了 lambda，且**派发只传 `(EventTag, Payload)`、不传订阅句柄**。后果是三个消费者**各自写了一遍**「每 tag 一条订阅 + 计数配对 + 生命周期摘除」。`TcsChainEventWaitRegistry.h` 头注原文：「每条等待各订一次并不能让回调自辨身份（收益为零、成本为正）」。<br>**硬伤 B｜能力位是给 struct 世界设计的，而实际消费者都需要 tag→句柄**：决策文档的「实例作为视图参数被路由」在这三个消费者里**一条都没用上**——它们要的都是「这个 tag 来了，按我自己的表找到相关的实例」。 |
| **7 V2 处置** | **注册口直接收回调**（`TFunction` 或函数对象），不再要求派生 `UObject`。沿用铁律 3。<br>**保留**：派发前快照 + 代际校验 + 惰性摘除（这三条正确且必要）。<br>**保留**：共享 Handler 作为**可选**形态（它是给「逻辑无状态、可被脚本继承」的场景准备的），但 MUST NOT 作为唯一通道——否则每个消费者都得派生一个空 `UObject`。<br>**待实测**：千级实体下 `TMultiMap::MultiFind` 的开销。若成瓶颈，改为按 Tag 分桶的 `TArray`。 |

## 机制 5｜帧末通道（`EED_FrameEnd` + `FlushFrameEnd`）

| 字段 | 内容 |
|---|---|
| **1 机制** | 第二种派发语义：`PublishFrameEnd` 入队（持载荷副本），由时钟泵第三步「换出队列 → 按入队序派发」。冲洗期间新入队的事件归下一拍。 |
| **2 设计原因** | **出处：`decisions/dec-2026-08-31-event-bus.md` §5 纪律 2**。<br>原文：「**事件分级**：查询类事件（能否施法）立即同步返回；状态类事件（伤害/死亡）帧末统一泵，Buff 连锁产生的新事件下一轮处理——**重入与无限循环被结构性切断**。」<br>`LOG-00-core` D0-3 也写了「M0 总线需先提供两种通道（立即 + 帧末队列）」。 |
| **3 业务需求** | **LAC**：设计意图强（防 Buff 连锁重入）。<br>**动作游戏**：**可能冲突**——同一帧内必须完成的事件（伤害判定 → 死亡 → 表现）延迟一拍会破坏手感。`TcsEffect` 的 `effect-trigger` 规格已经踩到这个点：「收集协议要求修正提交落在事件发布返回之前……订帧末会让修正晚一拍」。<br>**幸存者**：中性。 |
| **4 消费者现状** | **零发布者**。`PublishFrameEnd` 在整个 `Source/` 的业务调用点 = **0**（`PublishImmediate` = 11）。但时钟泵**每帧无条件调用** `FlushFrameEndQueue()`。 |
| **5 消费者归属** | **零消费者设施**，且属于「本该有消费者」的那一档（见 [01-定位与判据](../01-定位与判据.md) §3.1）。 |
| **6 是否重构** | **砍掉，但保留判据**。<br>**它的设计意图成立**（防重入），**但它从未实现**——根因是一条**从未答完的必答题**：<br>· `dec-2026-08-31-event-bus.md` §9 待定项：「**事件分级清单**（哪些事件同步立即、哪些帧末泵——按语义逐个裁决）」；<br>· `decisions/dec-2026-09-01-abilitykit.md:30` 把它**升级为必答题**：「否则「查询类立即返回」无处安放」；<br>· `log/log-00-core-m0m2.md` 的 D0-3 附注：「同步立即派发 vs 帧末泵的事件分类表是 M4a 决策点」。<br>**三次被点名，零次被回答**。于是通道建好了、泵每帧跑着、没有任何事件走它。 |
| **7 V2 处置** | **第一版砍掉帧末通道**，只保留立即派发。<br>**理由不是「帧末不好」**，而是「没有事件分类表的情况下，一个通道的存在只是每帧一次空函数调用」。<br>**保留的判据**：如果将来某个事件确实需要延迟一拍（防重入），那时**先写清分类表**，再加通道——一次只加一条通道，且它必须当场有发布者。 |

## 机制 6｜异步监听节点 `UTcsAsyncAction_ListenForCombatEvent`

| 字段 | 内容 |
|---|---|
| **1 机制** | 蓝图/脚本侧的事件订阅入口。绑 `UTcsEventBusSubsystem::OnEvent`（`BlueprintAssignable` 动态多播），在回调内按 Tag + 载荷类型过滤，命中才广播自身 `OnEvent`。 |
| **2 设计原因** | **出处：`LOG-00-core` 的 M9 收尾轮「A'」+ `spec/01-module-m0-core.md` §2.2**。<br>原文：「**BP/CS 动态监听层（M9 收尾轮拍板 A'，Lyra GMS 形态）**：router 内泛化动态多播 `(EventTag, FInstancedStruct)`……`UTcsAsyncAction_ListenForCombatEvent{Tag 过滤, PayloadType 类型匹配过滤, MatchType(精确/部分)}` 提供「绑定即过滤」的 BP/CS 订阅入口」。<br>同时明确标了验证项：「BP `InstancedStruct` 节点面版本覆盖、CS 读 `FInstancedStruct` 载荷实测」——**两条都未执行**。 |
| **3 业务需求** | **LAC**：低。宿主用 C#，且走的是 `TcsDev` 的直调装置。<br>**动作游戏**：中。若表现层用 BP 订阅战斗事件，这个入口有意义。<br>**幸存者**：低。 |
| **4 消费者现状** | **零**。C++ 侧 0 处，`TcsDev` 也不使用（`TcsDev` 走属性/技能/伤害门面直调）。 |
| **5 消费者归属** | **零消费者设施**。它是给**宿主**准备的（BP/CS 订阅面），所以「插件内零调用」本身正常；但它连一次真实使用都没有，**契约从未受检验**（§3.1 第二道判据）。 |
| **6 是否重构** | **保留，降级为可选模块**。<br>它与 `OnEvent` 动态多播是**一对重复入口**：`OnEvent` 已经是「全量事件流 + 绑定者自行过滤」，而 AsyncAction 是「绑定即过滤的封装」。在零使用的前提下，**两个入口只保留一个**就够。<br>V1 的问题不是建了它，而是**建了两个都没验证过的东西**。 |
| **7 V2 处置** | **第一版只保留 `OnEvent` 动态多播**（一个入口，最小面积）。<br>AsyncAction 作为「宿主用 BP 订阅时的便利封装」**推迟到第一个真实 BP 消费者出现**——那时再建，且必须同批补上 V1 欠的那两条验证。 |

## 复盘小结（1–6）

| 机制 | 判定 | 一句话 |
|---|---|---|
| 实例池 | **改造** | 池对，代际发号要从模板参数里抽出来 |
| 到期堆 | **改造** | 结构对，`OwnerId` 要变强类型句柄 |
| 时钟与泵 | **保留 + 划掉一层设计** | 「无 per-component tick」比原设计更好 |
| 事件总线 | **改造** | 注册口必须能收回调 |
| 帧末通道 | **砍** | 三次点名、零次回答的分类表导致空转 |
| 异步监听 | **降级** | 与 `OnEvent` 重复，且两条验证都没做 |

**这一组的共同病因只有一条**：

> **每建一个机制，先建「通道」，后找「事件」。而「事件分类」这件事从来没被做完，于是通道空转。**

V2 的顺序必须反过来：**先有事件（真实消费者），再决定用什么通道。**
