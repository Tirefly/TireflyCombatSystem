| **4 消费者现状** | 全插件。发号器 `FTcsCombatEntityHandleRegistry` 由 `UTcsAttributeSubsystem` 持有，`RegisterEntity` 插件内 2 处（实体组件 / 查询映射），宿主 0 处。 |
| **5 消费者归属** | 句柄本身：**框架机制**。发号：**框架机制**（但归属错位，见 6）。 |
| **6 是否重构** | **改造，这是本域最严重的归属问题**。<br>**证据**：一个「实体」的身份、发号、查询分居**三个模块**——<br>· 句柄类型住 `TcsCore`（依赖倒置让步）；<br>· **发号器由 `UTcsAttributeSubsystem` 持有**（属性模块在给整个战斗系统发实体号）；<br>· 查询契约 `ITcsEntityQuery` 住 `TcsCore`，实现住 `TcsIntegration`（`UTcsPieEntityQuery`）。<br>代码自己也承认这是临时的：「R3 由 M2 门面（`UTcsAttributeSubsystem::RegisterEntity`）发号，M6 世界注册表落地后**移交发号**」——而 M6 世界注册表（`UCombatWorldRegistrySubsystem`）**从未落地**。 |

## 机制 9｜属性定义 · 账本 · 容器（`UTcsAttributeDef` / `FTcsAttributeInstance` / `FTcsAttributeStore`）

| 字段 | 内容 |
|---|---|
| **1 机制** | 三段式：**定义资产**（`FTcsAttributeDefData`：BaseValue / Bounds / ValueDomain / OverrideTieBreak）→ **账本实例**（`FTcsAttributeInstance`：BaseValue + CachedCurrent + bDirty + Bounds + `AttrModInstances`）→ **每实体容器**（`FTcsAttributeStore`：Attributes / FrozenAttributes / Dependents / BatchDepth）。<br>另有**冻结/解冻**语义：`RemoveAttribute` 不销毁，搬入 `FrozenAttributes`；`AddAttribute` 优先解冻。 |
| **2 设计原因** | **出处：`LOG-00-core` D2-8 / D2-9 / D2-4 / D2-5**。<br>**D2-8** 定死数据宿主形态：「`UCombatAttributeSubsystem`(World) → `FAttributeStore`(句柄键控) → `FAttributeInstance{Base/CachedCurrent/Dirty/Bounds/ModifierSlots}`；Base = 宿主升级事务写入（等级→数值归项目）；**Current = 派生缓存非权威**」。<br>**D2-9**：「权威 = DefId（非指针）；热路径 = 解析缓存；**热路径零回查 Def**（信息进快照，否则 = 设计漏洞）」。<br>**D2-4**：「管线末端统一 clamp，边界三态可选（None / Static / **Dynamic = 另一属性**）」——「「最大生命上限降低」类 debuff 因此是纯数据行」。<br>**D2-5**：写时标脏 + 读时惰性重算 + 唯一提交点。<br>**双轨制（2026-09-17 用户拍板）**：表行 = 编辑期载体，资产 = 运行期载体，「运行期零 DataTable 加载路径」。 |
| **3 业务需求** | **LAC**：强。属性是数值地基。<br>**动作游戏**：强。<br>**幸存者**：强，但 **`FrozenAttributes` 的冻结/解冻语义存疑**——千级实体高频创建销毁时，「保留而非销毁」意味着暂存区会持续持有不再使用的实例。 |
| **4 消费者现状** | `TcsBuff`（修正器物化）、`TcsSkill`（Cost 读基值）、`TcsDamage`（流程属性容器）、`TcsEffect`（属性访问薄壳）。**健康**。 |
| **5 消费者归属** | **框架机制决定**（属性是框架的领域机制，不由宿主决定时机）。<br>但 `AddAttribute` / `RemoveAttribute` 是**业务向入口**（用户 2026-10-24 裁定）。实测：`AddAttribute` 插件内 0 / 装置 3；`RemoveAttribute` 插件内 0 / **装置 0**。 |
| **6 是否重构** | **保留，两处要重新论证**。<br>**核心三段式保留**：定义/账本/容器分离、「Current 是派生缓存非权威」、脏标记惰性重算——这三条都经受了完整实现的检验。<br>**`FrozenAttributes` 冻结语义要重估**：设计意图是「移除属性不等于销毁，回来时整条恢复」。这在自走棋（回合复用）里成立，但在幸存者（千级实体生灭）里，暂存区可能永不清理。<br>**双轨制（DataTable + 资产）存疑**：两轨一致性**靠一个人工维护的同步器**（`08 §5`，而该同步器从未实现，见 `TOOLS-3`）。这是典型的「双份真相 + 人工同步」。 |
| **7 V2 处置** | **三段式保留。**<br>`FrozenAttributes`：**改为可选能力**（默认销毁，需要复用时显式开启）。<br>**双轨制改为单轨**：只保留资产轨。DataTable 的批量编辑便利可以用「资产列表视图」替代，而不是再维护一份数据 + 一个同步器。<br>**业务向入口必须配装置走过**——`RemoveAttribute` 今天零调用是契约未受检验。 |

## 机制 10｜属性聚合管线 `FTcsAttributePipeline`

| 字段 | 内容 |
|---|---|
| **1 机制** | 值的唯一生产者与变更的唯一记账口。职责：脏则重算（收集 → 折叠 → 值域收口 → 写缓存）｜事务批与唯一提交点｜**读即登记依赖边** + 成环拒绝｜变化广播（epsilon 1e-5）｜按来源级联摘除。 |
| **2 设计原因** | **出处：`LOG-00-core` D2-3 / D2-4 / D2-5 + `decisions/dec-00-constitution.md` §2「反面平衡」**。<br>**D2-3（属性间依赖）** 三方案：A 不支持（「必然长出野生的同步代码」）/ **B 读即登记（推荐，TCS 已验证机制）** / C 显式声明 DAG（「属净新增，且声明与实际读取可能不一致」）。选 B 的关键理由：**策划零声明负担**。<br>规格还明确记了两条 TCS 的坑：「TCS 深链 >8 跳会被 clamp 轮上限**误判为环**——新系统需把「重算轮数上限」与「环判定」**解耦**」。<br>**宪法 §2** 独立印证：「属性管线（fixpoint 过滤 + 拓扑排序 + 单事务提交 + TG_PostUpdateWork flush + ongoing clamp）是调研确认「**做对了**」的部分……**思路全收、代码重写**」。 |
| **3 业务需求** | **LAC**：**极强**。派生属性（MaxHP ≤ 等级上限、Attack = Strength × 2）是自走棋的核心数值结构。<br>**动作游戏**：强。<br>**幸存者**：强，但**多轮扫描至收敛**在千级实体 × 复杂依赖下需要实测。 |
| **4 消费者现状** | `TcsBuff`、`TcsSkill`、`TcsDamage`、`TcsEffect` 四域驱动。`UTcsAttributeSubsystem::Resolve(World)` 是统一解析点。 |
| **5 消费者归属** | **框架机制决定**。 |
| **6 是否重构** | **保留，且是本域最有价值的资产**。<br>它做对的三件事：① **读即登记**（策划零声明负担，且不会声明与实现不一致）；② **单事务提交**（批内多次变更只重算一次）；③ **环检测与重算轮数解耦**（`TcsAttributePipeline.cpp:22` 明写：「重算收敛轮数的**安全网**（MUST NOT 作为环判据——环由 `RegisterDependency` 的 SCC 检测负责」——**这条正是 D2-3 记录的 TCS 缺陷的修正**）。<br>**一处观察**：`PeekPending`（未提交候选值预览）被三处规格当作机制引用，但它的消费者是表现层预览，而表现层模块（`TcsCue`）不存在。 |
| **7 V2 处置** | **原样继承。**<br>这是 V2 最不该动的部分——它的正确性有「宪法」级别的独立确认，且修正了 TCS 的真实缺陷。<br>`PeekPending` 保留（它是事务语义的自然产物，且动作游戏的「预判显示」会需要它）。 |

**要带走的精华**：读即登记。把「依赖关系的声明」变成「依赖关系的观测」——避免了两份真相。

## 机制 11｜带式折叠器 `FoldTcsAttributeBands`

| 字段 | 内容 |
|---|---|
| **1 机制** | 纯函数。封闭五带（Override / Add / PercentAdd / Mul / FlatAdd）。存在 Override 时按「优先级 → 同优先级策略 → 有符号值」**三级全序**选出一条直接作为结果；否则 `Final = ((Base + ΣAdd) × (1 + ΣPercentAdd)) × ΠMul + ΣFlatAdd`。**顺序无关**。 |
| **2 设计原因** | **出处：`LOG-00-core` D2-10 / D2-16 + `spec/02-module-attributes.md` §2.2**。<br>**D5-5 v3（2026-09-14）**：「本式 + Override 覆盖语义抽为一个纯函数**住本模块**，M5 参数链与 TcsDamage 流程属性容器**共用**」——归属依据：「三个消费者的编译边都已含 `TcsAttribute`（零新边）」。<br>**D2-16（2026-09-18 拍板）** 是这份设计里最值得读的一段：原口径「取 Override 组最大值」隐含「数值大 = 更强」，而**数值本身不含方向**——「对护甲（越大越强）对，对承伤倍率/冷却（越小越强）就取到最温和的一条，**同一套规则不可能两边都对**」。<br>决策文档还留了完整的**被否方案表（5 条）**与各自的否决理由——这是 V1 里少见的、把「为什么否决」写全的地方。 |
| **3 业务需求** | 三款游戏需要同一套数值聚合语义。**通用性最强的一个机制**。 |
| **4 消费者现状** | **3 处**：`TcsAttributePipeline.cpp:251`（M2 聚合）、`TcsParamChain_Evaluate.cpp:98`（技能参数链）、`TcsFlowAttributes.cpp:45`（伤害流程属性）。<br>`TcsSkill` 有纪律注释：「全模块唯一一处 `FoldTcsAttributeBands` 调用」。 |
| **5 消费者归属** | **框架机制决定**。 |
| **6 是否重构** | **原样保留。这是 V1 最佳设计。**<br>三个理由：<br>① **单一实现**（不是「同一形状各写一遍」，而是真的只有一个函数）；<br>② **顺序无关有严格证明**（三级比较构成全序，且比较一律用**精确关系**而非近似相等，避免破坏传递性）；<br>③ **封闭性有论证**（五带不开放 Custom op、OverrideTieBreak 不开放自定义——「热路径上的比较函数必须**全域且确定**」）。 |
| **7 V2 处置** | **原样继承。** |

**要带走的精华**：<br>· **数值本身不含方向**——任何「取最大/最小」的规则都要先问「这个字段的语义方向是什么」。<br>· **封闭枚举 + 明确拒绝理由**——比开放扩展更能保护热路径的正确性。

| **5 消费者归属** | **框架机制决定**。 |
| **6 是否重构** | **保留。这是一个「正确的留白」**——它没有违反纪律，因为：① 已建的那个方法有 4 个真实消费者；② 未建的方法明确标了「零消费者不预建」且写明了将来的消费者是谁。 |
| **7 V2 处置** | **保留，并把「留白要写清将来消费者是谁」这条做法推广。**<br>V1 的很多留白只写「未实现」，没写「将来谁会要」——这导致读者分不清「忘了」和「决定不做」。 |

## 机制 14｜值约定 `TcsNotation`（`ETcsValueConventionFlag` + `ConvertToCanonical`）

| 字段 | 内容 |
|---|---|
| **1 机制** | 策划语言值 ↔ 规范值的转换。四标志位：`Percent`（÷100）/ `OneMinus`（1−v）/ `Negate`（取负），**固定组合顺序**转换。无状态静态助手，**转换只发生在物化/注册边界**。 |
| **2 设计原因** | **出处：`decisions/dec-02-fold-display.md` 的 D5-18 v3**。<br>核心问题是「**哪些源可以配约定**」，解法是**能力位虚函数**而不是中心名单：`FTcsParamValueSource::AllowsValueConvention()`——注释明文：「消费方一律走本虚函数——**不得建立「源类型 × 可配约定」的中心名单或 switch**」。<br>ParamRef 与 AttributeScaled 覆写为 false，理由是「读到的已是规范值，再转 = 二次转换」。 |
| **3 业务需求** | **LAC**：强。策划写「减少 25%」比写 0.75 自然得多。<br>**动作游戏 / 幸存者**：同等需要。 |
| **4 消费者现状** | `TcsAttribute`（`TcsAttrModDef.cpp:67/75`）、`TcsBuff`（`TcsBuffDefAsset.cpp:127` / `TcsBuffModifierMaterializer.cpp:79` / `TcsBuffOps_Snapshot.cpp:72`）。**健康，且是跨模块契约**。 |
| **5 消费者归属** | **框架机制决定**。 |
| **6 是否重构** | **内容保留，载体重新论证**。<br>**它是整个 `TcsNotation` 模块（92 行 / 5 文件 / 独立编译单元）唯一的内容**。为这一个枚举开一个模块的代价是：多一个 `Build.cs`、多一个日志通道、多一次编译、多一条依赖边（`TcsAttribute` 与 `TcsBuff` 都要依赖它）。<br>**但它的设计判断是对的**：能力位虚函数优于中心名单（这正是 V2 铁律 1 的正面例子）。 |
| **7 V2 处置** | **机制保留，模块取消。**<br>值约定并入「数值与参数」域，不再独立成模块。<br>**能力位虚函数这条做法写入铁律**——「能力探测走虚分派，禁止中心 switch」是可推广的原则（V1 在 `AllowsValueConvention` 与 `GetTcsAttributeBandWeight` 两处都用了它）。 |

## 机制 15｜属性读口 `ITcsAttributeProvider`

| 字段 | 内容 |
|---|---|
| **1 机制** | `UINTERFACE(MinimalAPI)`，三个 `BlueprintNativeEvent`：`GetBaseValue` / `GetCurrentValue` / `PeekPending`。**签名不含实体**（「实体由实现者持有」）。 |
| **2 设计原因** | **出处：`spec/02-module-attributes.md` §2.3**。<br>原文：「属性读侧契约（**M2 对外唯一契约**）：计算器不关心实体载体，宿主适配在此收敛——军官组件 / Mass 存储桶适配器各自绑定自己的实体」。<br>意图是**为 Mass 铺路**：让无 Actor 的实体也能提供属性读取。 |
| **3 业务需求** | **LAC**：低——只有 20 个实体，且都有 Actor。<br>**动作游戏**：低。<br>**幸存者**：**可能强**——如果真用 Mass。但 V1 已裁定「**当前阶段不直接支持 Mass**」（`log-04-integration-m6.md` v2 修正 §2）。 |
| **4 消费者现状** | **零实现者**。只有 `FTcsParamSource_AttributeScaled` 一个理论消费者，而它的实际路径是「上下文不匹配或读口缺失 → 落 Fallback」。 |
| **5 消费者归属** | **零消费者设施**——且是「为未来架构（Mass）预留」的那一档，而那个未来架构已被明确排除。 |
| **6 是否重构** | **砍掉。**<br>它对「一个实现者不写接口」的违反是**最严重的**：不是 1 个实现者，是 **0 个**，而且它的**唯一潜在消费者自己也是零消费者**。<br>更关键的是：属性明明有一条**在用的**完整路径（`UTcsAttributeSubsystem::Resolve(World)`，`TcsBuff` 与 `TcsEffect` 都走它）。引入第二条读取路径本身就是设计问题。 |
| **7 V2 处置** | **删除。**<br>属性读取**只有一条路**：属性门面。<br>如果将来真需要 Mass 支持，那不是「加个接口」，而是「让桶适配器实现同一套门面契约」——**一条路，不是两条**。 |

## 机制 16｜实体查询契约 `ITcsEntityQuery`

| 字段 | 内容 |
|---|---|
| **1 机制** | 四方法：`EnumerateEntities` / `GetLocation` / `IsAlive` / `IsEntityReady`。**框架不持任何「世界有哪些战斗实体」的知识**——遍历、定位、存活都是宿主本体论。 |
| **2 设计原因** | **出处：`TcsEntityQuery.h` 类注释（2026-10-26 归属说明）+ R6 的 Q-11 裁定**。<br>归属判据写得很清楚：「**消费者的最近公共祖先**，不是「哪个模块名字听起来更底层」。四个消费者的 LCA = `TcsCore`」。<br>**`IsAlive` 与 `IsEntityReady` 正交**的理由也是实证的：「`IsAlive` 的 PIE 实现是「映射里还有这个句柄」而**不是「活着」**……拿它当门禁会**双向误判**」。 |
| **3 业务需求** | **LAC**：强（虽然实现是 PIE 简化）。<br>**动作游戏**：**极强**——目标选择、范围判定全靠它。<br>**幸存者**：**极强**——万级实体的空间查询。 |
| **4 消费者现状** | **1 个实现**（`UTcsPieEntityQuery`，住 `TcsIntegration`）。<br>**消费者 4 处**：`TcsEffect`（持注入槽位）、`TcsSkill`（`IsEntityReady` 门禁）、`TcsTargeting`（`GetLocation` 打分）、`TcsIntegration`（实现）。 |
| **5 消费者归属** | **框架机制决定**（框架内部机制在用它）。 |
| **6 是否重构** | **保留，它是合法的 (a) 类接口**（见 [01-定位与判据](../01-定位与判据.md) 铁律 2 的分类）。<br>唯一的缝，唯一实现——但**这个「唯一」是设计意图，不是缺失**：宿主必须填这个契约。<br>**问题在实现质量**：`UTcsPieEntityQuery::IsEntityReady` 直接 `return IsAlive(Entity)`，注释自承「PIE 简化……真项目 MUST 分开覆写」——这是一条**永远不会兑现的承诺**。 |
| **7 V2 处置** | **契约保留，且必须做成「可被真实项目填」的形态**：<br>① 实体世界（见机制 7）落地后，`IsEntityReady` 的判据来自实体状态机，不再是替身；<br>② `EnumerateEntities` 的稳定序遍历在千级实体下要提供**增量 / 范围**变体（幸存者需求）；<br>③ PIE 简化实现**标注为「示例」，不是契约的一部分**。 |

## 机制 17｜池与堆统计 CVar（`FTcsCorePoolStats` / `FTcsCoreHeapStats`）

| 字段 | 内容 |
|---|---|
| **1 机制** | 两个 `FAutoConsoleVariableRef`：`Tcs.Core.PoolSlots`（跨池已分配槽位总数）、`Tcs.Core.ExpiryHeapDepth`（到期堆有效条目数）。无参对（`Add` / `Remove`），正负号歧义在签名上杜绝。 |
| **2 设计原因** | **出处：`LOG-00-core` D0-6**。<br>D0-6 三轮演化的终点是「**日志归 UE 原生分类制、屏显归测试装置/宿主**」，而 TcsCore 的诊断退回两项：「**统计 CVar（池/堆）+ `UTcsDeveloperSettings`**」。 |
| **3 业务需求** | **LAC**：低。<br>**动作游戏**：低。<br>**幸存者**：**高**——千级实体下「池占用了多少槽位」是核心观测指标。 |
| **4 消费者现状** | 池与堆内部调用（维护计数）；读数靠人看 CVar。**无代码消费者**。 |
| **5 消费者归属** | **零消费者设施**，但**属于合法留白**：它是给开发者看的观测面，不是给代码调用的。 |
| **6 是否重构** | **保留。它比看起来重要。**<br>理由：V1 的五个空转机制都没有这种「零成本的观测面」。一个 CVar 的维护成本是每次 Allocate 一个自增——而它换来的是**性能问题发生时能立刻看到数字**。<br>**签名设计值得学**：「增/删为**无参对**——粒度恒为 1，正负号与数量的歧义在签名上杜绝」。 |
| **7 V2 处置** | **原样继承，并推广**：幸存者场景下，池槽位、堆深度、事件派发次数、脏属性数——都应该是 CVar。 |

## 复盘小结（7–18）

| 机制 | 判定 | 一句话 |
|---|---|---|
| 实体身份句柄 | **改造** | 实体必须是一等概念，不能寄居在属性模块下 |
| 来源句柄 | **原样继承** | 「只做归属、不承载因果链」 |
| 属性定义/账本/容器 | **保留 + 双轨改单轨** | 三段式对，冻结语义与 DataTable 轨要重估 |
| 属性聚合管线 | **原样继承** | 读即登记 + 环检测与重算轮数解耦 |
| 带式折叠器 | **原样继承** | V1 最佳设计 |
| 参数值来源体系 | **保留 + 补一处** | AttributeScaled 绕道要宿主接口，应直接走属性门面 |
| 可枚举源基类 | **原样继承** | 正确的留白：已建的有消费者，未建的写了将来是谁 |
| 值约定 | **机制留、模块砍** | 92 行模块只装一个枚举；能力位虚函数是对的 |
| 属性读口 | **砍** | 0 实现者，且属性已有一条在用的路 |
| 实体查询契约 | **保留 + 提升实现质量** | 合法的依赖倒置缝，但 PIE 替身不能当契约 |
| 池/堆统计 CVar | **原样继承并推广** | 零成本观测面 |
| DeveloperSettings | **砍** | 空壳占位，需要时再建 |

**这一组的共同教训**：

> **「为未来准备的接缝」和「为当下服务的机制」，在代码里看起来一模一样。**
> 区分它们的唯一办法不是看设计文档怎么说，而是**数今天的实现者和消费者**。
