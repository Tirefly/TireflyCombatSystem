## 背景

TCS 已经具备 `UTcsAttributeDefinition`、`UTcsStateDefinition`、`UTcsBuffDefinition` 等专用运行时定义资产类，但当前插件并没有为这整套类型提供完整的编辑器自有新建资产流程。中间生成文件表明过去某个阶段可能存在过工厂，但当前工作区里并没有编辑器模块源码，因此这次变更应把编辑器层视为一个缺失能力，并从源码层重新建立它。

最近的 State/Buff 拆分新增了具体类 `UTcsBuffDefinition`，同时也把 `UTcsStateDefinition` 改成了抽象类。这意味着当前编辑器层的范围已经与运行时事实主动失配：一个本该直接创作的定义资产没有出现在编辑器界面上，而另一个已有入口则指向了一个不应再直接实例化的类。

## 目标 / 非目标

- 目标：
  - 为所有应直接创作的具体 TCS 定义资产类型提供一等 Content Browser 创建入口。
  - 移除常见 TCS 流程中的额外 `Data Asset -> 选择父类` 步骤。
  - 保持运行时 Def 资产继续基于 `UPrimaryDataAsset`，确保 `AssetManager` 与既有 `PrimaryAssetId` 语义不变。
  - 让编辑器创作路径兼容未来的 `Def + Fragment[]` 组合模型。
- 非目标：
  - 本次不实现 Def 片段。
  - 本次不做运行时加载或热刷新重构。
  - 本次不做自定义独立资产编辑器工具。
  - 本次不尝试让任意下游 Def 子类自动变成一等创建入口。

## 决策

- 决策：新增专用 `TireflyCombatSystemEditor` 模块。
  - 原因：工厂与资产定义属于编辑器专属关注点，不应污染运行时模块。

- 决策：使用 `UFactory` + `UAssetDefinitionDefault`。
  - 原因：UE 5.6 在 Content Browser 行为层更偏向 `UAssetDefinitionDefault`，而 `UFactory` 仍然是创建新资产的正确路径。

- 决策：内建编辑器入口应覆盖 TCS 当前交付的全部规范、可直接创作的定义资产类型。
  - 原因：插件自有创作流程必须匹配插件真实的定义资产面，而不能停留在一个早于 `UTcsBuffDefinition` 等新具体类型出现之前的旧子集上。

- 决策：抽象 DefinitionAsset 类不应暴露为损坏的直接创建目标。
  - 原因：Content Browser 不应该提供一个最终解析到抽象类的创建入口。如果 `UTcsStateDefinition` 保持抽象，编辑器就必须暴露真正可创作的具体 State 侧定义资产类型，而不是假装抽象基类仍可直接创建。

- 决策：保持 Def 子类化兼容，但不把它当成主要方向。
  - 原因：组合式扩展仍然是更推荐的方向，尤其是在 TCS 未来引入 Def 片段的前提下；但基础系统也不应硬性破坏那些仅为了狭义编辑器校验或默认值而派生 Def 类的团队。

## 风险 / 取舍

- 风险：团队可能会误以为引入插件自有资产分类，就意味着不再允许基于子类的创作。
  - 缓解：文档中明确说明子类化仍然兼容，只是插件只为规范的内建定义资产类型提供工厂。

- 风险：把编辑器面扩到所有定义资产类型后，未来新增具体定义资产类时仍可能再次失配。
  - 缓解：将“新增可直接创作的定义资产类”视为一个显式触发条件，要求同步更新编辑器工厂、资产定义和本 spec。

- 风险：重新引入编辑器模块源码后，可能与过时的中间生成物出现偏差。
  - 缓解：将现有中间生成物视为非权威来源，并以仓库中提交的源码为准重建编辑器层。

## 迁移计划

1. 在插件描述文件中加入 `TireflyCombatSystemEditor`。
2. 重建缺失的编辑器模块源码。
3. 为所有可直接创作的定义资产类型补充或更新工厂，包括 `UTcsBuffDefinition`。
4. 调整抽象 `UTcsStateDefinition` 的入口，确保编辑器不会再指向不可实例化类。
5. 补上对应的资产定义和分类注册。
6. 更新创作文档。
