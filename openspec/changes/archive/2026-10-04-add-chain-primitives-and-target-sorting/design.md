# Design: 链原语批次与目标排序相位

## Context

本变更落在 `PLN-R4` 的 **Task 3.5**（`plan-r4-trigger-row.md`）。触发条件：R4 前三个 Task 已把"事件 → 触发行 → 效果链"的订阅侧与提交侧打通，但链里只有三个原语；同时 P-A 排序相位依"改动点复用"并入本批（本批本就要写提案、改 `TcsChainRun` 结构、补跑 Shipping）。

三处约束是**读源码时才发现**的，它们决定了本设计的形状：

1. `FTcsEventBus::Subscribe` 只接受 `UTcsEventHandler*`（UObject），**传不了 lambda**；订阅表对 Handler 持**弱引用**；派发时只传 `(EventTag, Payload)`，**不传订阅句柄**。
2. `FTcsStepExecute` 的签名是 `(const FInstancedStruct&, FTcsEffectContext& Context, FTcsChainRun& Run)`——**以引用传池元素**；而 `FTcsChainRun.h` 明文禁止"执行器持运行态/上下文引用期间起新链"（池元素住连续数组，扩容即搬移）。
3. `MaxStepsPerFrame` 是 `RunFrom` 的**局部**变量 ⇒ 每进一条链各拿一份新预算。

另有一处**既有文档的事实错误**（调研稿）：`FTcsCombatEntityHandle` 被写成带（Index, Generation），实际只有 `int64 Id`。

## Goals / Non-Goals

**Goals**

- 四个链原语落地：`SetVar` / `RunSubChain` / `Branch` / `WaitEvent`；
- 落齐唤醒源②（事件匹配）与③（子链完成），并把"运行态释放即解锚"补成协议的一部分；
- 补两条嵌套护栏（共享预算 + 深度上限）；
- P-A 排序相位：排序契约（字典序 + 稳定键 + 浮点边界）、唯一内置距离评分器、评分器宿主插槽、候选去重、`MaxCount`（K）；
- 同批消掉 `SPEC-06-targeting` §5 的假陈述。

**Non-Goals**（本批明确不做）

- Top-K 的**流式**实现（`O(H×K×M)`，其作者自警"不能仅凭『流式』名称推断更快"）；
- 候选来源组合器（交并差；触发条件 = 复合表达需求出现）；
- 空间索引（自走棋无空间维度 + `ITcsEntityQuery` 归宿主；零收益且违反最小编译集纪律）；
- `ITargetMapper<T>`（下游消费的就是句柄，加映射只多一层）；
- **P-B 形状族 / P-C 预览与逐候选诊断面**（提案已切分为 P-A → P-B → P-C）；
- **R-1 参数源插槽 / R-2 两张注册表插槽**（R4.5-b / R4.5-c，各自独立提案）；
- `Repeat` / `Parallel` / `OnError` 三个重原语（留 R5）；
- `FTcsSelEventTarget`（依赖"事件载荷 → 目标"通路的完善）。

## Decisions

### D-1 `WaitEvent` 的唤醒路由：共享订阅 + 门面等待表（`FTcsChainRun` 不持订阅句柄）

**做什么**：门面侧维护"等待中的运行态"索引（`Tag → 订阅句柄` 计数配对 + `Tag → 等待者集合`）；运行态只持**"在等哪个 tag"**这一可配平锚。事件到达时，共享 Handler **按 tag 取等待者快照 → 逐个代际校验 → 写载荷 → `ResumeRun`**。门面持一个 `UPROPERTY` 锚定的共享 `UTcsEventHandler` 子类承接订阅。

**为什么**：三条事实各堵死一条路——① Handler 必须是 UObject 且被强持有（弱引用会静默失效），而 `UTcsEffectSubsystem` 已是 Subsystem、不能双 UObject 基 ⇒ 必须有独立的小 Handler 对象；② 派发不带订阅句柄 ⇒ Handler **无法**从回调参数自辨"是哪条运行态在等"，只能靠门面侧索引认领；③ 本仓**已有明文纪律**禁止"每个订阅者各订一次"（`FTcsTriggerRegistry`：那会让订阅表随数量膨胀且退订易漏）。

**备选与取舍**：
- **每运行态一条订阅**（计划原建议）：实现最直白，但撞既有纪律；且同一 tag 的 N 条订阅会把同一回调打 N 次，每次都要靠索引认领——收益为零、成本为正。
- **扩总线契约**（把订阅句柄传进 `HandleEvent`）：能让 Handler 自带身份，但改的是 `TcsCore` 的公开契约、blast radius 跨模块，而收益只是省掉一张索引表。**否**。

### D-2 嵌套护栏：共享预算 + 固定深度上限（两条都要）

**做什么**：`MaxStepsPerFrame` 从"每次 `RunFrom` 一份"改为"**一次最外层进入一份**"，嵌套起链共用；另加一个**固定常量**的嵌套深度上限（超限熔断断链 + Error）。

**为什么**：这是**崩溃类**问题不是性能问题。原实现下 `A→B→A→B` 自激既绕过预算、又逐层吃调用栈。而只有预算还不够——预算值由链定义给出、**作者可配到很大**，故它 MUST NOT 是调用栈深度的唯一护栏。深度上限是**调用栈护栏**，不是行为语义，所以做成常量而非链定义字段。

**备选与取舍**：
- **只共享预算**：能拦住默认配置（64 步 ⇒ 深度 ≤ 64），但作者把上限配成 4096 时栈就没护栏了。
- **只加深度上限**：拦住栈，但 `A→B` 交替且层内步数多时仍可在一帧内跑掉几万步。
- **内层链定义的上限也参与裁定**（取 min）：语义更"保守"，但会让"子链单独跑没事、被父起就熔断"这种难解释的行为出现。本批取**最外层上限**，把这条取舍登记在此。

### D-3 子链完成唤醒挂在 `ReleaseRun` 上，且**异常结束同样唤醒**

**做什么**：运行态上记"谁在等我"；`ReleaseRun`（链结束的唯一汇聚点）通知等待方。

**为什么**：`ReleaseRun` 是四条路径（正常走完 / 单帧步数熔断 / 链定义不可解析 / 未知步骤类型）唯一的共同终点——挂它上面天然覆盖全部结束方式。**异常结束也唤醒父**是刻意的：不唤醒 = 父永久挂起 = **死链**，而"父错误地继续 + 一条 Error 日志"可被观测、可被排查，比静默死锁便宜得多。

**备选**：父每帧轮询 `IsRunActive(子句柄)`——直接违反"挂起中的运行态 MUST NOT 产生每帧成本"，**否**。

### D-4 `RunSubChain` / `Branch` 的步内起链纪律：起链前取齐数据，起链后不碰引用

**做什么**：两个步骤在调用 `ExecuteChain` 之前把所需数据（链 id、要传下去的黑板字段）**取成局部值**；起链之后 **MUST NOT 再触碰** `Context` 与 `Run`。解释器侧无需改动——`RunFrom` 已在步骤返回后**按句柄重解析**再推进 PC。

**为什么**：`FTcsStepExecute` 以引用传池元素，而池扩容即搬移；`TcsChainRun.h` 早已把这条写成纪律，本批是它**第一次被真正消费**。

### D-5 稳定键 = `FTcsCombatEntityHandle::Id` 升序；确定性收窄为"同进程"

**做什么**：全等后按 `Id` 升序决胜；规格把确定性承诺写成"同进程内同输入同输出"。

**为什么**：调研稿写的（Index, Generation）**在该句柄上不存在**（已核实：只有 `int64 Id`，头注释明文"无代际段——Id 单调递增且永不复用"）。用 `Id` 反而**更强**：永不复用 ⇒ 不存在"回收槽误命中"，天然是稳定序。**代价**：`Id` 由**进程内**原子发号器分配 ⇒ 两台机器对同一批实体的 `Id` 不同序 ⇒ 跨进程重算不保证一致。既有 `SPEC-06-targeting` §3 写着"客户端重算一致"——**这句跨进程承诺不成立**，本批如实收窄（依据：该文档 §4 已定"仅权威侧执行、选择结果不复制"）。

### D-6 去重放在执行器侧，`Resolve` 契约一字不改

**做什么**：执行器在**过滤之后、取前 K 之前**按句柄身份去重；`FTcsTargetSelectorStrategy::Resolve` 的契约不变（宿主自定义选择器**不被要求**自己去重）。

**为什么**：这是对两条看起来相反的外部经验的调和——"**不约束自定义选择器的输出**"与"**要有去重**"。TCS 里"候选数组"与"结果数组"是**同一个缓冲**（`Resolve` 填充 → 过滤 → 写回 `Context.Targets`），而外部参照是"候选流 → 命中集"两段结构。所以两句话在 TCS 侧分别落实为"**选择器不用自己去重**"与"**执行器负责去重**"。

**顺序的等价性论证**（避免将来有人照抄"去重必须在评分之后"却发现测不出来）：去重键 = 候选的**完整身份** ⇒ 重复项彼此**不可区分** ⇒ 去重发生在排序前还是排序后**无观测差异**。唯一有观测后果的约束是"**去重在取前 K 之前**"（放 K 之后会让结果数少于 K），故规格只钉这一条。

### D-7 `MaxCount`（K）进本批，只做非流式

**做什么**：`MaxCount` 按**完整字典序**取前 K，`0` = 不限；实现 = 排完序截取（数据本就在手上）。

**为什么**：不做 K，排序相位**没有可用消费者**——`Context.Targets` 排完序仍含全部候选，下游 `Damage` 会打全体；而用户 2026-09-30 的原话"先只内置一个**距离最近**"本身隐含 K=1。计划第 504 行的 MUST NOT 只点名"流式**实现**"，语义层并未被排除；按 Global Constraints"字段可先就位（设计承诺），不得为无消费者的字段造**机制**"——本项近于零机制。

### D-8 评分器插槽空 `Host` 的语义 = 中性分（0.0）+ Warning，**不是**淘汰全部

**做什么**：转发器在 `Host` 未配时对每个候选返回 0.0 并留 Warning。

**为什么**：照过滤器插槽"空 Host = 通过"的既有裁定理由——配置遗漏 SHOULD 表现成"这一项不区分候选"，而不是"淘汰全部候选"；后者会让配置残缺表现成"**打不到人**"，比中性更难排查。Warning 保证"不静默"。

### D-9 距离分数 = 真实欧氏距离（不是平方距离）

**做什么**：`FTcsScorerDistance` 返回 `FVector::Dist(CasterLocation, CandidateLocation)`。

**为什么**：分数是**可观测值**（P-C 的诊断/预览面会展示"首个排序项分数"），平方距离虽然排序同序，但显示出来是误导性的未声明变换。取"非负 + 可解释"。

### D-10 `Branch` 在链侧的条件上下文只有 `Caster` 有来源

**做什么**：链侧构造 `FTcsTriggerContext` 时，`Caster` 从黑板映射；`EventTag` 与 `ClassificationTags` 以无效 tag / 空数组构造 ⇒ 依赖它们的条件在链侧**恒不通过**。

**为什么**：`FTcsEffectContext` 只有 `EventPayload`（载荷本体，不含事件 tag），也没有分类标签来源；为它们加字段是另一个设计（"起链时把触发事件 tag 记进运行态"），本批不预建。**明示接受的限制**，登记进台账。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 共享订阅的计数配对**退订易漏**（正是这条纪律警戒的失败形态） | 三条退订路径写进规格（命中 / 超时 / 运行态释放），并给"释放后发事件不触发回调 + 订阅计数回落"的验收场景 |
| 共享预算**改变了既有语义**（内层链单独跑能用满 64 步，被父起时可能提前熔断） | 规格明写"取最外层上限"；此为刻意取舍（可预测 > 宽松），登记于 D-2 |
| 深度上限的**具体值未定** | 规格只钉"固定常量、非链定义字段"，值由实测决定并写进计划注记（Task 3.5 Step 4） |
| 排序引入后"保序"变成**有条件**的措辞 | 规格把它写成唯一例外条件（排序项为空时保序），并给"配了排序项 MUST NOT 再保序"的验收场景 |
| 评分器插槽的**性能边界只是 SHOULD**，无法强制 | 规格 + 类型注释两处提示，并在 `deferred-inputs-ledger` 登记"若实测热点落在脚本评分器，再考虑加限制" |
| `FInstancedStruct` 引用新原语类型后，若将来退役这些类型，**既有链资产会静默变空** | 与 `FTcsSelSelf` 的存在理由同款（内容引用的类型必须长于内容）；本批不引入额外风险，但在 `RunSubChain` 的 id 语义上重申"链 id 是宿主词汇、插件不声明" |

## Migration Plan

- **无需资产迁移**：四个原语是新类型（既有链资产不受影响）；`FTcsStepSelectTargets` 只**加**字段，既有资产不配 `SortItems` / `MaxCount` 时**顺序**与**截断**都不变（排序项为空 + `MaxCount = 0`）。
  - **唯一的无条件行为变化 = 候选去重**（它**不随字段门控**——去重是执行器的固定相位，见 D-6）：既有链若其选择器产出重复候选，结果集会变少。**为什么不做成"配了排序项才去重"**：那会让去重变成排序的附属品——不排序的链继续对同一目标打两次，而"打两次"是缺口不是特性；且判据会退化成"看你配没配排序"这种与去重无关的条件。既有回归资产（`DA_SliceChain` / `DA_FormulaChain`）用的都是单目标选择器（`FTcsSelSelf` 类），不产重复 ⇒ 对本批验收集合无影响。
- **旧链资产复核**：检查点 6 的"改 `DamageBase` 零 C++ 生效"证据链用的是 `DA_SliceChain` / `DA_FormulaChain` —— 本批 **MUST NOT** 修改它们（Task 3 已立同款纪律）。
- **回滚**：摘掉 `SortItems` 配置即回到旧行为；删新原语类型会让引用它们的链步骤静默变空，故回滚 MUST 连同资产一起处理。
- **验收顺序**：Development 编译 → Shipping 编译（本批含 `TcsChainRun` 结构改动与新 `UPROPERTY`，Shipping 必跑）→ 定向人工检查 → 台账/文档回写。

## Open Questions

1. **嵌套深度上限取多少**：取值待实测（护栏目标 = 不耗尽调用栈，且远高于任何合理内容嵌套）。写完实测值回写计划注记与本文。
2. **链侧 `EventTag` 的来源补法**：自然方案 = 起链时把触发事件 tag 记进运行态（触发行求值器已持有它）。归属轮次待定，本批只登记限制。
3. **`MaxCount` 与"再次 SelectTargets 显式改写"的交互**：多次 `SelectTargets` 各自截断是显式数据流语义，本批不额外约束；若出现"累积截断"的真实需求再议。
