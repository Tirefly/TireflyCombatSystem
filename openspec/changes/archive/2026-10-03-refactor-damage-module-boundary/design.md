## Context

框架本体边界审计（`Documents/combat-system-design/research/boundary-audit.md`）对 `Source/` 七模块做了全量只读复核。结论：**边界大体干净**（非 `TcsDamage` 模块零违规，已逐模块正面论证），实质问题全部集中在 `TcsDamage` 的 `Execute` / `Completed` 两个**默认模板步骤**的执行器内部——即"已被组装进默认模板的步骤，其内部硬编码不在内容层豁免范围内"（豁免边界的精确表述见审计报告 §2.2）。

审计的原始报告把这一批打包成"S1"，但实际混了**处置完全不同**的几类东西。本变更按定稿的五分处置逐类处理。

**提案与实现的分离**：本变更只产出提案与规格 delta；`Content/` 资产、ini、宿主仓、TGFS 仓一律不动。

## Goals / Non-Goals

- **Goals**
  - 把"框架替宿主下的结论"逐条改为**可被宿主覆盖的契约默认**，或**交回宿主已有的配置点**；
  - 保持**默认零行为变更**（除两处已显式声明的例外：`bHit` 语义、值域下限）；
  - 把修复面收束到最小——实测收束为**单文件（`TcsFlowStepsCore.cpp`）双函数**。
- **Non-Goals**
  - **不删任何"零消费者"字段**（判据 4：取值归属 > 有无消费者）；
  - **不动审计报告 §5 的 32 项删除禁令**；
  - **不含真缺陷 R-1 / R-2 / R-3**（那三者是缺陷而非边界问题，另排期）；
  - 不重构 `ITcsDamageFlowDelegate` 的既有 5 方法、不改其签名、不改流程解释器。

## Decisions

### D1 处置分类（S1–S7 → 五分）

| 审计原编号 | 内容 | 处置 | 动作 |
|---|---|---|---|
| S1a | `Record.bHit = true`（硬编码常量） | ① | 改为从 `DamageFlowKey.Hit` 读回（**不删字段**） |
| S1b | `Record.Element` 唯一写入点是置空 | ① | **删字段**（BREAKING，自换根提案移交） |
| S1c | `bCrit` / `Absorbed` 从契约键读回 | ② | **不删**，只补注释 |
| S1d | `bKill` 的 `<= 0.0` 阈值 | ③ | 改为经 `IsLethal`（中性默认 = 现状） |
| S2 | `Executed = max(0, Candidate - Absorbed)` | ③ 部分 | **下限钳保留**（④），**减法模型**改为经 `ResolveExecutedDamage` |
| S9 | `max(0.0, Current - Executed)` | ⑤ | **删除钳制**，值域交回属性层 |
| S4 / S5 | 事件词 / 黑板键整体 | — | **已降级，不算违规**（见审计报告 §6） |

**关键裁定：S2 必须拆开判。** `FMath::Max(0.0, ·)` 的下限钳只引用数值、方向收敛到"不介入"⇒ 契约默认；但 `Candidate - Absorbed` 的**减法模型**宿主无法替换 ⇒ 框架内定。**两者处置相反**（一个保留、一个要加覆盖点），合并判必错。

### D2 覆盖手法 = 新增委托方法（用户 2026-10-01 拍板）

**决策**：给 `ITcsDamageFlowDelegate` 新增 2 个 `BlueprintNativeEvent`（`ResolveExecutedDamage` / `IsLethal`），**中性默认实现 = 整肃前的现状行为**。

**为什么不是"新增契约键"**：S2 要交出的是**映射函数**，不是数值——黑板键装不下函数。S1d 虽是数值（阈值），但用键表达会引入"框架原生声明一个宿主玩法阈值"的新问题（阈值该由谁声明？声明在哪个根下？），而委托方法零新增词汇、且与既有 5 个中性默认同构。

**为什么默认零行为变更**：默认实现即现状表达式。故本变更对"不配 delegate 的项目"是**纯结构性**的——唯一例外是 `bHit`（D3）与值域（D4）。

**兼容性**：`BlueprintNativeEvent` + 接口内 `_Implementation` 默认体 ⇒ UHT 不生成 stub ⇒ **既有宿主实现类无需适配，只需重编译**。

> **实施期更正（2026-10-03）**：**"只需重编译"对 UnrealSharp 宿主不够**——跨模块（接口在插件、实现类在宿主）时宿主 glue 镜像不随接口刷新 ⇒ `CS0535`，需让实现模块重新导出。根因与处置见 `tasks.md` 7.5 / `log/decisions-log.md` 同日条目。**契约层面本条不动**（宿主源码确实零改动）；失效的是**构建层的增量假设**。

### D3 `bHit` 改为读契约键——**本提案唯一的默认行为变更**

**决策**：`ExecuteFlowCompleted` 不再写死 `true`，改为从 `DamageFlowKey.Hit` 读回。

**后果（MUST 让评审看到）**：默认模板**不含** `FTcsFlowHit` 步 ⇒ `Hit` 键无提交 ⇒ 折叠初值 0 ⇒ **`bHit` 由恒 `true` 变为 `false`**。依赖恒 `true` 的消费者会受影响。

**为什么仍然这么改**：`bHit = true` 是**硬编码常量字段**——取值恒定、零信息量（"记录存在"已蕴含它），且它在语义上是**替宿主断言"本次一定命中"**。保留它等于保留一个永不变化的字段。

**备选（未采纳，留待评审否决）**：把 `bHit` 的语义从"命中判定结果"改为"流程是否跑到完成"（即承认恒 `true` 是正确记账），仅补注释说明它是"流程完成"的同义字段。**否决理由**：那会留下一个永远为真的字段，且与同结构里的 `bCrit` / `Absorbed`（都从契约键读回）写法不一致，制造"同类字段两套取值来源"。

### D4 值域交回宿主——**本提案最强项**

**决策**：删除 `Execute` 步的 `FMath::Max(0.0, Current - Executed)`。

**依据（已独立复核的两处对照证据）**：属性层的值域收口只在宿主**显式配了边界**时才钳制（`TcsAttributePipeline.cpp:298-308` 的 `if (bHasMin && ...)` / `if (bHasMax && ...)`），而边界模式的默认是 `ABM_None`（"该侧不设边界"）⇒ **"过量伤害记为负数"本是宿主可表达的语义**，却被这一步抢先钉死。

**为什么这一档比"S2 缺覆盖点"更重**：S2 是"框架没给扩展面"，本项是"框架抢在宿主**已有的**配置点之前下了结论"——定性为**契约覆盖**，构成"框架与宿主各有一套值域结论"的双真相。

**迁移代价（MUST 交付）**：删除后宿主 MUST 给生命属性配 `Min = 0`，否则过量伤害记负值。**该动作归 LAC 侧**（`tasks.md` 第 7.1 项）。

> **实施期更正（2026-10-03，两点）**：
> ① **该动作 LAC 侧本就已满足** —— 经编辑器 MCP 实查，`DA_Health` 的 `Def.Bounds.Min` = `ABM_Static` / `StaticValue = 0`（资产 mtime `2026-10-02 19:13:16`，**早于本次改动**）⇒ 上面这条 MUST **不产生任何迁移工作**，"未配"是误判。
> ② **但该缓解只在读侧成立——本条措辞过宽**：`FTcsAttributePipeline::SetBaseValue` **不取值域**（`Instance->BaseValue = NewBaseValue;` 原样写），值域只在 `ComputeFoldedValue` 末端生效 ⇒ `Min = 0` 保证 `EvaluateCurrent` 恒 ≥ 0（`bKill` 与记录读的就是它），但**基础值仍可为负**；后续"抬血"会先填这个坑再上升。按设计这是**末端收口语义**的必然结果（**不是缺陷**），准确表述应为「**过量伤害在读侧不记负值；基础值仍可为负**」。

### D5 跨提案基准 = 换根后文本（用户 2026-10-01 拍板）

**决策**：本条 delta 里的 tag 名一律用**换根后的新名**（`TcsEvent.Damage.Recorded` / `DamageFlowKey.*`），并在提案里记明"换根 MUST 先归档"。

**依据**：OpenSpec 归档按 header **整条替换** ⇒ 两份未归档提案同时 MODIFY 同一条需求时，后归档者会用自己的粘贴全文**覆盖**前者，静默回滚其改动。本案与换根提案在「伤害记录与事件」与「标准步骤库（十步）」两条需求上重叠（即使把 `Element` 移交出去，**只要换根改这条需求的 tag 文本，重叠就存在**）。

### D6 `R-2` 规格与实现失步——**改规格，不改实现**（2026-10-01 用户裁定并入）

**决策**：把「Damage 链步骤与执行器」里"把 `DamageBase` 与 `FormulaParams` 写入上下文（**黑板契约键** `DamageFlowKey.BaseDamage` / 公式参数表）"改为"写入**上下文请求字段**（`Context.BaseDamageInput` / `Context.FormulaParams` / `Context.TargetAttrKey`）"，并补一条 **MUST NOT 写黑板** 的规范句。

**核实过的事实**（两条，均为本轮读源码所得）：

| 事实 | 落点 |
|---|---|
| 执行器**从不写黑板**，只写三个上下文请求字段 | `Source/TcsDamage/Private/Chain/TcsStepDamage.cpp`：`FlowContext.FormulaParams` / `BaseDamageInput` / `TargetAttrKey` |
| 黑板写入归流程内的 `FTcsFlowBaseDamage` 步（以 **Add** 提交到 `DamageFlowKey.BaseDamage`） | `Source/TcsDamage/Private/Flow/Steps/TcsFlowStepsCore.cpp` 的 `SubmitAddValue(Context.Blackboard, OutputKey, BaseDamage)` |

**为什么改规格而不是改实现**：实现的通道选择有**实测支撑**——黑板会被 `CollectStart` 重置（收集语义），输入是"请求"的一部分、不随收集清除；若改由本步骤从黑板读输入，"链侧预写 + 本步提交"会造成**重复计数（实测 `10 + 20 = 30`）**。**让实现去迁就一句写错的规格，等于把已修好的 bug 重新引入。**

**不改的代价（本项的存在理由）**：规格是本仓的唯一真相源。此处规格描述的是**已被证伪的实现** ⇒ 下一个照规格改代码的人会**重新引入**重复计数。这是最贵的一类失步——不崩溃、不报错，只在数值上错。

**并入本案的理由**：该失步落在伤害模块、与本案同属**规格一致性**，且该需求**同样被换根提案修改**（⇒ 同样 MUST 排在换根之后）——合并后跨提案归档依赖只需记**一条**。

**本项的可见性边界**：它是**纯规格文本更正，零代码改动、零行为变更**。评审时不必按行为变更对待。

## Migration Plan

1. **契约先行（本提案）**：2 份 delta + 提案三件套 → `openspec validate --strict` 通过 → 评审批准。
2. **前置确认**：换根提案已归档（`tasks.md` 1.6）。
3. **实现（本仓）**：D4 删钳制（1 行）→ D2 接两个委托钩子 → D3 改 `bHit` → `Element` 删除（BREAKING）→ 双配置编译 → PIE 兼容性验证。
4. **宿主迁移（LAC 仓）**：生命属性配 `Min = 0`；核 `bHit` 消费面；`Element` 消费面复验。
5. **回滚**：本变更的每一处都是**局部且可逆**的——删掉的钳制可加回、新增的委托钩子可回落为默认、`Element` 字段可恢复。**唯一不可逆的是宿主侧已按新语义写入的数据**（负生命值），故建议先落实现、观察一个验收周期再归档。

## Open Questions

1. **`bHit` 的最终语义**（D3）：保留"命中判定结果"（⇒ 默认变 `false`）还是改为"流程完成"（⇒ 恒 `true` 但改名/改注释）？本提案取前者并留了备选；**若 LAC 侧确有依赖恒 true 的读取点，应改采备选**。
2. **致死线是否需要"记账而非裁定"之外的表达**：现状框架只写 `Kill` 记账标志、不杀实体。若宿主希望框架提供一个"致死时自动执行某事"的扩展点，那属**新能力**，不在本提案范围（本提案只把裁定权交出去，不新增主动行为）。
3. **`ResolveExecutedDamage` 的形参是否够用**：现定为 `(目标句柄, 候选量, 吸收量, 视图)`。若宿主需要"未吸收的候选量 / 累计吸收量 / 护盾剩余"等更多输入，需在实现期回报——**形参一旦发布即不可轻易收窄**（UHT 反射面）。
   **已回报（2026-10-03，实施期）**：签名**够用且未收窄**，但暴露一处**口径不一致**——`Absorbed` 按现状是**全目标之和**（`ModifyShield` 逐目标累加），而签名却带"目标句柄" ⇒ 该映射实为**流程级**一次取值，调用点取 `Targets[0]`（与既有 `CalculateBaseDamage` 步同款）。**逐目标吸收 / 逐目标执行是行为变更**（会改 `Executed` 黑板键的单值语义与记录字段口径），**不在本提案范围**——若将来需要，另开提案并配新断言。**本次不因此收紧签名**（放宽容易、收窄不可）。
