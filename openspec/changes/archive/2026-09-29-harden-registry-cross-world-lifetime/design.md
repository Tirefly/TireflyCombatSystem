## Context

`DEC-04-callback-carriers` 裁定 ⑤ 要求"先做 A 类值语义改造"——它是 `LEDGER-reflection` R-2 跨世界寿命缺陷的兜底，也是 R-1/R-2 两张新注册表落地前的前置护栏（R-2 若照抄 SCRIPT-8 模式，会把同一缺陷复制成三份，调研已明确警告）。

现状的三个事实（2026-09-29 逐处实测，行号见 `proposal.md` 的 Why 节）：注册表进程级且无撤销入口；重复判定只看键、命中即"拒绝 + 保留首个"；门面 `Deinitialize` 不碰动态登记。

**关键约束（不可违背）**：注册表的**进程级 + 函数局部静态单例**必须保持——自注册器在模块静态初始化期构造，既有需求明令该时点 MUST NOT 触达 UObject 设施。故改造只能在**值**上做，不能在**容器级别**上做。

## Goals / Non-Goals

**Goals**
- 动态登记项具备寿命语义：UObject 被回收、或来源世界已结束 ⇒ 该条登记**自动失效**；
- 失效条目 MUST NOT 毒化后续登记（即消除"第二次 PIE 撞 `Contains` → 拒绝 → 复用 stale 指针"这条路径）；
- 跨世界查询 MUST 被判定为未命中，且**可诊断**（MUST NOT 静默装作"未登记"）；
- 静态自注册路径**行为零变化**，其"静态初始化期零 UObject 触达"纪律保持不变。

**Non-Goals**
- 不做条件求值器 / 载荷读取器的宿主脚本插槽（属 R-2）；
- 不改内置执行器的载体形态（保持纯函数，`DEC-04` 裁定 ① D 类）；
- 不改注册表的键与分派逻辑（D4-14 不变）；
- 不为 `ITcsEntityQuery` / `FTcsConsumePolicy::OnConsumed` 做任何改动（`DEC-04` 裁定 ③④）。

## Decisions

### D1：寿命语义放在"值"上，用弱引用而不是所有权

`FTcsStepExecute`（及同款三别名）本身是 `TFunction`，对 GC 不可见，**因此捕获了什么、指向哪个世界，注册表无从得知**。修法不是让注册表去"拥有"对象（那会与进程级容器冲突），而是**让注册表知道对象是谁、属于哪个世界**：

- 动态登记项额外记录 `TWeakObjectPtr<UObject>`（宿主执行器）+ `TWeakObjectPtr<UWorld>`（登记时的世界）；
- 静态自注册项这两个字段保持空 ⇒ "无寿命约束，永不过期"。

**为什么不用 `UPROPERTY` 强持有替代**：门面的 `UPROPERTY` 数组已经做了这件事（防静默回收），两者是**互补的两半**——`UPROPERTY` 管"别被收走"，弱引用管"收走了/换世界了就失效"。缺任一半都有洞：只强持有 ⇒ 跨世界 stale（本缺陷）；只弱引用 ⇒ 静默回收（WAIT-8 教训）。**本提案 MUST NOT 移除门面的 `UPROPERTY` 持有。**

### D2：世界校验用"弱世界指针 + 逐查询比对"

`UWorld` 是 `UObject`，其寿命与 GC 一致，`TWeakObjectPtr<UWorld>::Get()` 在实例被 GC 后返回 null——这是引擎标准模式。两个失效条件合并为一条判据：

```
条目失效 ⇔ (宿主弱引用为空) ∨ (条目世界弱引用为空) ∨ (条目世界 ≠ 调用方世界)
```

**为什么不改用"注册表挂到 `UWorldSubsystem` 上"**：那会破坏静态初始化期的可用性（约束见 Context）。**为什么不另建一张世界级表**：查表变两段、键空间分裂，且静态自注册项仍要在进程级表里 ⇒ 双真相。

**`Find` 签名改动的兼容处理**：`Find(const UScriptStruct* StepStruct)` → `Find(const UScriptStruct* StepStruct, const UWorld* World = nullptr)`。默认参数使未传世界的调用点仍可编译；但**所有 5 个真实调用点 MUST 显式传世界**（见 tasks），因为"不知道世界"就无法做跨世界判定。`World == nullptr` 时 MUST 跳过世界校验（只做弱引用校验）——这保留了测试装置/纯 C++ 场景的可用性，并把"无世界上下文"变成一个显式的、可 grep 的调用形态。

### D3：拒绝门收窄为"同世界活对象重复"

| 既有条目状态 | 新登记请求 | 行为 |
|---|---|---|
| 无条目 | — | 正常登记 |
| **已失效**（对象死 / 世界亡 / 世界不同） | 任意 | **替换**该条目（MUST NOT 拒绝）；记 Log 说明替换原因 |
| **有效且同世界** | 同键 | **拒绝**（ensure + false，保留首个）——沿用既有口径，防同世界内的真实登记冲突 |
| 有效但为静态自注册项 | 同键 | **拒绝**（同上）——静态项是代码，不允许被运行期覆写 |

> 被替换的失效条目不调用任何析构/回收逻辑——它已经没有活对象可回收；替换即丢弃。

### D4：显式 `Unregister` 是整理手段，不是正确性前提

注册表 MUST 提供按键移除动态条目的入口，门面 `Deinitialize` MUST 撤销本世界登记的动态条目。但**正确性不依赖它**：即使门面从不调用（或子系统被异常销毁），D2 的查询侧判定仍保证不野调用。这个设计次序直接对应用户 2026-09-27 的裁定——"**TCS 侧兜底优先**，A1（注销）作退路"。

`Unregister` MUST NOT 能移除静态自注册项（它们是代码而非登记）。

### D5：跨世界判定 MUST 可诊断

`Find` 判定为跨世界失效时 MUST 留 Warning 日志（含步骤类型名与两个世界），MUST NOT 静默返回 nullptr 了事。判据：静默会让"世界已更换"表现成"步骤类型未注册"，而后者会走 `effect-step-dispatch` 的"未知步骤类型 → 断链 + Error"路径——**把配置遗漏与世界切换混为一谈，是排障成本的主要来源**（本仓既有纪律的同类先例：`SCRIPT-7` 的"配置错误 → ensure；时序竞态 → Warning"）。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| `Find` 在热路径（条件求值器每候选行每条件一次）——新增弱指针解引用有成本 | 弱引用解引用是两次指针读；且 **`Find` 的结果在求值器内可缓存**（既有实现每行每条件调一次，本提案不改变调用频度）。实施时若实测有影响，可在解释器/求值器侧缓存"本帧解析结果"（属后续优化，不在本提案范围） |
| 默认参数 `World = nullptr` 可能被新调用点"顺手省略"而绕过校验 | ① 既有 5 个调用点全部显式传世界；② 需求明文要求"调用方持有世界时 MUST 传入"；③ 静态检查：`grep 'Find(' 应无省参调用（写入 tasks 的定向人工检查） |
| 替换失效条目会掩盖"同一世界内重复登记"的真实冲突 | D3 表格已把两种情形分开：**同世界且活对象**才拒绝。失效条目的替换会记 Log，不静默 |
| 静态自注册项的"永不过期"假设在未来被打破（若某天给内置执行器也加 UObject） | `DEC-04` 裁定 ① D 类已明文禁止；本提案的需求也 MUST NOT 被解释为允许 |

## Migration Plan

1. **先加字段与判定，不改拒绝门**（保证中间态可编译且行为不退化）；
2. 再收窄拒绝门（D3）——此时第二次 PIE 的行为从"拒绝 + stale"变为"替换 + 正确"；
3. 加 `Unregister` + 门面 `Deinitialize` 收口（D4）；
4. 5 个 `Find` 调用点显式传世界（D2）；
5. 编译（Development + Shipping）+ 定向人工检查 + 用户 PIE 验收（**连续两次 PIE**，不重启 Editor——这是本提案的核心判据）。

**回滚**：改动集中在 4 张注册表 + 2 个门面，无资产/规格数据结构变更 ⇒ `git revert` 即可回到当前行为（当前行为 = 缺陷仍在，但流程纪律仍在掩盖它）。
